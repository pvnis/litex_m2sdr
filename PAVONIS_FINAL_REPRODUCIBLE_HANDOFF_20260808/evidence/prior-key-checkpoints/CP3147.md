# CP3147 - NAS reject-cause probe, no RF

## Verdict

**STOP at the Part A gate. No RF was run.**

There is no standards-compliant cause-only change that can turn the CP3144
retained-state cycle into a fresh supported-DNN request.

The CP3144 shorthand needs one correction:

- the four unknown-session reactivation events did **not** carry a NAS cause
  value and did not exercise qcore's cause-54 branch;
- qcore answered them in Registration Accept with a failed PDU Session
  Reactivation Result bit and an inactive PDU Session Status bit;
- the four unsupported-IMS establishment requests exercised the 5GSM reject
  path with cause 27;
- the source contains the mandatory cause-54 path for a later explicit
  `existing PDU session` request, but CP3144 recorded zero such requests.

Changing the reactivation bitmap into a cause is therefore not a configuration
change. It would require a different NAS message/procedure. Substituting a 5GMM
cause that forces de-registration would be a standards workaround, not a
correct fix for either CP3144 event.

The primer-free data milestone remains **partial**: OCUDU/LiteX-M2SDR reaches
the real handset through registration, but no primer-free private PDU session
or user data has been established.

## TS 24.501 analysis

Reference: ETSI TS 124 501 V18.12.0, 3GPP TS 24.501 Release 18:

`https://www.etsi.org/deliver/etsi_ts/124500_124599/124501/18.12.00_60/ts_124501v181200p.pdf`

The relevant procedure semantics are:

1. **PDU Session Establishment Reject does not delete a retained session.**
   Clause 6.4.1.4.1 requires the UE to stop T3580, release the PTI, and consider
   the attempted PDU session not established. No establishment-reject cause is
   defined as a general retained-session deletion command.
2. **Cause 54 is the relevant local-release/fresh-request cause, but only in
   its defined existing-session context.** Clause 6.4.1.4.3 requires a UE
   performing handover of an existing session to release that session locally
   after cause 54 and permits a later `initial request`. Clause [ip-redacted](d)
   correspondingly requires cause 54 when request type is
   existing/existing-emergency and the SMF has no information for that session.
   CP3144 sent zero such requests. Its unknown-session events were Registration
   Request status reconciliation, which has no 5GSM reject-cause selector, and
   its unsupported-IMS establishment requests were initial requests. Injecting
   cause 54 into either path would change the procedure or violate the cause's
   request-type semantics.
3. **Cause 27 rejects only the unsupported DNN transaction.** Clauses
   6.4.1.4.3 and 6.4.1.4.1 associate retry suppression with the same DNN. They
   do not delete another retained session or require creation of a supported
   default-DNN session. With no explicit back-off IE, clause 6.4.1.4.3 defines
   configured/default retry timing rather than a fresh-DNN fallback.
4. **Registration status synchronization is the stale-session deletion
   mechanism.** Clause 5.5.1.3.4 requires local release when Registration
   Accept reports a UE-side active session inactive at the AMF, except for the
   explicitly listed UE states such as PDU SESSION ACTIVE PENDING. qcore
   already returns the inactive status and the reactivation failure bitmap.
5. **5GMM causes 9 and 10 can force fresh registration, but only on the
   procedures that define them.** Clauses 5.5.1.3.5 and [ip-redacted] make cause 9
   (`UE identity cannot be derived`) or cause 10 (`implicitly de-registered`)
   enter a de-registered state and initiate initial registration. In CP3144,
   qcore had already derived, authenticated, and registered the UE's 5GMM
   context. Sending either cause from a PDU-session mismatch would require a
   Registration/Service Reject and would falsely claim a missing 5GMM
   identity/context.
6. Other destructive Registration/Service Reject causes such as 3, 6, 7, 11,
   and 12 bar the UE, subscription, PLMN, or tracking area. They do not provide
   a legitimate fresh-session fallback and would damage the valid private-lab
   registration result.

A PDU Session Release Command or network de-registration procedure could
change UE state, but either is a new procedure rather than a cause-selection
change. Sending one for state that qcore does not own also needs a separate
standards and state-machine design; it is not earned by this cause-only probe.

## qcore classification

- Cause 27 and cause 54 are hard-coded procedure constants, not configuration
  values.
- The CP3144 reactivation response is a bitmap/status code path, not a cause
  selector.
- Keeping cause 27 for unsupported IMS is standards-compliant.
- Keeping cause 54 for an explicit missing-existing request is mandatory.
- Replacing either with a 5GMM de-registration cause would change protocol
  layer and message path and would be a non-compliant workaround in CP3144's
  established 5GMM context.
- No production cause or message behavior was changed in CP3147.

The evidence supports a device-state, downlink-delivery, or implementation
conformance limitation, not a qcore cause-selection defect. A strict handset
non-conformance label cannot be proven from host logs alone because the
handset's internal 5GSM state is opaque and clause 5.5.1.3.4 has an
ACTIVE-PENDING exception. The operational conclusion is still definitive:
there is no legitimate stronger reject cause to test over RF.
