# Stage 6 Checkpoint 18 - PRACH Frequency Offset Code Audit

Date: [date-redacted]

## Result

Static audit only. Stage 6 remains failed from CP17: the UE transmitted Msg1 seven times, while the gNB PRACH detector accepted zero occasions and logged no non-empty `detected_preambles`.

Do not advance to Stage 7.

## Question

CP17 showed an apparent PRACH placement mismatch:

- gNB SIB1 / PRACH context: `msg1-FrequencyStart: 8`
- UE runtime PRACH setup: `freq_offset=7`, `cell_nof_prb=50`, `carrier_nof_prb=52`

This checkpoint audited whether that is a direct bug.

## Evidence

CP17 gNB config only set `prach_config_index: 1`; it did not manually set `prach_frequency_start`. OCUDU therefore computed `msg1_frequency_start` automatically.

Relevant paths:

- `ocudu/apps/units/flexible_o_du/o_du_high/du_high/du_high_config_translators.cpp`
  - If no manual `prach_frequency_start` exists, `msg1_frequency_start` is recomputed after dependent PUCCH/SRS config.
- `ocudu/lib/du/du_update_config_helpers.cpp`
  - `compute_prach_frequency_start(...)` returns the start of the largest PUCCH-free interval plus a guardband.
  - For long PRACH, the guardband is `0`.
- `ocudu/lib/fapi_adaptor/phy/p7/pdu_translators/prach.cpp`
  - The FAPI-to-PHY translator copies `msg1_frequency_start` directly into `prach_buffer_context.rb_offset`.
- `ocudu/lib/phy/lower/modulation/ofdm_prach_demodulator_impl.cpp`
  - The demodulator uses `rb_offset` in `k_start = K * 12 * rb_offset + k_bar`.
- `ocudu/lib/ran/prach/prach_frequency_mapping.cpp`
  - For 1.25 kHz PRACH with 15 kHz PUSCH, OCUDU uses `nof_rb_ra=6`, `k_bar=7`.

For CP17, OCUDU therefore demodulates long-format PRACH on the 52-PRB UL grid with `rb_offset=8` and `k_bar=7`.

The UE-side `8 -> 7` conversion is intentional in `srsRAN_4G/srsue/src/phy/nr/worker_pool.cc`:

```c++
lte_nr_prach_offset = (new_cfg.carrier.nof_prb - cell.nof_prb) / 2;
prach_cfg.freq_offset -= lte_nr_prach_offset;
```

With `carrier_nof_prb=52` and the LTE-compatible generated cell at `nof_prb=50`, the conversion subtracts `1`. The UE runtime `freq_offset=7` is therefore the expected internal coordinate after receiving a BWP-side value of `8`.

The same compatibility conversion exists in the srsRAN gNB-side NR worker adapter, so this is not unique to the UE path.

## Long-Format Placement

CP17 is long-format PRACH:

- `prach_config_index=1`
- `L_ra=839`
- UE generated `N_seq=9216`, `N_cp=1188`
- OCUDU detector logged `cp_prach=108`, `L_ra=839`, `dft_size=1024`

The older short-format `begin -= 1` issue documented for B4 is present in the current srsRAN_4G tree, but it is not the direct CP17 failure mode. CP17 uses the long-format branch in `srsRAN_4G/lib/src/phy/phch/prach.c`.

For CP17's mu=0 long-format case, srsRAN_4G maps with the LTE-compatible 50-PRB cell:

```c++
k_0 = freq_offset * 12 - N_rb_ul * 12 / 2 + N_ifft_ul / 2;
begin = PHI + K * k_0;
```

OCUDU maps the receiver extraction on the 52-PRB BWP:

```c++
k_start = K * 12 * rb_offset + k_bar;
```

The two code paths are coordinate translations around the same physical PRACH start, but this audit does not prove the generated UE waveform is landing in the exact OCUDU extraction bins after all centering, DFT-size, and sample-rate conventions. It only proves that the visible `8` versus `7` is not, by itself, a configuration mismatch.

## Interpretation

The static audit removes a weak hypothesis:

- `msg1-FrequencyStart=8` on the gNB side is intentional OCUDU configuration derived from the PUCCH-free interval.
- `freq_offset=7` on the UE side is intentional srsRAN compatibility translation from the 52-PRB NR carrier to a 50-PRB LTE-style PRACH generator cell.
- The prior short-format one-subcarrier fix is already present and CP17 is not using that short-format branch.

The remaining Stage 6 risk is narrower:

- either the long-format UE generator and OCUDU demodulator still differ in centering/sample-order convention despite the nominal coordinate translation, or
- the uplink RF/RX path is not delivering a usable PRACH waveform to the gNB detector.
