## Interpretation

CP47 rules out two controlled-path explanations:

- late first SOB alone;
- small live-like TX scheduling margin for high-peak PRACH writes.

A known-good srsUE PRACH waveform still radiates when sent through the same srsRAN bladeRF plugin path with:

- first SOB later than the live run;
- high-peak write lead in the same range as the live run;
- TX gain `60`;
- RX load enabled;
- `status=0` and `meta_status=0x0`.

The remaining live-only difference is no longer basic bladeRF timed TX acceptance or queue lead. The failure is more likely tied to live srsUE's continuous runtime state, absolute stream alignment versus gNB PRACH windows, or some state transition not reproduced by the controlled replay.

## Next Step

Run a live UE attempt with an independent contiguous wide capture on [host-redacted] around the Msg1 interval, then search the full capture for the CP45/CP33 PRACH waveform. The gNB PRACH windows show no detection, but the next question is whether live srsUE emits the waveform anywhere nearby outside those windows.

If the waveform appears in the wide capture, the problem is timing/window alignment. If it is absent from the wide capture, the problem is live srsUE/bladeRF emission state despite accepted TX writes.
