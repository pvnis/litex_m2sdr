# Checkpoint 56 - TX timestamp probe keeps Msg1 failure at Stage 6

## Summary

CP56 added TX-domain timestamp telemetry to the CP55 `EOB then timed SOB|EOB` mode. The RF behavior was otherwise unchanged.

The run reached PRACH again and produced seven high-peak Msg1 buffers. The new telemetry shows that `status=-14 Requested timestamp is in the past` can occur even when the requested timestamp is still ahead of the sampled bladeRF TX timestamp by 17k-25k samples. This disproves the simple hypothesis that the old RX-side timestamp alone was misleading because the immediate TX timestamp was already past the request.

Stage classification remains Stage 6: srsUE transmits Msg1, but the gNB sees only empty PRACH detections.

## Interpretation

CP56 shows that the remaining `-14` failures are not explained by the sampled TX timestamp already being past the requested SOB timestamp. The failing writes still had positive TX-domain margins:

- `17752` samples
- `24956` samples
- `19519` samples

The likely remaining RF-side issue is an effective queued TX boundary or burst-state constraint not represented by `bladerf_get_timestamp(BLADERF_TX)`. The observed pattern still alternates after the first EOB-only close: later `SOB|EOB` writes return `-14, OK, -14, OK, -14, OK`.

## Next Experiment

CP57 should be one variable: keep CP55/CP56 mode but add an env-gated TX scheduling guard for forced high-peak `SOB|EOB` writes. Sample TX timestamp immediately before the write; if `meta.timestamp < pre_tx_timestamp + guard_samples`, move only that forced timed burst to `pre_tx_timestamp + guard_samples` and log the old timestamp, new timestamp, and applied guard.

Risk: this deliberately shifts PRACH later and may miss the gNB PRACH window, so the first CP57 acceptance target should be narrower: prove whether guarded forced `SOB|EOB` writes eliminate `-14` under live srsUE runtime. If it does, the next step is to recover PRACH alignment without reintroducing late writes.
