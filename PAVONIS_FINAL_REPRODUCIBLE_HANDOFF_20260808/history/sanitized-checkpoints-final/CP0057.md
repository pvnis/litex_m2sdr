# Checkpoint 57 - TX guard run did not reach usable PRACH

## Summary

CP57 added an env-gated TX guard for forced high-peak timed `SOB|EOB` writes and ran with:

```text
PAVONIS_RF_BLADE_TX_DBG_TX_GUARD_SAMPLES=30000
PAVONIS_RF_BLADE_HIGH_PEAK_EOB_THEN_SOB=1
PAVONIS_RF_BLADE_TX_DBG_PRE_TX=1
```

This run did not reach `Random Access Transmission`, so it did not exercise the intended guarded high-peak PRACH path. There were no high-peak RF TX lines, no PRACH TX dumps, and no `tx_guard_applied=1` lines. Treat this checkpoint as a no-usable-PRACH run, not as a verdict on whether a 30000-sample guard eliminates the live `-14` failures.

Stage classification for this run: Stage 6 was not classifiable because srsUE did not reach Msg1.

## Interpretation

CP57 does not falsify or confirm the TX guard idea. The intended code path depends on a high-peak PRACH buffer with `force_sob=1`, and this run never produced one.

The likely next step is a same-variable rerun before changing guard size. CP53/CP54 already showed that this lab path can have one no-PRACH acquisition run followed by a usable PRACH rerun under the same deployed code. If a rerun reaches high-peak PRACH, classify the guard directly:

- `status=-14` remains: 30000 samples is insufficient or the failure is not guardable this way.
- all high-peak writes become `status=0`: the guard fixes write acceptance, then we must solve the induced PRACH timing offset.
