## Interpretation

CP59 rules out the guard env alone as the reason CP57/CP58 did not reach PRACH. With guard unset, the deployed CP57 binary still failed before Msg1.

There are now two plausible branches:

1. The CP57 source change introduced a broader runtime perturbation, even when the guard is disabled.
2. The lab acquisition path became unstable after CP56 and the last three no-PRACH runs are runtime variability.

The cleanest next checkpoint is a source rollback control: redeploy the CP56 source from the remote CP57 backup and rerun the CP56 timestamp sequence. If PRACH returns, CP57 source is implicated. If it still fails, the issue is not the CP57 source delta and we should return to DL/acquisition health.
