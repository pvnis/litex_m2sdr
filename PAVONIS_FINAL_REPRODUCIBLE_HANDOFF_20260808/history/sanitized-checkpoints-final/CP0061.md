# Checkpoint 61 - CP56 to CP57 source delta audit

## Summary

CP61 fetched the restored CP56 `rf_blade_imp.c` from `[host-redacted]` and compared it against the local CP57 guard source.

The diff is small and confined to `rf_blade_send_timed()`. It adds:

- `PAVONIS_RF_BLADE_TX_DBG_TX_GUARD_SAMPLES`
- guard bookkeeping fields in log lines and dump metadata
- a guard branch that rewrites `meta.timestamp` only when `tx_dbg_tx_guard_samples > 0`, `tx_dbg_forced_sob` is true, `pre_tx_status == 0`, and `meta.timestamp != 0`

With the guard env unset, CP57 should not change TX timestamps. It still performs one extra env integer read per TX call and has a larger logging format, but it does not touch RX code or the acquisition path.

This weakens a strong source-causality claim for CP57/CP58/CP59 no-PRACH behavior. CP60 showed PRACH returned after rollback, but the source audit says the CP57 delta alone has no obvious active path before TX calls, especially in CP58/CP59 where there were zero RF TX debug lines.

In the CP59 guard-disabled control, `PAVONIS_RF_BLADE_TX_DBG_TX_GUARD_SAMPLES` was unset, so this branch should not have executed. CP57 still differs from CP56 by reading the new env var on every TX call and printing extra fields when a selected TX line is logged.

## Interpretation

CP60 made CP57 suspicious because Msg1 attempts returned immediately after rolling back to CP56 source. CP61 narrows that suspicion: there is no obvious source-level mechanism for CP57 to break DL acquisition or PRACH reachability when the guard env is unset, because the delta is isolated to TX send handling.

The most defensible interpretation is:

1. CP57 with `TX_GUARD_SAMPLES=30000` may perturb early TX timing or stream state when startup TX calls occur.
2. CP58/CP59 no-PRACH may be runtime/acquisition variability, not direct guard-source behavior.
3. CP57 source should not be modified further until an A/B redeploy test confirms whether CP57 guard-disabled behavior reproducibly loses PRACH after a known-good CP56 run.
