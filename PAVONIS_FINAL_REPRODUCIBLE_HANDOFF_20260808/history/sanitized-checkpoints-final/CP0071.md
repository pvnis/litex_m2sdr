# Checkpoint 71 - Sync guard deployed, run completed, but guard telemetry was absent

## Summary

CP71 deployed a UE-side PRACH sync guard experiment and ran the normal Stage 6 Msg1 ladder sequence with the CP68 RF guardrails still enabled.

The run completed and artifacts were collected. The gNB strict TX-timeout gate passed. The UE used the intended rebuilt `srsue` binary and `result.env` confirms `PAVONIS_SRSUE_PRACH_SYNC_GUARD_SLOTS=200`.

However, CP71 is inconclusive for the sync-gating hypothesis: no `PAVONIS_PRACH_SYNC_GUARD` lines appeared in either `srsue.stdout.log` or `ue_ota.detail.log`. PRACH was still generated and MAC still logged six Random Access transmissions. Therefore, CP71 did not prove that the guard was active, even though the binary and wrapper env looked correct.

## Interpretation

CP71 confirms the deploy and run path for UE PHY changes is feasible. It does not yet validate the sync guard behavior.

The important anomaly is that guard strings are present in the binary and the guard env is present in the wrapper artifacts, but no guard telemetry is emitted even though the UE reports thousands of sync-loss events. That leaves two likely explanations:

1. The guard env is not actually visible inside the `srsue` process despite being recorded by the wrapper.
2. The guard hook is present but its srslog output path is not emitted, so the current logs cannot prove whether it enabled or suppressed anything.

Because PRACH was still generated, CP71 should not be treated as a successful gating experiment. It is a deploy/run smoke checkpoint that exposed a telemetry gap in the guard implementation.

## Next Step

CP72 should add direct `stderr` guard telemetry, propagated with an explicit trace env:

```text
PAVONIS_SRSUE_PRACH_SYNC_GUARD_TRACE=1
```

The first CP72 objective is not RF success; it is to prove, in `srsue.stdout.log`, the actual env value seen by `srsue`, the parsed required-slot count, and whether `note_sync_camping_result()` and `prach_sync_guard_blocks()` are reached.
