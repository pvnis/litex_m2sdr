# Checkpoint 72 - Sync guard trace proves guard is active but run-camping stability is not enough

## Summary

CP72 reran Stage 6 Msg1 with direct UE-side PRACH sync-guard telemetry enabled.

This checkpoint answers the open CP71 question: the guard is active, the env is visible inside `srsue`, and the hook is reached. It suppressed two PRACH opportunities and allowed four once the configured `200` stable-slot threshold was met.

The gNB still detected no Msg1. The UE still showed severe PBCH SFN mismatch and out-of-sync churn, and CP72 shows the current guard only accounts for `run_camping()` failures. It does not gate on PBCH SFN mismatch. Therefore the next rung should feed PBCH-MIB SFN mismatch into the same PRACH guard or add an independent PBCH-mismatch PRACH holdoff.

## Interpretation

CP72 proves the run-camping sync guard works mechanically:

1. The env propagated into `srsue`.
2. The guard counted stable camping slots.
3. The guard suppressed PRACH before the threshold.
4. The guard allowed PRACH after the threshold.

It also proves that run-camping stability alone is insufficient for Msg1. The UE still logged PBCH SFN mismatches in the same early attach window, including around the allowed PRACH sequence. The current guard did not see those mismatches because they are logged in `cc_worker.cc`, not in `sync_sa::run_state_cell_camping()`.

The leading hypothesis becomes narrower: PRACH should also be held after PBCH-MIB SFN mismatch, not only after `run_camping()` out-of-sync. The PBCH mismatch path is likely correcting local worker slot config without resetting or informing the sync/PRACH scheduling state.

## Next Experiment

CP73 should add PBCH-MIB mismatch feedback into the PRACH guard:

- Add a worker-pool note method for PBCH SFN mismatch, or reuse the existing note path with a distinct reason.
- Call it from `cc_worker.cc` where `PBCH-MIB: NR SFN ... does not match current SFN` is emitted.
- Reuse the same guard threshold and trace output, with a reason field such as `reason=pbch_mib_sfn_mismatch`.
- Run with `PAVONIS_SRSUE_PRACH_SYNC_GUARD_SLOTS=200` and trace enabled.

Success criterion for CP73 is not yet attach. It is seeing PRACH blocked after PBCH SFN mismatch and observing whether any allowed PRACH after both camping and PBCH stability changes the gNB detector result.
