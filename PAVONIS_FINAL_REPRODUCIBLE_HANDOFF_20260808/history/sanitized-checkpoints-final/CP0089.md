## Interpretation

CP89 shows that the first CP79 dump is clean when replayed through the recovered controlled receive path. The exact dump that looked intermittent in CP80/CP81 now produces `7/7` selected windows above `0.50`, all with nominal OCUDU `rb8/p0` hits.

This changes the interpretation of CP80/CP81:

- CP80 CP79 dump with CP79 RF env, RX gain 40, BW 10 MHz: `3/7`
- CP81 CP79 dump baseline env, RX gain 40, BW 10 MHz: `2/7`
- CP88 CP45 known-good, RX gain 30, BW 3 MHz: `7/7`
- CP89 CP79 dump baseline, RX gain 30, BW 3 MHz: `7/7`

The CP79 dump content itself is not the primary problem. The earlier poor CP79 dump replay was caused by the degraded controlled receive condition, or at least was dominated by it.

The live CP79 failure therefore remains more likely in one of these areas:

- Live UE/gNB timing or scheduling context.
- The CP79 RF scheduling hooks as used live, not the CP79 waveform content.
- The gNB-side receive/detection path, which is separate from this [host-redacted] controlled capture.
- Physical/RF environment variability during live runs.

## Next Action

The next checkpoint should replay the same CP79 dump with the CP79 RF environment active, still using [host-redacted] RX gain `30` and bandwidth `3 MHz`. That will isolate whether the CP79 burst-only, guard, timestamp-offset, and after-error hook combination corrupts the transmitted dump under otherwise clean controlled receive settings.

If that also passes cleanly, the controlled dump path is exonerated and the ladder should return to a live UE/gNB run with an accompanying [host-redacted] sniffer capture at the recovered settings. If it fails while CP89 passes, the CP79 RF hook combination is the next target.
