# Checkpoint 114 - CP111 zero-sample EOB stream-state audit

## Scope

Audit the CP111 live UE bladeRF transmit evidence after CP113 showed that the
five valid UE PRACH dumps were not recognizable in the gNB raw PRACH windows.
This checkpoint also addresses the thermal/RF-path theory: whether an
overheating antenna or RF path could explain the live failure.

## RF-path/thermal context

The live attach path is OTA in the artifacts, not a known cabled loopback:

- gNB side: `[host-redacted]` M2SDR/OCUDU transmits downlink and receives uplink PRACH.
- UE side: `[host-redacted]` bladeRF/srsUE transmits PRACH toward `[host-redacted]`.
- CP29 explicitly used `[host-redacted]` bladeRF TX1 into `[host-redacted]` M2SDR RX at the
  uplink frequency and passed as a controlled PRACH RF-path test.
- CP102/CP103 replayed a real failed-live PRACH dump through the current
  `[host-redacted]`-to-`[host-redacted]` RF path and saw strong correlation, roughly `0.90`, with
  nominal hit counts `6/7` and `7/7`.

Thermal conclusion: a passive antenna overheating is not a leading hypothesis.
A temperature-sensitive active RF component, amplifier, LNA, connector, or SDR
front-end can fail in principle, but CP102/CP103 strongly argue against a
persistent dead or badly attenuated physical RF path. The remaining suspect is
more specific: live srsUE/bladeRF transmit stream state differs from the
controlled replay path.

## Source finding

`srsRAN_4G/lib/src/radio/radio.cc` emits a zero-length end-of-burst when ending
the RF burst:

```c++
srsran_rf_send_timed2(
    &rf_devices[i], zeros.data(), 0, end_of_burst_time[i].full_secs, end_of_burst_time[i].frac_secs, false, true);
```

`srsRAN_4G/lib/src/phy/rf/rf_blade_imp.c` converts metadata flags and currently
passes the requested `nsamples` through to libbladeRF:

```c
status = bladerf_sync_tx(handler->dev, handler->tx_buffer, nsamples, &meta, [date-redacted]);
```

For `nsamples=0`, `is_end_of_burst=true`, this creates metadata with
`BLADERF_META_FLAG_TX_BURST_END`, no start flag, and zero samples. In CP111,
libbladeRF returned `-3`, `Invalid operation or parameter`, for the logged
instances of exactly that shape.

## Interpretation

CP114 does not prove the zero-sample EOB invalid calls suppress later PRACH
radiation. The five high-peak PRACH writes still return success from
`bladerf_sync_tx()`.

It does prove that the live srsUE path repeatedly sends a bladeRF operation that
libbladeRF rejects, shortly before and during the PRACH attempt window. This
behavior is absent from the controlled replay argument that proved the physical
RF path can carry the waveform. That makes zero-sample EOB handling a stronger
next suspect than antenna overheating or another blind RX-gain sweep.

## Next checkpoint

Patch the bladeRF backend narrowly so zero-sample end-of-burst requests are not
sent to `bladerf_sync_tx()` as invalid libbladeRF operations. Preserve logging so
the next run can prove the skip happened, rebuild/deploy the UE plugin, then
rerun the timing-instrumented live PRACH checkpoint with the same RF settings:

- `[host-redacted]` RX gain `30`
- UE PRACH time offset `-16000`
- TX guard `40000`
- `PAVONIS_RF_BLADE_PRACH_BURST_ONLY=1`

Expected discriminant:

- If gNB PRACH appears or raw-window correlation rises materially, the live
  blocker was likely bladeRF TX stream-state handling around invalid EOB.
- If nothing changes and invalid EOBs are gone, deprioritize stream-state EOB
  and move to live independent uplink capture or hardware/thermal spot checks.
