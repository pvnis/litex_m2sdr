## Baseline check against CP163

CP163 used the same wall-clock join formula and produced near-zero phase error:

- minimum absolute CP163 join delta: `0.035 ms`
- representative CP163 deltas: `-0.296 ms`, `-0.235 ms`, `-0.137 ms`,
  `-0.035 ms`, `-0.052 ms`

This makes CP211's stable `~33.5 ms` phase offset much less likely to be a
generic flaw in the join script. It points to something different in the CP211
live timing path, especially the first-high-peak TX stream restart and the
device-time basis after that restart.

## Offset feasibility

At `11.52 MS/s`, `33.5 ms` is about `386k` samples:

- `33.535 ms * 11520 samples/ms = 386323 samples`
- average CP211 nearest-window error `33.750 ms` is about `388796 samples`

The current high-peak write is only `24000` TX-domain samples after
`pre_tx_timestamp`:

- `tx_guard_samples=40000`
- `prach_time_offset_samples=-16000`
- final `tx_domain_delta_samples=24000`

Blindly advancing the current metadata timestamp by `~386k` samples would place
the requested TX timestamp about `362k` samples before the observed TX hardware
time. That is expected to become a late/past timed write rather than a useful
RF experiment.

## Interpretation

CP215 strengthens the current diagnosis:

- The UE emits valid high-peak PRACH buffers and timed metadata writes.
- CP213 proves the exact CP211 waveform crosses the RF path cleanly under
  controlled replay.
- CP214 proves the waveform is not in the saved CP211 gNB detector windows.
- The CP211 UE metadata is internally consistent with PRACH TTI spacing.
- The CP211 wall-clock phase is consistently shifted by `~33.5 ms` relative to
  the gNB saved PRACH windows.
- The same join method aligned to within `0.035 ms` in CP163.

This does not support antenna overheating, a dead antenna path, or a bad PRACH
waveform as the primary failure mode. The strongest remaining hypothesis is a
live device-time/window-alignment bug introduced or exposed by the TX stream
restart path.

## Decision

Do not make a large `prach_time_offset_samples` jump yet. The needed adjustment
is far larger than the live callback's current TX-domain guard, so that knob is
not a safe first correction.

Next checkpoint should instrument the RF TX debug path with an explicit
wall-clock timestamp at each high-peak write. That will let us compare:

- UE wrapper `START_UTC`
- UE log `secs/frac`
- RF hook wall-clock at `bladerf_sync_tx`
- bladeRF pre-TX/pre-RX timestamps
- gNB manifest `wall_ns`

If the instrumentation shows the `~33.5 ms` phase is real at the RF hook, then
the next live experiment should change scheduling at a level that can maintain a
valid future TX timestamp, not just apply a large negative timestamp offset.
