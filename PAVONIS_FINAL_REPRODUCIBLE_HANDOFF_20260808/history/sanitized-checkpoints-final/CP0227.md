## CP219 vs CP225 Divergence

CP219 was the last live run that produced high-peak PRACH metadata. Its UE log
contained:

- initial placeholder PRACH config:
  `config_idx=0 root_seq_idx=0 freq_offset=0 num_ra_preambles=0`
- later real RACH config:
  `config_idx=1 root_seq_idx=1 freq_offset=7 num_ra_preambles=64`
- PRACH sync guard decisions, including `block=0 stable_slots=200`
- four `Random Access Transmission` lines
- four `PRACH-TX` lines
- four high-peak RF TX debug `OK` lines with `cf32_peak` around `0.9926-0.9929`

CP225 used the CP219-style negative-offset control but only contained:

- the initial placeholder PRACH config:
  `config_idx=0 root_seq_idx=0 freq_offset=0 num_ra_preambles=0`
- no later real RACH config
- no PRACH sync guard decision lines
- no `Random Access Transmission`
- no `PRACH-TX`
- no high-peak RF TX debug lines

So the earliest observed divergence is before Msg1 TX: CP225 never receives or
applies the real RACH configuration that CP219 received.

## Interpretation

The first-failed stage has moved upstream from TX timing to UE DL acquisition /
SIB/RACH-config reception:

- gNB starts and strict gate passes.
- Remote process state is clean after CP226.
- [host-redacted] host temperatures are normal.
- bladeRF is visible and initialized.
- CP225 does not receive the real RACH config, so it cannot generate Msg1.

This does not prove antenna overheating. There is no direct antenna temperature
sensor in the collected data. It does make a physical/RF receive-path issue more
plausible than it was after CP219, because the current failure is on the UE
side before PRACH generation, not on the gNB detector after a known transmitted
waveform.
