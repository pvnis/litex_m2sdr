# Checkpoint 249 - Offline PRACH timing and detector correlation

## Summary

CP249 is an offline analysis of CP219, CP245, and CP247. It compares the UE high-peak PRACH RF writes against the nearest gNB PRACH detector windows using the captured wall-clock metadata and detector traces.

The stable result is:

- every high-peak PRACH write was accepted by bladeRF (`status=0`, `meta_status=0x0`),
- every high-peak write was finally scheduled at `pre_tx_timestamp + 24000` samples,
- the nearest captured gNB PRACH detector window had already completed about 15-26 ms before the UE RF debug hook,
- detector peaks at those nearest windows stayed far below threshold, with `accepted=0`.

This strengthens the current first-failed stage: when UE DL acquisition succeeds and PRACH is generated, Msg1 still does not arrive at the gNB detector as an acceptable preamble.

## Important RF Timestamp Detail

The current RF debug path does not simply transmit at the UE's original PRACH timestamp.

For each high-peak write:

1. srsUE passes a timed transmit timestamp to the bladeRF plugin.
2. If that timestamp is too close or already behind the TX hardware timestamp, the debug guard rewrites it to `pre_tx_timestamp + 40000`.
3. `PAVONIS_RF_BLADE_TX_DBG_PRACH_TIME_OFFSET_SAMPLES=-16000` is then applied.
4. The final timestamp becomes `pre_tx_timestamp + 24000`.

At 11.52 Msps, `24000` samples is about `2.083 ms`.

This means a more negative RF timestamp offset alone cannot move a waveform tens of milliseconds earlier than the current RF call. Once the original timestamp is already late, the guard dominates the final transmit time.

## Interpretation

The repeated `pre_tx + 24000` outcome shows the RF debug guard is rescuing late or near-late timed writes. It is making bladeRF accept the transmit calls, but it is also decoupling the actual RF write from the UE's original timed PRACH timestamp.

The current evidence does not prove whether the waveform is late relative to the actual RF window, because the wall-clock comparison depends on host clock alignment between `[host-redacted]` and `[host-redacted]`. It does prove that the gNB detector rows nearest to the UE RF hook do not contain an acceptably strong preamble.

Before changing timing again, the next checkpoint should be a non-invasive host clock sanity check. If host clocks differ by tens of milliseconds, the wall-clock correlation is not precise enough. If host clocks agree within a few milliseconds, then the next live debugging step should move above RF timestamp offsets and instrument or change when the UE worker reaches `radio->tx()`, because the RF call itself appears late by roughly one to two PRACH-window intervals.
