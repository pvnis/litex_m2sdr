# Checkpoint 250 - Remote clock sanity check

## Summary

CP250 was a read-only SSH clock sanity check for `[host-redacted]` and `[host-redacted]`.

Result:

- SSH access to both hosts is still feasible through the project pexpect helper.
- Both hosts report `NTPSynchronized=yes`.
- `chronyc` is not installed on either host.
- Direct non-pexpect SSH failed authentication, so a low-latency millisecond-grade clock comparison was not available from this environment.
- The pexpect samples are too noisy to validate the CP249 15-26 ms wall-clock timing relationship precisely.

This means CP249's wall-clock correlation remains useful as a coarse repeated pattern, but it should not be treated as millisecond-accurate proof of lateness.

The lower-RTT samples suggest the two remotes are not obviously separated by hundreds of milliseconds, but this method cannot prove or disprove a 15-26 ms inter-host offset.

## Direct SSH Attempt

```text

ssh -F /dev/null -o BatchMode=yes -o ConnectTimeout=5 [host-redacted]@[host-redacted] date -u +%s%N
```

Both failed authentication:

```text
Permission denied (publickey,password).
```

## Interpretation

The remotes report NTP sync, which is good, but CP250 does not provide a tight enough clock comparison to rely on the 15-26 ms wall-clock delta as an exact timing measurement.

The next timing experiment should avoid relying on host wall clocks. The better diagnostic is to preserve the UE's own original timed PRACH phase and shift it by exactly one known PRACH period in SDR samples:

```text
guard samples: 0
PRACH timestamp offset: +1843200 samples
sample rate: 11.52 Msps
offset duration: 160 ms
```

If the waveform and RF path are valid, the gNB detector should see the same PRACH preamble one PRACH opportunity later. Attach/RAR may still fail because the UE's RA-RNTI expectation would refer to the original occasion, but a non-empty gNB detection would isolate the issue to timing rather than waveform/path/frequency.
