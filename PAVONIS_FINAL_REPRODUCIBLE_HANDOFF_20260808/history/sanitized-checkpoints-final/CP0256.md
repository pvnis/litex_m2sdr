# CHECKPOINT 256 - Local PRACH Domain and Mapping Sanity - [date-redacted]

## Purpose

After CP254 found no recognizable UE waveform in the CP251 gNB predemod raw corpus, and CP255 live remote health checks were blocked by the usage-limit guard, this checkpoint verifies locally whether the CP254 comparison domain and PRACH frequency mapping assumptions are valid.

## Findings

### 1. gNB predemod raw files are full baseband PRACH windows

Source inspected:

- `ocudu/lib/phy/lower/processors/uplink/prach/prach_processor_worker.cpp`
- `ocudu/lib/phy/lower/modulation/ofdm_prach_demodulator_impl.cpp`

The `pavonis_prach_predemod_*.cf32` files are written after the lower PRACH worker has collected and converted the raw `ci16` baseband samples to `cf32`, but before `demodulator->demodulate(...)`.

That means CP254 compared the UE TX cf32 waveform against a meaningful receiver-domain raw PRACH window. It is not comparing against post-demodulated ZC bins.

### 2. CP251 gNB advertises `msg1-FrequencyStart=8`

CP251 actual gNB run config:

`cp251_nuc4_artifacts_[date-redacted]/.../[date-redacted]_033934_ota-stage/gnb-run.yml`

It sets:

- `prach_config_index: 1`
- no explicit `prach_frequency_start`

The CP251 gNB log advertises:

- `msg1-FrequencyStart: 8`
- `prach-RootSequenceIndex: l839 = 1`
- `prach-ConfigurationIndex: 1`

The CP251 gNB predemod manifest also records:

- `rb_offset=8`
- `nof_prb_ul_grid=52`
- `format=0`
- `start_symbol=0`

### 3. CP251 UE generates with `freq_offset=7`, and that is expected

CP251 UE log records:

- `config_idx=1`
- `root_seq_idx=1`
- `zero_corr_zone=0`
- `freq_offset=7`
- `carrier_nof_prb=52`
- `cell_nof_prb=50`

Source inspected:

- `srsRAN_4G/lib/src/asn1/rrc_nr_utils.cc`
- `srsRAN_4G/srsue/src/phy/nr/worker_pool.cc`
- `srsRAN_4G/srsue/src/phy/prach.cc`
- `srsRAN_4G/lib/src/phy/phch/prach.c`

The UE first parses `msg1-FrequencyStart`, then converts the 52 PRB NR carrier coordinate into the legacy LTE-sized 50 PRB PRACH generator coordinate:

`lte_nr_prach_offset = (52 - 50) / 2 = 1`

So gNB `msg1-FrequencyStart=8` becomes UE generator `freq_offset=7`.

This is intentional compatibility logic, not by itself an off-by-one failure.

### 4. Synthetic compatibility still passes

Reran the existing local probe:

`./pavonis_stage6_agent_artifacts_[date-redacted]T0918Z/prearmed_raw512_fast_[date-redacted]T0045Z/cp20_ocudu_prach_demod_detect_probe`

Result:

- `rb_offset=6`: no preamble
- `rb_offset=7`: no preamble
- `rb_offset=8`: detected preamble index 0, metric `610.253`
- `rb_offset=9`: no preamble
- `rb_offset=10`: no preamble

This confirms that a srsRAN UE waveform generated with UE-side `freq_offset=7` is detected by OCUDU at gNB-side `rb_offset=8`.

## Conclusion

CP256 rules out the apparent `freq_offset=7` versus `rb_offset=8` mismatch as the primary failure. It is the expected coordinate conversion for this 52 PRB NR carrier / 50 PRB legacy PRACH generator path.

Combined with CP254, the current evidence remains:

- Static PRACH generation and OCUDU detection are compatible.
- CP251 UE generated and bladeRF accepted high-peak PRACH writes.
- CP251 gNB raw PRACH windows do not contain a recognizable copy of the UE waveform.
- CP251 gNB detector accepted no preambles.

The next useful rung remains live hardware/RF path discovery once SSH/SCP is available again, or a local analysis of historical RF-path sweep artifacts while remote access is blocked.
