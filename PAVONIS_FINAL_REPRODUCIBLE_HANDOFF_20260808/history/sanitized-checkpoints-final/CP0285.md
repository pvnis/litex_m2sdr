# Checkpoint 285 - [host-redacted] bladeRF gain readback smoke

Timestamp: `[date-redacted]`

## Scope

Run a scoped `[host-redacted]` bladeRF CLI/API sanity check after CP283 showed:

```text
requested rx_gain=30
srsUE immediate readback actual=60
```

No gNB was started, no srsUE was started, and no TX stream was enabled. The
probe only queried device state and tested RX1 gain commands through
`bladeRF-cli`.

## Gain Command Result

With AGC enabled, `set gain rx1 20` failed:

```text
Gain on RX1 cannot be changed while AGC is enabled.
Error: Operation invalid in current state
```

After explicitly disabling RX1 AGC:

```text
set agc rx1 off
RX1 AGC: Disabled
```

The CLI accepted lower gain requests:

```text
Setting RX1 overall gain to 20 dB
Setting RX1 overall gain to 30 dB
Setting RX1 overall gain to 40 dB
Setting RX1 overall gain to 60 dB
```

But each accepted set printed:

```text
Note: This change will not be visible until the channel is enabled.
```

Immediate readback stayed at `60 dB` while the RX channel was disabled. The
probe restored the prior CLI-visible state:

```text
set agc rx1 on
RX1 AGC: Enabled
RX2 AGC: Enabled
Gain RX1 overall: 60 dB
Gain RX2 overall: 60 dB
```

## Interpretation

CP285 explains why CP283's immediate srsUE gain readback was ambiguous. The
bladeRF 2.0 CLI accepts lower RX gain while the channel is disabled, but warns
that the change is not visible until the channel is enabled. The current srsUE
instrumentation logs `actual=60` immediately after `bladerf_set_gain`, before
`start_rx_stream` enables RX.

Therefore, CP283 did not prove that `rx_gain=30` failed to apply. It proved
only that the current readback point is too early to answer that question.
