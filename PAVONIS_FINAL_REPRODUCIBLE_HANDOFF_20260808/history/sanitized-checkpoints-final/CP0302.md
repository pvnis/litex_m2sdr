# Checkpoint 302: CP300 start-gNB uncertainty hardening

## Purpose

Further harden the CP300 watchdog launcher for unstable SSH/SCP conditions before attempting any live RF.

The user reported unstable internet and requested all-or-nothing planning so a TX opportunity is not wasted if RX/log retrieval may time out.

## Change

Updated:

- `cp300_run_stage6_native_timed_no_guard_no_offset_repeat_after_cp299_invalid_watchdog_sequence.sh`

The launcher now treats a local failure or timeout during `start_gnb` as an uncertain state where gNB may have started remotely.

Previous behavior:

- `start_gnb` was a mandatory top-level step.
- If the local SSH wrapper failed or timed out during that step, the script exited through cleanup before setting `GNB_STARTED=1`.
- The remote watchdog was armed, but immediate cleanup might not run.

New behavior:

- `start_gnb` is captured into `START_GNB_RC`.
- `GNB_STARTED=1` is set immediately after the `start_gnb` command returns, even on nonzero status.
- If `START_GNB_RC != 0`, the launcher logs:
  - `SKIP_GATE_AND_UE start_gnb_uncertain_or_failed rc=<rc>`
- It skips strict gate and UE launch.
- It still runs:
  - `stop_nuc4`
  - `disarm_nuc4_watchdog`
  - `package_nuc4`
  - artifact retrieval if packaging produced the tar
  - final process checks

This makes the failure mode conservative: a connection timeout during gNB startup is handled as "possibly started, clean up now" rather than "not started, rely only on delayed watchdog."
