# Checkpoint 312: self-contained positive-offset live run

## Purpose

Run the CP311 timing candidate under the unstable laptop-to-NUC control link:
keep the RF sequence NUC-owned after launch, wait for the gNB strict gate on
[host-redacted], then let [host-redacted] start UE only after [host-redacted] serves `GO`.

This rung used the CP300 acquisition condition with a positive PRACH timestamp
offset intended to target the next gNB PRACH receive window.

- `PAVONIS_RF_BLADE_TX_DBG_TX_GUARD_SAMPLES=0`

The `1631722` sample offset came from CP311's RF-hook timing audit. It was
chosen to move CP300's native scheduled PRACH writes from about `18.3-18.8 ms`
after the nearest gNB PRACH window to the next PRACH window, about
`141.4-141.8 ms` later.

## Interpretation

CP312 proves the new self-contained pattern is feasible under the lossy
laptop-to-NUC control link:

- [host-redacted] can wait on [host-redacted]'s HTTP gate.
- [host-redacted] can start gNB, pass strict gate, arm, serve `GO`, sleep for the bounded
  run window, stop gNB, and package artifacts without requiring the laptop link
  to stay stable.
- [host-redacted] can start the UE only after `GO` and package its artifacts.

CP312 does not test the positive PRACH offset hypothesis. The UE never reached
the real RACH configuration or any high-peak PRACH TX path, so the RF driver did
not exercise `PAVONIS_RF_BLADE_TX_DBG_PRACH_TIME_OFFSET_SAMPLES=1631722`.

The next useful rung is a self-contained CP300-style control run with offset
`0`. That separates two possible causes:

- self-contained orchestration or launch timing changed UE acquisition behavior
- the positive offset branch is fine, but this specific run lost DL/SFN sync
  before RACH
