# Checkpoint 380: no-RF source audit for next lower RX tap

## Purpose

After CP378 tested the active-gNB UL-center frequency hypothesis and still found
no gNB detection or CP361 waveform copy, identify the next receive-side
instrumentation point below the current PRACH and UL-symbol taps.

This checkpoint is source audit only. It consumes no RF.

## Lower receive path

The first OCUDU-owned receive point after the Soapy driver is:

```text
ocudu/lib/radio/soapy/radio_soapy_rx_stream.cpp
radio_soapy_rx_stream::receive(baseband_gateway_buffer_writer& buffs)
```

Key source flow:

```text
device.acquire_read_buffer(...)
memcpy into buffs[ch].subspan(...)
return baseband_gateway_receiver::metadata{ts=...}
```

Then lower PHY consumes the same buffer:

```text
ocudu/lib/phy/lower/lower_phy_baseband_processor.cpp
lower_phy_baseband_processor::ul_process()

rx_metadata = receiver.receive(rx_buffer->get_writer())
uplink_processor.process(ul_buffer->get_reader(), apply_timestamp_sfn0_ref(rx_metadata.ts))
```

That means a tap in `radio_soapy_rx_stream::receive()` sees raw `ci16_t` samples
after Soapy acquisition and before:

- lower PHY timestamp alignment,
- OFDM-symbol collection,
- `ci16 -> cf32` conversion in the uplink processor,
- CFO correction,
- PRACH worker collection,
- PRACH demodulation/detection.

## Finding

CP378 already ruled out the best simple replay phase/frequency explanations:

- strict gate passed with zero Soapy TX timeouts,
- replay TX emitted `47` high-peak bursts,
- phase sweep crossed within `0.095 ms` of PRACH row `idx=56`,
- active gNB accepted zero preambles,
- direct correlation stayed noise-like in PRACH rows and near-window rows.

The next useful discriminant is therefore not another replay timing/frequency
change. It is a lower receive tap that can answer:

1. Does the CP361 replay energy appear in raw Soapy RX buffers at all?
2. If yes, does it disappear between Soapy RX and the existing UL-symbol/PRACH
   taps?
3. If no, the problem is below OCUDU lower PHY: RF coupling, M2SDR RX path,
   Soapy stream/channel/frequency behavior, or physical/driver state.

## Recommended patch

Add env-gated debug-only instrumentation in
`lib/radio/soapy/radio_soapy_rx_stream.cpp`:

- `PAVONIS_SOAPY_RX_DUMP=1`
- `PAVONIS_SOAPY_RX_DUMP_ARM_FILE=/tmp/..._arm`
- `/tmp/pavonis_soapy_rx_manifest.tsv`
- bounded `/tmp/pavonis_soapy_rx_*.cf32`

The manifest should record one row per completed `receive()` buffer and port:

- index, wall-clock ns, returned baseband timestamp,
- sample count, Soapy loop/overflow counters,
- normalized `ci16` RMS/peak,
- arm file and optional raw snapshot path.

Raw snapshots should be bounded and triggerable by:

- `PAVONIS_SOAPY_RX_RAW_MAX`
- `PAVONIS_SOAPY_RX_RAW_PERIOD`
- `PAVONIS_SOAPY_RX_RAW_PEAK_MIN`
- `PAVONIS_SOAPY_RX_RAW_RMS_MIN`

For the next RF checkpoint, keep the strict gate and use the same arm file as
the existing taps. Save summaries for the full post-GO window, and save raw
buffers only on threshold or a bounded period so collection remains tractable
under unstable laptop networking.
