## Source Finding

The active gNB uses the ocudu Soapy radio path:

- `ocudu/lib/radio/soapy/radio_soapy_impl.cpp`
- `ocudu/lib/radio/soapy/radio_soapy_device.h`

Before CP425, that path configured Soapy sample rate, center frequency, and
gain, but did not call `setBandwidth()` and did not log Soapy bandwidth
readback.

The M2SDR Soapy driver applies default stream bandwidths:

```text
LiteXM2SDRDevice.cpp:704  Applying default RF settings
LiteXM2SDRDevice.cpp:709  _rx_stream.samplerate = 30.72e6
LiteXM2SDRDevice.cpp:713  _rx_stream.bandwidth  = 30.72e6
LiteXM2SDRDevice.cpp:714  _tx_stream.bandwidth  = 30.72e6
```

The same driver later reapplies the stored bandwidth during channel
configuration:

- TX `setBandwidth()` in `channel_configure()`
- RX `setBandwidth()` in `channel_configure()`

## Interpretation

CP424 found a concrete active-versus-controlled receive-path difference:

- CP422 controlled passive RX explicitly used `BW_HZ=10000000` and passed `7/7`
  at the active UL center.
- The active ocudu Soapy gNB path was not explicitly setting RF bandwidth.
- The LiteXM2SDR Soapy driver default is `30.72 MHz` bandwidth.

This is not yet RF proof that RF bandwidth is the active-gNB failure cause, but
it is a stronger hypothesis than another blind phase or frequency replay. The
next rung should make bandwidth explicit and log readbacks before spending
another sens TX attempt.
