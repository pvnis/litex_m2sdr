## Interpretation

CP470 did not validate the CP469 static timing estimate. Changing from CP467's
`FIRST_BURST_MS=605`, `PERIOD_MS=159` to CP470's `FIRST_BURST_MS=618`,
`PERIOD_MS=160` moved the nearest replay/PRACH timing to a stable but late
offset of about `+9 ms`, not the expected near-zero offset.

This means the absolute phase between [host-redacted]'s replay schedule and gNB PRACH
windows is not stable enough across runs to use a single wall-clock-derived
`FIRST_BURST_MS` as a phase lock. CP470 also did not improve active gNB
visibility: detector ratios and direct-correlation scores remain in the same
weak band as CP458/CP467.

The next timing-focused RF step, if one is still warranted, should sweep through
the offset inside one run rather than rely on a fixed static phase. The direct
variant from CP470 is `FIRST_BURST_MS=618`, `PERIOD_MS=159`: it should start
near the CP470 late side and drift about `1 ms` earlier per burst, crossing the
candidate PRACH phase during the run if the CP470 phase relationship repeats.
