# Checkpoint 506 - Active vs Standalone RX Activation Audit

Date: [date-redacted] UTC
Reference active stamp: [date-redacted]

## Purpose

After CP504 stayed negative with active-gNB TX payloads zeroed after arm, audit
the remaining active-vs-standalone radio configuration surface before spending
another RF run.

## Findings

The obvious RF settings match between the active negative and standalone
positive paths.

CP504 active gNB readback:

- RX frequency: `1747500000`
- TX frequency: `1842500000`
- sample rate: `11520000`
- RX gain: `50`
- TX gain: `0`
- RX bandwidth: `10000000`
- TX bandwidth: `10000000`
- RX stream channel: `0`

CP501 standalone positive settings:

- RX frequency: `1747500000`
- TX frequency: `1842500000`
- sample rate: `11520000`
- RX gain: `50`
- TX gain: `0`
- RX bandwidth: `10000000`
- TX bandwidth: `10000000`
- RX/TX format: `CS16`

The meaningful active-only difference visible in the logs is RX timed
activation:

- CP504 active gNB requested RX timed activation:
  `requested=712111518720 samples`
- LiteXM2SDR aligned in `readStream`
- alignment dropped `2255` packets / `1150050` samples before active RX delivery

The standalone CP499/CP500/CP501 recorder uses immediate RX activation:

- `dev.activateStream(rx_stream)`
- no `SOAPY_SDR_HAS_TIME` activation request
- no timed-start drop/alignment path

## Patch Prepared

Prepared a default-off LiteXM2SDR split:

`M2SDR_SOAPY_RX_IGNORE_TIMED_ACTIVATION=1`

When enabled, RX `activateStream(...SOAPY_SDR_HAS_TIME...)` logs:

`RX_IGNORE_TIMED_ACTIVATION active: ignoring requested RX timed activation ...`

and starts RX immediately instead of setting `timed_start_pending`. Existing
runs keep current behavior when the env var is unset or `0`.

The self-contained launcher and [host-redacted] active start helper now forward/log:

`M2SDR_SOAPY_RX_IGNORE_TIMED_ACTIVATION`

## Interpretation

The next build/run should test active gNB with RX timed activation ignored while
leaving the CP495 delayed raw-capture shape and strict GO/CANCEL gate intact.

Expected branch:

- If CP361 becomes visible, the active disappearance is tied to timed RX
  activation/drop/alignment.
- If CP361 remains absent, the problem is deeper active-gNB RX runtime state
  rather than obvious RF config, TX payload, or the timed-activation drop.
