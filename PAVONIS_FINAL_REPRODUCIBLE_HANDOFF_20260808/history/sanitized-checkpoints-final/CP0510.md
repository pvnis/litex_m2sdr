# Checkpoint 510 - Active vs Standalone RX Read API Audit and Local Build

Date: [date-redacted] UTC

## Purpose

After CP508 ruled out timed RX activation as the sufficient cause, audit the
remaining active-vs-standalone RX API difference before spending another RF
attempt.

## Finding

The active ocudu gNB RX path uses Soapy zero-copy read buffers:

- `lib/radio/soapy/radio_soapy_rx_stream.cpp`
- `radio_soapy_rx_stream::receive()`
- `device.acquire_read_buffer(...)`

The standalone full-duplex checks that recovered CP361 in CP499, CP500, and
CP501 use ordinary Soapy `readStream()` through:

- `cp498_nuc4_soapy_cs16_fullduplex_recorder.py`
- `dev.readStream(rx_stream, [rx_buf], chunk, timeoutUs=...)`

LiteXM2SDR implements both APIs. Its `readStream()` path internally uses
`acquireReadBuffer()`/`releaseReadBuffer()` but adds driver-side copy and
remainder handling. That makes the ocudu zero-copy receive loop a concrete
remaining split from the standalone positives.

## Local Patch

Added a default-off ocudu knob:

`OCUDU_SOAPY_RX_USE_READSTREAM=1`

When enabled, `radio_soapy_rx_stream::receive()` fills the caller's RX buffer
with `device.read_stream(...)` instead of using the ocudu zero-copy
`acquire_read_buffer(...)` loop. The default remains the existing zero-copy
path when the variable is unset or `0`.

Local source files touched:

- `/home/[host-redacted]/CLionProjects/ocudu/lib/radio/soapy/radio_soapy_device.h`
- `/home/[host-redacted]/CLionProjects/ocudu/lib/radio/soapy/radio_soapy_rx_stream.h`
- `/home/[host-redacted]/CLionProjects/ocudu/lib/radio/soapy/radio_soapy_rx_stream.cpp`

Local verification found the expected strings:

- `OCUDU_SOAPY_RX_USE_READSTREAM`
- `read_stream(...)`
- `Soapy RX stream {} using readStream fallback instead of acquireReadBuffer`
- `readStream returned`

Local build:

`cmake --build cmake-build-debug --target gnb -j2`

Result: passed. The build relinked ocudu radio libraries and
`apps/gnb/gnb`.
