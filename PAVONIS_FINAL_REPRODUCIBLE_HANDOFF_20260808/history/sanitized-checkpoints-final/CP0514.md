# Checkpoint 514 - Zero-Copy vs readStream Root-Cause Audit

Date: [date-redacted] UTC

## Purpose

Explain the CP512 result before spending another RF attempt. CP512 showed that
switching active ocudu RX from `acquireReadBuffer()` to `readStream()` recovers
CP361 strongly in active gNB Soapy raw, while PRACH predemod/detector still
remain negative.

## Source Finding

LiteXM2SDR's frame layout is always two-channel interleaved, even in 1T1R mode:

`LiteXM2SDRDevice.hpp`

- `_frameChannels = 2`
- comment: each DMA beat carries `IA, QA, IB, QB`
- disabled channel fields remain present in the frame

LiteXM2SDR `acquireReadBuffer()` exposes the raw packet payload:

`LiteXM2SDRStreaming.cpp`

- computes `byte_offset = packet_offset * _frameChannels * _bytesPerComplex`
- sets only `buffs[0] = pkt->data + byte_offset`
- returns `packet_samps`

It does not deinterleave selected logical channels for the direct-buffer API.

LiteXM2SDR `readStream()` does deinterleave:

- acquires the same read buffer internally
- tracks remainder state in the driver
- calls `deinterleave(...)` for each selected channel
- `deinterleaveCS16()` advances the source by
  `_frameChannels * _samplesPerComplex` for every output sample

ocudu's zero-copy path assumed each `rd_buffs[ch]` points to contiguous channel
samples:

`radio_soapy_rx_stream.cpp`

- calls `device.acquire_read_buffer(...)`
- casts `rd_buffs[ch]` to `const ci16_t*`
- copies `copy_samps * sizeof(ci16_t)` directly into the lower-PHY buffer

That assumption is invalid for LiteXM2SDR's direct RX buffers because the raw
payload is interleaved as `ch0, ch1, ch0, ch1, ...` in complex-sample units.

## Interpretation

CP512 recovered CP361 because `readStream()` performed the missing
deinterleave/copy step. CP495, CP504, and CP508 did not see CP361 in active
Soapy raw because ocudu's zero-copy consumer copied an interleaved two-channel
DMA payload as though it were a contiguous one-channel stream.

This is a concrete root cause for the active raw-RX disappearance:

`LiteXM2SDR acquireReadBuffer direct-buffer semantics are incompatible with the ocudu zero-copy consumer's contiguous-channel assumption.`

The least invasive operational fix is to keep using `readStream()` for
LiteXM2SDR active gNB RX. A deeper code fix would either:

- make ocudu avoid direct-buffer RX for LiteXM2SDR, or
- make LiteXM2SDR's direct-buffer API return per-channel contiguous buffers,
  likely by staging/deinterleaving and losing true zero-copy, or
- explicitly expose a driver capability/stream argument so ocudu can choose the
  safe copied `readStream()` path for interleaved direct buffers.

## Remaining Gap

CP512 is not a PRACH-detector recovery. Soapy raw now sees CP361 strongly, but
PRACH predemod correlation remains below `0.022` and detector accepted `0`.
The next branch is lower-PHY/PRACH window timestamp handoff: why the
readStream-recovered CP361 samples are not landing in the gNB PRACH predemod
windows.
