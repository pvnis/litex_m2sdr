# Checkpoint 576 - Live vs Controlled TX Path Source Audit

Date: [date-redacted] UTC

## Purpose

Audit the source/config difference between CP570 live UE PRACH and CP573
controlled replay. CP572/CP575 show no CP570 live waveform in any plausible
saved gNB PRACH window, while CP573 shows CP570 dump `000001` is strongly
RF-visible when replayed.

## Live Plugin Behavior

The local live source is:

- `/home/[host-redacted]/CLionProjects/srsRAN_4G/lib/src/phy/rf/rf_blade_imp.c`

Relevant behavior in `rf_blade_send_timed`:

- With `PAVONIS_RF_BLADE_PRACH_BURST_ONLY=1`, low-peak chunks are skipped.
- A high-peak chunk that is not already start-of-burst gets
  `BLADERF_META_FLAG_TX_BURST_START`.
- In burst-only mode, that same high-peak chunk also gets
  `BLADERF_META_FLAG_TX_BURST_END`.
- If `PAVONIS_RF_BLADE_TX_DBG_PRACH_TIME_OFFSET_SAMPLES` is nonzero, the code
  adjusts `meta.timestamp` after pre-TX timestamp probing.
- The write occurs only if it was not skipped and prior restart logic did not
  already set a failure status:
  `bladerf_sync_tx(handler->dev, handler->tx_buffer, nsamples, &meta, [date-redacted])`.

CP570 metadata confirms the live high-peak PRACH path was not intentionally
skipped:

- `force_sob=1`
- `force_eob=1`
- `flags=0x3`
- `prach_time_offset_applied=1`
- `tx_skipped_after_error=0`
- `status=0`
- `pre_tx_status=0`
- `post_tx_status=0`

The `tx_skip_after_error=1` setting was present, but the code only uses it to
skip after an error in the high-peak EOB-then-SOB mode. CP570 had
`PAVONIS_RF_BLADE_HIGH_PEAK_EOB_THEN_SOB=0`, and the metadata shows
`tx_skipped_after_error=0`.

## Controlled CP573 Replay Path

CP573 used:

- `cp47_srsran_blade_plugin_paced_sparse_timed_tx.c`
- the same RF plugin API via `api->srsran_rf_send_timed(...)`

But the controlled replay sends a timed sequence of chunks where only the first
chunk is start-of-burst and only the final chunk is end-of-burst. The replay's
high PRACH chunks are embedded in that continuous stream.

CP573 high-burst debug lines show:

- `has_time=1`
- `timestamp=0`
- `flags=0x0`
- `force_sob=0`
- `force_eob=0`
- `tx_delta_samples=0`
- `status_str=OK`
- `cf32_rms=0.564712405`
- `cf32_peak=0.998748481`

So CP573 proves the CP570 waveform and gross RF path are good, but it does not
exercise the live CP570 stand-alone timed SOB/EOB PRACH burst path.

## Interpretation

CP576 identifies the next concrete failure boundary. The controlled replay pass
is not equivalent to the live UE PRACH TX semantics:

- CP570 live PRACH: high peak, stand-alone timed SOB/EOB burst, positive
  timestamp offset, low chunks skipped.
- CP573 controlled replay: high peak inside a continuous timed stream, no
  forced SOB/EOB on the PRACH chunks.

This explains how CP573 can pass while CP570 live PRACH remains invisible at
the gNB. The next controlled rung should replay a CP570 dump while deliberately
enabling the live-style `PAVONIS_RF_BLADE_PRACH_BURST_ONLY=1` path, so the
controlled replay exercises forced timed SOB/EOB PRACH bursts. If that fails or
degrades, the failure is in the live-style bladeRF burst semantics. If it still
passes, the remaining difference is deeper in srsUE live scheduling/state rather
than the RF plugin's burst-only timed write path.
