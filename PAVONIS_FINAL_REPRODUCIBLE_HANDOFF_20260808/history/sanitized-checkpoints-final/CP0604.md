## Purpose

CP603 showed that CP599/CP601 no-accept repeats had strong lower-RX copies about
`0.74 ms` late relative to the detector-max PRACH windows, while CP597 accepted

## Findings

The live CP570 wrappers set the active recipe through CP579:

- `PERIOD_MS=159`
- `FIRST_BURST_MS=585`
- `TIMED_LEAD_MS=0`
- `PACE_LEAD_MS=2.0`
- `RF_ENV_TX_DBG_PRACH_TIME_OFFSET_SAMPLES=1773655` from the CP597/599/601
  wrappers

The two-NUC gate is safe but not phase-locked:

- [host-redacted] starts first, builds the TX helper, and waits on the [host-redacted] HTTP gate
- [host-redacted] starts gNB, runs strict gate, arms dumps/probes, and publishes `GO`
- [host-redacted] starts timed replay only after reading `GO`
- no [host-redacted] code reads the gNB PRACH window timestamps before choosing its
  first TX timestamp

The TX harness has millisecond chunk granularity for burst placement:

- `CHUNK_SAMPLES=11520`
- `FS_HZ=11520000`
- one chunk is exactly `1 ms`
- `FIRST_BURST_MS` is rounded to `first_burst_chunk`
- `PERIOD_MS=159` is rounded to `period_chunks=159`

The harness can still shift all timed chunks by sub-millisecond values:

- it samples bladeRF device time with `srsran_rf_get_time`
- it adds `TIMED_LEAD_MS / 1000.0` to `TX_START`
- every chunk timestamp is then `TX_START + c * 1 ms`

The plugin-side PRACH offset is also sub-millisecond and sample-accurate:

- `PAVONIS_RF_BLADE_TX_DBG_PRACH_TIME_OFFSET_SAMPLES` is applied only to
  high-peak chunks
- for a positive value, it directly adds samples to `meta.timestamp`
- for a negative value, it subtracts samples from `meta.timestamp`
- the debug log records old/new timestamps and post-offset deltas

The arm file starts [host-redacted]-side dumps/probes and detector instrumentation. It does
not create a closed-loop timing relationship between [host-redacted] TX and active gNB
PRACH windows.

## Decision

Do not use `FIRST_BURST_MS` for the next sub-millisecond correction. It is a
coarse whole-millisecond burst-index knob in the current harness.

Do not spend the next live attempt on another tiny `PRACH_TIME_OFFSET` nudge.
CP593/CP595 already showed that one-sample offset changes did not behave like a
smooth alignment control in the active run.

The next live hypothesis should preserve the proven CP597 offset and apply a
sub-millisecond `TIMED_LEAD_MS` correction:

- keep `RF_ENV_TX_DBG_PRACH_TIME_OFFSET_SAMPLES=1773655`
- set `TIMED_LEAD_MS=-0.67`
- keep threshold `0.24`, RX/TX BW `10 MHz`, gNB RX gain `50`, TX backoff `20`

Rationale:

- CP599 detector max lower-RX alignment: `+0.738542 ms`
- CP601 detector max lower-RX alignment: `+0.747309 ms`
- CP597 accepted alignment band: `+0.053646 ms` to `+0.085330 ms`
- a `-0.67 ms` timed-start shift should move the no-accept late-copy mode into
  roughly `+0.07 ms`

This is still a live hypothesis, not a guarantee. The key improvement is that it
tests a specific phase error measured from two valid negative repeats.
