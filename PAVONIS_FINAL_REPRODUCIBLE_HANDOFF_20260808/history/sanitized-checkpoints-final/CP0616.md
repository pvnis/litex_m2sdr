# CHECKPOINT 616 - Live gNB BW10 control audit

Date: [date-redacted]

## Verdict

`CP616_NO_RF_LIVE_GNB_BW10_CONTROL_AUDIT_PASS`

The next live rung is feasible, but it should not reuse the active-replay
`cp485` start helper directly.  The clean one-variable follow-up to CP614 is a
minimal live gNB start helper cloned from the CP614 live helper with only
explicit Soapy RX/TX bandwidth control added.

## Context

CP614 was a valid live UE run:

- UE reached real live Msg1 attempts: `Random Access Transmission=6`,
  `PRACH-TX=6`.
- UE TX debug showed six healthy high-peak timed PRACH writes with
  `prach_time_offset_samples=1765915` and `prach_time_offset_applied=1`.
- gNB did not detect Msg1: accepted rows `0`, threshold-pass rows `0`,
  non-empty `detected_preambles=0`.
- CP614 gNB log readback showed RX/TX bandwidth at `30720000`, while the CP611
  active-replay accept used explicit Soapy RX/TX bandwidth `10 MHz`.

## Files audited

- `cp95_nuc4_start_stage6_rxgain30_remote.sh`
- `cp454_nuc4_strict_gnb_gate_soapy_rx_tx_bw10m_remote.sh`
- `cp485_nuc4_start_stage6_rxgain50_soapy_rxtxbw10m_txbackoff20_tsbridge_txprobe_remote.sh`
- `cp614_launch_selfcontained_liveue_netcp611offset1765915_rxgain50_prachdetthr0p24_syncguard80_raw512.sh`
- `cp557_nuc4_selfcontained_positive_offset_orchestrator_remote.sh`

## Findings

`cp95_nuc4_start_stage6_rxgain30_remote.sh`, the live start helper used by the
CP557/CP614 pattern, only patches `rx_gain` in the gNB config and exports the
PRACH/UL-symbol tracing controls. It does not set:

- `OCUDU_SOAPY_RX_BW_HZ`
- `OCUDU_SOAPY_TX_BW_HZ`
- `OCUDU_SOAPY_RF_BW_HZ`

`cp454_nuc4_strict_gnb_gate_soapy_rx_tx_bw10m_remote.sh` is already suitable as
the gNB strict gate for a BW10 live rung. It verifies:

- no `SoapySDR TX: writeStream timeout` entries,
- `Setting RX ch0 bandwidth to 10.000 MHz`,
- `Soapy RX ch0 readback:.*bandwidth_Hz=10000000`,
- `Setting TX ch0 bandwidth to 10.000 MHz`,
- `Soapy TX ch0 readback:.*bandwidth_Hz=10000000`.

`cp485_nuc4_start_stage6_rxgain50_soapy_rxtxbw10m_txbackoff20_tsbridge_txprobe_remote.sh`
does set the desired bandwidth exports, but it also changes other active-replay
runtime conditions including TX backoff, lower-PHY timestamp bridge/probe
instrumentation, Soapy RX dump controls, and M2SDR TX probe/dumps. Using it
directly for the next live UE rung would not isolate the bandwidth variable from
CP614.

`cp557_nuc4_selfcontained_positive_offset_orchestrator_remote.sh` can still be
used unchanged. It runs whichever remote files are installed as
`stage6_cp557_start_nuc4.sh` and `stage6_cp557_strict_gate_nuc4.sh`, so a launch
wrapper can stage a CP617-specific start helper and the existing BW10 strict
gate at those remote paths.

## Decision

Create CP617 as a live UE follow-up to CP614 with one intended gNB-side change:
force Soapy RX/TX bandwidth to `10 MHz`.

Keep from CP614:

- live UE path,
- `PRACH_OFFSET_SAMPLES=1765915`,
- `PRACH_SYNC_GUARD_SLOTS=80`,
- detector threshold `0.24`,
- gNB RX gain `50`,
- raw PRACH window max `512`,
- targeted UL-symbol capture,
- strict GO/CANCEL orchestration.

Change from CP614:

- use a minimal new [host-redacted] start helper that exports
  `OCUDU_SOAPY_RX_BW_HZ=10000000` and `OCUDU_SOAPY_TX_BW_HZ=10000000`,
- use `cp454_nuc4_strict_gnb_gate_soapy_rx_tx_bw10m_remote.sh` so the run is
  invalid unless the 10 MHz RX/TX readbacks are observed.
