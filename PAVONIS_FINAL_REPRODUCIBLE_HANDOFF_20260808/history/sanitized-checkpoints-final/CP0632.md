## Detector gate source

Relevant source observations:

- Threshold selection happens via `detail::get_threshold_and_margin(th_params)`.
- `PAVONIS_PRACHDET_THRESHOLD_OVERRIDE` replaces `threshold` only when present,
  finite, and positive.
- `max_delay_samples` is computed from `cp_prach`, `N_cs`, `dft_size`, and
  `L_ra`.
- `result.time_advance_max` and the trace use `max_delay_samples * 0.8`.
- The acceptance condition is:

```cpp
if ((delay < metric_global.size()) && (peak > threshold) &&
    (delay < static_cast<float>(max_delay_samples) * 0.8)) {
  result.preambles.emplace_back();
  info.detection_metric = peak / threshold;
}
```

The trace's `best_ratio` is also `peak / threshold`, so CP630's lower threshold
inflates ratio but does not change the raw metric value.

## Interpretation

CP626, CP628, and CP630 already showed strong lower Soapy RX copies while the
active detector missed. CP632 adds that the detector-input pre-demod raw power
around the decisive failed rows is not obviously weaker than CP611.

The next unknown is inside the normalized detector metric:

- Is the numerator at preamble 0 lower?
- Is the denominator/noise estimate higher?
- Is the reference window contaminated by the replay/timing placement?
- Is the peak split across adjacent delays or preambles?
- Does the local metric neighborhood differ between CP611 and the repeats?

The current trace cannot answer those questions because it logs only the final
`peak` and `delay`.
