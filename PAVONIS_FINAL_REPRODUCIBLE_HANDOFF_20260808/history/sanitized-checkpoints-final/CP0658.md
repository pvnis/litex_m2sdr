## Answer to overheating theory

Current evidence does not support ordinary host or CPU overheating as the immediate cause:

- [host-redacted] CPU package was only about `54 C`.
- [host-redacted] CPU package was only about `57 C`.
- Both are far below the `100 C` high/critical thresholds reported by `sensors`.
- Historical throttle counters exist, especially on [host-redacted], but they are cumulative since boot and were not measured as deltas around a run.

The probe does not directly measure antenna temperature. A passive antenna is not expected to overheat in this setup; an active RF component, SDR, USB path, cable, or power state can still be unstable. The strongest observed lead is not temperature but transmitter-side USB resets of the bladeRF path.

## Interpretation

CP658 shifts the leading failure branch to `[host-redacted]` bladeRF USB path stability:

- CP653 accepted once using the baseline settings.
- CP657 repeated those baseline settings and did not accept.
- The CP657 gNB and sens wrappers completed cleanly at the application level, but the detector saw no accepted PRACH.
- [host-redacted] kernel logs show `usb 4-2` SuperSpeed resets aligned with both CP656 and CP657, and another reset when the health probe touched the bladeRF.

This is a plausible explanation for why the RF path changed after CP653: the TX device may be resetting or reinitializing around runs, changing timing/state or disrupting the replay path even when the higher-level TX process returns success.
