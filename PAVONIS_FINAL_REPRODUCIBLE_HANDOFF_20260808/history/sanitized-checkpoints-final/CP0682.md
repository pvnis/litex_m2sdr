## srsUE retry source

srsUE NR RA behavior is governed by the RACH config:

- `proc_ra_nr::set_config()` logs config index, `preambleTransMax`, and response
  window.
- `ra_procedure_initialization()` sets `preamble_transmission_counter = 1`.
- it copies `rach_cfg.preambleTransMax` into the RA procedure state.
- `ra_error()` increments the preamble counter after a RAR timeout or other RA
  error.
- it stops retrying when
  `preamble_transmission_counter >= rach_cfg.preambleTransMax + 1`.
- `prach_sent()` prints the console line
  `Random Access Transmission: ...` and starts the RAR timeout.

Relevant source lines:

- `proc_ra_nr.cc:70`: config log includes `preambleTransMax`.
- `proc_ra_nr.cc:150`: retry log prints current counter and max.
- `proc_ra_nr.cc:165`: stores `rach_cfg.preambleTransMax`.
- `proc_ra_nr.cc:318`: max-transmission stop condition.
- `proc_ra_nr.cc:319`: max-transmission warning.
- `proc_ra_nr.cc:366`: console `Random Access Transmission` line.
- `proc_ra_nr.cc:373`: RAR timeout uses `ra_responseWindow + 3 + 10`.

CP678 did not expose the exact `preambleTransMax` value in the captured logs,
because the normal srsUE logger was configured at `all_level = error` and the
RACH config line is an info-level log. CP682 therefore does not claim the exact
encoded live value was directly observed.

## OCUDU/gNB knob audit

The CP678 [host-redacted] run config contained only:

```yaml
cell_cfg:
  prach:
    prach_config_index: 1
```

It did not explicitly set:

- `preamble_trans_max`
- `ra_resp_window`

Local OCUDU source supports an explicit RACH retry knob:

- `du_high_config.h:966-968` documents valid values
  `{3, 4, 5, 6, 7, 8, 10, 20, 50, 100, 200}` and defaults
  `preamble_trans_max = 7`.
- `du_high_config_cli11_schema.cpp:1451-1457` exposes
  `--preamble_trans_max` and validates those values.
- `du_high_config_translators.cpp:573-580` forwards
  `base_cell.prach_cfg.preamble_trans_max` into the common RACH config.
- `asn1_rrc_config_helpers.cpp:731-740` converts that field into ASN.1
  `preamb_trans_max`.

Interpretation:

OCUDU has a supported path for setting `preamble_trans_max`, but CP678 did not
set it explicitly. The five live attempts disagree with the local source
default of seven, so the next live run should not rely on an assumed default.
It should either force the value in gNB YAML or add a temporary UE-side
observable/override before burning RF time.

## Rejected or weakened theories

Outer runtime too short:

- rejected. CP678 ran `240.178393 s`.

Live waveform still malformed:

- weakened by CP679 and CP680. CP680 accepted the exact CP678 live dump.

Missing live `+500 Hz` or timing offset hook:

- rejected for CP678. The five high-peak rows show both hooks applied.

Need more live opportunity count or phase coverage:

- strengthened. CP678 gave `5` opportunities; CP680 gave `198`.

## Decision

Do not run the next live RF checkpoint as a blind repeat.

The safest next branch is CP683 as a no-RF prep/dry-run that proves one of
these before live RF:

1. exact gNB YAML injection of an explicit `cell_cfg.prach.preamble_trans_max`
   value, probably `20` first rather than jumping to `100` or `200`;
2. or a temporary srsUE/PAVONIS console log/override that prints and optionally
   overrides `rach_cfg.preambleTransMax` at `proc_ra_nr::set_config()`.

The next live RF run should keep the validated waveform settings unchanged:

- live PRACH frequency rotation: `+500 Hz`
- live PRACH time offset: `1773617`
- UE TX gain: `59`
- gNB bandwidth: `10 MHz`
- detector threshold: `0.24`

The only intentional change should be more live Msg1 opportunities, or a
deliberate live start/frame-phase sweep that produces more opportunities under
the same waveform settings.
