# CHECKPOINT 696 - Detector transform sweep: origin shift versus input length

Date: [date-redacted] UTC

## Scope

CP696 follows CP694 and CP695.

Question:

```text
Did CP694 rescue CP691 because the detector input was shortened, or because
the detector input origin was shifted later into the predemod buffer?
```

This is a no-RF local detector sweep. It reuses the CP694 selected predemod
windows and the same local OCUDU detector harness.

## Transform modes

For each selected predemod window and each sample offset `0..1116`, CP696 ran:

| Mode | Meaning | Effective length |
| --- | --- | ---: |
| `crop_short` | CP694 behavior: pass `samples[offset:]` | `11520 - offset` |
| `crop_zeropad_tail` | pass `samples[offset:]` at the front and zero-fill the tail | `11520` |
| `circular_left` | rotate `samples[offset:]` to the front and wrap the dropped prefix to the tail | `11520` |
| `zero_prefix_delay` | prepend zeros and move the original samples later | `11520` |

The left-shift modes test whether moving the detector input origin later is
sufficient. `zero_prefix_delay` tests the opposite direction.

## Controls

CP691 idx147 at `rb_offset=7` never accepts under any transform mode.

CP691 idx201 never accepts under any transform mode or RB offset. This confirms
that the CP691 idx147 behavior is a property of that strong failed window, not
a parser artifact or universal acceptance bug.

CP680 idx156 remains alignment-sensitive:

- at `rb_offset=7`, it accepts widely under left-shift modes;
- at `rb_offset=8`, left-shift modes do not accept;
- at `rb_offset=8`, `zero_prefix_delay` produces `123` accepted rows, with best
  accepted offset `1114`, P0 peak `0.2952612042`, delay `9`.

So a single RB offset or direction-of-shift explanation is still incomplete.

## Interpretation

CP696 strengthens the timing/origin branch.

CP695 ruled out a gross PRACH manifest scheduling shift. CP696 now shows that
the CP694 CP691 rescue is not caused by the shorter detector span. It persists
when the shifted input is padded back to full length or circularly wrapped.

The best current model is:

- the saved CP691 predemod buffer contains a detectable PRACH signature;
- the nominal gNB detector origin sees it below threshold;
- moving the detector/demodulator input origin later by about `847` samples
  exposes a strong accepted view;
- the tail after that shifted origin does not materially affect this detector
  result.

This points at an internal PRACH demodulator input-origin or window-start
choice, not at raw RF power, antenna overheating, or missing samples in the
saved buffer.

## Next rung

The next checkpoint should inspect the PRACH demodulator code path and identify
where a controlled late-origin offset could be applied without blindly shifting
all unrelated UL processing.

Concrete CP697 target:

- audit `ofdm_prach_demodulator` and the surrounding call site that supplies
  the predemod samples;
- identify whether the demodulator consumes only the first PRACH-needed portion
  of the input span;
- locate the sample-origin calculation for format 0, `start_symbol=0`,
  `rb_offset=8`, `11.52 Msps`;
- prepare a minimal guarded local patch or harness parameter for a late PRACH
  demod input offset, then test it no-RF on CP680/CP691 saved windows before
  considering another live RF run.
