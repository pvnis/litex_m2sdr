Behavior:

- default unset or non-positive value: no change;
- only active for the current guarded diagnostic case:
  - `prach_context.format == prach_format_type::zero`;
  - `prach_context.start_symbol == 0`;
  - `prach_context.nof_td_occasions == 1`;
  - `prach_context.nof_fd_occasions == 1`;
- positive value smaller than the demod input size:
  - passes `cf_buf.subspan(offset, cf_buf.size() - offset)` to the PRACH OFDM
    demodulator;
  - leaves the collected baseband buffer unchanged;
  - leaves the existing predemod dump as the original full window;
  - leaves detector threshold and detector implementation unchanged.

The key source block now prepares a separate demod view:


## Interpretation

CP698 turns the CP696/CP697 finding into a live-path diagnostic knob.

The patch is deliberately narrow:

- it does not change when PRACH samples are collected;
- it does not alter the 1 ms rounded capture window;
- it does not alter saved predemod raw windows;
- it does not alter detector code;
- it only changes which suffix of the already-collected PRACH window is passed
  into the OFDM PRACH demodulator.

For the first live diagnostic, the candidate value remains:

```text
PAVONIS_PRACH_DEMOD_INPUT_OFFSET_SAMPLES=847
```

because CP696 showed that CP691 idx147 at `rb_offset=8` accepts at that origin:

```text
P0 peak 0.7613193393
delay 104
accepted 1
```

## Caveats

This checkpoint only built the narrow PRACH processor static-library target.
It did not rebuild or run a complete gNB binary, and it did not run RF.

The worktree was already dirty before CP698. CP698 only adds the guarded
demod-input-offset block on top of the existing project/debug changes in
`prach_processor_worker.cpp`.
