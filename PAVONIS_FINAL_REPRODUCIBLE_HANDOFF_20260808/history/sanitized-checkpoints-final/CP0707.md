# CHECKPOINT 707 - CP705 live dump/window no-RF audit

Date: [date-redacted] Europe/Zurich

Scope: no-RF audit after CP706 showed that live UE with
`PAVONIS_PRACH_DEMOD_INPUT_OFFSET_SAMPLES=847` still did not accept Msg1.

No SSH, SCP, remote command, or RF command was run. No tarballs were extracted.
The audit read the CP705 [host-redacted] and [host-redacted] tarballs in place, reconstructed the
saved live UE PRACH TX dumps in memory, compared those waveforms to accepted
references, and joined saved TX dump wall times to nearest gNB predemod and
detector rows.

## Question

Was CP705's live failure caused by a bad UE-side PRACH waveform, or did a good
waveform still fail to appear strongly in the gNB receiver windows?

## Interpretation

CP707 is a no-RF negative receiver-window audit, not a new RF run.

The result argues against "bad live waveform generation" as the primary CP705
failure mode. The saved live dumps are highly correlated with controlled inputs
that can accept. The missing piece is on the RF/receiver/timing side: in live
conditions the gNB predemod windows near the UE TX events remain at low raw
amplitude and low detector metrics.

This keeps the current lead branch as live-vs-controlled RF/stream semantics,
not a simple demod offset transfer:

- CP704 proved demod input offset `847` is real and can rescue controlled
  replay;
- CP706 proved that same gNB knob does not make the current live UE run accept;
- CP707 shows CP705's saved UE TX waveform is still the expected waveform
  family, while the nearby receiver windows are weak.

## Regressions and theories

| Theory | CP707 update |
| --- | --- |
| Live UE waveform malformed | Weakened. Saved CP705 dumps correlate `0.981-0.993` to the CP704 input and `0.997-1.000` to the CP667 `+500 Hz` accepted template. |
| Demod input-origin offset is fake | Weakened by CP704, unchanged here. The knob is real for controlled replay. |
| Demod offset alone fixes live | Weakened by CP706 and CP707. Live receiver windows remain too weak. |
| Passive antenna overheating | Still unlikely as a primary explanation. CP707 has no temperature evidence; it points to live RF/receiver visibility rather than waveform drift. |
| Active RF-chain or stream timing state | Still plausible. The gNB-side windows nearest live TX events do not resemble the strong controlled-replay receiver case. |
| More live attempts only | Still weakened. CP684/CP705 increased attempts but did not create a threshold-crossing tail. |

## Next rung

Do not spend RF immediately just to repeat CP705.

The next useful rung is a no-RF analysis of CP705 receiver windows and local
detector offsets:

1. Select the strongest CP705 predemod windows, including the global best rows
   and the nearest saved-TX rows.
2. Run a local detector offset/origin sweep on those windows, as CP694 did for
   CP680/CP691.
3. Decide whether any CP705 live receiver window can be rescued locally by a
   different origin or RB setting.

If no CP705 receiver window can be rescued locally, the next RF test should
change the live RF visibility problem directly, not keep changing the UE
waveform family. Candidate changes would be receiver gain/path, TX path
position/cabling/attenuation, or a controlled/live side-by-side run that
captures the same receiver taps under the same gNB state.

## Bottom line

CP707 says CP705 transmitted the right kind of PRACH waveform on the UE side,
but the gNB did not receive a strong enough or correctly placed live PRACH copy
near those TX events. The blocker is now squarely in live RF/receiver window
visibility, after controlled replay and UE-side waveform generation have both
been shown viable.
