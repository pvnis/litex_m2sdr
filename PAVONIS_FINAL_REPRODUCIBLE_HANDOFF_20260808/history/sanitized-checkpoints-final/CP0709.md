# CHECKPOINT 709 - CP705 receiver-window local offset sweep

Date: [date-redacted] Europe/Zurich

Scope: no-RF detector-domain follow-up to CP707.

No SSH, SCP, remote command, or RF command was run. No tarballs were broadly
extracted. The checkpoint staged only 23 selected CP705 predemod `.cf32`
windows from the [host-redacted] tarball into a small local directory (`2.1M`) so the local
OCUDU detector probe could read them from the filesystem.

## Question

Can any saved CP705 live receiver window be rescued locally by changing detector
input origin or nearby RB offset?

This is the CP705 equivalent of the CP694 CP680/CP691 local sweep. CP694 showed
that the failed CP691 controlled-replay window could be rescued by later sample
origin around `847`. CP709 asks whether the CP705 live receiver windows have a
similar hidden recoverable PRACH copy.

## Important offset convention

CP705/CP706 ran the live gNB with:

```text
PAVONIS_PRACH_DEMOD_INPUT_OFFSET_SAMPLES=847
```

The saved predemod raw windows remain full pre-offset windows. Therefore, in
this local sweep:

| Local sample offset | Meaning |
| ---: | --- |
| `0` | raw saved predemod window origin |
| `847` | CP705 live-equivalent gNB demod input origin |

The report includes both, but the live-equivalent row is `sample_offset=847`.

This is the key separator. CP691 had a strong hidden PRACH copy inside the
saved predemod window that could be revealed by moving the detector input
origin. CP705's saved live windows do not show that pattern.

## Interpretation

CP709 strengthens the CP707 conclusion.

CP707 showed CP705's UE-side saved TX waveforms still match accepted waveform
families, but the gNB windows near those TX events were weak. CP709 now shows
that the saved CP705 receiver windows are not merely mis-originated in the same
way CP691 was. Sweeping the detector origin through `0..1116` samples and
trying RB offsets `7` and `8` did not reveal any accepted PRACH candidate.

That means another demod-origin tweak is unlikely to be the next useful live
fix for CP705. The remaining blocker is more likely upstream of this detector
domain:

- live RF path visibility;
- receiver gain/path/cabling/antenna placement;
- stream state under live UE timing;
- or another reason the gNB predemod windows do not contain a strong copy of
  the UE PRACH burst.

## Regressions and caveats

No RF regression was introduced because CP709 was local/no-RF.

Caveats:

- Only the first `900` CP705 predemod raw windows were preserved in the tarball.
  Later global-best trace rows such as idx `1234` were not available as `.cf32`
  inputs for local detector replay.
- The local linked detector emitted only main trace rows, so concentration
  fields are unavailable in the summary.
- The selected set was targeted, not exhaustive over all `900` saved windows:
  nearest saved-TX windows plus strongest saved best/P0 rows.

## Next rung

The next RF checkpoint should change live RF/receiver visibility directly
rather than spend another run on the same waveform/demod-origin settings.

Candidate next run shape:

- preserve the known live UE waveform family:
  `+500 Hz`, PRACH offset `1773617`, UE TX gain `59`, preamble max `20`;
- preserve the proven gNB diagnostics:
  `PAVONIS_PRACH_DEMOD_INPUT_OFFSET_SAMPLES=847`,
  `PAVONIS_PRACHDET_THRESHOLD_OVERRIDE=0.24`;
- change one RF visibility variable, with strict gates and no-extract
  collection.

Reasonable first visibility variable:

```text
increase gNB RX gain above 50 for one controlled live-UE test, if the existing
RF path can tolerate it
```

If gain headroom is uncertain, the safer prep checkpoint is a no-RF audit of
prior RX-gain runs and gNB config limits, then a single-variable launcher prep.

## Bottom line

CP709 says CP705's saved live receiver windows are not locally recoverable by
the CP694-style origin/RB sweep. The live blocker has moved past "detector
origin can rescue this saved window" and is now best treated as a live
RF/receiver visibility problem.
