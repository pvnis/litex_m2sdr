# CHECKPOINT 717 - CP714 TX waveform frequency-correction no-RF sweep

Date: [date-redacted] Europe/Zurich

Scope: no-RF waveform follow-up after CP716 showed CP714 saved TX dumps drifted
away from the accepted CP705/CP667/CP680/CP704 waveform family.

No SSH, SCP, remote command, gNB process, UE process, RF command, or tarball
extraction was run. The script opened the existing CP714 [host-redacted] tarball in
memory and wrote small JSON/TSV summaries.

## Question

Can a small additional complex frequency rotation recover CP714 saved TX dumps
back to the accepted waveform family?

CP716 found CP714 saved dumps had:

```text
corr to CP667 accepted template: 0.8830-0.9024
corr to CP680 accepted reference: 0.9292-0.9444
corr to CP704 controlled input:   0.8247-0.8480
```

while CP705's saved dumps were near-identical to those references. CP717 tests
whether this was mainly residual frequency/phase rotation.

## Method

Script:

```text
cp717_cp714_tx_freq_correction_sweep.py
```

Inputs:

```text
codex_stage6_cp714_liveue_plus500hz_offset1773617_txgain59p0_preamblemax20_demodoffset847_rxgain55_sensnuc7_[date-redacted].tar.gz
```

References:

```text
cp667_plus500_accept_template
cp680_cp678_dump000001_accept
cp704_cp684_dump000001_replay_input
```

For each of the 8 saved CP714 PRACH TX debug dumps, the script reconstructed
the CF32 waveform and swept:

```text
extra rotation = -1200..+1200 Hz, step 25 Hz
sample rate = tx_rate from dump metadata, normally 11.52 Msps
```

The correction applied to saved samples was:

```text
x[n] * exp(+j * 2*pi * freq_hz * n / sample_rate)
```

Then it scored normalized correlation against each reference.

## Interpretation

CP717 explains the CP716 waveform drift.

CP714's saved PRACH TX dumps were waveform-family valid after a small negative
frequency correction. The drift is consistent with the CFO shift observed in
the UE PRACH debug logs:

```text
CP705 mean CFO: -0.089289 kHz
CP714 mean CFO: +0.169226 kHz
delta: about +0.2585 kHz
```

The sweep independently recovered best corrections around `-225` to `-350 Hz`,
depending on the accepted reference. The CP680 reference, which is the closest
prior exact-live-dump accepted reference, points to about `-225 Hz`.

Because the current live hook applied:

```text
PRACH_FREQ_ROT_HZ=500
```

and CP717 applied an additional `-225 Hz` to the already-saved samples, the
next live candidate should likely reduce the live PRACH rotation rather than
increase RX gain again. Under the same sign convention, the CP680-centered
candidate would be:

```text
PRACH_FREQ_ROT_HZ ~= 275
```

The CP667 and CP704 references bracket that estimate:

```text
500 - 275 = 225 Hz
500 - 350 = 150 Hz
```

So a conservative practical candidate range is roughly:

```text
PRACH_FREQ_ROT_HZ = 250 to 300
```

with `275 Hz` as the first narrow test.

## What this does and does not prove

Proves:

- CP714 saved TX dumps can be made near-identical to accepted references by a
  small extra frequency rotation.
- CP714's poor raw correlation in CP716 was primarily correctable residual
  rotation, not an arbitrary waveform corruption.
- The next branch should be PRACH frequency rotation/CFO, not another RX-gain
  increase.

Does not prove:

- that a live `PRACH_FREQ_ROT_HZ=275` run will accept Msg1;
- that receiver-window visibility is fixed;
- that Stage 7 is reachable.

## Next rung

Prepare a no-RF launcher for a live candidate that changes PRACH frequency
rotation, not receiver gain.

Suggested first candidate:

```text
PRACH_FREQ_ROT_HZ=275
```

Two reasonable ways to choose the rest of the settings:

1. Preserve CP714 and change only frequency rotation:

```text
GNB_RX_GAIN=55
PRACH_FREQ_ROT_HZ=275
```

This isolates the CP717 correction against the most recent live run.

2. Return to CP705 gain while changing only frequency rotation relative to the
previous waveform-good CP705 branch:

```text
GNB_RX_GAIN=50
PRACH_FREQ_ROT_HZ=275
```

This avoids carrying the RX-gain-55 change that did not help, but changes two
variables relative to CP714.

The cleaner experimental rung is option 1: preserve CP714 and change only
`PRACH_FREQ_ROT_HZ` from `500` to `275`, with a no-RF dry-run before any RF.

## Bottom line

CP717 finds a strong no-RF explanation for the CP714 TX waveform drift. A small
negative correction, especially around `-225 Hz`, restores CP714 saved dumps to
accepted-template correlations near `0.9998`. The next live branch should test
PRACH frequency rotation around `275 Hz`, not higher gNB RX gain.
