# CHECKPOINT 722 - Receiver-window neighborhood no-RF audit

Date: [date-redacted] Europe/Zurich

Scope: no-RF, no-SSH receiver-window neighborhood audit across CP705, CP714,
and CP718. This checkpoint reads existing audit JSON plus `[host-redacted]` predemod
manifests and detector traces from already-collected tarballs using Python
`tarfile`, without extracting tarballs to disk.

No RF command, gNB process, UE process, SSH, SCP, or tarball extraction was run
for this checkpoint.

## Question

CP721 showed that CP718's saved UE TX dumps are back near the accepted CP704
waveform family, but the nearest receiver windows remain weak. CP722 asks a
wider question:

```text
Is there a stronger receiver-side PRACH-like row nearby, but not exactly at the
nearest manifest row selected by CP721?
```

## Method

Created and ran:

```text
cp722_receiver_window_neighborhood_noextract.py
```

For each saved TX dump in CP705, CP714, and CP718, the script inspected
predemod/detector rows within these wall-time radii around the saved UE TX dump
wall time:

```text
25 ms, 50 ms, 100 ms, 200 ms
```

The script recorded, per run and radius:

- total candidate detector rows;
- total accepted detector rows;
- maximum detector best peak;
- maximum Preamble 0 peak;
- maximum raw peak;
- maximum raw RMS.

Because the live PRACH attempts are about `160 ms` apart, the `200 ms` radius
also includes adjacent-attempt neighborhoods. That makes it a broad local
check, not just a nearest-window check.

## Interpretation

CP722 did not find a hidden strong receive-side PRACH row near the CP718 saved
TX events. Expanding the local window from nearest row to `25/50/100/200 ms`
neighborhoods did not produce:

- any accepted detector row;
- any best peak near threshold;
- any Preamble 0 peak near threshold;
- any raw-power increase that would explain a missed detector-origin alignment.

This strengthens the CP721 conclusion: CP718 fixed the obvious TX waveform
drift, but the live PRACH copy is not arriving in the gNB saved receiver
windows with usable strength/alignment.

## Recommended next rung

The next useful rung should no longer be another UE waveform-only adjustment.
The current evidence supports a lower-rung RF health check focused on receiver
visibility:

```text
CP723: controlled-replay receiver health at the current live settings
```

Use a known accepted replay waveform, keep the current gNB-side knobs
(`readStream`, threshold `0.24`, demod input offset `847`, RX gain `55`,
10 MHz bandwidth), and verify whether the gNB can still produce a strong
accepted controlled Msg1 before spending another live UE attempt.

If that controlled replay passes, the live-specific problem is likely timing,
closed-loop UE/RF geometry, or active RF-chain state during live UE operation.
If it fails, the lower RF receiver path has regressed and should be repaired
before attempting live UE again.
