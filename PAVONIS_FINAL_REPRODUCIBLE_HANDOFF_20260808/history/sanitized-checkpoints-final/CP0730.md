stages:

```text
DL/camping -> live PRACH Msg1 -> Msg2/RAR + Msg3 -> registration -> PDU/IP
```

| Ladder stage | Status |
| --- | --- |

## Historical phase roll-up

CP1-CP75: added predemod dumps, manifests, RAW512 capture, controlled PRACH
replay, SOB/EOB diagnostics, TX guards, and early camping/sync checks. The UE
could camp or reach cell selection and emit PRACH, but live Msg1 did not accept.

CP76-CP160: tested RF health, no-TX floor, cooldown, RX gain changes, and
bandwidth variants. Some controlled replay health was recovered, but it did not
transfer to live UE Msg1.

CP161-CP257: added UL symbol dumps, TX-now variants, high-peak-first runs,
restart-stream tests, wallclock debug, delay variants, and DL reacquisition
checks. This separated "UE transmitted" from "gNB accepted."

CP258-CP324: hardened remote operations with self-contained scripts,
watchdogs, SSH recovery patterns, and safer artifact collection. This made the
workflow survivable under laptop network instability but did not recover live
PRACH acceptance.

CP325-CP404: added strict gNB gates, RX-gain experiments, active replay,
qcore/gate audits, and targeted UL capture under active gNB conditions. The RF
path was not simply dead, but active gNB behavior stayed state-sensitive.

CP405-CP514: found a real LiteXM2SDR/Soapy visibility bug. Direct buffers are
two-channel interleaved, while the zero-copy consumer assumed contiguous
one-channel samples. `OCUDU_SOAPY_RX_USE_READSTREAM=1` recovered strong active
raw copies, but live Msg1 still did not accept.

CP515-CP557: added detector traces, timestamp bridge, negative timed-lead
helpers, and threshold diagnostics. CP551 showed fixed replay can accept Msg1
and trigger RAR/Msg3 scheduling evidence. That proves part of the RA path, but
not live UE Stage 7.

CP558-CP603: compared RAW512 live/control captures, live-derived dump replay,
active replay repetitions, and phase/window behavior. CP597 accepted active
replay. Similar settings could still pass or fail, so phase/window/state
variability became a major suspect.

CP604-CP652: found and patched a real live upper PRACH config bug: long-format
format0 was paired with invalid `15 kHz` `ra_scs`. The CP652 patch was
necessary, but not sufficient.

CP653-CP684: tested UE TX gain `59`, live PRACH `+500 Hz`, PRACH offset
`1773617`, and `preamble_trans_max: 20`. CP667 and CP680 accepted controlled
replay of live-derived dumps, while live runs such as CP678, CP684, and CP687
still had zero accepted Msg1 rows.

CP686-CP704: audited CP684/CP691 dumps, swept detector input origins, checked
timing geometry, and added `PAVONIS_PRACH_DEMOD_INPUT_OFFSET_SAMPLES`. CP704
proved that CP684 `dump000001` can accept when replayed with demod input offset
`847`.

CP705-CP719: tried to transfer the CP704 controlled recipe to live. UE
transmitted and saved TX dumps matched accepted waveform families, but no live
Msg1 accepted. RX gain `55` did not fix it. CP717 found residual CP714 TX
rotation and proposed freqrot `275 Hz`; CP719 showed freqrot `275` still did
not recover live Msg1.

CP721-CP722: no-RF audits showed CP718 freqrot `275` fixed the obvious TX
waveform drift, but the receiver windows stayed weak. A wider `25/50/100/200 ms`
search around saved TX events found zero accepted rows and no hidden strong
receiver row.

CP723-CP727: prepared and summarized controlled receiver-health regression.
The known-good CP684 replay was rerun under current conditions. CP724/CP725
failed at RX gain `55`; CP726 also failed after restoring RX gain `50`.

CP728: audited CP704 vs CP724/CP725/CP726 with no RF and no broad extraction.
The controlled replay source CF32 was byte-identical and launch mechanics were
clean, so the regression was not caused by a changed replay waveform.

CP729: ran a local selected-window detector transform sweep. All failed
controlled windows contained recoverable PRACH signatures offline under shifted
or delayed detector views. That points to nominal gNB receive-window/input-origin
or RB/delay view, not an intrinsically undetectable sample set.

## What worked

- Controlled replay accepted Msg1 in multiple historical checkpoints,
  especially CP704.
- Fixed/control replay exercised enough of the RA path to show RAR/Msg3
  scheduling evidence after accepted Msg1.
- Live UE can cell-select and transmit PRACH.
- Strict gates now check startup health, bandwidth readback, RX gain, and
  TX-timeout absence before RF.
- The Soapy direct-buffer visibility bug was found and worked around.
- The live `ra_scs` source bug was found and patched.
- The demod input offset knob was built, deployed, and proven in CP704.
- Saved live TX waveforms can match accepted waveform families.
- The self-contained launch/collect/report flow works under intermittent
  laptop connectivity.
- CP728 proved the current controlled regression is not a changed replay
  source waveform.
- CP729 proved the failed controlled windows still contain recoverable PRACH
  signatures offline.

## What did not work

- No live UE Msg1 accept has been achieved in the current branch.
- More live attempts did not solve the issue.
- Threshold lowering remains diagnostic only.
- `+500 Hz`, offset `1773617`, TX gain `59`, demod offset `847`, RX gain `55`,
  and freqrot `275 Hz` did not transfer to live accept.
- CP705/CP714/CP718 receiver windows were too weak or unrecoverable near saved
  live TX events.
- The current known-good controlled replay baseline is regressed: CP724, CP725,
  and CP726 all failed against the CP704 accepting family.
- Restoring RX gain `50` did not restore the CP704 controlled accept in CP726.

## Regressions and operational risks

- Controlled replay is state-sensitive. CP704 accepted; CP724-CP726 did not,
  even though the replay source waveform was byte-identical.
- Similar nominal RF settings can behave differently after idle time, gain/BW
  changes, USB or stream-state changes, stale processes, or other active RF
  state changes.
- Stale `run_ota_stage_template.sh` wrappers still appear and require CP98
  cleanup before some runs.
- CP712 exposed a real `/tmp` risk: stale `/tmp/pavonis_soapy_rx_*.cf32` files
  can grow until startup cleanup fails with `ARG_MAX`.
- CP678 had an early partial-gzip collection issue. Current practice is to poll
  remote gzip validity before collection.
- CP658/CP659 saw bladeRF USB resets aligned with failing runs.
- The local shell often prints `Failed to create stream fd: Operation not
  permitted`; treat this as local tool noise unless the command return code
  fails.
- The `ocudu` worktree is intentionally dirty with diagnostic source work,
  including the CP698 demod input offset knob.

## Current state

The broad question is no longer:

```text
Can this waveform family ever be accepted?
```

The answer is yes. CP704 accepted it, and CP729 shows CP724/CP725/CP726 contain
recoverable PRACH signatures offline.

The current narrow question is:

```text
Why does the gNB nominal detector view fail while shifted/delayed offline views
of the same controlled samples accept?
```

The most likely branch is receiver-side timing/window/input-origin/RB view or
stream-state behavior. The problem is not yet narrowed enough to choose a live
UE run.

## Recommended next rung

Do not run live UE next.

Run a no-RF source and metadata audit as CP731:

```text
Map the CP729 recoverable offsets to the gNB PRACH demodulator call-site,
receive-window origin, metadata time, SFN/slot handling, and RB-offset path.
```

The purpose is to decide whether the recoverable transforms correspond to:

- a bounded software timing-origin bug;
- an RB selection/view mismatch;
- a stale stream-state or RF-chain state issue;
- or a need for a conservative controlled RF reset/cooldown/state experiment.

Only after that mapping should the next controlled RF rung be chosen. Live UE
should wait until the controlled CP704-like baseline is healthy again.
