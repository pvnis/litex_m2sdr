# CHECKPOINT 737 - CP736 dump/window no-RF audit

Date: [date-redacted] Europe/Zurich

Scope: no-RF, no-SSH audit of the CP736 live UE artifacts. CP737 reads the
existing CP736 tarballs through Python `tarfile`, compares saved UE TX dumps
against accepted waveform references, inspects nearest gNB predemod windows,
and compares CP736 against CP705/CP714/CP718 and the CP733 controlled accept.

No RF command, gNB process, UE process, SSH command, SCP command, or broad
tarball extraction was run for this checkpoint.

## Purpose

CP736 tried to transfer the CP733 controlled recovery to live UE:

```text
RX gain 50, demod input offset 562, freqrot 275, PRACH offset 1773617, TX gain 59
```

CP736 still produced zero live Msg1 accepts. CP737 asks:

```text
Was CP736 primarily a live TX waveform problem, a weak/late receiver-window
problem, or both?
```

## Method

Created and ran:

```text
cp737_audit_cp736_live_offset562_dump_window_noextract.py
```

The script reuses the prior CP707/CP721 no-extract audit path with CP736
inputs:

- reconstructs saved `pavonis_rf_blade_tx_dbg_*.sc16` dumps using their
  metadata from the CP736 [host-redacted] tarball;
- compares those dumps to accepted references:
  - CP667 `+500 Hz` accepted template;
  - CP680 accepted CP678 dump000001 reference;
  - CP704/CP684 reconstructed replay input;
- runs a frequency-correction sweep from `-1200 Hz` to `+1200 Hz` in `25 Hz`
  steps;
- aligns saved UE TX debug dump wall-clock timestamps to nearest CP736 gNB
  predemod rows;
- compares CP736 with CP705, CP714, and CP718 prior live runs.

The script passed bytecode compilation and exited with return code `0`.

## Interpretation

CP737 splits the CP736 failure into two facts:

1. CP736's saved TX dumps are frequency-correctable back to the accepted family.
   They are not structurally malformed, but the as-run residual rotation is not
   the same as CP718 or CP733 references.
2. CP736's nearest gNB receiver windows are still in the weak live family:
   low raw RMS/peak, no threshold pass, no accepted rows, and no non-empty gNB
   PRACH line.

This means demod input offset `562` did not solve the live-specific blocker.
The current branch is not ready for registration/NAS/PDU work.

## Recommended next rung

Do not spend another live RF run yet.

Run a no-RF source/timing audit as CP738:

```text
Why are saved live TX dump wall-clock timestamps consistently aligning about
16-17 ms after the nearest predemod row, and is the nearest-window mapping
missing the actual receiver energy because of wall-clock, SFN/slot, or trace
index semantics?
```

That audit should:

- map CP736 UE TX TTI values to expected gNB SFN/slot occasions;
- compare wall-clock nearest rows against SFN/slot-derived expected rows;
- inspect the CP736 detector/top rows near TX-derived expected occasions;
- decide whether a bounded CP736 local detector origin/RB sweep is justified.

If that audit shows the receiver windows are genuinely weak even at the
SFN/slot-derived expected rows, then the next RF branch should target live RF
path strength or TX residual frequency, not another demod-input offset alone.
