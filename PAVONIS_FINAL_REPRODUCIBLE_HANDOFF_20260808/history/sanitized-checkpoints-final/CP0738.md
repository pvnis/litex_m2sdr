# CHECKPOINT 738 - CP736 TTI/SFN-slot timing no-RF audit

Date: [date-redacted] Europe/Zurich

Scope: no-RF, no-SSH audit of CP736 live UE timing semantics. CP738 checks
whether the CP737 receiver-window audit may have selected the wrong gNB
windows because of wall-clock offset, repeated SFN/slot values, or UE TTI to
gNB SFN/slot mapping.

No RF command, gNB process, UE process, SSH command, SCP command, or broad
tarball extraction was run. The audit reads the existing CP736 tarballs through
Python `tarfile`.

## Purpose

CP737 found that CP736 saved UE TX dumps aligned to nearest gNB predemod rows
with a consistent wall-clock delta around `-16` to `-17 ms`, and those receiver
windows were weak.

CP738 asks:

```text
Is that wall-clock delta a sign that the audit is looking at the wrong receiver
rows, or do the UE TTI and gNB SFN/slot semantics confirm those weak rows are
the intended PRACH occasions?
```

## Method

Created and ran:

```text
cp738_audit_cp736_tti_sfnslot_timing_noextract.py
```

The script:

- extracts UE Random Access TTIs and PRACH-TX TTIs from the CP736 [host-redacted]
  tarball;
- maps each UE TTI to expected `SFN.slot` using `sfn=(tti//10)%1024` and
  `slot=tti%10`;
- reads CP736 gNB predemod manifest rows and PRACH detector trace rows;
- handles repeated SFN/slot occurrences by anchoring to the saved TX dump
  wall-nearest sequence, not the first matching SFN/slot in the run;
- checks exact expected rows for all 18 RA attempts;
- checks a `+/-4` PRACH-row neighborhood around each expected row.

The first implementation found repeated SFN/slot matches and was patched so
the selected occurrence is near the saved live TX sequence. The final audit
used the corrected selection.

separate TX residual-frequency issue, but it does not explain away the weak
receiver windows.

## Interpretation

CP738 narrows the CP736 failure:

```text
The CP736 live UE PRACH occasions were inspected at the right SFN/slot rows,
and nearby rows were also weak. The failure is not an audit artifact caused by
the -16 ms wall-clock delta.
```

Therefore:

- demod input offset `562` did not transfer controlled recovery to live;
- CP736's as-run TX waveform still had residual frequency mismatch;
- the live gNB receiver view at actual RA occasions remained weak;
- a bounded local detector-origin sweep on CP736 expected rows is not strongly
  justified because there is no strong raw/metric row near the actual RA
  windows.

## Recommended next rung

Do not run registration/NAS/PDU work.

The next useful checkpoint should be no-RF planning/prep for a narrow live RF
branch that changes only the TX residual-frequency correction while preserving
the CP736/CP733 receiver settings:

```text
CP739: no-RF prep for live UE with demod offset 562, RX gain 50, and a
CP737-derived PRACH frequency rotation candidate around 725 Hz.
```

Rationale:

- CP737 showed CP736's saved TX dumps need about `+450 Hz` extra rotation to
  best match the CP704 reference after running with `275 Hz`;
- `275 + 450 = 725 Hz`;
- CP738 ruled out the nearest-row timing-audit artifact as the reason for the
  weak live windows.

This remains a risky live RF candidate because receiver strength is still weak.
If the next prep finds a lower-risk controlled or no-RF way to validate the
frequency candidate first, take that before transmitting again.
