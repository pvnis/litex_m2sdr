## Method

For each UE PRACH attempt, CP746 parsed:

- `tti_tx`
- expected SFN: `(tti_tx // 10) % 1024`
- expected slot: `tti_tx % 10`
- CFO estimate
- `PRACH-TX` max amplitude and TX time

It then matched each attempt to the gNB predemod manifest by expected SFN/slot and estimated wall position. The wall delta is used only to disambiguate repeated SFN cycles; it should not be read as RF timing error because [host-redacted] and [host-redacted] host clocks are separate.

## Important correction to CP745 global-peak interpretation

CP745's global detector summary reported:

- global best-any: 0.1792014539 at SFN 337.4, preamble 29
- global best P0: 0.1136284173 at SFN 289.4

CP746 shows those SFNs are not among the 18 UE PRACH attempt SFNs:

`785, 801, 817, 833, 849, 865, 881, 897, 913, 929, 945, 961, 993, 1009, 1, 17, 33, 49`

Therefore the global 0.179 and 0.113 peaks should be treated as background or unrelated detector peaks, not as evidence that the actual UE PRACH attempts nearly reached threshold.

The matched UE attempt windows are weaker:

- actual-window P0 max: 0.05956436321
- actual-window best-any max: 0.1385535151, but on preamble 17, not preamble 0

## Interpretation

CP746 narrows the failure again. The UE really did transmit in the expected SFN/slot sequence, and the gNB had matching predemod/detector windows for all 18 attempts. Those windows did not contain a meaningful P0 signature: every P0 peak stayed below 0.10 and every accepted flag stayed 0.

This makes a simple lower-threshold RF retry less compelling. A threshold below 0.10 would be operating beneath even the strongest actual P0 window in CP745. It also makes the earlier global P0 evidence less useful, because that stronger global P0 was outside the UE transmit windows.

The current leading issue is not "the analyzer looked at the wrong SFN/slot." It is that the live UE waveform, as received in the correct windows, is far below the controlled replay signal level. Since CP745 controlled pre and post both accepted, the next isolation step should focus on the difference between controlled CP684 replay and live UE TX, not on another blind live run.

## Recommended next checkpoint

CP747 should remain no-RF if possible:

- Compare the captured live UE TX debug `.sc16` dumps against the accepted CP684 replay waveform and expected preamble-0 sequence.
- If practical, prepare a controlled replay of the captured live UE TX dump itself. If replaying the live dump is accepted, the live failure is likely runtime scheduling/RF path/coupling. If replaying the live dump is also weak, the live UE-generated waveform or its scaling/rotation is suspect.

Only after that comparison should we choose the next RF run. Based on CP746, a pure threshold-lowering run is lower value than a waveform/replay isolation step.
