## Interpretation

CP764 did not test live Msg1 and did not test whether `350 Hz` fixes Msg1. It
instead answered the lower-rung question:

```text
Can the previous 725 Hz family still reach cell select/PRACH?
```

The answer for this run is no.

The current first failed stage is now:

```text
UE downlink cell search before cell select and before PRACH.
```

That means more PRACH-specific RF is currently low value. The live path must
first recover DL/cell-search reliability.

The antenna-overheating theory remains unsupported as a primary conclusion from
this evidence. CP764 has no temperature telemetry, and the gNB-side strict gate
looks healthy. The remaining plausible branch is a DL/RF-path/runtime-state
problem affecting the UE's ability to see the cell: bladeRF RX/DL path,
receiver gain/path, physical RF condition, timing/state, or an active RF-chain
state issue.

## Recommended next checkpoint

Do not rerun PRACH frequency candidates yet.

Next should be a no-RF or RF-light DL-specific checkpoint:

```text
Audit or run an independent downlink SSB/cell-search health check from the UE
side, using the same gNB strict gate, before any more PRACH Msg1 experiments.
```

Useful directions:

1. Compare CP740/CP745 versus CP760/CP764 UE-side cell-search traces and
   bladeRF RX/path logs for RX-side state differences.
2. Check whether the UE-side bladeRF RX path or gain/readback is present in the
   available logs; if not, add a narrow health probe.
3. Consider a dedicated SSB capture/cell-search-only gate before running the
   full PRACH wrapper again.

Do not debug registration, NAS, PDU, or IP.
