it remains a bladeRF reporting/control quirk to keep in mind.

## Interpretation

`CP775_GENERIC_RX_MATCHES_EXPLICIT_RX1_RX2_IS_QUIETER_NO_TX`

CP775 rules out a simple "capture helper accidentally used a different bladeRF
channel than RX1" explanation. The current helper's generic `rx` commands map
to the same observed receive path as explicit `rx1/channel=1`.

RX2 is software-selectable and works, but its no-TX floor is much lower. That
suggests the current installed receive path/noise pickup is on RX1, not RX2.
Switching live captures to RX2 is therefore unlikely to recover CP772 unless the
physical path is unexpectedly connected to RX2 while the ambient/noise pickup is
not.

The first failed rung remains independent DL/SSB/PBCH visibility:

- CP770: weak ambiguous SSB at old CP199 geometry.
- CP772: +10 dB TX power increased level but did not recover expected PCI.
- CP773: SSB-center offset sweep did not recover expected PCI.
- CP774: independent PBCH/MIB scan found no CRC-valid decode.
- CP775: capture channel mapping is not an obvious software mistake; generic
  capture is RX1-equivalent.

The next useful RF-spending checkpoint should use one bounded gNB window and
explicit channel labeling, comparing `rx1/channel=1` against `rx2/channel=2`
under the same downlink TX. That would close the remaining software-selectable
RX-port question without requiring a physical swap.
