## Interpretation

CP795 did not reproduce CP794's PRACH-emission state. It reached cell select, but the UE landed in a bad post-cell-select/control-plane state:

- PRACH config stayed at `config_idx=0/root_seq_idx=0/num_ra_preambles=0`.
- No Random Access transmissions occurred.
- The TX debug path saw only zero/low-peak writes.
- The UE detail log showed thousands of out-of-sync lines.

The immediate blocker for CP795 is therefore not `350 Hz` PRACH acceptance. It is that the UE did not obtain a usable PRACH config or stable enough post-cell-select state to transmit PRACH.

CP794 and CP795 together show current intermittency:

- CP794 at `725 Hz`: cell select succeeded, real PRACH config was present, 19 PRACH transmissions occurred, no Msg1 accept.
- CP795 at `350 Hz`: cell select succeeded, but PRACH config was zero-preamble and no PRACH occurred.

This is a lower-rung instability/regression relative to the desired candidate test. A fair `350 Hz` Msg1 comparison still requires a run that reaches real PRACH emission.

## Next Step

Run an immediate discriminator to separate PRACH-frequency effects from intermittent DL/control acquisition:

- Repeat the short `725 Hz` baseline once. If it again emits PRACH, then the hardware/gNB state is still capable and the issue is run-to-run UE acquisition/control stability or something specific to the `350 Hz` wrapper path.
- If the repeat `725 Hz` run also lands in zero-preamble/no-PRACH or SFN instability, stop moving upward and debug post-cell-select/SIB/PRACH-config stability.
