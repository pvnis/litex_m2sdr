# Checkpoint 797 - bladeRF TX1 To LiteX RX Gain 50 Tone Baseline Invalidated By TX Permission Failure

Date: [date-redacted]

## Purpose

CP790 proved the LiteX/M2SDR Soapy RX/TX path without bladeRF. CP791 proved LiteX/M2SDR Soapy TX is visible to bladeRF RX. CP792 then proved the independent gNB SSB/PCI downlink is visible again.

The missing physical-direction baseline was the uplink direction: bladeRF TX into LiteX/M2SDR RX. CP797 attempted to send a controlled `+100 kHz` tone from bladeRF TX1 at the live uplink center and capture it with LiteX/M2SDR RX gain 50. This was intended to isolate the bladeRF TX and uplink RF path from srsUE cell select, PRACH generation, and gNB PRACH detection.

## Outcome

Result: invalid test, failed before RF-path proof.

The remote mechanics worked, and the LiteX capture completed, but the bladeRF TX process did not open the bladeRF device:

```text
bladeRF_tx_exit=1
[WARNING ...] Found a bladeRF via VID/PID, but could not open it due to insufficient permissions.
No bladeRF device(s) available.
```

The wrapper exited nonzero:

- `cleanup_before rc=0`
- `launch rc=0`
- `collect rc=0`
- `summarize rc=1`
- `cleanup_after rc=0`
- overall rc: `1`

The older CP329 helper reports `SENS_RUN_RC=0` because the helper itself exits normally after logging the bladeRF CLI result. The real TX status is `bladeRF_tx_exit=1`, so CP797 did not actually transmit the controlled tone.

## Capture Results

The [host-redacted]/LiteX capture itself succeeded:

- `NUC_FINAL_RC=0`

But the controlled tone was not present:

- `RX_PEAK_FREQ_HZ=2492402.34`
- `RX_PEAK_OVER_MEDIAN_DB=28.59`
- `RX_EXPECTED_TONE_BIN_FREQ_HZ=100019.53`
- `RX_EXPECTED_TONE_BIN_DB_OVER_MEDIAN=-1.84`
- `FREQ_ERR_HZ=2392402.34`
- `PEAK_NEAR_TONE_PASS=0`
- `EXACT_BIN_PASS=0`
- `GROSS_TONE_PATH_PASS=0`
- `TONE_GATE_PASS=0`

Because bladeRF TX failed to open, these capture metrics mostly describe the background/spur field, not the bladeRF TX1 to LiteX RX physical path.

## Interpretation

CP797 does not prove the reverse RF path is dead. It proves the current CP329/CP797 tone helper is no longer sufficient because it invokes plain `bladeRF-cli`, and [host-redacted] currently requires elevated access for bladeRF TX control.

This matters because CP329/CP331 from [date-redacted] had previously shown a gross bladeRF TX to LiteX RX tone near `+97.1 kHz` with strong peak-over-median margin. CP797 is therefore a regression in test validity, not yet a physical-path regression.

The next checkpoint should repeat the same bladeRF TX1 to LiteX RX gain 50 baseline with a corrected sudo-backed bladeRF helper and with `bladeRF_tx_exit=0` required for pass. Only then can the result be used to isolate or exonerate the uplink physical path.
