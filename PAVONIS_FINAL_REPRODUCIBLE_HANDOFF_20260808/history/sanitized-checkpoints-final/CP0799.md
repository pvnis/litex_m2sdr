# Checkpoint 799 - bladeRF TX1 To LiteX RX Gain 50 Sudo Tone Clean Exit Pass

Date: [date-redacted]

## Purpose

CP798 proved the reverse RF path, bladeRF TX1 into LiteX/M2SDR RX gain 50, but the wrapper returned nonzero because the bladeRF CLI was killed by the outer timeout after transmitting a long `REPEAT=300` tone.

CP799 repeated the same RF baseline with a shorter finite tone:

- `REPEAT=90`, about 9 seconds of tone data
- `CLI_TIMEOUT=30`

This still covers the delayed 6-second LiteX capture, but should allow `bladeRF-cli` to exit cleanly.

TX script:

```text

set samplerate tx1 11520000
set bandwidth tx1 10000000
```

The CLI returned `bladeRF_tx_exit=0`. It printed one `Operation invalid in current state` line near the end, likely from `tx stop` after the finite transmit had already completed. That line did not cause a nonzero exit and did not prevent a strong RF tone from being captured.

## Interpretation

CP799 is the clean reverse-path baseline:

- bladeRF TX1 can emit a controlled uplink-frequency tone.
- LiteX/M2SDR RX gain 50 receives it at the expected offset with high margin.
- The bladeRF CLI exits cleanly with the shorter finite tone.
- Cleanup before and after completed cleanly.

This closes the gross physical-path question for both directions:

- LiteX TX to bladeRF RX passed in CP791.
- bladeRF TX to LiteX RX passed in CP799.

The recent live failures are therefore more likely in UE DL/SFN/control stability, PRACH generation/timing/frequency, or gNB PRACH acceptance logic than in a fully dead RX/TX RF path.

## Next Step

Return to the live ladder. The immediate target is reproducing whether the UE can reliably progress from PCI to SFN/cell-select to real PRACH after the RF baselines. A short `725 Hz` live baseline is the next useful rung because CP794 reached PRACH while CP796 later failed below PRACH.
