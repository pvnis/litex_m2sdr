## Interpretation

CP800 is a lower-rung gNB/LiteX TX startup regression, not a live UE/SFN datapoint.

The important distinction is:

- CP799 proved the bladeRF TX to LiteX RX physical direction moments earlier.
- CP800 failed before UE start because the gNB strict gate saw thousands of Soapy TX write timeouts.
- Therefore CP800 cannot be used to reason about PRACH frequency rotation, UE SFN stability, or Msg1 acceptance.

This resembles a transient or stateful gNB/LiteX TX startup issue. CP792 and CP794 had clean gNB strict gates earlier, so the next step should be to drop down one rung and repeat an independent downlink/gNB smoke test before attempting another live UE run.

Run an independent downlink/gNB smoke checkpoint to test whether the LiteX/gNB TX path is currently healthy. If that passes, repeat the short live `725 Hz` baseline. If it fails with TX timeouts again, stay on the gNB/LiteX TX rung and diagnose the timeout condition before involving the UE.
