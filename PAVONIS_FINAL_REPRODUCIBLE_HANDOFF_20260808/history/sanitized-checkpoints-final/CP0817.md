# Checkpoint 817 - CP813 pattern/duplex PBCH sweep, no CRC OK

## Purpose

CP814 showed that aligned short windows from the CP813 RF capture can still
produce CSI PCI `1`, but PBCH CRC remains `KO`. CP815 then showed that simple
residual CFO correction does not recover PBCH.

CP817 tested whether the remaining failure was caused by a wrong
`ssb_file_test` SSB pattern or duplex argument. It replayed the strongest CP814
CSI-PCI1 windows through `ssb_file_test` while sweeping SSB patterns `A/B/C/D`,
duplex modes `fdd/tdd`, and a small set of CFO corrections.

## Interpretation

CP817 rules out a simple `ssb_file_test` pattern or duplex mismatch for the
current PBCH failure. The same windows can frequently preserve CSI PCI `1`,
including cases with reported CSI SNR near `-9.2 dB`, but PBCH stays on PCI `0`
with CRC `KO` for every tested pattern and duplex combination.

Current downlink state after CP817:

```text
PSS/SSS/PCI over RF: present at best CP813 settings
PBCH/SFN over RF: not decoded
First failed stage: downlink PBCH/SFN decode
Current best RF setting: TX_BACKOFF=20, bladeRF gain=45, BW=5.6 MHz, SSB-centered
```

The next useful isolation step is not PRACH. It is to separate "RF corrupts
PBCH" from "the transmitted gNB/LiteX waveform has PBCH content or geometry
that `ssb_file_test` cannot decode" by adding a fresh LiteX-only RX/TX baseline
and then comparing PBCH behavior against a non-bladeRF capture or digital/baseband
reference if available.
