# Checkpoint 821 - Copy-mode TX DMA PBCH control passes

## Purpose

CP819 proved that the current gNB pre-DMA transmit samples contain a decodable
PBCH/MIB for PCI `1`, but the post-DMA file was missing because the active
zero-copy path does not currently call the diagnostic DMA dump hook. CP821 runs
a labelled copy-mode control with `M2SDR_LITEPCIE_ZERO_COPY=0` so the existing
post-DMA dump hook can observe the framed buffer.

This is a control of the copy-mode handoff. It is not a validation of the normal
zero-copy RF path.

## Interpretation

CP821 proves that when the existing post-DMA dump hook is active in copy-mode,
the framed channel-0 DMA payload still contains a decodable PCI `1` PBCH/MIB.
Combined with CP819, this removes a broad "digital TX framing always breaks
PBCH" explanation.

Current boundary:

```text
LiteX/M2SDR Soapy RX/TX tone path: PASS at CP818 and CP820
Current gNB pre-DMA PBCH/MIB: PASS at CP819 and CP821
Copy-mode post-DMA framed channel-0 PBCH/MIB: PASS at CP821
Normal zero-copy post-DMA framed payload: NOT YET OBSERVED
bladeRF RF PSS/SSS/PCI at best CP813 setting: present
bladeRF RF PBCH/SFN: still KO through CP814-CP817 sweeps
```

The next most precise diagnostic is an exact zero-copy post-DMA observation.
That likely requires adding the same one-shot DMA dump call to the zero-copy
release path and rebuilding the build-tree Soapy plugin on [host-redacted]. Without that,
the remaining unknown still spans the normal zero-copy handoff, the LiteX RF
egress chain, and the bladeRF receive/demod chain.
