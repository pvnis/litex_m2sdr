# Checkpoint 822 - Zero-copy TX DMA PBCH control passes

## Purpose

CP819 proved current pre-DMA PBCH/MIB was decodable, but did not collect the
post-DMA zero-copy ring payload. CP821 proved the same post-frame buffer format
decodes in copy-mode. CP822 adds the missing one-shot dump call to the normal
zero-copy release path, rebuilds the build-tree Soapy plugin on [host-redacted], and reruns
the current gNB zero-copy TX dump control.

This checkpoint intentionally changed the diagnostic plugin, but did not change
the TX scheduling or ring update behavior. The added dump is inert unless
`M2SDR_SOAPY_TX_DMA_DUMP_PATH` is set.

## Interpretation

CP822 proves that the exact normal zero-copy TX ring payload contains a
decodable PCI `1` PBCH/MIB before the LitePCIe reader is advanced. This closes
the CP819 uncertainty about whether PBCH was lost between gNB pre-DMA samples
and the zero-copy handoff.

Current boundary after CP822:

```text
LiteX/M2SDR Soapy RX/TX tone path: PASS at CP818 and CP820
Current gNB pre-DMA PBCH/MIB: PASS at CP819, CP821, CP822
Copy-mode post-DMA framed channel-0 PBCH/MIB: PASS at CP821
Normal zero-copy TX ring channel-0 PBCH/MIB: PASS at CP822
bladeRF RF PSS/SSS/PCI at best CP813 setting: present
bladeRF RF PBCH/SFN: still KO through CP814-CP817 sweeps
```

The narrowed remaining failure area is now downstream of the verified zero-copy
TX ring payload:

```text
LitePCIe reader/FPGA transmit consumption
AD9361/RF egress and physical path
bladeRF receive/clocking/filtering/scaling
offline PBCH decode tolerance on bladeRF RF captures
```

The most useful next step is to rerun a CP813-style bladeRF RF capture using
the rebuilt diagnostic plugin, while keeping CP822's zero-copy dump enabled in
the same TX window. That would pair the exact TX ring payload with the RF
capture that still fails PBCH, instead of comparing across separate runs.
