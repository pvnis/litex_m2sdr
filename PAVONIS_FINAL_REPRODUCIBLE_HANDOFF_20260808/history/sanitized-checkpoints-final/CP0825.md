# Checkpoint 825 - Zero-copy 1024-buffer post-DMA PBCH KO

## Purpose

CP824 introduced a new anomaly: pre-DMA PBCH decoded, but the 256-buffer
zero-copy post-DMA slice did not. CP825 reruns a TX-only zero-copy dump with
`DMA_DUMP_BUFFERS=1024` to test whether the CP824 miss was only a short dump
window problem.

## Run

- Harness: `cp822_run_zero_copy_tx_dma_pbch_control.sh`
- Stamp: `[date-redacted]`
- gNB settings: Band 3, `TX_BACKOFF=20`, `IFACE=[interface-redacted]`
- Delivery mode: normal zero-copy, with `M2SDR_LITEPCIE_ZERO_COPY` unset
- DMA dump buffers: `1024`

## Interpretation

CP825 makes the post-DMA anomaly more credible than a simple 256-buffer window
miss. The recent sequence is now:

```text
CP822 zero-copy 256 buffers: post-DMA PBCH OK
CP823 paired gain45 256 buffers: post-DMA PBCH OK
CP824 paired gain43 256 buffers: post-DMA PBCH KO
CP825 zero-copy 1024 buffers: post-DMA PBCH KO
```

This suggests either an intermittent zero-copy ring/framing issue, a decoder
sensitivity to the post-DMA vector contents, or a stateful hardware/plugin
condition that appeared after CP823. A copy-mode repeat is the next useful
control because it reuses the post-frame dump path without zero-copy ring
semantics.
