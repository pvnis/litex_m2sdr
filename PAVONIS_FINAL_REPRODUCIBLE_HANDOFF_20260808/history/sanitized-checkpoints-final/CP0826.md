# Checkpoint 826 - CP825 post-DMA targeted windows do not recover PBCH

## Purpose

CP825's full post-DMA vector saw CSI PCI `1` but PBCH CRC KO. CP826 performs a
small targeted `ssb_file_test` sweep over the CP825 `post_dma_scale32768_ch0`
CF32 vector to check whether short windows recover PBCH.

## Run

- Script: `cp826_postdma_cf32_targeted_decode.py`
- Input: `cp822_zero_copy_tx_dma_pbch_control_analysis_[date-redacted]/vectors/post_dma_scale32768_ch0.cf32`
- Fs: `11520000`
- Carrier center: `1842500000`
- SSB center: `1839650000`
- Cases: `108`

## Result

The targeted windows did not recover PBCH:

```text
PBCH CRC OK cases: 0
PBCH PCI 1 cases: 0
CSI PCI 1 cases: 0
```

The targeted-window method also did not reproduce the full-vector CSI PCI `1`
detection from CP825, so this is a limited negative result. It does not replace
the CP825 full-vector observation.

## Interpretation

CP826 does not explain away CP825. The post-DMA anomaly remains open. The next
control should be a fresh copy-mode TX dump: if copy-mode PBCH is still OK while
zero-copy remains KO, the suspect narrows to zero-copy ring semantics or the
new zero-copy dump point. If copy-mode also fails, the problem is more general
than zero-copy.
