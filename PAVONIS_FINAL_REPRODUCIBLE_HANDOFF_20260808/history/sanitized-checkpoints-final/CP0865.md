## Script Behavior

The remote capture helper is:

- `$HOME/pavonis_bladerf/scripts/capture_bladerf_sc16.sh`
- local wrapper: `/home/[host-redacted]/CLionProjects/pavonis_toolkit/scripts/pavonis_capture_bladerf_sensnuc7.sh`

The wrapper forwards:

- `FC`
- `FS`
- `BW`
- `GAIN`
- `N`

The remote script tries capture modes in this order:

1. `manual_gain`
2. `agc`
3. `no_gain`

For `manual_gain`, it writes a bladeRF script containing:

```text
set frequency rx $FC
set samplerate rx $FS
set bandwidth rx $BW
set agc rx off
set gain rx $GAIN
rx config file=$TMPRAW format=bin n=$N
rx start
rx wait
```

Recent CP863/CP864 logs show the successful captures used:

- `CAPTURE_MODE=manual_gain`
- `set agc rx off`
- `set gain rx 42`

## Important Finding

The capture summary parser reports a gain readback mismatch in recent captures:

- requested: `42`
- compact summary readback: `GAIN_READBACK_DB=60`
- `GAIN_READBACK_MATCH=0`

This may be a parser artifact or stale/default bladeRF state included in the log, because the successful capture mode clearly writes `set agc rx off` and `set gain rx 42`. But it means we should not treat the compact `GAIN_READBACK_DB` field as reliable without a targeted receive-setting test.

## Interpretation

CP865 explains why the next step should be a focused bladeRF RX configuration probe, not more waveform or gNB/PBCH debugging.

The current knowns are:

- Successful captures use the manual-gain branch.
- The branch requests AGC off and `GAIN=42`.
- The compact gain readback field still reports `60`, so the capture helper's gain readback is not trustworthy as-is.
- The bladeRF path remains weak even when the signal level is high and the waveform is offset away from DC.

Next useful test: compare manual-gain and AGC/no-gain capture behavior on the same high-SNR offset probe, or add an explicit `print gain rx1; print agc rx1` after the capture configuration in a temporary helper to verify the actual bladeRF state during capture.
