## CLI Surface

The CLI exposes bladeRF2 clock controls:

- `set clock_sel ...`, but this build did not print parameter-specific help
  without arguments.
- `set clock_out <bool>`
- `set clock_ref <on|off>`
- `set refin_freq <frequency>`

It exposes [interface-redacted]/filter/mux controls:

- `set [interface-redacted] <host|FPGA>`
- `set filter <rx|tx> <mode>`
- RX filter modes: `default`, `normal`, `bypass`, `custom`, `dec2`, `dec4`
- TX filter modes: `default`, `normal`, `bypass`, `custom`, `int2`, `int4`
- `set rx_mux <BASEBAND|12BIT_COUNTER|32BIT_COUNTER|DIGITAL_LOOPBACK>`
- `set loopback <rfic_bist|firmware|none>`

It exposes calibration commands from CP867:

- `calibrate dc <rx|tx> [<I> <Q>]`
- `calibrate dc <rxtx>`
- `calibrate iq <rx|tx> <gain|phase> <value>`
- `calibrate table dc <rx|tx> ...`
- `calibrate table agc <rx|tx> ...`

`calibrate lms show` is not usable on this board:

## Interpretation

CP900 does not show a clock, mux, filter, loopback, bitmode, or bias tee
misconfiguration that would explain the bladeRF coherence failure.

The bladeRF is using its onboard VCTCXO, with the stored trim value loaded. It is
not configured for external reference input or clock output. The RX mux is the
normal baseband path, loopback is disabled, sample bit width is normal `16 bit`,
RX FIR is the default normal mode, TX FIR is the default bypass mode, and both
bias tees are off.

This leaves two realistic software-side branches before touching hardware:

1. Test whether an explicit receive retune/config-reset sequence changes the
   manual-gain-42 deterministic tone result.
2. Test the bladeRF's internal non-RF sample paths (`rx_mux` counter or
   firmware/RFIC loopback) to separate USB/streaming/sample-format health from
   the analog RF path.

Blind calibration is still not justified by the evidence. The CLI can mutate DC
and IQ corrections, but cannot print the existing correction values on this
build, and LMS calibration is not available for bladeRF2.
