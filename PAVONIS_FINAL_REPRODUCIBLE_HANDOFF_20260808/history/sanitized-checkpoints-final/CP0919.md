# Checkpoint 919 - bladeRF Read-only State Audit

## Purpose

Record a fresh read-only bladeRF state snapshot after CP916-CP918 isolated the
Stage 5 failure to the bladeRF/external RF receive boundary.

This checkpoint does not transmit, receive, retune, change loopback mode,
change `rx_mux`, change filters, or modify calibration/correction state.

## Command

```sh
python3 ssh_pexpect_run.py \
  --host [host-redacted] \
  --out cp919_[date-redacted]TREADONLYBLADESTATE1_sens_bladerf_readonly_state_audit.log \
  --timeout 240 \
  -- bash -lc 'set +e; date -u +%FT%TZ; hostname; ... bladeRF-cli read-only print commands ...'
```

The command collected:

- `version; info`
- `help print`
- full `print`
- targeted `print` state for loopback, mux, bitmode, filters, hardware,
  frequency, sample rate, bandwidth, AGC, and gain
- attempted correction print readback
- final process check

## Interpretation

The bladeRF is not accidentally left in an obvious bad digital state:

- loopback is `none`;
- `rx_mux` is `BASEBAND`;
- bit mode is `16 bit samples`;
- RX FIR is `normal`;
- bias tees are off;
- clock source is onboard VCTCXO;
- temperature and power monitor are normal;
- no stale bladeRF/SDR process was visible in the final process check.

This does not explain the CP915 failure. It also does not clear the remaining
suspects, because the current CLI cannot directly print correction state and
this audit is an idle snapshot, not an active in-capture RF-chain measurement.

Current boundary after CP916-CP919:

```text
LiteX-only PBCH decode: PASS
bladeRF internal firmware/RFIC loopbacks: PASS
bladeRF idle digital state: normal
external LiteX -> bladeRF normal RF receive: FAIL
```

The remaining candidates are still:

- bladeRF normal RF receive behavior under active external capture,
- physical RF/cable/attenuator path into bladeRF,
- bladeRF normal RF correction/calibration state.

Calibration/correction writes remain a separate, approval-worthy branch.
