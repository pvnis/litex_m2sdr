# Checkpoint 926 - Transient bladeRF DC calibration guard dry-run

## Purpose

Prepare the next bladeRF-side experiment without mutating device state.

CP922 showed that the installed bladeRF CLI can apply DC/IQ calibration changes
but cannot read back current bladeRF2 DC/IQ correction values. Therefore any
runtime calibration/correction experiment remains an explicit-approval branch.

CP926 adds a guarded wrapper for one narrow future experiment:

```text
before capture -> runtime calibrate dc rx -> after capture -> restore normal RX route
```

This checkpoint only verifies the guard and dry-run behavior. No calibration
was run, no `bladeRF-cli` calibration command was executed, and no flash command
was planned or executed.

The dry-run printed the planned bladeRF scripts. The calibration script is
restricted to:

```text
set loopback none
set rx_mux BASEBAND
set filter rx normal
set agc rx off
set frequency rx 1839650000
set samplerate rx 5760000
set bandwidth rx 5600000
set gain rx 42
calibrate dc rx
```

It does not include `flash_restore`, `flash_backup`, `flash_init_cal`,
`calibrate table`, or `calibrate iq`.

## Safety Boundary

The guard script defaults to refusal. It will not run the calibration branch
unless the exact environment variable below is present:

```sh
CP926_ARM_TRANSIENT_CAL=YES_I_APPROVE_RUNTIME_BLADERF_DC_RX_CAL
```

Even in the armed branch, the script is scoped to a runtime `calibrate dc rx`
operation with before/after captures and a normal-route restore:

```text
set loopback none
set rx_mux BASEBAND
set filter rx normal
```

This still does not make the operation fully reversible, because CP922 found no
CLI readback for current bladeRF2 DC/IQ correction values. Running the armed
branch therefore still requires explicit user approval.

future transient bladeRF DC calibration test, but it does not answer whether
