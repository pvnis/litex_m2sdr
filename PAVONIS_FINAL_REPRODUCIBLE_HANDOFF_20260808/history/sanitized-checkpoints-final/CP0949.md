# Checkpoint 949 - x4 centered PBCH source validation is not clean for external use

## Purpose

CP947 showed that a narrow 500 kHz tone reaches the external bladeRF route,
while CP942-CP944 showed that the centered PBCH waveform does not recover there.
One plausible explanation is link margin: the tone has high narrowband spectral
density, while PBCH is spread over MHz.

CP949 tested a cautious boosted PBCH source before using it externally:

```text
CP918 centered PBCH-positive CF32
  -> x4 linear scale, no clipping
  -> local PBCH decode
  -> LiteX-only RX/TX loopbacks: none, phy, ad9361
```

No bladeRF commands were used.

## Interpretation

The x4 source is locally valid and survives the LiteX `none` and `phy`
loopbacks with PBCH CRC OK. However, it is not a clean all-loopback baseline:
the `ad9361` capture has strong x4-reference correlation but the full-capture
PBCH decoder locks onto a bad window and returns `crc=KO`.

Because the goal is to isolate variables, CP949 should not be used as the next
external bladeRF source without additional work. The prudent next step is to
step down to a lower boost, starting with x2, and require the same checks:

```text
local source decode OK
LiteX-only none/phy/ad9361 PBCH OK
then external bladeRF capture
```

This avoids mixing the external bladeRF failure with a new x4-specific
LiteX/AD9361 decode regression.
