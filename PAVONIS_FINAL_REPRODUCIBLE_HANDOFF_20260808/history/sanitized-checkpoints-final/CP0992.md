## Purpose

CP992 is a readback-only diagnostic after CP991 showed that requesting
`TX_ATT_DB=26` did not lower the bladeRF receive level relative to the
`TX_ATT_DB=20` runs.

No TX stream was activated in CP992. The probe only opened the same LiteX Soapy
device constructor used by `test_play.py`, inspected TX gain metadata, set a few
candidate values, and read them back.

## Interpretation

CP992 shows the software control exists and is exposed as an `ATT` gain element
with a plausible attenuation-like range. It also shows that the driver readback
accepts the values used in the ladder.

This does not explain CP991's RF observation:

- CP989/CP987 with request `20` and `AMPL=8` were around `-10.8 dBFS` in the
  one-second PBCH wrapper.
- CP991 with request `26` and `AMPL=8` was also around `-10.73 dBFS`.
- CP990 with request `20` and `AMPL=4` dropped to `-16.59 dBFS`.

So digital replay scaling is definitely affecting RF level, while the `ATT`
request did not measurably affect the CP991 receive level.

## Verdict

Readback-only Soapy gain/ATT semantics check: PASS.

Control exposed and readback values accepted: PASS.

RF attenuation effect: UNPROVEN/CONTRADICTED by CP991 receive level.

## Next Step

Do not treat `TX_ATT_DB` as a clean RF ladder variable yet. The next diagnostic
should verify whether the Soapy `ATT` value changes underlying AD9361 TX
attenuation registers, or whether the replay path overwrites/ignores the value
when streaming.

The safest next check is still readback/register-oriented:

- run a no-stream probe that sets `ATT=20`, `26`, and `40`,
- read the relevant AD9361 TX attenuation registers after each set,
- only after register behavior is understood, decide whether an RF run at a
  larger attenuation value is worth doing.
