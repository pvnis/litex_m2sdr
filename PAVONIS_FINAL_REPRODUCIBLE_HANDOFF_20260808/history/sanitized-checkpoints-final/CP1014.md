## Routing Observations

The idle `OPEN` route is stable and appears to be normal disabled-channel
behavior. During an active RX1 stream, both generic `rx` and explicit RX1 route
the active receive path to `RF3(B)`:

```text
RX1: RFIC 0x1 (B_BAL  ) <= SW 0x2 (RF3(B) )
RX2: RFIC 0x1 (B_BAL  ) <= SW 0x0 (OPEN   )
```

During explicit RX2, the active route is valid but goes through RX2 instead:

```text
RX1: RFIC 0x1 (B_BAL  ) <= SW 0x0 (OPEN   )
RX2: RFIC 0x1 (B_BAL  ) <= SW 0x2 (RF3(B) )
```

The gain readback still shows the known stale/default `60 dB` before the
channel is enabled and `42 dB` after the capture. This matches earlier
observations and is not a new regression.

## Interpretation

CP1014 confirms the current bladeRF receive software path is not silently
disabled and is not accidentally using RX2:

- Generic bladeRF `rx` behaves like explicit RX1.
- RX1 active route is `RX1 <= RF3(B)` at both BW200K and BW5.6M.
- RX2 can be selected and routes while active, but its no-TX level is much
  lower than RX1.
- The BW200K and full-BW no-TX levels match CP1011 and CP1012.
- The idle `OPEN` state is repeatable disabled-channel behavior, not a route
  fault by itself.

This strengthens the boundary: LiteX-only source path is good, bladeRF
receive-only routing/state is good enough to capture stable floors, and active
LiteX TX to bladeRF RX captures are signal-related but do not preserve enough
long-window coherence for decode.

## Verdict

bladeRF no-TX RX route audit: PASS.

No evidence of a current RX route/mux/channel-selection regression.
