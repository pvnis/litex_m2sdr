# Checkpoint 1064 - CP1063 Local Acquisition And Trimmed-Window Decode

Date: [date-redacted]

## Purpose

Use the CP1063 repeat capture to isolate decoder/acquisition behavior without
spending RF time. This checkpoint asks two questions:

1. Can the CP1063 full one-second buffer be recovered by changing the declared
   SSB frequency offset?
2. Can longer trimmed captures around the CP1063 PBCH-positive short-window
   clusters produce PBCH CRC OK?

This follows the CP1059 LiteX-only RX/TX baseline, which passed with no bladeRF
in the path. CP1059 remains the current source-side control: LiteX can transmit
and receive the centered CP918 source locally, and the centered source itself is
PBCH-decodable.

## Interpretation

The CP1063 capture is not a no-receive capture. CP1064 recovers PBCH CRC OK
from the same raw file when the decoder is given better start/window context,
including `200 ms` and `500 ms` trimmed buffers. The full one-second buffer
still fails, and the SSB-offset sweep does not fix it.

The successful trimmed rows all use nominal SSB offset `0 Hz`. The `+[date-redacted] Hz`
correlation result remains useful for waveform similarity scoring, but it did
not translate into `ssb_file_test` PBCH recovery in this run.

The current failure mode is therefore most consistent with acquisition/candidate
selection being confused by buffer contents or capture alignment. It is not
consistent with "the external path cannot carry PBCH at all."

## Verdict

CP1064: PASS for proving longer local trimmed windows can recover PBCH from the
CP1063 external LiteX-to-bladeRF capture; FAIL for full one-second PBCH
acquisition. Continue by making acquisition robust around the CP1063/CP1062
PBCH-positive regions before spending more RF time.
