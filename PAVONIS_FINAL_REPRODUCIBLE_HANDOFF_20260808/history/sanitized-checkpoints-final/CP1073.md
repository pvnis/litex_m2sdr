# Checkpoint 1073 - Decoder Full-Buffer Versus Window Fingerprints

Date: [date-redacted]

## Purpose

Compare the raw `ssb_file_test` log fingerprints for the failing full-buffer
decode and successful strict sliding windows on CP1062, CP1063, and CP1070.

This follows CP1071 and CP1072:

- CP1071 made the sliding-window smoke rule reusable and showed strict pass on
  all three corrected external captures.
- CP1072 showed a fixed sample-zero prefix is still brittle.
- CP1073 asks whether the full-buffer failure has a repeatable decoder
  signature.

No RF hardware was used in this checkpoint.

## Tool

New helper:

```sh
cp1073_decoder_log_fingerprint.py
```

It parses `measure`, `search`, and `PBCH-MIB` lines from selected
`ssb_file_test` logs. For each case it reports:

- full one-second decode fingerprint,
- first strict sliding-window success,
- best-SNR strict sliding-window success.

## Interpretation

The full-buffer failure has a consistent fingerprint:

- PBCH PCI is `0`, not expected PCI `1`.
- CRC is `KO`.
- `t_offset=0`.
- payload is `00 00 00`.
- decoded MIB fields are the dummy-looking `sfn=0` and `barred=y`.
- reported CSI delay is very large, around `600k-816k` samples for these
  captures.

The successful strict windows have a different and consistent fingerprint:

- CSI PCI and PBCH PCI are both `1`.
- CRC is `OK`.
- PBCH t_offset is nonzero.
- payload is nonzero.
- MIB SFN is nonzero and `barred=n`.
- absolute search samples line up with the known PBCH-positive regions.

This makes the full-buffer problem more concrete. It is not merely a weak signal
or missing PBCH; it is a repeatable bad PBCH candidate at the beginning of the
reported full-buffer search result.

## Verdict

CP1073: PASS for identifying a repeatable full-buffer failure fingerprint. The
next decoder-side step should test whether rejecting the `PBCH PCI 0,
t_offset=0, payload=00 00 00, barred=y` candidate and continuing the search
would reveal the same PCI 1 windows that the sliding-window evaluator already
finds.
