## RX Failure

The scanner returned `NR_CELL_SEARCH_RF_RC=134`.

Two independent problems were exposed:

1. Normal-user bladeRF open failed:
   - `Unable to open device: No devices available`
   - Existing srsUE paths use `sudo -n`, so the scanner harness needed the same privilege model.

2. The scanner started on an invalid sync-raster point:
   - `Measuring SSB frequency 1.25 MHz, center 0.00 MHz`
   - Then asserted at `intra_measure.set_config(meas_cfg)`.
   - This showed a sync-raster initialization bug before any useful target-frequency RF result could be trusted.

## Conclusion

CP1077 did not test the intended target SSB path. It proved the LiteX replay remained healthy, but the RX-side scanner needed:

- a sudo wrapper for bladeRF access;
- a band-helper sync-raster fix for band 3;
- a scanner retune policy that keeps each SSB near the receiver center.

Note: `nr_cell_search_rf` is application-level RX-only. The bladeRF RF plugin still enables both bladeRF RX and TX modules when starting an RX stream, so this is a "no application TX / no PRACH" test, not proof that the bladeRF TX module is never enabled.
