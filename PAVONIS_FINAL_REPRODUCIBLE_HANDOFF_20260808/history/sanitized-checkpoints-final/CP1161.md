## Interpretation

CP1161 passes PBCH with the exact CP1145 metadata pattern when samples are sent through the CF32 path. This closes the specific theory that duplicate metadata flags, split row boundaries, or timestamp gaps alone are sufficient to break PBCH.

The CP1157-CP1160 failure branch is now better explained as a CS16 replay-format problem: the dumped `pre_dma_tx.cs16` bytes are not currently a validated Soapy CS16 API replay input, even though the same samples converted to CF32 are valid.

The remaining live-vs-replay difference is narrower:

- CP1145 live paired TX dump: digital pre/post-DMA decodes, same-window RF fails.
- CP1150/CP1152/CP1161 standalone CF32 replays: RF PBCH passes.
- Therefore the live failure is not the sample vector, not the RF path in general, and not the stored metadata pattern by itself.

The next useful isolation is live-like pacing/runtime:

- replay the same CF32 metadata rows with wall-clock pacing instead of pre-queueing the whole future schedule quickly,
- keep a small lead time so writes are not late,
- if paced CF32 metadata replay passes, remaining suspect is the live gNB/runtime state;
- if paced CF32 metadata replay fails, the issue is likely tied to live write pacing or driver queue behavior rather than vector content.

Android/ADB remains out of scope until PBCH is stable. LiteX-only OTA remains the fallback baseline if bladeRF/LiteX RF behavior becomes ambiguous again.
