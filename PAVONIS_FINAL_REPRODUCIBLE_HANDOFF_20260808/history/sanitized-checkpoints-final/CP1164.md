## Purpose

Test the failing CP1159 continuous CS16 replay branch with
`M2SDR_SOAPY_TX_CS16_TO_SC12=1` forced and logged. This was intended to check
whether the LiteX Soapy CS16 path can be repaired by enabling the source-tree
CS16-to-SC12 conversion.

## Installed Module Audit

The remote source tree contains the env hook, but a read-only audit of the
installed Soapy module binaries did not find the env string in either installed
module:

```text
/usr/lib/x86_64-linux-gnu/SoapySDR/modules0.8/libSoapyLiteXM2SDR.so
  sha256 eeff3bddbc08ab7ea9d931e7be7e00b43ab3a924a14f6a80b420ab190469aeb3

  sha256 f13e498559e8b699617cd7bd3a96a6b1b814804041105d03e4b3f63d93c430fb
```

`strings | grep M2SDR_SOAPY_TX_CS16_TO_SC12` produced no matches for both
installed binaries. Replay stdout also showed a duplicate module warning, with
the `/usr/lib/x86_64-linux-gnu/...` module taking precedence over the
`/usr/local/...` duplicate.

## Interpretation

CP1164 does **not** prove that CS16-to-SC12 conversion fails. It proves the
forced env was not available in the installed active Soapy module, so the run
effectively repeated the unconverted CS16 TX_ATT5 behavior.

The comparison is consistent:

- CP1157 unconverted exact CS16 TX_ATT5 clipped and failed.
- CP1164 forced-env continuous CS16 TX_ATT5 clipped and failed similarly.
- CP1161/CP1162 CF32 conversions of the same CS16 payload passed at TX_ATT5.

The next useful step is not a live gNB retry. First make the active LiteX Soapy
module match the source tree that contains `M2SDR_SOAPY_TX_CS16_TO_SC12`, or run
the replay with a confirmed patched module loaded via a controlled plugin path.
Then repeat the CS16 replay A/B.
