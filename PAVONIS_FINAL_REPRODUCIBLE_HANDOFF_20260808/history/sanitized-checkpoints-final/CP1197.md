# Checkpoint 1197 - Live gNB TX Slip Trace Produces No Driver Lines

Date: [date-redacted] Europe/Zurich

Scope: short [host-redacted]-only live gNB run with the patched LiteX Soapy module,
`OCUDU_SOAPY_TX_SUPPRESS_EMPTY_EOB=1`, OCUDU direct-stderr TX summaries, and
LiteX driver `M2SDR_SOAPY_TX_SLIP_TRACE=1`. No bladeRF capture, UE, PRACH,
NRSA, or Android test was run.

## Result

Diagnostic partial pass.

The live gNB path started cleanly, used the patched LiteX Soapy module, and
kept the clean OCUDU caller-side summary profile. The gNB process environment
contained the slip-trace variables, and a read-only remote module check proved
the loaded module contains the `M2SDR_SOAPY_TX_SLIP_TRACE` hook and exact
`TX timed commit slip` log string.

However, the full fetched gNB log contains zero `TX timed commit slip` lines.
That does not yet prove timed worker commits are early/on-time, because the
current LiteX trace logs only inside:

```text
(pkt->flags & SOAPY_SDR_HAS_TIME) && pkt->timeNs > 0
```

The OCUDU summary proves many `HAS_TIME` writes occurred, but it does not yet
record whether their `timeNs` values were positive. CP1197 therefore narrows
the next test to timestamp visibility or direct driver counters rather than
closing the LiteX worker-latency theory.

## Verdict And Next Step

CP1197 does not recover Stage 5 and does not test RF. It proves that the
post-CP1196 live no-RF gNB TX path remains clean while the LiteX slip-trace log
hook produces no lines despite the hook being present and enabled.

Do not repeat CP1197 as-is. The next useful checkpoint should add a low-volume
direct-stderr timestamp summary at OCUDU or LiteX-driver level so we can
distinguish:

1. `HAS_TIME` writes with `timeNs=0` or non-positive timestamps.
2. Positive-timestamp writes where Soapy INFO log routing hides the current
   driver trace.
3. Positive-timestamp writes with direct driver slip counters indicating late
   or on-time worker commits.
