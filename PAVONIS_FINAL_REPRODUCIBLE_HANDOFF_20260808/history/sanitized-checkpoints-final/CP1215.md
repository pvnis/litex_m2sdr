## Method

Added and ran:

```sh
python3 cp1215_paced_capture_phase_diagnostic_[date-redacted]/cp1215_capture_phase_diagnostic.py
```

The diagnostic computes the CS16 replay metadata period from row timestamps and
row lengths. It then maps the CP851 reference template start sample into that
period, using sample rate `11520000` and template start sample `163840`.

Metadata anchor:

- Metadata rows: `4028`
- Metadata first/last timestamp span: `0.673532291 s`
- Replay period from max row end: `0.673611110444 s`
- Template start sample: `163840`
- Template schedule time: `0.053205207778 s`

For each paced capture, capture sample zero is estimated from the
reference-correlation best start:

```text
capture0_phase_s = (template_sched_s - refcorr_best_start_s) mod period_s
pbch_metadata_phase_s = (capture0_phase_s + pbch_capture_start_s) mod period_s
```

This does not prove the absolute bladeRF capture hardware timestamp; CP920
capture logs do not include that. It is a refcorr-derived placement diagnostic
using the known template as the anchor.

## Interpretation

CP1215 closes the open placement diagnostic in favor of a capture-phase/window
placement explanation. The tested paced-CS16 captures do not share a stable
capture sample-zero phase relative to the CS16 replay metadata period. Because
the PBCH OK windows are sparse, a 20-50 ms analysis can easily call a capture
"failed" even when decodable PBCH appears later in the same 250 ms capture.

The key practical conclusions are:

- CP1208 50 ms lookahead remains an early-window miss, not a no-PBCH RF
  capture.
- CP1211 and CP1212, the two 100 ms runs, align strongly after metadata-phase
  remap despite looking different in early capture time.
- CP1209 and CP1210 overlap part of the same late-period phase families seen
  in the 100 ms runs.
- The apparent non-monotonic lookahead ladder is partly analysis-window
  placement, not a stable queue-depth threshold.

## Current frontier update

The next RF rung should not be another short-window-only lookahead test. If a
75 ms paced-CS16 patched-module replay is run, analyze it over 250 ms from the
start, preserve the reference-correlation JSON, and preferably repeat it for
variance. Better still, add high-resolution capture-start or hardware-timestamp
logging to CP920 so future placement does not have to be inferred from
reference correlation.

Do not reinterpret CP1208 as a total paced-CS16 failure, and do not rerun the
50-250 ms lookahead ladder only to classify first-50-ms windows again.
