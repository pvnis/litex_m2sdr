# CHECKPOINT 1218: bladeRF RX metadata capture feasibility passes

Date: [date-redacted] Europe/Zurich

## Goal

Before spending another RF capture on the paced-CS16 50 ms versus 75 ms
comparison, determine whether the bladeRF side can expose a sample-zero receive
timestamp. CP1215-CP1217 showed that capture placement matters; CP920/CP905
currently captures through `bladeRF-cli`, which writes raw samples but does not
record a metadata timestamp for sample zero.

This checkpoint is a tooling and feasibility smoke test. It does not transmit
from LiteX, run PBCH analysis, run NRSA, or touch Android.

## Interpretation

CP1218 closes the capture-timestamp feasibility question:

- Do not use Python `SoapySDR` on `[host-redacted]` for the next step; the module is
  not installed.
- Do not depend on `SoapySDRUtil`; it is not installed.
- A C libbladeRF helper is feasible and can return metadata timestamps with
  `BLADERF_FORMAT_SC16_Q11_META`.
- The next 50 ms versus 75 ms paced-CS16 comparison can be done with a
  timestamped bladeRF capture helper rather than another raw `bladeRF-cli`
  capture.

`META_STATUS=0x00030000` was reported, while the public overrun/underrun flags
in this header are low bits `0x1` and `0x2`; the smoke still returned
`BLADERF_SYNC_RX_RC=0` and `META_ACTUAL_COUNT=32768`. The production helper
should decode and report overrun/underrun explicitly, but CP1218 is enough to
prove the timestamp path exists.

## Next Step

Build a CP920-style timestamped capture variant using the libbladeRF metadata
helper, then run the paced-CS16 comparison that CP1217 opened:

1. One 50 ms patched-module CS16 paced replay with metadata capture timestamp.
2. One 75 ms patched-module CS16 paced replay with metadata capture timestamp.
3. Correct off-center 250 ms PBCH sweep and phase-aware placement for both.

This should give one branch-level answer to whether 50 ms and 75 ms differ in
capture/sample-zero placement, RF coherence, or replay scheduling rather than
only in short-window labels.
