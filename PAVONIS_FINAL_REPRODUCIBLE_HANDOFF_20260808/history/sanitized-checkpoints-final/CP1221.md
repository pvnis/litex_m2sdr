# CHECKPOINT 1221: CP1220 timestamp/phase post-analysis

Date: [date-redacted] Europe/Zurich

## Goal

Use only existing artifacts to interpret CP1220's timestamped 50 ms and
75 ms paced-CS16 captures. The specific question is whether CP1220's bladeRF
metadata, replay logs, reference-correlation starts, and 250 ms PBCH windows
can turn the paced-CS16 results into a reliable scheduling/capture-placement
diagnostic.

This checkpoint is local post-analysis only: no SSH, no TX, no RX, no UE, no
Android operation, no source rebuild, and no new RF capture.

## Method

Added and ran:

```sh
python3 cp1221_cp1220_timestamp_phase_post_analysis_[date-redacted]/cp1221_timestamp_phase_post_analysis.py
```

The script reuses the CP1215 metadata-period method:

```text
capture0_phase_s = (template_sched_s - refcorr_best_start_s) mod period_s
pbch_metadata_phase_s = (capture0_phase_s + pbch_capture_start_s) mod period_s
```

It also parses the CP1220 bladeRF metadata capture logs and [host-redacted] replay logs
for a host-clock diagnostic. That diagnostic is deliberately weaker evidence:
it combines [host-redacted] replay host times with [host-redacted] bladeRF capture host times and
user-space call boundaries.

## Interpretation

CP1221 passes as a local diagnostic and reinforces the CP1215 interpretation.
Both CP1220 timestamped captures are PBCH-positive paced-CS16 examples whose
PBCH windows map into already-seen metadata-phase families:

- CP1220A lines up with prior late-period paced-CS16 families near
  `0.58`, `0.64`, and `0.66 s`, plus early-period families around
  `0.09` and `0.12 s`.
- CP1220B wraps near the metadata-period boundary and overlaps earlier
  families around `0.03`, `0.04`, `0.07`, and `0.18 s`.

The 50 ms versus 75 ms difference in CP1220 is therefore not a stable
monotonic lookahead threshold. It is another instance of capture phase,
coherence, and sparse PBCH-positive windows controlling the short-window
classification.

The bladeRF metadata harness is still valuable: it proves complete capture
length and no timestamp gaps. It does not prove absolute LiteX/bladeRF
alignment by itself. Cross-host epoch logs are useful sanity checks, but CP1221
shows they are not strong enough to replace reference correlation.

## Current Frontier Update

Do not repeat 50 ms or 75 ms paced-CS16 RF replays only to prove PBCH exists.
The next useful rung should either:

- instrument live gNB schedule/capture placement with a tighter anchor than
  cross-host wall-clock deltas, or
- build a minimal live-cadence replay that preserves OCUDU-like timing,
  chunking, format, and discontinuity behavior while still allowing controlled
  250 ms or phase-aware PBCH analysis.

If this branch stalls, use the LiteX-only TX/RX OTA baseline to isolate the
bladeRF interaction before spending another full live RF proof.
