## `ue_sync_nr` Trace Findings

The new trace produced:

```text
PAVONIS_UE_SYNC_NR_TRACE lines: 101
find_attempt events: 32
update_ssb events: 7
state_transition events: 5
track_opportunity events: 53
```

All 53 tracked SSB opportunities had `pbch_crc=0`.
The tracked SNR range was about `-15.157` to `-28.474 dB`, average
`-21.855 dB`.

Three FIND-to-TRACK transitions were observed:

```text
attempt=289 meas_delay_us=-194.770828 q_delay=-194.770828 next_rf_offset=-1122 new_state=TRACK
attempt=360 meas_delay_us=-32.516510  q_delay=-32.516510  next_rf_offset=-187  new_state=TRACK
attempt=1087 meas_delay_us=-192.434494 q_delay=-192.434494 next_rf_offset=-1108 new_state=TRACK
```

The first two TRACK periods dropped back to FIND after exactly 20 consecutive
PBCH misses:

```text
opportunity=20 miss_before=19 miss_after=0 drop_to_find=1 state=FIND
opportunity=40 miss_before=19 miss_after=0 drop_to_find=1 state=FIND
```

The third TRACK period reached `miss_after=13` by the end of the NRSA run and
did not reach the 20-miss drop threshold before the process exited.

Several PBCH-CRC-true FIND updates with large positive delay did not enter
TRACK:

```text
delay_us=78.813469  new_state=FIND sample_offset_after=454
delay_us=286.087433 new_state=FIND sample_offset_after=1648
delay_us=423.327942 new_state=FIND sample_offset_after=2438
delay_us=321.036926 new_state=FIND sample_offset_after=1849
```

The important asymmetry is that very large negative delays did enter TRACK,
because the current source gate is:

```c
// Transition to track only if the measured delay is below 2.4 microseconds
if (measurements->delay_us < 2.4f) {
  q->state = SRSRAN_UE_SYNC_NR_STATE_TRACK;
}
```

This accepts `-194 us` and `-32 us` as "below 2.4 us" even though their
magnitude is much larger than the intended timing window. The resulting RF
sample offsets were large negative corrections (`-1122`, `-187`, `-1108`
samples at 5.76 Msps).

## Interpretation

CP1250 confirms the post-camping failure is indeed the TRACK PBCH-miss path:
the trace shows two complete 20-miss TRACK-to-FIND cycles and a third partial
cycle. It also sharpens the next software suspect: `ue_sync_nr_update_ssb()`
enters TRACK on large negative `delay_us` values because it tests only
`delay_us < 2.4f`, not an absolute or bounded signed delay.

This is stronger than the prior "simple overflow" theory. CP1248 nearly
eliminated overflow/gap symptoms but still failed out-of-sync; CP1250, with
the same nominal RX gain and TX backoff, had more RF overflow/gap symptoms,
yet the new trace exposes a deterministic state-machine behavior independent
of the gNB's clean TX counters: all TRACK PBCH opportunities after those
large negative delay transitions had CRC false.

The next rung should be a minimal diagnostic/guard branch around the
`ue_sync_nr_update_ssb()` delay gate. A conservative first step is to trace or
guard acceptance with an absolute delay condition, for example requiring a
small bounded signed delay such as `fabsf(measurements->delay_us) < 2.4f`
before transitioning FIND to TRACK. If patched, the run should repeat the
CP1250 RF point and verify whether large negative delay PBCH hits stay in FIND
and whether a later sane-delay hit can camp/track without immediate 20-miss
loss.
