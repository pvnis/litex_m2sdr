## Interpretation

CP1252 validates the CP1251 gate mechanism but does not recover camping. The
failure moved from CP1250's post-camping TRACK PBCH-miss cycle to SFN-sync
failure: the stack found the cell, then every PBCH hit seen by `ue_sync_nr`
during SFN sync had absolute delay far above `2.4 us`, so all were rejected and
no FIND-to-TRACK transition occurred.

Important nuance: the current CP1251 implementation still applies CFO/delay
feedback before deciding whether the absolute gate rejects the TRACK transition.
In CP1252, rejected hits still changed `q_delay` and `next_rf_sample_offset`
while the state remained FIND. The next rung should test a stricter reject path
that does not apply feedback or update timing state for large-absolute-delay
FIND hits. That isolates "bad TRACK entry" from "bad feedback poisoning FIND."

## Checkpoint Status

Result: **CELL FOUND, ABS-GATE REJECTS LARGE DELAYS, SFN FAIL, NO CAMPING**.

Reusable conclusion: strict `fabs(delay_us) < 2.4 us` prevents the large
negative delay FIND-to-TRACK entries seen in CP1250, but at the current live RF
point it also prevents camping because no small-absolute-delay SFN-sync PBCH hit
appears within 100 trials. Do not repeat CP1252 unchanged; the next test should
reject bad-delay feedback before it updates the UE sync timing/CFO state.
