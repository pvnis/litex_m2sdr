# CHECKPOINT 1253: `ue_sync_nr` Reject Bad-Delay Feedback Build/Deploy

Date: [date-redacted] Europe/Zurich

## Goal

CP1252 proved that the opt-in absolute-delay gate blocks large negative
FIND-to-TRACK transitions, but it also showed that the CP1251 implementation
still applies the rejected PBCH hit's feedback before staying in FIND. This
checkpoint adds a second opt-in diagnostic guard that rejects bad-absolute-delay
feedback before it mutates `q_delay`, `q_cfo`, `next_rf_sample_offset`,
`ssb_idx`, `sf_idx`, or `sfn`.


New env control:

```text

```

The new guard is active only when both of these are true:

```text
PAVONIS_SRSUE_UE_SYNC_NR_DELAY_ABS_GATE=1
PAVONIS_SRSUE_UE_SYNC_NR_REJECT_DELAY_FEEDBACK=1
```

When active, a FIND-state PBCH hit that fails the selected absolute delay gate
returns success while leaving timing/CFO/context state unchanged. Default
behavior remains CP1251-compatible unless the new env is enabled.

## Interpretation

CP1253 is a build/deploy checkpoint, not an RF result. It prepares the next live
RF rung: repeat CP1252's live NRSA point with both the absolute-delay gate and
the new feedback-reject guard enabled. The discriminating question is whether
bad large-delay FIND PBCH hits still appear but no longer perturb the next FIND
attempts' timing/CFO state, and whether that is enough to recover SFN sync or
camping.
