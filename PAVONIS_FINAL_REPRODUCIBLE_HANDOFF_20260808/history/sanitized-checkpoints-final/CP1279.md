# Checkpoint 1279: TRACK Direct-Offset Diagnostic Live Run

Date: [date-redacted] Europe/Zurich

## Goal

Test whether the scheduled TRACK PBCH decoder can decode when run at the
blind-search offset that finds PBCH, instead of the static scheduled
`selected_sf_offset=825`. This separates "TRACK decoder assumptions are bad"
from "scheduled TRACK is pointed at the wrong samples."

## Implementation

Added a default-off diagnostic in `srsRAN_4G`:

- public helper `srsran_ssb_track_at_offset(...)`;
- env knobs:
  - `PAVONIS_SRSUE_UE_SYNC_NR_TRACK_DIRECT_OFFSET_CHECK`;
  - `PAVONIS_SRSUE_UE_SYNC_NR_TRACK_DIRECT_OFFSET_CHECK_LIMIT`;
- trace event `track_direct_offset_check`, emitted only when a same-buffer or
  rolling blind sidecheck has PBCH CRC true.

the TRACK decoder directly at those offsets produced PBCH CRC true every time,
while the scheduled TRACK call at `selected_sf_offset=825` produced CRC false.

## Conclusion

CP1279 closes the "TRACK decoder cannot decode this SSB class" theory for the
current-buffer blind hits. The same TRACK demod/decode path succeeds when
called at the blind-search offset, without using a search-specific CFO input.

The active frontier is now the scheduled TRACK anchor policy: `ue_sync_nr`
continues to schedule TRACK at static `selected_sf_offset=825`, while the
actual PBCH-valid offsets in this run were `541`, `368`, and `749`. The next
rung should be an opt-in selected-offset follow/override experiment that makes
scheduled TRACK use the most recent validated direct/blind offset, then checks
whether scheduled TRACK PBCH CRC becomes nonzero and whether camping remains
stable without relying on blind fallback.
