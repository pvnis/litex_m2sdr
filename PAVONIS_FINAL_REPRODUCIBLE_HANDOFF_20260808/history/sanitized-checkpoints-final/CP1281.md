# Checkpoint 1281 - Live Direct Offset Override Without Stored Follow

Date: [date-redacted] Europe/Zurich

## Goal

Separate CP1280's useful behavior from its failed behavior. CP1280 showed that
same-opportunity direct blind-offset promotion can create normal TRACK PBCH
hits, while stored last-good offset follow was `0/58`. CP1281 makes direct
offset override its own opt-in path and reruns the same live RF point with
stored follow disabled.

## Pre-Run bladeRF Residual Check

The CP1280 post-cleanup `bladeRF-cli -p` message was diagnosed before running
RF again. Plain `bladeRF-cli` as `[host-redacted]` still reports the device as
inaccessible, but `/dev/bus/usb/004/002` is `root:plugdev` with mode `0660`
and `[host-redacted]` is not in `plugdev`. The RF harness uses `sudo -n`, and
`sudo -n bladeRF-cli -e ...` succeeded before and after CP1281. No stale
NRSA/gNB/qcore owner was found. Treat the CP1280 plain-probe warning as a
permission artifact, not an active hardware-owner blocker.

## Interpretation

CP1281 proves the CP1280 immediate-override result does not depend on stored
last-good offset follow. Direct override alone produced all four TRACK PBCH
hits, while stored follow stayed completely inactive. This closes the
"CP1280 worked because follow state was also enabled" concern.

The active frontier remains a per-opportunity adaptive TRACK anchor or timing
model. The valid current-buffer offsets continue to move substantially relative
to `selected_sf_offset=825`, and scheduled TRACK at the static selected offset
still does not independently recover. A next rung should make the
current blind/direct evidence the primary TRACK anchor earlier in the
opportunity, or redesign how the selected offset is derived for each TRACK
attempt. It should not re-enable simple stored offset follow as the main
mechanism.
