# Checkpoint 1285: direct-primary timing prediction trace live run

Date: [date-redacted] Europe/Zurich

## Goal

CP1284 proved that direct-primary timing correction applies and is consumed by
`recv_adjust`, but scheduled TRACK still does not recover. CP1285 keeps the
CP1284 behavior and adds a prediction trace: after one direct-primary timing
correction is applied, the next CRC-valid direct/blind candidate is compared
against the previous correction to see whether the correction moved the SSB
toward or away from the scheduled anchor.

## Code Change

Edited:

```text
srsRAN_4G/lib/src/phy/ue/ue_sync_nr.c
```

New default-off control:

```text
PAVONIS_SRSUE_UE_SYNC_NR_TRACK_DIRECT_OFFSET_PRIMARY_TIMING_PREDICT_TRACE=1
```

When enabled, a successful direct-primary timing correction stores its
opportunity, selected offset, direct offset, delta, residual feedback offset,
and corrected `next_rf_sample_offset`. The next CRC-valid direct-offset check
then emits:

```text
event=track_direct_offset_primary_timing_predict
```

The event reports the observed direct offset after correction and an estimated
uncorrected offset:

```text
estimated_uncorrected_offset = observed_offset + previous_corrected_next_rf_offset
```

This is a diagnostic only. It does not change TRACK decode decisions.

## Interpretation

PASS for the CP1285 diagnostic. The new prediction event fired once and showed
that the CP1284 correction sign is directionally useful: after a `+1606`
sample correction, the estimated uncorrected residual would have been
`+2807` samples, while the observed residual after correction was `+1201`
samples. That rules out a simple "the correction sign is backwards" theory for
this run.

FAIL for the hypothesis that CP1284's simple receive realignment is close
enough to recover scheduled TRACK. The correction reduced the offset error but
left the next direct candidate still far from the static scheduled anchor
(`[date-redacted]` observed versus `825` scheduled). Scheduled TRACK remained `0/74`.

The next useful rung should stop treating this as a scalar sign-only correction
problem. Either make the current direct/blind candidate the active scheduled
TRACK anchor for that same opportunity, or add a small candidate-set scheduler
around the static anchor and direct candidate so the state machine can use
current-offset evidence without waiting for future receive realignment to make
`selected_sf_offset=825` correct.
