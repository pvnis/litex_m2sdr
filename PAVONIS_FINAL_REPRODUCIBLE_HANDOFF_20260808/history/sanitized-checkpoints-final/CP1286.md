# Checkpoint 1286: Candidate-Anchor TRACK Scheduler

Date: [date-redacted]

## Goal

Test the next rung after CP1285: keep direct-primary, direct override, offset
follow, and fallback actions disabled, but allow the TRACK scheduler to use a
same-opportunity direct-offset candidate as the active PBCH/TRACK result before
falling back to the old static scheduled SSB offset. This isolates whether the
frontier is simply "use the candidate as the anchor" or whether the remaining
problem is stateful/predictive scheduling across opportunities.

The new path:

- runs the existing sidecheck/direct-offset diagnostics when direct-primary or
  candidate-anchor mode is enabled;
- keeps direct-primary selection gated strictly by
  `track_direct_offset_primary_enabled`;
- if direct-primary did not apply and candidate-anchor is enabled, promotes a
  direct-offset candidate into the normal TRACK result;
- then runs the old static scheduled `srsran_ssb_track` only if no
  candidate-anchor result applied;
- logs `track_candidate_anchor` and `track_candidate_anchor_static` counters.

## Conclusion

CP1286 validates the candidate-anchor scheduler path in isolation:

- direct-primary was disabled and produced zero direct-primary events in the
  corrected run;
- one same-current candidate anchor was promoted into a normal TRACK hit;
- the old static scheduled TRACK anchor still failed `0/73` under the same
  run;
- candidate-anchor scheduling as implemented is not enough to maintain TRACK
  because usable candidate evidence appeared only once while rolling sidecheck
  saw three hits.

The next rung should move from one-shot same-opportunity candidate substitution
to active/stateful candidate-anchor scheduling. The most direct hypothesis is
to carry a candidate anchor with TTL or promote rolling-tail/current candidate
anchors into subsequent scheduled TRACK offsets, while keeping direct-primary,
fallback actions, and offset-follow disabled until the scheduler effect is
isolated.
