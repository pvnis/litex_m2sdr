# CHECKPOINT 1287 - Candidate-Anchor Stateful Scheduler Deploy, Live SFN-Fail Before TRACK

Date: [date-redacted] Europe/Zurich

## Goal

Test whether a default-off stateful candidate-anchor scheduler can carry a
CRC-valid same-opportunity candidate offset forward as the active TRACK anchor,
with direct-primary, direct override, offset follow, and all fallback actions
disabled.

This was intended as the next rung after CP1286B, where a one-shot same-current
candidate anchor produced one normal TRACK hit while static scheduled TRACK
remained `0/73`.

Behavior:

- `pavonis_ue_sync_nr_track_candidate_anchor_stateful_update()` stores a

- `pavonis_ue_sync_nr_track_candidate_anchor_stateful_attempt()` tries the
  stored offset via `srsran_ssb_track_at_offset()` before static scheduled
  TRACK.
- Same-opportunity candidate-anchor updates are intended to feed future TRACK
  opportunities while static scheduled TRACK remains available as the last
  path.

## Conclusion

CP1287 is a valid build/deploy/run checkpoint, but it is not evidence for or
against the stateful candidate-anchor scheduler. The run found PCI1 quickly,
but failed all SFN sync trials and never entered CAMPING or TRACK. Therefore
the new stateful path had zero update or attempt opportunities.

This looks like the same live acquisition variability seen in nearby rungs
where a first run SFN-failed before TRACK and a same-point rerun was needed to
exercise the intended TRACK logic. Because CP1286B reached TRACK at the same RF
point and this CP1287 run did not, the next rung should be a same-code,
same-wrapper rerun before changing scheduler semantics.
