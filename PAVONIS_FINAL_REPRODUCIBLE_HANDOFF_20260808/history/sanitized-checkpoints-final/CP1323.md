## Goal

Test one RF-path difference between the independent bladeRF capture helper and
the srsUE bladeRF RF plugin without editing `ue_sync_nr.c` sync/anchor logic.
The helper configures/enables RX only. The srsUE plugin historically configures
and enables the bladeRF TX path inside `rf_blade_start_rx_stream()`, before any
UE uplink is needed.

CP1323 adds a default-off RF-plugin diagnostic:

```text
PAVONIS_RF_BLADE_RX_START_SKIP_TX_ENABLE
```

When set, the plugin skips the TX `bladerf_sync_config()` and
`bladerf_enable_module(... TX ...)` calls during RX stream start. Default
behavior is unchanged.

## Interpretation

Skipping srsUE's TX-path pre-enable during RX stream start does not raise the
raw scheduled TRACK downlink metric. At this RF point it fails earlier, during
SFN synchronization, and produces zero TRACK opportunities.

This weakens the theory that simply having the bladeRF TX module pre-enabled is
the cause of the current sub-threshold scheduled TRACK windows. The active gate
remains unchanged: do not resume `ue_sync_nr.c` sync/anchor scheduler work until
a raw scheduled-TRACK run raises mean `meas_snr` and the fraction of
opportunities at or above `-10 dB`.

The next RF-path comparison should keep default srsUE TX pre-enable restored
and inspect another helper-vs-plugin difference, such as RX metadata/read
semantics or an explicit raw sample dump from the srsUE plugin receive path for
offline PBCH comparison.
