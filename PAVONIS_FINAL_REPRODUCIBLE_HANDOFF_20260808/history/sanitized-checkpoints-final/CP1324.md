## Goal

Test another RF-path difference between the independent bladeRF capture helper
and the srsUE bladeRF RF plugin without editing `ue_sync_nr.c` sync/anchor
logic.

The helper uses `BLADERF_META_FLAG_RX_NOW` only on the first receive and then
requests `last_timestamp + last_count`. The srsUE plugin normally uses
`BLADERF_META_FLAG_RX_NOW` on every receive. CP1324 adds a default-off RF
plugin diagnostic:

```text
PAVONIS_RF_BLADE_RX_CONTIGUOUS_META
PAVONIS_RF_BLADE_RX_DBG
```

When enabled, `rf_blade_recv_with_time()` uses helper-like timestamp-contiguous
metadata after the first read and logs bounded RX metadata/amplitude evidence.
Default behavior remains unchanged.

## Interpretation

Helper-style timestamp-contiguous metadata is not a usable direct replacement
for srsUE's repeated `RX_NOW` receive loop. It keeps exact timestamps while the
UE loop keeps pace, but once libbladeRF returns a short read, the next exact
timestamp can already be in the past, producing receive errors under the live
NRSA pacing.

The raw scheduled TRACK gate remains unchanged: mean `meas_snr` is still about
`-21.6 dB`, with `0/73` opportunities at or above `-10 dB` and zero PBCH hits.

Do not resume `ue_sync_nr.c` sync/anchor scheduler work and do not move to
PRACH/Android/NAS. The next RF-path comparison should restore default repeated
`RX_NOW` behavior and make the next diagnostic observational only: bounded
sample/metadata capture from the srsUE plugin receive path for offline PBCH or
amplitude comparison against the independent helper capture.
