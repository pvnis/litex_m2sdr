# CHECKPOINT 1384 - CP1383 Offline TRACK Window Replay

Date: [date-redacted] Europe/Zurich

## Purpose

Replay CP1383's live TRACK-era receive windows offline from the bounded
srsUE `rf_blade_recv_with_time()` RXNOW dump. This is a no-RF checkpoint: no
source changes to `ue_sync_nr.c`, no PRACH/Android/NAS work, and no ladder
movement. The question is whether CP1383's raw RX dump fails at the same static
scheduled TRACK window offline, or whether nearby windows decode PBCH.

## Interpretation

CP1384 reproduces the important CP1365 pattern at CP1383's 7.68 Msps geometry:
the static live-equivalent scheduled TRACK window fails offline exactly like
the live run (`0/77`, mean `-21.799 dB`, `0/77 >= -10 dB`, `0/77 >= -15 dB`),
but nearby windows in the same captured RX buffer decode PBCH.

This further weakens a broad "srsUE RX dump path conversion/downsample destroys
the samples" theory: the CP1383 RX dump contains decodable PCI1 PBCH with
positive SNR at nearby offsets. It does not prove the live scheduler is the
only problem, because the usable alternate windows are mostly different
`sfn % 16` phases and therefore may be adjacent SSB instances rather than the
exact live scheduled one.

The raw live gate is still closed. CP1384 is not a ladder unlock and does not
justify PRACH/Android/NAS work. The active frontier remains the raw scheduled
TRACK downlink metric: mean `event=track_opportunity meas_snr`, percentage of
opportunities `>= -10 dB`, and TRACK PBCH hits.

## Decision

- Do not edit `ue_sync_nr.c` sync/anchor logic.
- Do not move up the ladder from this checkpoint.
- Continue with RF/link-budget or receive-window timing diagnostics that can
  raise the live scheduled TRACK metric, or isolate why the live static window
  is consistently the wrong/sub-threshold window even when nearby dump windows
  decode.
