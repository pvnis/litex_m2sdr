# CHECKPOINT 1385 - Live gNB With Same-Device LiteX RX Capture

Date: [date-redacted] Europe/Zurich

## Goal

Try to build a LiteX-only live-gNB RX baseline at the CP1373 geometry:

- [host-redacted] live gNB TX through LiteX-M2SDR
- LiteX-M2SDR RX capture at the SSB-centered CP1373 receive geometry
- no bladeRF, no srsUE, no Android, no PRACH, no NAS
- no `ue_sync_nr.c` sync/anchor edits

This was meant to isolate whether the live M2SDR gNB waveform is visible to
LiteX RX without involving the bladeRF/srsUE receive path.

## Context

The user's "make live gNB emit native CF32" theory is already covered by
CP1363/CP1368/CP1369. A config-only CF32 switch does not exist; an env-gated
OCUDU TX-CF32 patch was built and run with `OCUDU_SOAPY_TX_FORMAT=cf32`, and
that live A/B still failed the raw scheduled TRACK gate at mean `-21.932 dB`,
`0/96 >= -10 dB`, and zero PBCH hits.

CP1385 therefore did not repeat live TX CF32. It tested a different isolation:
use LiteX RX as the live receive observer.

## Critical Caveat

This is not a clean passive same-device RX baseline. The LiteX RX helper opened
a second `SoapySDR.Device({"driver": "LiteXM2SDR"})` while the gNB was already
running. The RX log shows that this second open reinitialized the device:

```text
SoapyLiteXM2SDR initializing...
Configuring bitmode
Configuring PCIe DMA headers
Initializing SI5351
Powering up AD9361
Initializing AD9361 SPI
Initializing AD9361 RFIC
Configuring AD9361 FIRs
Applying default RF settings
Configuring RX/TX channel 0
Configuring RX/TX channel 1
```

The gNB digital dump remained decodable, but the live TX runtime also showed
stress after the second-device interaction:

```text
SOAPY_TX_TIMEOUT_COUNT=0 in grep of explicit timeout warnings
Soapy TX summary tail: timeouts increased to 1843, errors=0, tx_format=CS16
LiteX worker summary tail: late_count increased to 822, underflow_count=0,
                           acquire_errors=0
release late trace lines=16
```

So CP1385 proves that the separate LiteX RX process can mechanically open and
capture CF32 while the gNB window is up, but it likely perturbs the live RF
state. The negative PBCH decode from this capture should not be treated as
evidence that the undisturbed live M2SDR TX cannot be received by LiteX RX.

## Conclusion

CP1385 is a feasibility/diagnostic checkpoint, not a ladder unlock.

What worked:

- gNB live start/stop/package completed.
- Same-device LiteX RX opened and captured a 1 s CF32 file.
- Corrected digital TX dump still contains decodable PBCH before and after DMA.
- `[host-redacted]` is reachable after the checkpoint.

What did not work:

- The LiteX RX capture had `0/210` targeted PBCH decodes and `0/847` aligned
  sweep PBCH decodes.
- The separate RX `Device` open reinitialized M2SDR/AD9361 while gNB was live,
  so this is not a clean passive baseline.

Interpretation:

Do not repeat this same second-process same-device LiteX RX method as if it
were a transparent OTA baseline. The next LiteX-only live receive isolation
should avoid opening a second M2SDR device while gNB owns TX. Better options
are an in-process/gNB-owned RX dump hook, an existing M2SDR Soapy RX dump path
if one exists, or an independent receiver path. The active ladder gate remains
mean scheduled TRACK `meas_snr` and percentage of TRACK opportunities
`>= -10 dB`; CP1385 does not justify PRACH/Android/NAS or `ue_sync_nr.c`
sync/anchor edits.
