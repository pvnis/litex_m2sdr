# Checkpoint 1392: Live gNB In-Process RX Append At CP1373 Geometry

Date: [date-redacted] Europe/Zurich

## Purpose

CP1392 reruns the CP1390 gNB-owned LiteX RX diagnostic after CP1391's
instrumentation build-smoke. The goal is to capture a longer same-process RX
stream while the live gNB owns the M2SDR, without opening a second Soapy device
and without changing the transmitter away from the normal live path.

This checkpoint does not edit `srsRAN_4G/lib/src/phy/ue/ue_sync_nr.c` sync or
anchor logic and does not run srsUE, PRACH, Android, NAS, or a ladder
promotion. It is not a raw scheduled-TRACK gate pass.

## CF32 Context

The live-gNB "native CF32" suspicion remains useful as a mental model, but it
should not be repeated as a blind TX A/B:

- CP1369 already ran live gNB TX CF32 at the older `5.76 Msps` class and still
  failed the raw gate: mean TRACK SNR `-21.932 dB`, `0/96 >= -10 dB`, zero
  TRACK PBCH hits.
- CP1388 repeated live gNB TX CF32 at the current CP1373
  `7.68 Msps`/default-BW class and still failed: mean TRACK SNR `-22.281 dB`,
  `0/75 >= -10 dB`, zero TRACK PBCH hits.

CP1392 therefore leaves TX on the default path:

- OCUDU TX format: `CS16`
- `M2SDR_SOAPY_TX_CS16_TO_SC12=1`
- `TX_BACKOFF=3`

The new CF32 material in this checkpoint is receive-side diagnostic capture:
the gNB process appends RX channel-buffer samples to a bounded CF32 file.

## Caveats And Regressions

The main caveat remains the RX readback marker gap. CP1392's `cp1392_env.txt`
proves the gNB process had:

- `PAVONIS_SOAPY_RX_FORCE_CENTER_HZ=1839650000`
- `PAVONIS_SOAPY_RX_DUMP=1`
- `PAVONIS_SOAPY_RX_APPEND_CF32_PATH=/tmp/pavonis_soapy_rx_append_p0.cf32`
- the rebuilt binary containing the RX force/readback/append marker strings

The RX manifest and append CF32 file prove the dump/append path ran. However,
the actual `gnb.log` grep counts are still:

- `RX_FORCE_LINE_COUNT=0`
- `RX_DUMP_ACTIVE_LINE_COUNT=0`
- `RX_DUMP_READBACK_LINE_COUNT=0`
- `RX_RECEIVE_LINE_COUNT=0`

So CP1392 does not prove through `gnb.log` that RX was read back at the forced
SSB center. It does prove that relying on logger-side RX readback markers is
not sufficient. The next instrumentation should write an RX setup/readback
sidecar or manifest header from the same dump path, rather than depending on
`logger.info()` appearing in the gNB log.

The result is not a regression in TX: same-run digital TX is clean and decodes
PBCH pre/post DMA. The regression is in the diagnostic expectation from CP1391:
binary marker presence did not translate into runtime marker lines.

## Verdict

CP1392 does not raise the active raw scheduled-TRACK gate and does not move up
the ladder.

It shows:

- the live gNB digital TX path remains decodable pre/post DMA;
- the gNB-owned LiteX RX append path can capture a full 250 ms CF32 stream
  without opening a second Soapy device;
- that same-process RX append stream still has no PBCH CRC OK and only weak
  CSI PCI1 evidence around `-24.1 dB`;
- the CP1391 logger-based RX readback markers still do not appear in
  `gnb.log`, despite the env, binary markers, manifest, and append output.

The next branch should not repeat TX CF32. It should harden RX readback into a
sidecar/manifest proof, then either:

- rerun this gNB-owned RX append once readback is provable, or
- switch to a LiteX-only TX/RX OTA baseline to isolate whether LiteX RX is
  broadly weak/deaf independently of live gNB scheduling.
