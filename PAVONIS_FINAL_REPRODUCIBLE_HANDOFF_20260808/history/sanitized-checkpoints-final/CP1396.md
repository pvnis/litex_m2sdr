# CP1396 Live gNB RX Append Sidecar With TX-CF32 Env Attempt

Date: [date-redacted]

## Purpose

CP1395 showed that standalone LiteX file TX/RX can decode the CP1394
full-geometry source strongly when TX is carrier-centered and RX is
SSB-centered. CP1396 tests the next narrow suspicion: if the live gNB TX path
is asked to use the already-built OCUDU Soapy TX CF32 path, does the
gNB-owned RX append level/decode improve relative to CP1394?

This is still a [host-redacted]-only gNB-owned RX diagnostic. It does not use srsUE,
bladeRF, Android, PRACH, NAS, or `ue_sync_nr.c` sync/anchor edits.

## Important Caveat

The CP1396 start wrapper exported `OCUDU_SOAPY_TX_FORMAT=cf32`, and the remote
gNB binary contains the CF32 support strings including
`OCUDU_SOAPY_TX_FORMAT_CF32 enabled`. However, the retained runtime logs did
not include a live `OCUDU_SOAPY_TX_FORMAT_CF32 enabled` or `tx_format=CF32`
line, and a post-run grep of the referenced [host-redacted] `gnb.log` also found no such
line.

So CP1396 should be treated as a TX-CF32 environment attempt plus RX-append
measurement, not as a cleaner runtime-CF32 proof than CP1388. CP1388 remains
the live srsUE raw-gate run that confirmed active CF32 in logs and still
failed the raw gate.

## Conclusion

CP1396 did not reproduce CP1395's strong standalone LiteX RX baseline in the
live gNB-owned append path. Even with the TX-CF32 env attempt, RX append level
stayed essentially at CP1394's weak value and still decoded no PBCH/CSI PCI1.

Because the retained logs did not print the live CF32 activation marker,
CP1396 is not a perfect standalone closure of "live TX-CF32 sidecar append."
But it is enough to say that merely exporting the CF32 TX env into this live
append harness did not raise the gNB-owned RX append level. The raw live
scheduled-TRACK gate remains locked. Further work should instrument or change
the live gNB runtime TX/RX level/path more directly, for example by packaging
the actual `gnb.log`/TX-format marker in the sidecar run or adding a TX-format
sidecar, rather than repeating the same append capture or returning to
`ue_sync_nr.c` scheduler edits.
