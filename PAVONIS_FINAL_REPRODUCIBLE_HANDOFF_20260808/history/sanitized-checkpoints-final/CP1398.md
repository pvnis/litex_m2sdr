## Purpose

CP1398 closes the remaining CP1396 ambiguity. CP1396 exported
`OCUDU_SOAPY_TX_FORMAT=cf32`, but retained runtime logs did not prove the live
TX stream actually opened as CF32. CP1397 added the default-off TX readback
sidecar. CP1398 reruns the live gNB-owned RX append diagnostic at the CP1373
geometry with both sidecars enabled:

```text
PAVONIS_SOAPY_TX_READBACK_PATH=/tmp/pavonis_soapy_tx_readback.txt
PAVONIS_SOAPY_RX_READBACK_PATH=/tmp/pavonis_soapy_rx_readback.txt
OCUDU_SOAPY_TX_FORMAT=cf32
```

This is not an srsUE scheduled-TRACK rung, PRACH test, Android test, NAS test,
or `ue_sync_nr.c` sync/anchor edit. It is a live gNB/M2SDR runtime path proof
for TX format, RX readback, append level, and TX guard health.

## Conclusion

CP1398 proves the live gNB TX stream really used the OCUDU Soapy CF32 API path:
`tx_format=CF32`, `tx_cf32_format=1`, and clean TX summaries with
`tx_format=CF32`. It also proves the gNB-owned RX append stream was at the
intended SSB-centered receive geometry with zero sidecar overflows.

That did not raise the live gNB-owned RX append level. The append RMS is
slightly below CP1394, below CP1396, and still about `25.4 dB` below the
standalone LiteX split-frequency `none` baseline from CP1395. Decode remains
fully negative. Therefore the "maybe live gNB CF32 fixes the conversion or
downsample path" theory is closed for this implementation and geometry unless
the implementation changes materially below the current CF32 API boundary.

The raw live scheduled-TRACK gate remains locked. Next work should target a
real live runtime TX/RX level/path change or path isolation, not another
unchanged CF32/sidecar append repeat and not `ue_sync_nr.c` scheduler edits.
