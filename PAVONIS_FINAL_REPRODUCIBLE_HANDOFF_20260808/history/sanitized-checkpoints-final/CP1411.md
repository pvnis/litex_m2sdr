## Regression

Unlike CP1409, the same-run TX guard did not pass post-DMA/digital PBCH:

- CP1411 TX analysis: `2/14` PBCH CRC OK cases.
- `PRE_DMA_PBCH_OK=1`
- `POST_DMA_PBCH_OK=0`
- `DIGITAL_TX_PBCH_OK=0`
- CP1411 post-DMA ch0 still had normal-looking magnitude
  (`RMS 0.157394` at scale2048, `0.009837` at scale32768), but CSI SNR was
  `-32.5 dB` and PBCH CRC was KO.
- CP1409 immediately before CP1410/CP1411 had `6/14` PBCH CRC OK cases with
  `POST_DMA_PBCH_OK=1` and `DIGITAL_TX_PBCH_OK=1`.
- DMA capture metadata itself looked normal in both runs: `1024` buffers,
  `8192` byte writes, no short logical payload, and the same header/flag
  pattern.

Therefore CP1411 is a good proof that the state dump is mechanically feasible
and that the weak RX append persists, but it is not a clean TX-health baseline.
The post-DMA regression needs a control run before treating the active state
dump as fully non-perturbative.

## Conclusion

CP1411 keeps the raw live RX gate locked: the gNB-owned LiteX RX append remains
around `0.00020 RMS` and decodes `0/198` targeted, `0/847` sweep. The new
in-process state dump captured useful live AD9361/LiteX state and rules out
several simple live-state mistakes: active TX is `CF32`, final TX/RX LO/rate/BW
readbacks match the intended geometry, TX attenuation is `20 dB`, RX gain is
high, and release/write accounting is clean.

The new issue is the CP1411 post-DMA TX guard regression. Next checkpoint
should rerun the CP1409 live path on the CP1410 module with
`M2SDR_SOAPY_STATE_DUMP_PATH` disabled. If post-DMA PBCH recovers, the active
state dump itself is likely perturbative enough to avoid during future RF
baseline runs. If it stays KO, the regression is either from the CP1410 module
change/default-off code, current hardware state, or nondeterminism in the live
lower path.
