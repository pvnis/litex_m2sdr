dual-sidecar TX-CF32/RX-append path on the current CP1410 LiteX Soapy module,

## Comparison With CP1411

CP1411 enabled active in-process state dumping and produced:

- RX append still weak: RMS `0.0002007299`, targeted `0/198`, sweep `0/847`.
- State dump captured four useful `setupStream`/`activateStream` blocks.
- TX guard regressed: `POST_DMA_PBCH_OK=0`, `DIGITAL_TX_PBCH_OK=0`.

CP1412 disabled only `M2SDR_SOAPY_STATE_DUMP_PATH` while keeping the current
CP1410 module and the same CP1409 live path:

- RX append still weak: RMS `0.0001867307`, targeted `0/198`, sweep `0/847`.
- TX guard recovered: `POST_DMA_PBCH_OK=1`, `DIGITAL_TX_PBCH_OK=1`.

This separates the regression from the default-off CP1410 module code. The
best current interpretation is that the active CP1411 state dump is
perturbative enough to disturb the TX DMA/post-DMA guard, even though the
release/write counters stay clean and the dump is mechanically useful.

## Conclusion

The raw live RX gate remains locked; disabling the state dump does not raise
the gNB-owned LiteX RX append level. CP1412 confirms the CP1410 module with
state dumping default-off still behaves like the CP1409 path for TX health and
weak RX append.

Use CP1411's captured state as diagnostic evidence, but do not enable
`M2SDR_SOAPY_STATE_DUMP_PATH` during future baseline RF runs unless the goal is
explicitly to inspect state and accept possible TX perturbation. Further live
ladder work should treat the state dump as a diagnostic-only probe and keep
raw downlink/RX level as the gate.
