# Checkpoint 1416: gNB-Owned readStream RX Append Arm-File Control With No srsUE

Date: [date-redacted] Europe/Zurich

## Goal

Reproduce CP1414's positive gNB-owned LiteX RX readStream append class using
the CP1415 arm-file mechanism, but without starting srsUE or any bladeRF
receive path. This was intended to isolate whether CP1415's gNB-owned RX
regression was caused by concurrent srsUE/bladeRF activity or by the gNB-owned
LiteX RX state/arm path itself.

This checkpoint also records the current native-CF32 answer:

- Live gNB can already open Soapy TX as `CF32` with
  `OCUDU_SOAPY_TX_FORMAT=cf32`.
- That is not float-native end to end. OCUDU baseband buffers are still
  `ci16_t`, and the LiteX/AD9361/DMA stream is still integer IQ below the
  Soapy API boundary.
- CP1405 and CP1406 already dumped the live C++ `ci16_t` to `CF32` buffer
  handed to Soapy `writeStream()` and found it strong and near-identical to
  the same-run pre-DMA reference.
- CP1416 therefore does not reopen the TX conversion/chunking theory. Its new
  fault line is the gNB-owned LiteX RX gain/readback state.

## Comparison To CP1414 And CP1415

- CP1414: same live gNB-owned readStream append decoded PBCH
  (`64/198` targeted, `87/847` aligned sweep), with RX gain readback `67` and
  clean TX guard.
- CP1415: same-window srsUE/bladeRF raw run failed the raw gate
  (`92` TRACK opportunities, mean `-22.201587 dB`, `0/92 >= -10 dB`, zero
  PBCH hits), and the companion gNB-owned append also failed (`0/50`,
  `0/847`) with RX gain readback `44`.
- CP1416: no srsUE and no bladeRF receive path were active, yet the
  gNB-owned append still failed (`0/30`, `0/847`) with RX gain readback `42`.

CP1416 rules out concurrent srsUE/bladeRF receive activity as the immediate
cause of the gNB-owned LiteX RX append regression. The regression is already
present in the gNB-owned arm-file/no-srsUE path.

## Interpretation

CP1416 is mechanically successful but diagnostically negative. It does not
unlock the ladder.

The key new result is that CP1415's low-gain/no-decode gNB-owned append class
reproduces without srsUE. The next issue to isolate is the gNB-owned LiteX RX
gain/gain-control/readback state, not the bladeRF path and not the live TX
CF32 conversion boundary.

The TX side remains live `CF32`, and CP1405/CP1406 already showed the
write-boundary CF32 buffer is strong and near-identical to the pre-DMA
reference. Making the gNB "more native CF32" at the current boundary is
therefore unlikely to raise the raw scheduled-TRACK gate unless the
implementation changes materially below the current Soapy/writeStream boundary.

## Next Step

Before another concurrent bladeRF isolation run, force or verify the
gNB-owned LiteX RX gain/gain-control/readback state back to the CP1414
`66-67 dB` class, then rerun the no-srsUE readStream append control. Only after
that baseline is stable should the same-window srsUE/bladeRF isolation be
repeated.
