## Interpretation

CP1418 is a successful diagnostic checkpoint but a failed RX-baseline
recovery. It rules out "the forced-gain env did not reach runtime" and shows
that the current OCUDU forced-gain patch only changes the requested gain value;
it does not force the LiteX/AD9361 RX path into manual gain mode by the time
the sidecar is written.

This also refines the user's live-CF32 suspicion. The live gNB can already
emit `CF32` at the OCUDU Soapy TX boundary when `OCUDU_SOAPY_TX_FORMAT=cf32`
is set, and CP1405/CP1406 showed the CI16-to-CF32 buffer handed to
`writeStream()` is high-level and near-identical to pre-DMA. That does not make
the whole path float-native to the antenna: OCUDU baseband remains `ci16_t`,
and the LiteX/AD9361/DMA path remains integer below Soapy. But the current
evidence does not support the Soapy-boundary CF32 conversion/chunking as the
SNR-breaking point.

The immediate next step is no-RF: add an explicit Soapy RX gain-mode setter in
OCUDU and, when `PAVONIS_SOAPY_RX_FORCE_GAIN_DB` is active, call
`setGainMode(SOAPY_SDR_RX, channel, false)` before setting the gain, then log
immediate post-set gain and gain-mode readback. Only after a [host-redacted] build-smoke
passes should the no-srsUE RF append control be repeated.

Do not rerun CP1418 unchanged. Do not treat CP1418 as a clean TX baseline
because the same-run post-DMA/digital TX guard regressed.
