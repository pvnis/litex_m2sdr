## Interpretation

CP1420 is a successful diagnostic and a failed RX-state recovery.

It proves the CP1419 binary was deployed and that the forced-gain environment
reached the live run, but it does not recover manual RX gain mode. The final
gNB-owned LiteX RX readback remains automatic gain (`gain_mode_auto=1`) and
low gain (`41 dB`), and the readStream append remains undecodable.

TX is not the limiting variable in this checkpoint: live TX is `CF32`, pre-DMA
and post-DMA PBCH decode pass, and the Soapy/LiteX TX counters are clean. This
also weakens the current "live CF32 conversion/chunking breaks SNR" theory for
this branch; the checkpoint failure is on RX gain/mode state.

The strongest code-level explanation found after the run is in the LiteX Soapy
stream setup path. OCUDU applies RX gain before `setupStream()`, but
`LiteXM2SDRStreaming.cpp::setupStream()` calls `ad9361_set_no_ch_mode()`
after that and then reapplies rate, bandwidth, frequency, and TX attenuation
only. It does not reapply RX gain mode or RX gain. Since `getGainMode()` reads
the AD9361 driver's `phy->agc_mode[ch]`, CP1420's final `gain_mode_auto=1`
means the lower driver state still thinks it is in AGC by the time RX append
readback runs.

## Next

Do not rerun CP1420 unchanged. The next checkpoint should be no-RF: patch the
post-`setupStream()` path to reassert forced RX manual gain mode and gain after
the final AD9361 channel-mode setup. The least invasive option is in OCUDU:
after `device.setup_stream(SOAPY_SDR_RX, ...)` succeeds, call the same forced
`set_rx_gain_unprotected()` path again for the stream's RX ports and log a
post-setup readback marker. Then build-smoke on [host-redacted] and rerun this same
no-srsUE RF control.
