## Goal

Build-smoke the CP1420 follow-up without RF. CP1420 showed that forcing manual
RX gain before the Soapy stream setup was not enough: final readback stayed
`gain_db=41`, `gain_mode_auto=1`, and the readStream append decoded no PBCH.

The hypothesis for this checkpoint was that the LiteX Soapy `setupStream()`
path resets or overwrites the AD9361 RX gain mode after OCUDU's first gain set.
The patch therefore reasserts the same forced manual RX gain path after
`device.setup_stream(SOAPY_SDR_RX, ...)` returns.

## Change

When `PAVONIS_SOAPY_RX_FORCE_GAIN_DB` is finite, OCUDU now logs:

```text
PAVONIS_SOAPY_RX_FORCE_GAIN_DB post-setup reassert active: stream={} channels={}
```

It then maps each RX stream channel back to its configured RX port and calls
`set_rx_gain_unprotected()` again. The change is default-off and only runs in
the forced-gain diagnostic path.

## Interpretation

CP1421 is a successful implementation and deployment checkpoint. It does not
prove the live RX path is recovered because no RF was run. It only proves the
next RF control can test the intended thing: whether post-`setupStream()` forced
manual gain reassertion makes the final live RX sidecar read
`gain_mode_auto=0` and CP1414-class `66-67 dB` gain again.

This checkpoint also preserves the current CF32 interpretation: live gNB TX can
already be asked to write CF32 at the Soapy boundary, but this is not a
float-native end-to-end hardware path. Previous CP1405/CP1406 write-boundary
dumps showed the live CI16-to-CF32 conversion handed to Soapy is strong and
near-identical to the pre-DMA reference, so the active failure being tested here
is RX gain/mode state, not TX CF32 conversion.
