# Checkpoint 1423: CP1414 vs CP1422 RX Append Diff, No RF

Date: [date-redacted] Europe/Zurich

## Goal

Compare the last known decodable live gNB-owned LiteX RX append, CP1414,
against CP1422, which restored post-`setupStream()` manual RX gain but still
failed append decode. This checkpoint is local/no-RF: no gNB transmit window,
no bladeRF/srsUE receive, no Android/NAS, and no `ue_sync_nr.c` sync/anchor
edits.

This also answers the renewed "native CF32" suspicion:

- Live gNB can already request Soapy TX `CF32` with
  `OCUDU_SOAPY_TX_FORMAT=cf32` or `OCUDU_SOAPY_TX_CF32=1`.
- That path is not float-native end to end. OCUDU still carries `ci16_t`
  baseband buffers and converts chunks to `cf_t` at the Soapy `writeStream()`
  boundary; the LiteX/AD9361/DMA hardware path remains an integer-IQ radio
  path.
- The current CP1414/CP1422 split is not explained by TX CF32. Both sides are
  live `CF32` at the Soapy TX boundary and both have healthy same-run TX
  guards.

The gNB binary differs:

- CP1414 gNB hash: `ce2bc59fb4be0f4d268912fa3688d49007b66b7e7d980cda640cce9487d6f8d8`
- CP1422 gNB hash: `90c5cc41452f91777d9d484f80d6ca70fe1f1e149a3e1d98569e9f215b79ec8f`
- The Soapy module hash is the same class in both reports:
  `6fc1ff4c20f9cdf2b69f10bf9c6ff2bfc53fe4ea6e7b5bf283566654383e9abf`
  for CP1414 and CP1422.

The RX append control differs:

- CP1414 is the CP1400-style immediate readStream append:
  `OCUDU_SOAPY_RX_USE_READSTREAM=1`, no
  `PAVONIS_SOAPY_RX_FORCE_GAIN_DB`, no arm file, no
  `PAVONIS_SOAPY_RX_ARM_POLL_PERIOD`.
- CP1422 is the CP1420/CP1416-style armed append:
  `OCUDU_SOAPY_RX_USE_READSTREAM=1`,
  `PAVONIS_SOAPY_RX_FORCE_GAIN_DB=67`,
  `PAVONIS_SOAPY_RX_DUMP_ARM_FILE=/tmp/cp1420_pavonis_soapy_rx_append.arm`,
  and `PAVONIS_SOAPY_RX_ARM_POLL_PERIOD=1`.

The RX sidecar schema and gain state differ:

- CP1414 old binary sidecar reports `gain=67`, `loops=2`, `overflows=0`, but
  has no `gain_mode_auto` fields.
- CP1422 new binary sidecar reports `gain_db=67`,
  `gain_mode_ok=1`, `gain_mode_auto=0`, `overflows=0`, proving the CP1421
  post-setup manual-gain reassertion did what it was meant to do.

The append content/decode differs sharply:

- CP1414 append sha256
  `1e71a2afb9039c1963d7e69ef1cab949d76cc2a6a4abbff4cd4b8ec4c8eef99b`
- CP1414 RMS `0.0002950823`, RMS dBFS `-70.6011`, peak `0.0033570`,
  zero fraction `0.350016`
- CP1414 decode: targeted `64/198` PBCH CRC OK PCI1, aligned sweep
  `87/847` PBCH CRC OK PCI1
- CP1422 append sha256
  `1f62a4b1ef1960a8dc0e4b17e5a551c0577b348aaf49d699825eb1031efbedc7`
- CP1422 RMS `0.0007178347`, RMS dBFS `-62.8795`, peak `0.0033888`,
  zero fraction `0.0000396`
- CP1422 decode: targeted `0/30` PBCH CRC OK PCI1, aligned sweep
  `0/847` PBCH CRC OK PCI1

Higher RMS and fewer zero samples in CP1422 therefore do not imply a better
SSB/PBCH capture. The failure is not a simple sample-level amplitude shortage
inside the gNB-owned append file.

## Interpretation

CP1423 narrows the branch:

- The low/auto RX gain regression is closed by CP1422: final state is manual
  gain mode at `67 dB`.
- Manual `67 dB` is necessary but not sufficient to recover the CP1414-class
  decodable append.
- The shared config, prequiet sequence, RX/TX geometry, live TX `CF32`, and
  healthy TX guards weaken TX-format/conversion/downsampling as the immediate
  explanation.
- The strongest next variable is the receive-control/capture timing path:
  CP1414's immediate CP1400-style readStream append versus CP1422's delayed
  arm-file append plus new gain instrumentation.

Do not rerun live TX CF32 unchanged as a raw-gate fix. The code already has
the Soapy-boundary CF32 mode, and the live A/B branch CP1369/CP1388 plus the
write-boundary sidecar branch do not support it as the current SNR killer.

## Next

Run a minimal CP1414-style control on the current CP1421/CP1422 binary:

- state dump disabled,
- live TX still `CF32`,
- `OCUDU_SOAPY_RX_USE_READSTREAM=1`,
- immediate CP1400-style append, no arm file,
- first without the forced-gain wrapper if matching CP1414 is the priority,
  or as a second variant with immediate forced gain if the no-force run
  regresses gain state.

This tests whether the arm-file/delayed append path is the non-gain difference
that broke the gNB-owned LiteX RX baseline. Only after the immediate append is
recovered or definitively fails should the ladder move back to concurrent
bladeRF/srsUE isolation.
