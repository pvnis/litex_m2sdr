## Interpretation

CP1424 is a clean recovery of the CP1414 gNB-owned LiteX RX baseline on the
current CP1421/CP1422 binary.

It proves the CP1422 failure is not caused by:

- the current `90c5...` gNB binary itself,
- live TX `CF32`,
- the OCUDU CI16-to-CF32 TX write-boundary conversion,
- lack of final manual `67 dB` gain state,
- broad current LiteX TX/RX failure.

The key discriminator is now the capture-control path. CP1424 uses immediate
CP1400-style readStream append and decodes (`76/198`, `109/847`) even with
`gain_mode_auto=1` and `gain_db=66`. CP1422 uses the delayed arm-file append
path and fails (`0/30`, `0/847`) even with `gain_mode_auto=0` and
`gain_db=67`.

Therefore the delayed arm-file/control path, not native-CF32 or simple RX gain
mode, is the current bad variable for gNB-owned LiteX RX append diagnostics.

This still does not unlock the original srsUE/bladeRF scheduled TRACK gate:
CP1424 did not run srsUE/bladeRF and produced no `event=track_opportunity`
metric. It restores a trustworthy LiteX baseline for the next isolation step.
