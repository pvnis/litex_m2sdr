# Checkpoint 1426: No-srsUE CP1425 Immediate Helper RX Append Control

Date: [date-redacted] Europe/Zurich

## Goal

Isolate CP1425's companion LiteX RX append regression by running the exact
CP1425 immediate gNB-owned `readStream()` RX append helper and append sizing,
but without starting srsUE, bladeRF, or any NRSA raw TRACK command.

This checkpoint also addresses the live-gNB native-CF32 concern:

- The live gNB already opens Soapy TX as `CF32` when
  `OCUDU_SOAPY_TX_FORMAT=cf32` is set.
- The current implementation is not float-native end to end. OCUDU still
  presents `ci16_t` chunks to `radio_soapy_tx_stream`, which converts to
  `cf_t` immediately before Soapy `writeStream()`.
- CP1405, CP1406, CP1425, and this CP1426 keep the same conclusion: the
  Soapy/writeStream CF32 boundary and TX waveform are not the current raw-SNR
  limiter.

## Interpretation

CP1426 is mechanically clean and diagnostically negative.

It rules out concurrent [host-redacted]/bladeRF/srsUE activity as the immediate cause
of CP1425's companion LiteX append regression. The failing class reproduces
with [host-redacted]-only gNB ownership when using the CP1425 helper and its larger
immediate append sizing/window.

The most useful next discriminator is no longer "same CP1425 but without
srsUE"; that has now been tested. The next rung should compare the CP1424
working immediate append mechanics against CP1425/CP1426 by holding everything
else fixed and changing the capture sizing/timing back toward the CP1424
`0.25 s` append class. Only after the [host-redacted]-owned append is again PBCH-decodable
should the same-window NRSA raw TRACK gate be repeated.
