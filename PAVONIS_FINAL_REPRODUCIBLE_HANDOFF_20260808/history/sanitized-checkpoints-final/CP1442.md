# Checkpoint 1442 - Live-Geometry LiteX Tone To bladeRF Gain Sweep

Date: [date-redacted] Europe/Zurich

## Goal

Run a software-only controlled-tone discriminator after CP1441. The test keeps
the live downlink RF geometry but removes gNB scheduling, PBCH content, srsUE,
Android, NAS, and `ue_sync_nr.c` sync/anchor logic.

The question is whether the M2SDR can emit a simple tone that the bladeRF RX
path captures strongly and stably at the same center/frequency class that just
failed PBCH. If the tone is strong and stable while PBCH is not, the problem is
more protocol/waveform specific. If the tone has level but weak/unstable
coherence, the external bladeRF/OTA receive path remains the leading branch.

## Interpretation

CP1442 confirms that the live-geometry M2SDR TX to bladeRF RX path can move a
controlled tone to the expected RF location, and that bladeRF gain commands
produce a large raw-level response. It does not show a clean, stable receive
path: the tone remains weak by the CP847 threshold and unstable in 10 ms CP892
windows at all tested gains.

This is consistent with CP1023/CP1024's older "level without stable long-window
coherence" result and with CP1441's gain48 observation: raising bladeRF gain
raises total raw level, but does not recover coherent PBCH or stable tone
quality. The leading branch remains external bladeRF/OTA receive path,
coupling/routing state, or bladeRF receive-state/noise behavior rather than
live gNB TX content, native CF32, or srsUE acquisition alone.

## Next Step

Do not rerun CP1442 unchanged. The next best discriminator is physical path or
coupling inspection/control swap. If staying software-only, vary only one
receiver-side parameter from CP1442, such as bladeRF bandwidth/filter or RX
channel/path, using the same live-geometry tone and requiring both raw level
and 10 ms tone stability to improve before returning to scheduled TRACK.
