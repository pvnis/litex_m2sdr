samples, retuning, calibrating, toggling bias tees, poking registers, restoring

receive-frontier state fault that could explain the no-TX-like external

## Range Semantics

CP1463's CLI help text suggested `num_addresses` was an additional-address
count. The actual CP1465 output behaved like a total-address count: for
example, `peek rfic 0x013 0x004` emitted `0x013` through `0x016`, not
`0x013` through `0x017`.

To avoid rerunning the whole read, CP1465 ran a supplemental read of only the
intended final addresses:

`0x017`, `0x036`, `0x04e`, `0x055`, `0x10e`, `0x12a`, `0x15d`, `0x163`,
`0x181`, `0x194`, `0x1a5`, `0x1ae`, `0x1fc`, `0x251`, `0x2b9`, `0x3f6`.

Future `peek rfic` range harnesses should either use explicit single-address
reads for important endpoints or treat the third argument as the total count
for this installed CLI.

## Conclusion

Status: read-only diagnostic complete, no ladder unlock.

CP1465 found no clear idle bladeRF/AD9361 register state fault that explains
the external bladeRF no-TX-like receive behavior. It weakens the specific
theories of a latched BIST/test mode, obvious RX overrange latch, invalid ENSM
state, RX VCO unlock, asymmetric RX1/RX2 gain readback, or gross RX ADC/LO
power-down override in the idle state.

It does not prove the active receive chain is healthy under a live capture, and
it does not improve the raw scheduled-TRACK metric. CP1425/CP1431 and the
later same-window self-RX checks already cover the user's proposed
self-RX-versus-bladeRF discriminator: M2SDR self-RX decodes in the same
window while bladeRF/srsUE or independent bladeRF remains weak or PBCH-negative.

The frontier remains external bladeRF/OTA receive path, physical coupling, or
a bounded explicitly approved hardware-affecting branch such as calibration/
correction or bias-tee testing. Do not rerun CP1425-CP1465 unchanged.
