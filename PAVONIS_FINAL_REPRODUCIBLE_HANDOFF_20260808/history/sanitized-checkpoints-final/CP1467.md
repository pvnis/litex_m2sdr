# CP1467 - bladeRF Active-RX In-Process RFIC Readback

Date: [date-redacted] Europe/Zurich

## Goal

CP1465 and CP1466 found no clear bladeRF/AD9361 fault in idle or configured
RX-only state. CP1467 checks the next safe rung: read key AD9361/RFIC state
from inside the same process while the bladeRF RX module is enabled and a small
SC16 metadata receive is active.

This checkpoint did not start a transmitter, run srsUE/gNB, edit
`ue_sync_nr.c`, write RFIC registers, run calibration, toggle bias tees, poke
registers, or restore flash. It is not a raw scheduled-TRACK metric checkpoint.

## Conclusion

Status: active-RX in-process readback complete, no ladder unlock.

CP1467 closes the remaining safe read-only/in-process gap after CP1465 and
CP1466. The bladeRF can be opened through the established sudo path, configured
to the CP1437/CP1438 RX-only geometry, have RX enabled, capture a metadata
chunk, and read RFIC/RF-switch state from the same process. Active-state
readback does not show RX power-down, VCO unlock, invalid state, asymmetric
gain readback, or BIST/test mode. It also explains the earlier open RF-routing
prints: the RF switch closes only while RX is enabled.

This does not raise the live scheduled-TRACK link budget, and it does not
change the CP1425/CP1431/CP1433/CP1434 conclusion that live TX/M2SDR self-RX
can be healthy while the bladeRF/OTA receive path remains sub-threshold or
PBCH-negative. The frontier remains the external bladeRF/OTA receive path,
physical coupling/routing, or an explicitly approved bounded
hardware-affecting branch such as calibration/correction or bias-tee testing.
Do not rerun CP1425-CP1467 unchanged.
