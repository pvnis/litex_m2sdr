# CP1475 - Self-RX Fallback Guard

Date: [date-redacted] Europe/Zurich

## Goal

CP1475 turns the latest self-RX thought into a guarded fallback rule without
starting RF or changing hardware state. The question was whether, if the
self-RX instrument keeps fighting back, we should stabilize its
deinterleave/scaling/control path enough for one same-window capture while
srsUE/bladeRF runs concurrently.

The answer encoded here is: yes, but only as a materially changed diagnostic
path. Unchanged same-window repeats are refused because CP1425, CP1433,
CP1434, CP1440, and CP1441 already cover the key pattern.

This checkpoint did not start a transmitter, receive RF samples, run gNB,
srsUE, bladeRF capture, retune, set bladeRF state, calibrate, toggle bias tees,
poke registers, restore flash, edit `ue_sync_nr.c`, or move to
Android/NAS/PRACH.
