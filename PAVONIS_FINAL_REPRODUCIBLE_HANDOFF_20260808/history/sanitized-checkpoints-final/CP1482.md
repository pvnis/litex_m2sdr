## Comparison to CP1481

CP1481 live gNB used the same payload source family and same receive geometry,
with clean host-visible TX and PBCH-decodable pre/post-DMA material, but RF was
decoder-negative:

```text
CP1481 live: RMS=-30.16 dBFS, max=265, PBCH KO, CSI SNR=-25.2 dB
CP1481 sweep: 0/847 PBCH CRC OK, 10/847 CSI PCI1
CP1481 same-window pre-DMA refcorr: 0.097629795 at +[date-redacted] Hz
```

CP1482 replayed that CP1481 live pre-DMA payload through the continuous helper
and made the same RF path decode:

```text
CP1482 helper replay: RMS=-27.72 dBFS, max=522, PBCH OK, CSI SNR=+6.1 dB
CP1482 sweep: 317/847 PBCH CRC OK, 333/847 CSI PCI1
CP1482 same-window pre-DMA refcorr: 0.6641383298984551 at +2500 Hz
```

This is the decisive split requested after CP1481: CP1481's content is valid
and the current LiteX-to-bladeRF RF path can carry it at decode quality when
the continuous helper presents it. The live gNB failure is therefore below the
host-visible pre-DMA dump and is tied to live real-time TX presentation/cadence
or a live-only lower-device path, not to weak RF path/power, payload content,
or bladeRF capture mechanics.

## Verdict

CP1482 passes. It validates CP1481's live pre-DMA payload and the current
LiteX-to-bladeRF RF receive path when the CP1166 continuous helper is used.
The CP1481 live gNB RF failure is isolated to live real-time TX
presentation/cadence below the host-visible pre-DMA dump, or to a live-only
lower-device behavior that the continuous helper does not reproduce.

This does not unlock NRSA, PRACH, Android, NAS, or scheduler/sync-anchor edits.
The next checkpoint should stay software-only and split continuous helper
presentation from live timed/gapped presentation. The most direct next variable
is a timed/gapped replay of CP1481's actual pre-DMA/DMA metadata at the same RF
geometry; if that fails like live, the timed/discontinuous presentation itself
is implicated, and if it passes, the live runtime path differs below the dumped
metadata.
