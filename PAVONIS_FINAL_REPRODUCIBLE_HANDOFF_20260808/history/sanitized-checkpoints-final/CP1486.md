captures against the adjacent CP1482/CP1483 good controls. The question was
whether CP1484 is mostly a wrong frame phase/window placement issue, or whether

Key cluster observations:

- `CP1482_CONT` is PBCH-dense across almost the whole first 250 ms sweep.
  This is the current same-payload good-control class.
- `CP1483_EXACT` is less dense but still broadly recoverable, with many
  PBCH clusters and `270/847` CSI.
- `CP1483_PACED75` is sparser but still has strong local PBCH islands,
  including `+11.30 dB` max PBCH SNR.
- `CP1484_HELPER` has `269/847` CSI, essentially the same CSI count as
  `CP1483_EXACT`, but PBCH collapses to `34/847` and PBCH SNR mean falls to
  `-18.48 dB`. This is the strongest new split.
- `CP1484_LIVE` has only `59/847` CSI and `9/847` PBCH. It remains worse than
  the helper, but the helper control is already PBCH-coherence degraded.

## Interpretation

CP1486 weakens the idea that CP1484 is mainly a single wrong 20 ms frame phase
or a simple window-placement issue. The CP1484 helper still has abundant CSI
windows (`269/847`), but those windows usually do not carry PBCH coherently
enough to decode. That is different from CP1483 exact metadata, where nearly
the same CSI count (`270/847`) supports much more PBCH (`142/847`) and a much
higher max PBCH SNR.

The CP1484 live leg is still worse than helper, but CP1484 helper already shows
the important failure mode. The current boundary is therefore PBCH-level
coherence/cadence inside CSI-visible windows, not simply raw RF power, declared
SSB offset, static CFO, or one missed frame phase.

The helper refcorr frequency also changes sign in the degraded CP1484 helper
run (`-9000 Hz`) versus the CP1482/CP1483 good controls (`+[date-redacted]` to
`+2500 Hz`). Treat that as a clue for the next offline check, not as a direct
fix by itself, because CP1485 already showed that simple static CFO correction
does not recover the bad windows.

## Verdict

Do not rerun CP1478-CP1486 unchanged. Do not start a hardware branch or edit
sync/anchor logic. The next useful step is still no-RF: compare the CP1482 and
CP1484 continuous-helper runs at the sequence/log/config level and, if needed,
run a time-local reference-correlation scan around PBCH/CSI islands. The goal
is to isolate why the same payload/helper class can be PBCH-dense in CP1482
but CSI-rich/PBCH-poor in CP1484.
