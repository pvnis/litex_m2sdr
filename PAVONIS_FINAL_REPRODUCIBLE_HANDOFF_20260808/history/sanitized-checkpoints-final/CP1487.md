## Goal

Compare the CP1482 continuous-helper good control with the CP1484
continuous-helper degraded control at the log/config level. The question was
whether an obvious run-configuration, payload, helper, TX counter, capture
counter, or capture-start phase difference explains why CP1482 is PBCH-dense
while CP1484 helper is CSI-rich but PBCH-poor.

This checkpoint is local-only. It does not run RF, edit `ue_sync_nr.c`, change
hardware state, or move to NRSA/PRACH/Android/NAS.

## Interpretation

CP1487 does not find a sequence/config/runtime-mechanics difference that
explains the CP1484 helper degradation. The same payload, pre-DMA buffer,
metadata, Soapy module, helper script, TX geometry, capture geometry, TX write
totals, and bladeRF metadata health are reused.

The capture-phase shift explains the refcorr start-position movement between
CP1482 and CP1484. It does not explain the PBCH collapse by itself, because
CP1486 already showed CP1484 helper remains CSI-rich while PBCH-poor.

No overheating clue is visible here: CP1484 bladeRF pre-state temperature is
lower than CP1482 (`30.7 C` vs `31.6 C`), with the same power monitor reading
(`2.66 W`).

## Verdict

Do not rerun CP1478-CP1487 unchanged. Sequence/config mismatch is not the
explanation for CP1482 vs CP1484 continuous-helper divergence. The active
software-only boundary is now time-local PBCH coherence/frequency behavior
inside CSI-visible windows.

Recommended next checkpoint: run time-local refcorr/CFO analysis around
CP1482 and CP1484 PBCH/CSI islands, using the existing captures only. If that
does not isolate the coherence split, the next RF step should be a tightly
controlled helper reproducibility bracket rather than a hardware branch.
