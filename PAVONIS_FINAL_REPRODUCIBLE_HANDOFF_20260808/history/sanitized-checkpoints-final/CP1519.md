start the post-DMA payload/header dump near the bladeRF RF capture interval
instead of at gNB startup. The question was whether the actual capture-window

## Verdict

CP1519 proves the capture-window post-DMA payload/header material is
PBCH-decodable, while the bladeRF RF capture remains only intermittently
coherent/decoder-visible. This keeps the live failure below clean OCUDU writes,
below clean plugin HAS_TIME release, and below host-visible capture-window
post-DMA contents.

The remaining software-only boundary is now lower than "what bytes did the
host write into the DMA ring?" It is likely in effective LitePCIe reader /
TimedTXArbiter / FPGA / AD9361 egress cadence, or in a perturbation caused by
heavy diagnostic dumping. Do not rerun CP1519 unchanged.

Next useful work is a lower-overhead same-hardware continuous-helper versus
live-gNB comparison, or a lower-overhead effective-egress timing/counter
instrument, before considering any hardware branch. Continue to avoid
`ue_sync_nr.c` sync/anchor edits, PRACH/Android/NAS, and hardware-affecting
calibration/bias/route changes.
