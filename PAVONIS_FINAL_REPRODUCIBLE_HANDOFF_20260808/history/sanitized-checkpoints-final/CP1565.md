# Checkpoint 1565 - Force-Continuous Live gNB Stage 6 UE/PRACH Smoke

Date: [date-redacted] Europe/Zurich

## Goal

After CP1564 raised the raw scheduled-TRACK downlink gate by forcing live gNB
TX into helper-like continuous untimed writes, run one diagnostic ladder smoke
with a real srsUE/bladeRF UE and PRACH debug enabled.

This checkpoint is intentionally not an amplitude/RX/EOB sweep. It uses the
CP1564 continuous-TX presentation, verified TX `ATT=5 dB`, and a CP289-style
Stage 6 PRACH debug envelope to see whether the first hard failure moves above
cell selection and total PRACH invisibility.

No `ue_sync_nr.c` sync/anchor logic was edited.

## gNB PRACH Detector Result

The PRACH detector trace contains `6128` lines. The generated JSON counted
`accepted_rows=4`, but those are the TRACE/TOP3/TOP8/SPLIT companion rows for
one detector event, not four independent accepted PRACH events.

The unique accepted TRACE event is:

```text
line=5953
sfn=417
slot=4
best_preamble=42
best_delay=37
best_peak=1.478522718e-01
threshold=1.469999999e-01
best_ratio=1.006
best_pass_thr=1
best_pass_delay=1
accepted=1
p0_seen=1
p0_delay=41
p0_peak=4.234404862e-02
p0_ratio=0.288
p0_pass_thr=0
```

This is important: the UE transmitted preamble `0`, but the only accepted
detector event is `best_preamble=42`. Preamble `0` was visible in that window
but below threshold. The normal gNB log has no Msg1/RAR/Random Access log
evidence.

Therefore CP1565 is not a clean Msg1 or RAR success. It is a diagnostic
ladder movement from "cell/PRACH invisible" to "cell selected, UE transmitted
PRACH, and the gNB detector accepted one non-p0 candidate."

## Conclusion

CP1565 keeps CP1564's force-continuous live gNB TX baseline valid during a full
UE/PRACH smoke. It shows real higher-ladder movement:

- downlink cell search and SFN/cell selection succeed;
- the UE emits five PRACH preamble-0 bursts with clean bladeRF TX metadata;
- the gNB detector reaches one accepted PRACH-threshold event.

The new first hard failure is not raw downlink acquisition and not total PRACH
TX invisibility. It is the mismatch between the UE's transmitted preamble `0`
and the gNB detector's only accepted candidate `42`, plus the absence of normal
Msg1/RAR log evidence.

Do not rerun CP1565 unchanged. Next work should stay on the continuous-TX
baseline and analyze CP1565's PRACH timing/preamble mapping offline, then
instrument the detector-to-MAC/RAR path only enough to prove whether the
accepted candidate is a false positive, a timing/preamble-index mapping issue,
or a real detection that is discarded above the detector.
