# CP1572 Standalone M2SDR Full-Duplex TX-Active bladeRF Uplink Tone Report

Date: [date-redacted] Europe/Zurich

## Goal

CP1571 proved the current standalone bladeRF TX1 to LiteX/M2SDR raw RX uplink tone path is grossly alive. CP1570 still showed that a live gNB-owned M2SDR RX append did not see the same class of tone. CP1572 tested the next discriminator: whether standalone M2SDR RX still sees the bladeRF uplink tone while the same standalone M2SDR process also has TX active at the downlink center.

This is not a PRACH threshold experiment. It isolates TX-active/full-duplex M2SDR state from the live gNB stack.

## Interpretation

CP1572 is not a clean full-duplex RF pass/fail because the standalone M2SDR TX worker failed after repeated `writeStream()` errors and the RX capture only lasted `27 ms`. However, it is still a useful changed checkpoint:

```text
standalone raw RX alone sees the bladeRF uplink tone strongly (CP1571);
standalone M2SDR TX-active/full-duplex state failed early and produced a CP1570-like no-tone floor capture (CP1572).
```

This shifts the branch away from a dead physical bladeRF-to-M2SDR path and toward M2SDR full-duplex/TX-active control state or TX worker/write-path interaction. It also introduces a current regression against historical CP500, where standalone CS16 full-duplex with a modest nonzero downlink-frequency tone completed cleanly and received the external signal.

Do not rerun CP1572 unchanged. The next clean discriminator should be a CP1572-adjacent zero-TX full-duplex control using the same bladeRF uplink tone:

```text
M2SDR TX/RX streams active, TX mode zero, same RX center/gain/BW, same bladeRF tone.
```

If zero-TX full-duplex sees the tone, the nonzero TX worker/path is the immediate suspect. If zero-TX also misses or the TX worker still fails, the problem is broader full-duplex stream/control state. Do not run threshold-only PRACH or higher ladder work until this is separated.
