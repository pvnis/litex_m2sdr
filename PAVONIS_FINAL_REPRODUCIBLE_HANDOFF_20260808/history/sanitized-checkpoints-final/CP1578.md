# Checkpoint CP1578: Native Continuous TX-Zero-After-Arm gNB RX-Append UL Tone

Date: [date-redacted]

## Goal

CP1578 attempted a software-only discriminator for the live gNB/M2SDR uplink
visibility blocker:

- keep the CP1575 native continuous downlink baseline active
- arm a gNB-owned M2SDR RX append at the uplink center
- transmit the same CP1571 clean bladeRF TX1 `+100 kHz` uplink tone from
  `[host-redacted]`
- ask the LiteX Soapy TX path to zero downlink payloads after the shared arm
  file appears, so the RX append would run under live gNB control but with
  post-arm TX payload suppressed

The intended question was whether the missing uplink tone is caused by nonzero
live downlink TX/full-duplex activity rather than by the gNB-owned RX append
path itself.

## Critical Validity Failure

The intended discriminator required proof that TX payload zeroing actually
activated after the arm file appeared. CP1578 does **not** provide that proof.

Evidence:

```text
TX_READY.env:
M2SDR_SOAPY_TX_ZERO_AFTER_ARM=1
M2SDR_SOAPY_TX_PROBE_ARM_FILE=/tmp/pavonis_rxappend_ul_tone_cp1578_..._arm

summary gnb_log.tx_zero_after_arm_active_count=0
rg "TX_ZERO_AFTER_ARM active" gnb.log -> no matches
```

Therefore CP1578 is a diagnostic/invalid discriminator. It proves the
environment was requested and read back into sidecars, but it does not prove
the LiteX Soapy path actually replaced live TX writes with zero payloads during
the RX append window.

Do not use CP1578's missing tone as evidence that TX payload activity is
irrelevant.

## Interpretation

CP1578 should be retained as an invalid/diagnostic checkpoint:

- CP1578 does not close the live TX-active uplink visibility theory.
- CP1578 does not invalidate CP1577 or CP1576.
- CP1578 does not justify more amplitude/RX/EOB sweeps.
- CP1562's RSRP audit remains negative for a power-only explanation.
- CP1564/CP1575 already answer the downlink continuous-TX question: continuous
  live gNB TX restored scheduled TRACK quality compared with segmented timed
  bursts.

## Next Step

Do not rerun CP1578 unchanged.

If this zero-after-arm discriminator is still useful, the next checkpoint
should first make activation observable and unambiguous: add default-off LiteX
Soapy counters/sidecar fields for zero-after-arm enabled, armed, zeroed write
count, and zeroed sample count, then rerun the same RF discriminator only after
the no-RF/build/string gate proves those counters exist.

For the downlink branch requested by the user, do not repeat CP1564 or CP1575
unchanged. The current evidence already shows:

- CP1562 ATT=5 alone did not raise RSRP or SNR materially.
- CP1564 forced continuous writes restored raw scheduled TRACK.
- CP1575 reproduced that result via native YAML `tx_mode: continuous` with the
  force override disabled.

The active ladder should therefore treat continuous/cadence presentation as the
downlink solution direction and avoid further amplitude/RX/EOB variable tests.
