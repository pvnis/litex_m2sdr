# Checkpoint 1586 - No-RF Live gNB RX Format Audit

Date: [date-redacted]

## Goal

Compare the known-positive standalone uplink-tone RX path from CP1571 with
the live gNB-owned RX append path from CP1577-CP1585, without running RF, to
find a software-path difference that could explain why standalone raw RX sees
the bladeRF `+100 kHz` tone while the live gNB append does not.

## Inputs Reviewed

- CP1571 standalone wrapper:
  `cp1571_run_current_standalone_litex_rx_bladerf_ul_tone_cleancli.sh`
- CP798/CP329 standalone receiver path:
  `cp798_run_bladerf_tx1_100k_to_litex_rxgain50_tone_sudo_baseline.sh`
  and `cp23_nuc4_capture_ul_tone_remote.sh`
- LiteX standalone recorder:
  `litex_m2sdr/litex_m2sdr/software/soapysdr/test_record.py`
- OCUDU Soapy device/RX stream code:
  `ocudu/lib/radio/soapy/radio_soapy_device.h`
  and `ocudu/lib/radio/soapy/radio_soapy_rx_stream.cpp`
- CP1585 native-continuous TX skip-setup+I/O RF result.

## Findings

CP1571's passing standalone receiver uses direct LiteX Soapy RX as CF32:

- `test_record.py` imports `SOAPY_SDR_CF32`.
- It calls `setupStream(SOAPY_SDR_RX, SOAPY_SDR_CF32, [channel])`.
- It records `np.complex64` samples directly.
- CP1571 result: `BLADE_EXIT=0`, `RX_RMS_ALL=4.876705818e-03`,
  peak `97558.59 Hz`, `61.18 dB` over median, and
  `GROSS_TONE_PATH_PASS=1`.

The live gNB/OCUDU path opens RX as CS16 by default:

- `radio_soapy_device::setup_stream()` defaults `format = SOAPY_SDR_CS16`.
- The existing CF32 override logic is TX-only (`OCUDU_SOAPY_TX_FORMAT` /
  `OCUDU_SOAPY_TX_CF32`); there is no matching RX CF32 override.
- CP1585 used `OCUDU_SOAPY_RX_USE_READSTREAM=1`, so it did avoid the old
  direct-buffer append issue, but it still read into OCUDU `ci16_t` buffers.

The live gNB append writes those `ci16_t` buffers as CF32 after dividing by
`32767`:

- `radio_soapy_rx_stream.cpp` appends `channel_buffer[i].real()/32767` and
  `channel_buffer[i].imag()/32767`.
- CP1585 append RMS was `3.791511117e-04`, roughly `22.2 dB` below CP1571's
  standalone RMS. That is in the same class as the known CS16-vs-CF32
  presentation/scaling issue already noted in CP1413.
- CP1585 also had healthy RX readback (`1747500000 Hz`, `11.52 Msps`,
  `10 MHz`, gain `69`) and all TX setup/I/O bypass gates proven, so this is
  not another TX power, RX gain, or EOB variable.

## Interpretation

The strongest new software hypothesis is an RX sample-format/scaling
presentation mismatch:

- Standalone positive control: LiteX Soapy `CF32` RX, direct complex64 file.
- Live gNB negative controls: OCUDU `CS16` RX, then append scaled by `32767`.

If the LiteX driver's normal CF32 scale corresponds to a much smaller internal
integer range than full int16, the OCUDU CS16 path can quantize the current
uplink tone into a low-count signal before the append and lower-PHY path see
it. That would match the level gap and explain why CP1571 sees a strong tone
while CP1577-CP1585 do not, without contradicting the successful downlink
continuous-TX work.

## Recommended Next Checkpoint

Implement a default-off diagnostic RX CF32 path in OCUDU:

- Add `OCUDU_SOAPY_RX_FORMAT=cf32` or `OCUDU_SOAPY_RX_CF32=1`.
- Open RX Soapy streams as `SOAPY_SDR_CF32` under that env.
- Force/use the `readStream()` fallback for the diagnostic path.
- Convert CF32 samples back into OCUDU `ci16_t` buffers for the existing
  lower-PHY interface using a documented scale and clamp.
- Keep the append path downstream of that conversion so the same CP1585
  analyzer can compare whether the `+100 kHz` tone becomes visible.

If the CP1585-style live gNB RX append tone recovers under RX-CF32, the
blocker is the OCUDU RX sample-format/scaling path. If it still fails, the
remaining suspect stays deeper in live gNB RX/control or predemod behavior.
