# Checkpoint 1590 - Live RX Append Source Audit

Date: [date-redacted]

## Goal

Run a no-RF source and artifact audit after CP1589 to compare the live
OCUDU/gNB RX append path against the known-positive standalone M2SDR RX tone
paths. The audit focused on simple mistakes that could explain the missing
bladeRF `+100 kHz` uplink tone:

- Wrong RX center/frequency translation.
- Wrong RX channel or append port.
- RX sample-format/content routing mismatch.
- Appending after a destructive OCUDU copy/conversion boundary.

## Findings

The live RX configuration path does not show a simple wrong-center or
wrong-channel bug:

- OCUDU RX frequency setup calls `PAVONIS_SOAPY_RX_FORCE_CENTER_HZ` in
  `set_rx_port_freq()` before `device.set_frequency()`; CP1588 set this to
  `1747500000`.
- OCUDU configures RX sample rate, frequency, gain, and bandwidth before
  RX `setupStream()`.
- RX stream channels are built as `[0]` for the one-channel live config, and
  the append port was `0`.
- CP1588 readback proves channel 0 at `1747500000 Hz`, `11.52 Msps`,
  `10 MHz`, `gain_db=71`, `rx_use_read_stream=1`, `rx_cf32_stream=1`,
  `rx_format=CF32`, `env_PAVONIS_SOAPY_RX_FORCE_CENTER_HZ=1747500000`,
  `env_OCUDU_SOAPY_RX_BW_HZ=10000000`, and `env_PAVONIS_SOAPY_RX_APPEND_PORT=0`.

The known-positive standalone paths align on RF geometry but differ in where
samples are tapped:

- CP1571 `test_record.py` opens LiteX RX as `SOAPY_SDR_CF32` on channel 0,
  directly `readStream()`s into a NumPy `complex64` buffer, and writes that
  buffer.
- CP1574 opens full-duplex standalone streams as `SOAPY_SDR_CS16`, keeps TX
  active with zero samples, `readStream()`s into a CS16 buffer, converts
  directly to CF32, and writes the capture. CP1574 was positive despite CS16,
  so CS16 conversion alone is not sufficient to explain live failure.
- CP1574 recorder readback was RX `1747500000 Hz`, `11.52 Msps`,
  `10 MHz`, `gain_db=50`, channel 0, `format=CS16`, and it produced the
  positive `+100 kHz` tone class.

The live append point is not a true raw Soapy readStream tap:

- In RX-CF32 mode, `radio_soapy_rx_stream::receive()` calls Soapy
  `readStream()` into `rx_cf32_read_buffers`.
- It then converts that CF32 scratch buffer back into OCUDU `ci16_t` channel
  buffers with `cf32_to_ci16_component()`.
- The existing `PAVONIS_SOAPY_RX_APPEND_CF32_PATH` writer later iterates
  `buffs.get_channel_buffer(ch)`, divides those `ci16_t` samples by `32767`,
  and appends that converted/copy-layer view.
- Therefore CP1588 proved the live RX stream can be opened as CF32 and can
  lift presentation level, but it did not prove that the raw Soapy
  `readStream()` output before OCUDU conversion/copy has the same content as
  the existing append.

The comment at `radio_soapy_rx_stream.cpp` describing the debug dump as
"raw Soapy RX buffers after acquireReadBuffer()" is stale for the RX-CF32
readStream path. In the current CP1588 path, the append is after the
readStream-to-`ci16_t` conversion, not the raw `rx_cf32_read_buffers` content.

## Conclusion

CP1590 closes the simple live RX misconfiguration theory for this branch:
the saved CP1588 evidence shows the intended RX center, sample rate,
bandwidth, channel, append port, and RX-CF32/readStream state.

The next changed software-only rung should add a default-off raw Soapy
readStream append tap inside `radio_soapy_rx_stream::receive()`, before
CF32-to-`ci16_t` conversion and before the existing `buffs` append. Then rerun
the CP1588 no-TX-stream live gNB RX append tone gate with both taps enabled
and compare raw-preconversion CF32 against the current post-conversion append.

Do not rerun CP1588/CP1589 unchanged, do not turn this into an RX-gain or
amplitude sweep, and do not edit `ue_sync_nr.c`.
