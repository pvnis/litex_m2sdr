## Diagnosis

CP1592 is not valid evidence about whether the CF32-to-`ci16_t` conversion or
legacy append path destroys the uplink tone. The raw CF32 tap added in CP1591
started as soon as RX-CF32 `readStream()` samples arrived, while the legacy
post-conversion append remained gated by the delayed
`PAVONIS_SOAPY_RX_DUMP_ARM_FILE` logic. The two full-length files therefore
cover different windows.

The failed tone result in the raw file should not be promoted into a new RF
conclusion. It is a diagnostic/instrumentation failure: the new tap needs the
same arm semantics as the legacy append before the conversion boundary can be
tested.

## Conclusion

CP1592 is a useful diagnostic checkpoint, not a raw-vs-post conversion result.
It proves the raw-preconversion tap can produce a complete 3 s file on [host-redacted],
and it proves [host-redacted]-side analysis is the right approach under bad local WiFi.
It also proves CP1591 missed the delayed-arm requirement for same-window
comparison.

Do not rerun CP1592 unchanged. The next changed software-only step is to make
`PAVONIS_SOAPY_RX_APPEND_RAW_CF32_PATH` honor the same
`PAVONIS_SOAPY_RX_DUMP_ARM_FILE`/poll behavior as the legacy append, build-smoke
that on [host-redacted], and only then rerun the RF same-window comparison.
