# CHECKPOINT 1616 - Current-Time CP1576 No-Append Real-UE Control

Date: [date-redacted]

## Goal

CP1614 and CP1615 kept the CP1606-CP1613 raw/post append, predemod, and
alignment instrumentation active but never produced real UE PRACH events.
CP1616 checks whether the known CP1576 no-append, native-continuous downlink
control still emits PRACH on the current hardware. The wrapper reuses the
CP1576 runner with a CP1616 stamp/tag, then runs the CP1615 real-UE event
alignment analyzer on the fetched no-append artifacts.

CP1616 does not reproduce CP1576's PRACH emissions.

The no-append path still acquires the downlink better than CP1614/CP1615:

- `cell_search_done result=1`
- `trials=33`
- `pci=1`
- SNR `9.558 dB`
- CFO `-3944.783`
- RSRP `-10.390`
- `pbch_crc=1`
- SFN sync succeeds once at `trial=52`, `tti=4141`
- `cell_select_done status=successful trials=51 tti=4141`

But it never emits Msg1:

- `Random Access Transmission` count: `0`
- `PAVONIS_SRSUE_PRACH_CFG transmitted` rows: `0`
- `PRACH-TX wall_ns` rows: `0`
- `PAVONIS_SRSUE_RA_TIMING` rows: `0`
- `prach_tx_count=0`
- `rf_overflow_lines=0`
- UE exits the bounded run with `RC=124`.

The guard/camping trace reaches at least:

```text
PAVONIS_PRACH_SYNC_GUARD_NOTE tti=4220 ... stable_slots=80 required_slots=200
```

The UE detail log has `6622` lines, with `6620` matching the broad
`out-of-sync/SYNC/PAVONIS/PRACH/RRC/...` audit pattern and repeated
`SYNC: detected out-of-sync... skipping slot ...` entries. So this is a
current-time downlink stability/UE-progress failure after cell selection, not
a gNB PRACH detector timing datapoint.

## Comparison

CP1576, earlier on the same native-continuous no-append rung, had SNR
`11.547 dB`, cell selection success, and five strong preamble-0 PRACH bursts.
CP1616 gets closer to that downlink state than CP1614/CP1615 but still emits
zero PRACH:

- CP1614: SNR `1.174 dB`, cell select then out-of-sync, zero PRACH.
- CP1615: SNR `4.571 dB`, SFN sync fails, zero PRACH.
- CP1616: SNR `9.558 dB`, cell select and SFN sync pass, but stable/camping
  progress does not reach PRACH emission before out-of-sync behavior.

This means the current no-PRACH blocker is not unique to the CP1606/CF32/
readStream append instrumentation path.

## Conclusion

CP1616 is mechanically clean and closes the immediate "append instrumentation
alone prevents PRACH" hypothesis. The no-append CP1576-style control has also
drifted: it still reaches cell select and SFN sync but no longer emits PRACH
under the `200`-slot PRACH sync guard.

The next useful changed rung is not PRACH demod-offset work yet. First force a
real UE Msg1 timestamp again by shortening or disabling the temporary
`PAVONIS_SRSUE_PRACH_SYNC_GUARD_SLOTS=200` guard on the no-append control. If
that produces real PRACH rows, then repeat the instrumented CP1606-style
append/predemod run with the same guard setting and use the event-alignment
analyzer to classify "missed window" versus "hit but weak/delay-gated."
