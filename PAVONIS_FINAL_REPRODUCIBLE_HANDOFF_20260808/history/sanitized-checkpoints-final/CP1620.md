## Interpretation

CP1620 supersedes the raw-append side of CP1619.

CP1619 correctly showed that predemod remains weak at the seven CP1618
manifest rows, but its raw-append event-window comparison used a first-ret_ts
delta mapping that does not match the actual append file offsets recorded in
`pavonis_soapy_rx_append_meta.tsv`.

The exact UE waveform family is not absent from the CP1618 raw append. It is
present strongly, with normalized correlation around `0.93`, but the best
matches cluster at append-file offsets that do not equal the old CP1619
event-window offsets.

This moves the immediate blocker from "raw append does not see the real UE" to
"append-file offset, hardware timestamp, predemod manifest, and detector window
alignment are inconsistent." The detector/predemod side still sees weak p0 at
the nominal manifest rows, so the next step is a corrected event-window compare
using the per-row append metadata mapping, not the old first-ret_ts delta.

## Conclusion

CP1620 is a no-RF positive raw-append visibility result. The CP1618 raw M2SDR
append contains strong exact matches to the real UE TX debug dumps.

Do not rerun CP1619 unchanged. The next checkpoint should redo the CP1619
event compare with metadata-row mapping from `ret_ts` to
`append_file_offset_samples`, and should score both exact UE SC16 dumps and the
CP19 template at the corrected event windows. If the corrected raw append hits
but predemod stays weak, then reuse the CP651-CP733 demod-offset findings
against this corrected timing model.
