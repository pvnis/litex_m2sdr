# Checkpoint 1630 - CP1618 raw-hit windows through actual gNB PRACH detector

Date: [date-redacted] Europe/Zurich

## Goal

Run the no-RF decisive test requested after CP1629: feed the seven CP1618 raw
append windows at the CP1621 raw-hit offsets through the actual OCUDU gNB PRACH
demodulator and detector offline.

This tests whether the CP1618/CP1621 window-mapping hypothesis is real using
data already on disk, without spending another RF run while current UE
RACH-config/Msg1 emission is intermittent.

## Method

I added a narrow local/offline harness:

```text

sha256 910a83c9a881a4c990460e5a94a2d8c1426659de79554520be316e0c6628f3d2
```

It links against the existing [host-redacted] OCUDU build and calls:

```text
create_ofdm_prach_demodulator_factory_sw(...)

ofdm_prach_demodulator::demodulate(...)
prach_detector::detect(...)
```

Input offset table from CP1621:

```text

sha256 b591c8a5ef26dfafdaf0c5a980dabd9a850457083ea283d23482b4d73e75980b
```

Each of the seven CP1618 events was replayed in three variants:

```text
direct_corrected: CP1621 corrected metadata offset, the nominal CP1618 predemod window
raw_exact_hit:    CP1621 best exact-UE raw append hit offset
raw_cp19_hit:     CP1621 best CP19-template raw append hit offset
```

The replay uses the CP1618 live gNB PRACH geometry:

```text

window length: 11520 samples
format: 0
root_sequence_index: 1

rb_offset/nof_prb_ul_grid: 8/52
nof_td_occasions/nof_fd_occasions: 1/1
detector ra_scs: 4 / kHz1_25
threshold: 0.1469999999
delay_limit: 104.80 detector samples
```

Note: an initial clean run used detector `ra_scs=0` by mistake. It produced
the same qualitative direct-fail/raw-hit-pass pattern but the threshold was
wrong (`0.61`), so it is diagnostic only and not the CP1630 result. The final
run below matches the CP1618 live detector trace geometry (`ra_scs=4`,
threshold `0.147`).

## Interpretation

CP1630 proves the window-mapping hypothesis from saved data: the UE waveform is
present in the CP1618 raw append and is detector-acceptable when the gNB PRACH
collection/demod window is moved to the CP1621 raw-hit offsets. The failure in
the original CP1618 predemod/detector rows is not that the detector cannot
accept the waveform; it is that the 1 ms window is too early for the raw
waveform instance that is actually in the append.

The per-event spread remains the important design constraint. CP1621 raw-exact
hit offsets are about `+11.806..+18.903 ms` after the corrected metadata
offsets, and the CP19-hit offsets are about `+11.794..+18.916 ms`. A single
static 1 ms delayed collection can miss events even when the mapping hypothesis
is correct. The next implementation should use per-event metadata/window
mapping or a wider/remapped diagnostic, not another static-delay RF sweep.

CP1630 does not explain the newer CP1627-CP1629 no-PRACH/RACH-config
intermittency; it deliberately avoids RF and current UE behavior. It closes
the CP1618 saved-data question and gives a concrete target for the next
software-only patch: make the live PRACH collection path place the detector
window at the raw-hit-mapped position, with proof fields, before spending RF.
