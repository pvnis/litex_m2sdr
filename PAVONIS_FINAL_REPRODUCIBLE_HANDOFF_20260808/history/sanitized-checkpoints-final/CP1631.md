# Checkpoint 1631 - PRACH collection-delay sequence diagnostic build

Date: [date-redacted] Europe/Zurich

## Goal

Move one software-only rung above CP1630 without spending RF on another static
delay knob. CP1630 proved that CP1618 raw-hit windows are accepted by the
actual gNB PRACH detector, while nominal/direct windows fail, but the raw-hit
offsets spread by about `+11.8..+18.9 ms`. A single static 1 ms delayed
collection can therefore still miss real events.

CP1631 adds a default-off delay-sequence diagnostic so a future single RF run
can map successive PRACH opportunities to different CP1630-derived collection
offsets and prove which table entry was used in the predemod manifest.

## Code Change

Touched source:

```text
ocudu/lib/phy/lower/processors/uplink/prach/prach_processor_worker.cpp
ocudu/lib/phy/lower/processors/uplink/prach/prach_processor_worker.h
```

New default-off envs:

```text
PAVONIS_PRACH_COLLECTION_DELAY_SEQUENCE_SAMPLES
PAVONIS_PRACH_COLLECTION_DELAY_SEQUENCE_START_INDEX
```

Behavior:

- Existing `PAVONIS_PRACH_COLLECTION_DELAY_SAMPLES` is preserved as the static
  fallback when the sequence env is unset.
- When `PAVONIS_PRACH_COLLECTION_DELAY_SEQUENCE_SAMPLES` is set, the worker
  parses up to `64` positive sample delays from a delimiter-tolerant string.
- Each eligible format-zero/start-symbol-zero/single-TD/single-FD PRACH
  request selects:

```text
index = (request_index + PAVONIS_PRACH_COLLECTION_DELAY_SEQUENCE_START_INDEX) % sequence_len
collection_delay_samples = sequence[index]
```

- The selected delay then uses the existing CP1624 delayed-collection path.
- Predemod manifest proof columns now include:

```text
collection_delay_sequence_active
collection_delay_sequence_len
collection_delay_sequence_index
collection_delay_sequence_request_index
```

This is deliberately still a diagnostic, not a production PRACH timing policy.

## Conclusion

CP1631 is a no-RF/build checkpoint. It successfully deploys and builds a
default-off PRACH collection-delay sequence diagnostic on [host-redacted]. The target gNB
can now run a CP1630-derived delay table in one real-UE RF attempt, while the
predemod manifest proves the chosen sequence entry for each PRACH opportunity.

Recommended next RF rung, once the UE/RACH-config baseline is stable enough to
interpret, is a guarded real-UE PRACH run using CP1618/CP1621/CP1630-derived
delays, for example:

```text
PAVONIS_PRACH_COLLECTION_DELAY_SEQUENCE_SAMPLES=217768,136008,145327,142494,138408,146349,142513
```

Use `PAVONIS_PRACH_COLLECTION_DELAY_SEQUENCE_START_INDEX` only to rotate the
table if the request/event alignment needs a known offset. Do not rerun
CP1624/CP1625 static delay unchanged, and do not treat CP1631 as RF evidence.
