# Checkpoint 1634 - CP1632 vs CP1633 acquisition/runtime audit

Date: [date-redacted] Europe/Zurich

## Goal

Close the no-RF audit requested by CP1633 before spending another RF run on
PRACH collection-delay sequence timing.

CP1632 was the last clean no-delay/no-sequence real-UE baseline: the UE reached
RACH config and emitted seven Msg1/PRACH events. CP1633 proved the new sequence
instrumentation active, but the UE failed SFN sync and emitted no Msg1, making
that checkpoint invalid as timing evidence.

This checkpoint compares the saved artifacts only. No RF run, SSH session, or
hardware state change was performed.

python3 cp1634_compare_cp1632_cp1633_acquisition.py cp1634_cp1632_vs_cp1633_acquisition_audit.json

## Conclusion

CP1634 closes UE config and material TX readback as explanations for the CP1633
pre-Msg1 regression. CP1633 changed sequence mode plus companion RX CF32/
readStream append instrumentation, then the UE failed SFN sync before any
RACH config transmission or Msg1. The sequence timing data from CP1633 remains
invalid.

Do not run another sequence/static-delay RF timing attempt now. The no-RF
actual-detector proof requested for the CP1618/CP1621 raw-hit windows is
already CP1630 and should not be rerun unchanged. Next work should either
audit the CP1632-vs-CP1633 harness/runtime lineage further without RF, or use a
minimal acquisition-only RF baseline that separates sequence mode from the
companion RX append/readStream path before interpreting any PRACH timing result.
