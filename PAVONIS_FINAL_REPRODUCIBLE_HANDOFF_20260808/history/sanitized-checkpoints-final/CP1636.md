about `11.795..18.916 ms`.

## Interpretation

CP1630 already proves the window-mapping hypothesis from data on disk: the
CP1618 raw append contains detector-acceptable UE PRACH, and the detector fails
the original CP1618 predemod rows because the 1 ms collection/demod window is
too early, not because the waveform is intrinsically undetectable.

CP1636 therefore cancels the planned RF delay/acquisition checkpoint as the
next immediate step. The right frontier is now software-side window mapping:
build or audit a per-event/window-mapped or wider/remapped diagnostic with
manifest proof fields, and only spend RF again once the UE acquisition/RACH
config path is stable enough to produce real Msg1 events. A single static delay
can still misalign a 1 ms window because CP1618's per-event spread is about
`11.8..18.9 ms`.

Do not rerun CP1630 unchanged. Do not run another sequence/static-delay RF
timing attempt while the UE is intermittently failing before RACH config/Msg1.
