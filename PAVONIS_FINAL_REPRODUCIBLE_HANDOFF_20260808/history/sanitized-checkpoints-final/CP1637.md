# CP1637 PRACH mod-7 retirement and TX-latency frontier audit

Date: [date-redacted] Europe/Zurich

## Goal

Retire the CP1631 mod-7 collection-delay table as the next live PRACH timing
strategy, per the new working rule:

- A past run's per-event delays cannot be assigned reliably to future PRACH
  occasions by request counter.
- The CP1618/CP1621 raw-hit spread is about `11.8..18.9 ms`, while the useful
  detector slack is only about `0.1 ms`.
- Any future RF run where the UE emits no real Msg1 is a void retry, not a
  PRACH timing datapoint.

The audit compared the two requested alternatives:

1. widen PRACH collection enough to cover the whole `11..20 ms` uncertainty
   and let the detector search inside it;
2. measure the likely source of the per-run offset, namely the continuous-TX
   pipeline latency from lower-PHY slot timestamp to actual RF emission.

## Source audit

The current PRACH collection path cannot simply widen to `11..20 ms` by
changing an environment value. `prach_processor_worker` still allocates its
temporary PRACH buffers from `prach_constants::MAX_WINDOW_LENGTH`, and that
constant is `5e-3` seconds:

- `ocudu/include/ocudu/ran/prach/prach_constants.h`: `MAX_WINDOW_LENGTH = 5 ms`
- `ocudu/lib/phy/lower/processors/uplink/prach/prach_processor_worker.h`:
  `temp_baseband` and `temp_cf_baseband` are sized from that maximum

Therefore a true `11..20 ms` collection/search window is a behavioral patch:
larger buffering plus detector-side subwindow/search semantics and manifest
proof fields. It should not be treated as a quick delay-knob rerun.

The TX timing instrumentation already exists at the software/DMA boundary:

- OCUDU Soapy TX computes `time_ns` from `tx_md.ts` and can write
  `PAVONIS_SOAPY_TX_WRITE_DUMP_META_PATH` rows with `logical_ts`,
  `logical_offset`, `time_ns`, requested samples, return value, and flags.
- LiteX M2SDR parses `M2SDR_SOAPY_TX_TIME_OFFSET_NS`, computes
  `release_timeNs = source_timeNs + offset`, and records commit timing through
  `M2SDR_SOAPY_TX_WORKER_TRACE_PATH`.
- The worker trace columns include `source_time_ns`, `release_time_ns`,
  `hw_now_ns`, `slip_ns`, ring counters, flags, and submit stage
  (`copy_submit` / `zero_copy_submit` / `liteeth_submit`).
- The DMA release path writes `release_time_ns` into the TX DMA header as a
  sample-count timestamp when `HAS_TIME` survives deduplication.

That is enough to measure lower-PHY timestamp to scheduled DMA/header release
on each run. It is not enough by itself to observe the analog RF emission time
at the antenna; that requires a paired RF/self-RX measurement or an explicit
loopback/tone/edge observable.

## Decision

CP1637 closes the mod-7 sequence table as the recommended live RF next step.
CP1631 remains useful as a diagnostic proof mechanism, but not as a predictor
for future live UE occasions.

The practical next rung is:

1. use the existing OCUDU write metadata plus M2SDR worker trace to measure the
   per-run software commit/release timing;
2. if the question is actual RF emission latency, add a self-contained
   same-run RF/self-RX observable and compare it to the worker trace;
3. only count a real-UE PRACH RF run as a datapoint if the UE emits real Msg1.
