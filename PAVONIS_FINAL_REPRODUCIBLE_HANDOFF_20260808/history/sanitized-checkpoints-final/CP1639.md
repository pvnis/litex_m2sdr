# Checkpoint 1639: CP1532 TX-Marker Latency Artifact Audit

Date: [date-redacted] Europe/Zurich

## Purpose

Test whether the saved CP1532 live gNB self-RX artifacts can provide the
requested lower-PHY timestamp to actual RF/self-RX emission latency without a
new RF run. This follows CP1638, which showed that the first PBCH-positive RX
window is not itself a latency marker.

## Method

No RF was transmitted and no OCUDU/LiteX source was changed. I added and ran a
local artifact analyzer:

- `cp1639_cp1532_tx_marker_latency_estimate.py`
- Output directory: `cp1639_cp1532_tx_marker_latency_estimate_[date-redacted]`

The analyzer uses CP1532's saved data:

- RX append: `pavonis_soapy_rx_append_p0.cf32`
- RX append metadata: `pavonis_soapy_rx_append_meta_[date-redacted]CP1532_LIVE_GNB_SELFRX_RXAPPEND_META_NO_SENS.tsv`
- TX references: `pre_dma_full_scale32768.cf32` and `post_dma_scale32768_ch0.cf32`
- TX metadata: `pre_dma_tx.cs16.meta.jsonl`
- Worker trace: `litex_tx_worker_trace.tsv`

It first tries an unconstrained high-energy-template correlation from TX
reference into the same-run RX append. Because that can match the wrong
periodic downlink occurrence, it also runs a timestamp-constrained scan from
`-5..+25 ms` scheduled-to-RX delay at `0.1 ms` resolution.

## Results

Instrumentation health is clean:

- RX append/meta samples: `2880000 / 2880000`
- TX reference/meta samples: `6000000 / 6000000`
- RX metadata anomalies: `0` overflows, `0` no-time chunks, `0` time regressions, `0` read-chunk overflows
- Worker rows/HAS_TIME/dedup/late: `77099 / 4959 / 0 / 0`

The unconstrained template correlation is not physically usable:

- `pre_dma`: best score `0.332005667` at CFO `2850000 Hz`, but mapped deltas are impossible (`scheduled_to_rx_ms` median `-942.561545 ms`)
- `post_dma_ch0`: best score `0.433939929`, also impossible (`scheduled_to_rx_ms` median `-1848.727517 ms`)

The timestamp-constrained scan is weak and non-agreeing:

- `pre_dma`: best scheduled-to-RX delay `12.0 ms`, score only `0.008834314`; separated peaks also appear at `22.0`, `17.0`, `7.0`, `2.0`, and `-4.0 ms`
- `post_dma_ch0`: best scheduled-to-RX delay `21.6 ms`, score only `0.004476896`; secondary peak near `12.1 ms`

## Conclusion

CP1532's saved live waveform is not a reliable RF-emission marker. The
unconstrained correlation matches repeated/periodic structure and produces
impossible negative latencies. The timestamp-constrained scan has no dominant,
high-confidence peak and the pre-DMA and post-DMA references disagree
materially (`12.0 ms` versus `21.6 ms`).

Do not treat CP1639 as a measured TX-pipeline latency. It closes the
artifact-only shortcut from CP1532. The next decisive work should either:

- run one purpose-built [host-redacted]-only same-run marker measurement with OCUDU write
  metadata, M2SDR worker trace, RX append metadata, and an RF-visible marker
  tied to a known TX source timestamp; or
- implement the real widened PRACH collection/search path from CP1637, because
  the current `5 ms` PRACH worker buffer cap cannot cover the `11..20 ms`
  uncertainty.

For future real-UE PRACH RF timing runs, keep the gate: if the UE emits no real
Msg1, the run is a void retry, not a datapoint.
