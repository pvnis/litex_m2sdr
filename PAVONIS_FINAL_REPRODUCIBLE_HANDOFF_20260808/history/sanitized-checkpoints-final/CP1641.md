## Purpose

same-run RF/self-RX marker tied to a known TX source timestamp, rather than
editing the widened PRACH collection window. CP1640 closed CP1532's MIB/SFN

and maps received marker positions back through RX read metadata.

## Method

The CP1641 script:

- opens one LiteX-M2SDR Soapy device on [host-redacted];
- schedules TX with Soapy `SOAPY_SDR_HAS_TIME`;
- emits explicit QPSK PN markers at known source sample offsets;
- enables LiteX `M2SDR_SOAPY_TX_WORKER_TRACE_PATH`;
- records TX write metadata and RX per-read metadata;
- correlates RX marker hits against the known templates;
- maps RX sample offsets to hardware time through `rx_read_meta.jsonl`, not by
  assuming a continuous first-RX timestamp when overflows occur.

The runner performs the usual pre-run quieting:

- AD9361 BIST config `0x3f4 <- 0x00`;
- AD9361 BIST port `0x3f6 <- 0x03`;
- crossbar `0xc800 <- 0`.

## Attempts

1. Initial 11.52 Msps, single timed first row, 75 ms write-ahead:
   invalid. TX queue filled before scheduled release, `RUN_RC=2`,
   `tx_errors=1`, only `510` RX samples captured.

2. 11.52 Msps with 5 ms write-ahead but pre-fix scheduler:
   invalid. The script paced against `wall0 + row_offset` instead of
   `wall0 + timed_lead + row_offset`, so writes were still attempted about
   `750 ms` early and blocked. Full capture completed, but
   `timed_max_late_s=0.742969942`; apparent marker delays
   `18.414584`, `17.662154`, `-9.626735`, and `8.506598 ms` are not valid.

3. 11.52 Msps fixed scheduler, repeated same marker, first-RX timestamp
   mapping:
   mechanically clean TX (`tx_errors=0`) but still not valid. RX had
   `12` overflows and first-timestamp mapping produced unstable apparent
   delays from `-21.048437` to `6.240452 ms`.

4. 11.52 Msps fixed scheduler, unique markers, per-read RX metadata:
   TX clean, but RX still had `12` overflows and `12` hardware-time gaps
   up to `11.908854 ms`. Only markers 2 and 3 were strong; their latencies
   split between `0.094271 ms` and `22.805382 ms`.

5. 11.52 Msps, all rows HAS_TIME-tagged:
   TX clean and worker trace now has timed rows throughout, but RX still had
   `12` overflows / `12` hardware-time gaps. Strong markers again split:
   `-0.013541 ms` and `22.604168 ms`.

6. 11.52 Msps short capture, all-timed, unique markers:
   shortened to `0.070 s` TX waveform and `1,267,200` RX samples. RX gaps
   improved but did not disappear: `4` RX overflows and `4` hardware-time
   gaps up to `11.731771 ms`. Strong marker delays still disagreed:
   `-11.746180 ms` and `22.631946 ms`.

7. 3.84 Msps lower-rate control, all-timed, unique markers:
   no RX overflows, no RX metadata gaps, no TX errors. All three marker
   latencies clustered at `0.016407`, `-0.063281`, and `-0.112240 ms`
   (`128.647 us` total range). The scripted gate still failed because marker 0
   had score `0.171951` against a `0.20` good-marker threshold, leaving only
   two counted good markers, but the timing cluster itself was stable.

8. 3.84 Msps lower-rate control with marker amplitude `0.20`:
   repeats the same low-rate conclusion: no RX overflows, no RX metadata gaps,
   no TX errors. Marker latencies were `0.016407`, `-0.063280`, and
   `-0.112239 ms`. The scripted gate still counted only two good markers
   because marker 0 scored `0.169825`, but the all-marker latency range stayed
   `128.646 us`.

## Result

CP1641 does not produce a valid 11.52 Msps CP1624 delay value.

The explicit-marker idea is sound: at 3.84 Msps the same all-timed marker
method has no RX metadata gaps and produces a stable sub-`0.13 ms` cluster
around a median of about `-0.088 ms`. However, at the live `11.52 Msps` rate
the Python Soapy self-RX reader cannot keep up reliably. Every 11.52 Msps
variant that reached capture had RX overflows and per-read hardware-time gaps
up to about `11.7-11.9 ms`, exactly large enough to create the false
frame-scale marker offsets we are trying to avoid.

## Conclusion

Do not use CP1641's 11.52 Msps apparent offsets as a PRACH delay knob value.
The values around `22.6 ms`, `-11.7 ms`, or similar are artifacts of the
standalone Python RX capture gaps and/or missing marker windows, not measured
TX-pipeline latency.

The next latency rung should keep the CP1641 marker design but move the
11.52 Msps RX side out of this Python reader:

- use a C++/OCUDU-style RX append or direct M2SDR DMA recorder that can keep up
  at `11.52 Msps`;
- keep unique PN markers;
- keep all rows HAS_TIME-tagged for the marker waveform;
- keep LiteX worker trace active;
- keep per-read/per-append RX metadata and map RX marker time through that
  metadata.

Until a live-rate marker run has zero RX metadata gaps and stable marker
latencies, do not feed a CP1641-derived value into CP1624 and do not spend
real-UE PRACH RF attempts on this branch.
