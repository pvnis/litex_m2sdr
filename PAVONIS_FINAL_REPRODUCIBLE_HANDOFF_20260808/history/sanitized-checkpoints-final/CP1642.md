# Checkpoint 1642 - [host-redacted] C++ Live-Rate Timed Marker Latency

Date: [date-redacted] Europe/Zurich

## Goal

Continue the user-selected [host-redacted]-only latency branch, after CP1640 closed the
CP1532 MIB/SFN shortcut and CP1641 showed Python RX cannot keep up at
`11.52 Msps`. The specific goal was to keep CP1641's unique/all-timed marker
design, but move live-rate RX into a C++/Soapy path with per-read metadata, so
the run can distinguish real TX/RX timing from Python RX gaps.

No UE, bladeRF, or [host-redacted] RF path was used in the experiment. This was a
[host-redacted] M2SDR TX-to-M2SDR self-RX run.

## Verdict

`LIVE_RATE_CPP_RX_METADATA_PASS_BOUNDED_MARKER_LATENCY_STABLE_BROAD_SEARCH_TRAP`

CP1642 proves the C++ [host-redacted]-only live-rate RX path is feasible at `11.52 Msps`:
there are no RX metadata gaps, no RX overflows, no time regressions, no TX
worker late rows, and all TX worker rows are timed.

The usable near-scheduled marker latency in this run is stable at roughly
`-14 us` to `-33 us`, median `-28.818 us`. However, the delayed marker-2 copy
means a broad `±25 ms` peak search is unsafe. Do not use the `+22.631945 ms`
broad-search marker-2 hit as a CP1624 delay value.

CP1642 is a valid harness baseline and strongly improves CP1641, but one run
is not enough to declare a run-stable per-run delay for CP1624. The next rung
should repeat the live-rate C++ marker measurement with the bounded analyzer
as the primary gate, preferably with more markers away from the waveform tail
or an explicit duplicate/echo guard, then compare the bounded cluster across
runs before applying any PRACH collection delay.
