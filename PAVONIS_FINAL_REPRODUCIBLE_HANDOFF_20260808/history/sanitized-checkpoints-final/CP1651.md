# Checkpoint 1651 - Live Native-Continuous TX Marker Sequence Harness Cap

Date: [date-redacted] Europe/Zurich

## Goal

Run the CP1650 sequence-marker implementation in one live native-continuous
gNB stream, with one early marker and one late marker:

```text
marker 0: +23040000 samples  (+2 s at 11.52 Msps)
marker 1: +691200000 samples (+60 s at 11.52 Msps)
```

This was intended to answer the user's warning that an early-only marker can
falsely clear the live path if untimed continuation chunks drift or jump later
in the run.

## What Failed

Marker 1 did not fail as RF evidence; the RX append did not cover it. The
inherited CP1577 start helper hardcoded:

```text
PAVONIS_SOAPY_RX_SUMMARY_MAX=200000
```

The CP1651 run ended with:

```text
RX_META_ROWS=200000
rx_samples=102000000
rx_bytes=816000000
```

That is exactly `200000 * 510 = 102000000` samples, so the append stopped at
about `8.85 s`, despite the requested `748800000` samples. The late marker's
expected sample was far beyond the saved file:

```text
MARKER_1_EXPECTED_RX_SAMPLE=679470431
rx_samples=102000000
MARKER_1_PASS=0
MARKER_1_SCORE=0.0
```

Therefore CP1651 is a harness-cap diagnostic, not a late-marker timing
datapoint.

## Verdict

`INVALID_LATE_MARKER_DATAPOINT_RX_SUMMARY_CAP`

CP1651 proves CP1650's sequence overlay works and re-proves the early marker,
but it does not test the `+60 s` marker because the inherited RX summary/meta
cap stopped capture at `102000000` samples. The next run must raise
`PAVONIS_SOAPY_RX_SUMMARY_MAX` above the required append rows and make the
wait gate fail if the requested byte count is not reached.
