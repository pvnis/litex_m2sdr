# Checkpoint 1652 - Live Native-Continuous TX Marker Sequence Late Drift

Date: [date-redacted] Europe/Zurich

## Goal

Rerun the CP1650/CP1651 two-marker live native-continuous TX marker test with
the RX append cap fixed, so both markers are measured in the same live stream:

```text
marker 0: +23040000 samples  (+2 s at 11.52 Msps)
marker 1: +691200000 samples (+60 s at 11.52 Msps)
```

This directly tests the user's warning that an early-only marker can falsely
clear the path if untimed continuation chunks drift or jump later in the run.

## Interpretation

`PASS_TWO_MARKERS_FAIL_TIMING_STABILITY`

CP1652 closes the CP1651 harness-cap problem and gives the requested two-point
same-stream measurement. It is not a positive timing-stability result. The
early marker is around `+1.37 ms`, while the late marker is around `+7.76 ms`,
a `+6.3875 ms` divergence over the `58 s` marker separation.

That result supports the suspected mechanism: an early-only marker would have
missed a late-run timing drift/jump in the live native-continuous path after
the single `HAS_TIME` anchor and many untimed continuation packets. The run is
mechanically clean, both markers have `0 Hz` CFO, RX metadata has no no-time,
overflow, or regression rows, and TX counters show no late/underflow/acquire
errors, so this is not explained by the CP1651 capture cap or by marker
detection failure.

Do not use CP1649, CP1651, or the CP1652 early-marker latency as a standalone
CP1624 delay value. A run-start static delay would be wrong by about `6.39 ms`
by the `+60 s` marker epoch in this run. The next changed work should stay on
the TX-cadence/timestamp branch: either source-audit and patch a periodic
timed re-anchor/all-timed native-continuous mode, or otherwise prove where the
single-anchor-to-RF timestamp mapping accumulates the late offset, then rerun
the same two-marker test.
