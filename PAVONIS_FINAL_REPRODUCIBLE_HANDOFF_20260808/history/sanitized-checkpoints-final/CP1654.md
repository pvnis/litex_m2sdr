# Checkpoint 1654 - Live Native-Continuous Reanchor Two-Marker RF Test

Date: [date-redacted] Europe/Zurich

## Goal

Rerun the CP1652 two-marker same-device self-RX latency measurement with the
CP1653 periodic TX re-anchor lever enabled.

The hypothesis was that CP1652's late marker drift came from the live
native-continuous stream using one opening `SOAPY_SDR_HAS_TIME` anchor followed
by untimed continuation chunks. CP1654 therefore used periodic timed re-anchors
while keeping the same early/late marker structure.

## Verdict

`REANCHOR_PROPAGATED_BUT_TIMING_STABILITY_FAIL`

CP1654 is mechanically valid and proves the CP1653 software lever activated:
`685` timed writes reached the LiteX TX worker/release path, with `684`
re-anchor writes and no LiteX late/underflow/acquire errors.

But it does not fix the timing problem. The early marker latency was
`+0.934 ms`, the late marker latency was `+9.028 ms`, and the same-stream
range was `8.094 ms`, worse than CP1652's `6.388 ms`. Therefore the next rung
should not assume the one-opening-`HAS_TIME` descriptor shape was the whole
cause. Periodic timed descriptors, as currently implemented, do not re-lock
the live RF timing over the 60 s interval.

Do not use CP1654 marker latencies as a CP1624 delay value, and do not rerun
CP1654 unchanged.

Next work should first audit the LiteX timed-descriptor semantics under an
already-running continuous DMA stream. The key question is whether later
`HAS_TIME` descriptors actually re-anchor RF emission timing, or whether they
are accepted and counted but cannot correct an active continuation stream. A
changed follow-up could test an all-timed/live-chunk mode only after that audit
defines what driver behavior it is supposed to exercise.
