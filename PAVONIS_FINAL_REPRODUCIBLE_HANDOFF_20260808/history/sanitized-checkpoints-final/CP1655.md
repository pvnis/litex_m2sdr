# CHECKPOINT 1655 - LiteX Timed-Descriptor Semantics Audit

Date: [date-redacted]

## Goal

Close the no-RF source audit requested after CP1654. CP1654 proved that
`PAVONIS_SOAPY_TX_REANCHOR_INTERVAL_SAMPLES=1152000` produced many later
`HAS_TIME` descriptors (`has_time_writes=685`, `reanchor_writes=684`,
LiteX worker/release `has_time=685`), but the two-marker live measurement
still drifted from `+0.9344618055555556 ms` at `+2 s` to
`+9.[subscriber-redacted] ms` at `+60 s`.

The question for CP1655 was whether later `HAS_TIME` descriptors in an
already-running native-continuous DMA stream are real timing descriptors or
only accepted/counted without affecting the active stream.

## Findings

1. The LiteX TX DMA header has explicit per-frame timing semantics:
   bit 63 is `HAS_TIME`, bit 62 is `END_BURST`, and the second 64-bit word
   is the sample-count timestamp. The Soapy boundary converts nanoseconds to
   this sample-count timestamp.

2. `writeStream()` preserves `HAS_TIME` when it opens a fresh DMA buffer. With
   `M2SDR_SOAPY_TX_ALIGN_HAS_TIME_REMAINDER=1`, an incoming timed write first
   releases a partial untimed remainder buffer so the timed write starts a new
   buffer. This aligns the descriptor to a DMA frame, but it does not split a
   live chunk at an exact reanchor threshold or force all neighboring
   continuation chunks to become timed.

3. `_dmaReleaseWrite()` writes the final per-buffer LiteX header before the
   buffer is made visible to the DMA reader. Unique later `HAS_TIME` timestamps
   survive deduplication; the dedup path only suppresses exact duplicate
   timestamps. CP1654 had `dedup_suppressed=0`, so its later timed descriptors
   were not removed at the driver boundary.

4. In zero-copy mode, later submissions update `sw_count`; the DMA reader is
   started only if it was not already enabled. There is no source-level reset
   or restart for each later `HAS_TIME`, but the buffer header still reaches
   the FPGA stream.

5. `TXHeaderExtractor` owns fixed frame markers. It extracts one header and
   timestamp per DMA frame and drives `header.update`; it does not depend on
   upstream `last` to define the timed descriptor cadence.

6. `TimedTXArbiter` pushes one descriptor per DMA frame as soon as
   `header.update` fires. In `IDLE`, if that descriptor has `has_time=1` and
   `sample_count <= ts`, the FSM waits until `sample_count >= ts` and then
   streams that frame. If the descriptor is late, it drops the frame and
   increments `late_count`. CP1654 had zero late/underflow/acquire errors.

7. The RF path wiring is `header.tx.source -> timed_tx.sink ->
   txrx_loopback.tx_sink -> ad9361.sink`, with the timed arbiter comparing
   against the shared sample counter used for RX timestamps.

8. The OCUDU CP1653 reanchor implementation marks only chunks whose
   `chunk_start_ts >= tx_reanchor_next_ts`. It does not mark chunks that cross
   the reanchor threshold before their start, and it does not convert the whole
   live stream into timed chunks. CP1654 marker metadata showed marker chunks
   beginning 150 samples before the selected marker timestamp, so marker
   content can straddle an untimed/timed boundary even when remainder alignment
   is enabled.

## Verdict

`LATER_HAS_TIME_DESCRIPTORS_ARE_REAL_BUT_REANCHOR_IS_INSUFFICIENT`

The audited source does not support the theory that later `HAS_TIME`
descriptors are merely counted and ignored. They should produce real FPGA
timed descriptors for the DMA frames that carry them.

CP1654 therefore remains a valid negative for the current periodic-reanchor
implementation: the lever propagated, but timed single frames every 100 ms did
not discipline the intervening native-continuous untimed continuation stream
or stabilize the live lower-PHY-to-RF latency. Do not rerun CP1654 unchanged
and do not use CP1654 marker latencies as CP1624 delay values.

## Next Checkpoint Guidance

The next RF timing run should test a stronger software variant, such as an
all-timed live-chunk mode or a reanchor mode that applies timing to the exact
chunk crossing the boundary rather than only chunks whose start is already
past it.

Per user instruction, that next marker run must measure at two well-separated
points in the same stream: one shortly after stream start and another around
`60-120 s`. An early-only marker result must not be treated as clearing the
live native-continuous path.
