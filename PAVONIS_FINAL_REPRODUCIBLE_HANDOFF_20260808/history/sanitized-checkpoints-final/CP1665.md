does not recover RACH config:


CP1665's first out-of-sync burst occurs tens of seconds after UE start and
after the initial aligned camping traces. CP1632 had already emitted seven
Msg1 events before its first out-of-sync burst. Therefore the CP1660/CP1665
no-RACH-config failure is not explained solely by immediate out-of-sync.

## Verdict

CP1665 is a useful negative offset-bracket checkpoint:

```text
TX pre-UE late gate: PASS
Full-run TX cleanliness: MARGINAL, one late descriptor after UE start
UE DL/SFN acquisition: PASS
Real RACH config / Msg1: FAIL / VOID
PRACH detector timing evidence: VOID, no Msg1 emitted
```

Lowering the all-timed TX offset from `30 ms` to `10 ms` improves post-SFN
out-of-sync behavior but still does not restore real RACH config or Msg1. The
next changed rung should run a current CP1632-style native-continuous
guard0/no-append control with all-timed chunks disabled. If that current
control again receives real RACH config and emits Msg1, the blocker is tied to
the all-timed real-UE presentation/offset path. If it also fails, the RACH
config regression is broader than all-timed mode and the frontier should pivot
to current UE/gNB SIB/RACH-config observability rather than more offset
bracketing.

Do not rerun CP1665 unchanged, and do not interpret it as a PRACH detector
datapoint.
