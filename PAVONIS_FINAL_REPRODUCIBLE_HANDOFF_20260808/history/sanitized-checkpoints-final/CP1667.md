## Interpretation

The all-timed no-RACH-config failure is not explained by a simple camping TTI
alignment mismatch. CP1665 and CP1666 both show `160` aligned camping trace
rows with `0` mismatches, but CP1665 never receives real RACH config while
CP1666 does.

The out-of-sync count alone is also not sufficient. CP1665 and CP1666 both
have `30` detail-log out-of-sync rows. The difference is placement relative to
usable RACH config: CP1665 never reaches real config before its failure, while
CP1666 receives real config and emits seven Msg1 attempts before its later
out-of-sync burst.

Therefore the all-timed branch appears to preserve PBCH/SFN and the immediate
camping TTI trace but still prevents the UE from receiving or applying the
post-SFN RACH-config/SIB path before it loses sync. CP1666 proves the current
UE/gNB configs can still deliver that config under native-continuous TX.

## Verdict

CP1667 strengthens the CP1666 conclusion: the blocker is specifically the
all-timed real-UE post-SFN downlink/RACH-config path, not a broad current
RACH-config regression and not an obvious first-160-TTI camping mismatch.

Do not spend more RF on all-timed offset-only sweeps unless the run is gated on
real RACH config/Msg1, not only PBCH/SFN or camping alignment. The next changed
work should inspect or instrument the SIB/RACH-config decode path under
all-timed TX, or test a software TX presentation variant that keeps CP1658's
raw PBCH/TRACK quality without breaking the post-SFN SIB/RACH-config window.
