```text

```

The `si_pdcch` trace starts immediately after SFN sync:

```text
slot=3021 sif=1 n_dl=0 candidates=6 max_epre=1.002 max_corr=0.079499
```

and reaches the trace limit at:

```text
slot=3820 sif=0 n_dl=0 candidates=6 max_epre=1.128 max_corr=0.049109
```

Every traced SI-RNTI PDCCH search reported `n_dl=0`; no SI PDSCH grant was
ever produced in the first 800 post-SFN slots.

The detail log is much worse than CP1666:

- `out-of-sync` rows: `5000`
- first row: `[date-redacted]`

## Verdict

CP1670 is a failed positive control. It does not reproduce CP1666's native-
continuous RACH-config/Msg1 success under the new heavy SIB1 trace. Therefore
CP1669's no-SI-grant result is a valid observation of that all-timed run, but
the all-timed presentation is not yet isolated as the cause. The leading risk is
that the CP1668 trace is perturbative, especially the per-slot `si_pdcch`
stderr line emitted during realtime post-SFN processing.

## Next

Do not run more RF with the current per-slot `si_pdcch` trace unchanged.
Patch the trace to be low-impact: keep grant/SIB/RACH-apply events immediate,
but replace per-slot no-grant `si_pdcch` stderr with a sampled or aggregated
counter summary. Rebuild `srsue`, then first rerun the native-continuous
control; only if that recovers CP1666-class SIB1/RACH config should the
all-timed A/B be repeated.
