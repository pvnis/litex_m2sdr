# CHECKPOINT 1703 - OCUDU TX timeout-carry lag-observe build

## Goal

Stay no-RF and close the CP1702 destructive deadline-carry failure mode in
source before any further RF run. CP1702 proved that the `1 ms` deadline cap
kept pending carry small only by deleting almost the whole stream, so CP1703
changes that behavior to observe/report stale carry lag by default and drop
only when explicitly requested.

## Method

Edited only:

```text
ocudu/lib/radio/soapy/radio_soapy_tx_stream.cpp
ocudu/lib/radio/soapy/radio_soapy_tx_stream.h
```

The patch adds:

```text
OCUDU_SOAPY_TX_TIMEOUT_CARRY_DEADLINE_DROP
tx_timeout_carry_deadline_drop_enabled
timeout_carry_deadline_lag_events
timeout_carry_deadline_max_observed_lag_samples
timeout_carry_deadline_would_drop_samples
```

`OCUDU_SOAPY_TX_TIMEOUT_CARRY_DEADLINE_DROP` defaults off. With it off,
`trim_tx_pending_for_lag()` records that the pending queue exceeded
`tx_timeout_carry_max_lag_samples`, records the maximum observed lag and the
number of samples the old policy would have dropped, but leaves the pending
queue intact. With the env enabled, the old destructive drop path remains
available for reproducibility and still fills the existing dropped-sample
counters.

No RF run was performed.

## Conclusion

CP1703 is a no-RF build checkpoint, not a SIB1/PRACH datapoint.

The destructive CP1701/CP1702 deadline-drop policy is no longer default
behavior. Future runs can distinguish three cases:

```text
timeout_carry_deadline_lag_events > 0
timeout_carry_deadline_would_drop_samples > 0
timeout_carry_deadline_dropped_samples > 0
```

The first two mean the TX queue exceeded the lag budget without deleting data.
The last one means an explicitly enabled destructive-drop experiment occurred
and the RF run must be treated as invalid unless that was the checkpoint goal.

Next RF work, if resumed, should gate on these counters and on SI-era
`timeout_carry_pending_samples`, not just stop-time `stream_deficit=0`.
