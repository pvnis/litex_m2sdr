## Source Finding

The local OCUDU source matches the CP1706 hashes, so the inspected code is the
policy that CP1715 tested.

`select_tx_data_write_timeout()` selects:

```text
selected_timeout_us = min(tx_deadline_write_max_timeout_us, guarded_lead_us)
```

where:

```text
guarded_lead_us = (chunk_time_ns - hw_now_ns) / 1000 - tx_deadline_write_guard_us
```

With the CP1715 settings, this allows the direct write to wait up to `50000 us`
for an MTU-class chunk of only about `1022` samples, roughly `88.7 us` at
`11.52 Msps`.

The transmit loop then treats either exhausted guarded lead or a
deadline-controlled timeout as final for that logical buffer:

```text
ret = SOAPY_SDR_TIMEOUT
deadline_write_expired = true
...
deadline_write_abandoned_samples += data_nof_samples - sent_total
return
```

The timeout-carry path is explicitly bypassed in that case. This is why CP1715
has `timeout_carry_queued_chunks=0`, `timeout_carry_drained_chunks=0`, and
`timeout_carry_pending_samples=0`, while `timeout_carry_abandoned_samples`
still rises: the deadline-expired direct-write branch counts unsent logical
tails as abandoned and returns before carry can queue anything.

## Conclusion

CP1716 closes the CP1706 deadline-aware direct-write shape as currently
implemented. It is not a viable next RF/UE gate because the `50000 us`
per-chunk wait can burn the finite TX lead, after which nearly every later
chunk reaches the "guarded lead exhausted" path and is abandoned before LiteX
can see it.

Do not rerun CP1715 unchanged and do not start UE on this TX shape.

The next TX-policy code change should preserve the RF lead instead of spending
large waits on individual ~89 us chunks. A candidate direction is to cap direct
deadline-controlled write polling to the existing short-write class or another
lead-preserving bound, then use explicit counters/gates to distinguish short
poll misses from stale-data drops. That should be designed as a new no-RF
patch/build checkpoint before another UE/SIB1/PRACH run.

Per the user's current hardware update, the next RF action can be a separate
OTA/path smoke with the attenuator installed. That smoke is only a hardware
path check; it should not be treated as a ladder datapoint or as a validation
of CP1706 deadline-write.
