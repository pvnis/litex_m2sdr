## Purpose

bladeRF, Android, or any hardware-affecting command.

## Source Findings

`radio_soapy_tx_stream.cpp` records three different sample domains:

- `stream_samples`: logical transmit duration, including native-continuous
  empty/gap spans.
- `data_samples`: non-empty logical data presented by the upper layer.
- `requested_samples` / `returned_samples`: samples actually requested from
  and accepted by Soapy `writeStream()` calls.

Therefore CP1723's `stream_deficit = stream_samples - returned_samples` is
not a pure direct-write deficit in sparse reanchor/native-continuous modes. At
stop time CP1723 reports:

- `stream_samples=742037610`
- `data_samples=189861120`
- `samples_req=1372848`
- `samples_ret=1032284`
- `stream_deficit=741005326`
- direct requested/write returned deficit:
  `samples_req - samples_ret = 340564`

So the field name can overstate the direct write shortfall. That is an
accounting ambiguity in the gate/reporting, not a pass condition.

The real CP1723 failure is the ordered carry queue latch:

- `transmit()` drains pending chunks at call start when the queue is non-empty.
- If the queue remains non-empty, subsequent current chunks are queued behind
  it instead of being written directly.
- `trim_tx_pending_for_lag()` only observes stale lag while
  `OCUDU_SOAPY_TX_TIMEOUT_CARRY_DEADLINE_DROP=0`; it increments
  lag/would-drop counters but leaves the stale queue in place.
- `queue_tx_pending_chunk()` caps the queue at
  `tx_timeout_carry_max_samples=1152000`; once full, later chunks overflow and
  are abandoned.

The CP1723 log shows this latch starts immediately:

- first periodic summary (`logical=100`):
  - `samples_req=507900`, `samples_ret=473298`
  - direct write deficit `34602`
  - `timeouts=33`, `partial_ret=2`
  - `timeout_carry_pending_samples=678552`
  - `timeout_carry_deadline_lag_events=899`
  - `timeout_carry_deadline_would_drop_samples=863338`
- second periodic summary (`logical=200`):
  - `writes` still `527`
  - queue almost capped at `1151894`
  - overflow and abandonment already started:
    `timeout_carry_overflow_samples=60298`,
    `timeout_carry_abandoned_samples=678658`
- strict-gate periodic summary:
  - `timeout_carry_pending_samples=1152000`
  - `timeout_carry_abandoned_samples=712613636`
  - `timeout_carry_overflow_samples=63219898`
  - `timeout_carry_deadline_lag_events=63252`
  - `timeout_carry_deadline_would_drop_samples=59591476`
- stop summary:
  - `timeouts=472`, `partial_ret=6`
  - `timeout_carry_pending_samples=593930`
  - `timeout_carry_max_pending_samples=1152000`
  - `timeout_carry_abandoned_samples=740411396`
  - `timeout_carry_overflow_samples=65685984`
  - `timeout_carry_drain_timeouts=471`

CP1720's new carry-on-timeout feature works only in the narrow sense:
`deadline_write_timeouts=1`, `deadline_write_carry_timeouts=1`,
`deadline_write_abandoned_samples=0`, and `deadline_write_breaks=0`.
It changes the first failure from immediate deadline-write abandonment into
ordered carry backlog. That backlog then saturates and abandons the stream.

## HAS_TIME Path Audit

The CP1718 no-RF audit remains valid and CP1723 does not contradict it:

- OCUDU all-timed mode marks every non-empty MTU chunk with
  `SOAPY_SDR_HAS_TIME`; at `11.52 Msps`, the `1022`-sample MTU is about
  `88.7 us`.
- Periodic reanchor marks only chunks whose logical start crosses the interval,
  so CP1723 has sparse `has_time_writes=5` / `reanchor_writes=3215` at stop,
  not dense all-timed descriptors.
- LiteX's PCIe path uses a looping descriptor ring. The driver clears consumed
  `HAS_TIME`/EOB header bits after the FPGA reader has consumed each slot so
  later loop reads are untimed.
- `_dmaReleaseWrite()` maps post-dedup `HAS_TIME` to bit 63 in the DMA header
  and writes the timestamp in sample units.
- `timed_tx.py` pushes one descriptor per DMA frame when a header is extracted;
  untimed descriptors pass through immediately, while timed descriptors wait on
  `sample_count >= ts`. The timestamp FIFO is only `32` entries and the data
  FIFO defaults to `512`.

This explains the family split:

- native single-anchor avoids ongoing timed-descriptor pressure but drifts;
- all-timed preserves timing but stresses the timed-descriptor/ring path;
- 20 ms reanchor stabilizes two-point marker timing, but still causes timeout
  pressure by CP1718 and, with carry-on-timeout enabled in CP1723, falls into a
  persistent carry queue.

## Verdict

CP1725 closes CP1723 as a real queue-latch/backpressure failure plus a reporting
ambiguity. CP1723 was not only a bad gate name: even after separating direct
`samples_req - samples_ret`, the run has immediate timeout-carry backlog,
queue cap saturation, deadline lag/would-drop, overflow, abandonment, and
pending samples at stop.

Do not rerun CP1723 unchanged, do not start UE on this shape, and do not [interface-redacted]
only the CP1723 constants. The next changed work should either:

- add explicit diagnostic/gate fields separating logical stream deficit,
  non-empty data deficit, and direct write-return deficit, or
- change the TX presentation/policy materially so stale carry cannot latch the
  current stream while preserving CP1658-class timing.
