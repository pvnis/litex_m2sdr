ladder.

deadline-write policy branches so they cannot mask the CP1658 baseline:

- `UE_STARTED=0`
- post `[host-redacted]` helper SSH: pass

Readback matched the intended baseline shape:

- native continuous/discontinuous off
- all-timed chunks on
- re-anchor off

was too strict and treated `logical_data_deficit=-538721040` as a failure. That
field is diagnostic-noisy in this mode because `data_samples` and
`data_samples_ret` count different levels of chunking. The gate was corrected
and rerun offline on the fetched gNB log without any additional RF.

## Interpretation

CP1729 clears the CP1727 stale-carry-latch failure mode when the later
backpressure policies are disabled. It does not meet a strict zero-returned
sample criterion, but its residual direct deficit is CP1658-class rather than a
runaway carry queue: there is no retry/carry/deadline backlog, no overflow, no
abandonment, and no LiteX late evidence.

This is not a SIB1, PRACH, UE, or raw-TRACK datapoint. It only says the current
binary can still run a CP1658-compatible no-UE TX baseline for the next RF
ladder step.

Next valid ladder move should re-measure the raw scheduled-TRACK gate using the
CP1658 cadence on the current binary before starting real-UE/SIB1/PRACH work.
