# CHECKPOINT 1746 - No-RF gNB SI demarginalization YAML audit

Date: [date-redacted]

## Purpose

After CP1745 failed SIB1 with `write_timeout_us=1000`, stay no-RF and prepare a
configuration-level SI robustness test for the current CP1733/CP1658 all-timed
`30 ms` real-UE path.

The requested direction was to de-marginalize SIB1/SI-PDCCH before spending
more RF on the parked `321600` PRACH-window test.

## Source audit

The current generated M2SDR gNB YAML starts from:

`litex_m2sdr/litex_m2sdr/software/validation/ocudu/configs/gnb_m2sdr_band3_ota.template.yml`

That template has no explicit `pdcch`, `pdsch`, or `ssb` sections. The CP1733
runner previously patched only TX/RX gain, backoff, and `tx_mode: continuous`.

Supported YAML knobs found in OCUDU source/examples:

- `cell_cfg.pdcch.common.ss0_index`
- `cell_cfg.pdcch.common.coreset0_index`
- `cell_cfg.pdcch.common.max_coreset0_duration`
- `cell_cfg.pdcch.dedicated.ss2_type`
- `cell_cfg.pdcch.dedicated.dci_format_0_1_and_1_1`
- `cell_cfg.pdsch.fixed_sib1_mcs`
- `cell_cfg.ssb.ssb_block_power_dbm`

The srsUE example config uses:

```yaml
pdcch:
  dedicated:
    ss2_type: common
    dci_format_0_1_and_1_1: false
  common:
    ss0_index: 0
    coreset0_index: 12
pdsch:
  mcs_table: qam64
```

Important limit: SI DCI aggregation is not currently a YAML key in this tree.
The translator hard-codes:

```cpp
out_cfg.si.sib1_dci_aggr_lev = aggregation_level::n4;
```

So CP1746 stays YAML-only and does not raise SI aggregation beyond `n4`. A real
aggregation-level change would require a source patch or a new YAML-facing knob.

## Script changes

Patched:

- `cp1660_run_gnb_b3_txatt5_nativecontinuous_alltimed_lead30ms_stage6_prachtrace_detached.sh`
- `cp1733_run_stage6_currentbinary_cp1658cadence_realue_sib1_rachconfig.sh`

The new knobs are default-off:

- `GNB_SRSUE_PDCCH_COMPAT=1`
- `GNB_CORESET0_INDEX=<value>`
- `GNB_SS0_INDEX=<value>`
- `GNB_MAX_CORESET0_DURATION=<value>`
- `GNB_FIXED_SIB1_MCS=<value>`
- `GNB_SSB_BLOCK_POWER_DBM=<value>`

The remote [host-redacted] environment names are the same with the `PAVONIS_GNB_` prefix.
When `GNB_SRSUE_PDCCH_COMPAT=1`, the CP1733 wrapper fills empty
`GNB_CORESET0_INDEX` / `GNB_SS0_INDEX` as `12` / `0` before exporting to [host-redacted].

Also added `PAVONIS_GNB_CONFIG_ONLY=1` to the gNB-start helper. In that mode it
generates and prints the run YAML, then exits before starting the OTA harness or
opening an RF TX window.

Local syntax checks passed:

- `bash -n cp1660_run_gnb_b3_txatt5_nativecontinuous_alltimed_lead30ms_stage6_prachtrace_detached.sh`
- `bash -n cp1733_run_stage6_currentbinary_cp1658cadence_realue_sib1_rachconfig.sh`

## [host-redacted] config-only check

No RF TX was started.

Uploaded the patched helper to [host-redacted] and ran:

- `PAVONIS_GNB_CONFIG_ONLY=1`
- `PAVONIS_GNB_SRSUE_PDCCH_COMPAT=1`
- `PAVONIS_GNB_FIXED_SIB1_MCS=0`
- `PAVONIS_GNB_SSB_BLOCK_POWER_DBM=-4`
- `TX_ATT=5`
- `TX_BACKOFF=10`
- `GNB_RX_GAIN=40`

The config-only run returned `WRAPPER_RC=0` and printed:

- `pavonis_gnb_demarginalization_yaml=1`
- `MARKED_TX_DETACHED_RC=0`
- `TX_READBACK_MISSING=1`, expected because no RF/gNB stream was started

Generated YAML proof:

```yaml
cell_cfg:
  ...
  pdcch:
    dedicated:
      ss2_type: common
      dci_format_0_1_and_1_1: false
    common:
      ss0_index: 0
      coreset0_index: 12
  pdsch:
    fixed_sib1_mcs: 0
  ssb:
    ssb_block_power_dbm: -4
  prach:
    prach_config_index: 1
```

No separate no-RF `gnb --validate-config` mode was found in the source audit;
CLI parsing and full validation happen on normal gNB start. The next RF run
must therefore treat gNB start/readback as the first gate.

## Interpretation

CP1746 creates a controlled YAML-only demarginalization rung:

- srsUE-compatible PDCCH common/dedicated block
- SIB1 MCS lowered from the default `5` to `0`
- SSB block power raised from default `-16 dBm` to `-4 dBm`

This is not a PRACH datapoint and does not alter the parked `321600` collection
delay hypothesis. The next valid RF checkpoint should run the CP1733/no-delay
real-UE shape with these config knobs and first require gNB start/readback and
normal PBCH/SFN/SIB1/Msg1 supply before interpreting PRACH.
