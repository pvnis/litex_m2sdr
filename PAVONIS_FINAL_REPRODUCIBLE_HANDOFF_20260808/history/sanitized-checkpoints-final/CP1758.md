## RX Append Result

The same-device append path itself did work:

- `pavonis_soapy_rx_append_p0.cf32`: `816000000` bytes
- `pavonis_soapy_rx_append_meta.tsv`: `64671672` bytes
- `pavonis_soapy_rx_readback.txt`: `1410` bytes
- [host-redacted] tar: `130015213` bytes
- summary JSON found `soapy_rx_append_cf32=1`
- readback: `rx_use_read_stream=1`, `rx_format=CS16`,
  `PAVONIS_SOAPY_RX_DUMP_ARM_FILE` set to the PRACH arm file,
  append armed, `overflows=0`
- RX readback center/gain: `1747500000 Hz`, `11.52 Msps`,
  `30.72 MHz`, gain `71 dB`, auto gain mode
- append metadata has timed readStream chunks with contiguous `ret_ts`
  increments of `510` samples

However the requested `230400000` sample append cap was not reached. The
append stopped after `200000` receive rows, each `510` samples, for
`102000000` complex samples (`8.854167 s`). The immediate cause is that
`radio_soapy_rx_stream.cpp` gates the append writer inside the
`PAVONIS_SOAPY_RX_SUMMARY_MAX` row limit, and the harness did not raise that
summary limit when enabling the append.

## Conclusion

CP1758 is a mechanically clean but void no-Msg1 RF run. Do not use it as
PRACH timing evidence and do not [interface-redacted] `PRACH_COLLECTION_DELAY_SAMPLES` from it.

The append instrumentation is viable, but before retrying the real-UE
measurement, fix the harness so `PAVONIS_SOAPY_RX_SUMMARY_MAX` is high enough
for the intended append duration. Then rerun the same measurement shape with
`GNB_POWER_CONTROL_OFFSET_SS_DB=6`, `PRACH_COLLECTION_DELAY_SAMPLES=0`, append
enabled, and no delay-constant change.
