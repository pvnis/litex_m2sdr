# CHECKPOINT 1776 - No-RF Accepted PRACH To RAR Path Trace

Date: [date-redacted]

## Goal

Trace CP1775's accepted PRACH detections from the detector upward into
FAPI/MAC/scheduler without running RF. Determine whether accepted p0 results
are dropped because of stale nominal occasion timing, expired
`ra-ResponseWindow`, delay/TA bounds, or another filter.

## Source Path

The accepted count in `/tmp/pavonis_prachdet_trace.log` is not just a sidecar
threshold marker. In `prach_detector_generic_impl.cpp`, the trace field
`accepted` is `result.preambles.size()`, and entries are only added when:

```text
peak > threshold
delay < max_delay_samples * 0.8
```

CP1775's real accepted p0 rows all satisfy the delay limit:

```text
sfn=705 slot=4 p0_delay=25 p0_ratio=2.378 accepted=1
sfn=817 slot=4 p0_delay=10 p0_ratio=1.300 accepted=1
sfn=129 slot=4 p0_delay=23 p0_ratio=2.274 accepted=1
sfn=241 slot=4 p0_delay=37 p0_ratio=2.218 accepted=1
delay_limit=104.80
```

The lower/upper path is:

```text
prach_processor_worker::notifier->on_rx_prach_window(buffer, prach_context)
processor_notifier_adaptor::prach_adaptor::on_rx_prach_window()
ru_lower_phy_rx_symbol_adapter::on_rx_prach_window()

uplink_processor_impl::process_prach()
prach->detect(...)
upper_phy_rx_results_notifier::on_new_prach_results()

mac_cell_rach_handler_impl::handle_rach_indication()
ra_scheduler::handle_rach_indication()
ra_scheduler::run_slot()
```

There is no source-level age filter in `process_prach()` beyond the local
state-machine admission check, and CP1775 proves the accepted events reached
the scheduler.

## Interpretation

The accepted PRACH result is not dropped by:

- the PRACH detector delay gate: accepted rows have `p0_pass_delay=1`;
- FAPI negative-TA filtering: `time_advance` is positive;
- MAC TC-RNTI allocation: the scheduler event log shows TC-RNTIs
  `0x4601..0x4604`;
- PDCCH/PDSCH/PUSCH resource allocation: every expired-RAR warning has
  `failed_attempts={pdcch=0, pdsch=0, pusch=0}`.

The actual drop point is the RA scheduler's RAR expiry path:

```text
ra_scheduler::update_pending_rars()
```

The result is attributed to the original nominal PRACH occasion
(`prach_slot=705.4`, `817.4`, `129.4`, `241.4`) even though the delayed
collection/demodulation result reaches the scheduler around `36..37` slots
later (`slot_tx=709.0`, `821.1`, `133.1`, `245.0`). The RAR window in this
configuration is `10` slots long, e.g. `[705.5..706.5)`, so the scheduler
expires the pending RAR before trying any allocation.

This matches the CP1770/CP1775 timing class: `352536` samples at
`11.52 Msps` is about `30.6 ms`, and the remaining few milliseconds are
collection/demod/scheduler latency. The diagnostic delayed collection recovers
p0 detection, but it necessarily makes the result stale relative to the
nominal scheduler occasion.

## Decision

Do not [interface-redacted] the PRACH detection window further. CP1775 already supplies
accepted real p0 detections.

A naive result-slot-attribution patch is unsafe as the ladder fix: simply
changing `prach_slot_rx` affects RA-RNTI/window semantics and can make the gNB
schedule a RAR that is inconsistent with the UE's actual RA response window.

The next source-level fix should move or compensate the UL/RACH timing
reference by the TX offset, so that the gNB can collect the RF-delayed PRACH
samples while handing MAC/scheduler a timely event for the UE's RA response
window. If a smaller diagnostic patch is used first, it must explicitly
separate the RA-RNTI origin slot from the RAR scheduling/window slot; do not
blindly overwrite the PRACH occasion slot.
