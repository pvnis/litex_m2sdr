## CP1775 no-RF path trace

The source path is direct:

- `prach_processor_worker` can delay collection, then notifies upstream with a
  `prach_buffer_context`. In the CP1779 path, the notified context slot is
  shifted by `timing_compensation_report_slot_offset`.
- `uplink_processor_impl::process_prach()` assigns that context to
  `ul_results.context` and calls `prach->detect(...)`.
- `phy_to_fapi_results_event_fastpath_translator::on_new_prach_results()`
  drops only empty detections or negative-TA preambles; otherwise it emits
  `RACH.indication` using `result.context.slot`.
- MAC copies this to scheduler `slot_rx` and allocates TC-RNTI for
  contention-based preambles.
- `ra_scheduler` derives RA-RNTI and the RAR window from `msg.slot_rx`, then
  expires pending RARs in `update_pending_rars()` if the PDCCH slot is outside
  the window.

CP1775 accepted real preamble-0 rows:

```text
row 62:  sfn=705 slot=4 p0_ratio=2.378 p0_delay=25 accepted=1
row 69:  sfn=817 slot=4 p0_ratio=1.300 p0_delay=10 accepted=1
row 90:  sfn=129 slot=4 p0_ratio=2.274 p0_delay=23 accepted=1
row 97:  sfn=241 slot=4 p0_ratio=2.218 p0_delay=37 accepted=1
```

Those were not dropped before scheduler. CP1775's verbose gNB log shows:

```text
prach_slot=705.4 slot_tx=709.0 window=[705.5..706.5) tc-rnti=0x4601
prach_slot=817.4 slot_tx=821.1 window=[817.5..818.5) tc-rnti=0x4602
prach_slot=129.4 slot_tx=133.1 window=[129.5..130.5) tc-rnti=0x4603
prach_slot=241.4 slot_tx=245.0 window=[241.5..242.5) tc-rnti=0x4604
```

Each expired with:

```text

```

So CP1775 was not blocked by detector delay/TA bounds, FAPI negative-TA
filtering, MAC TC-RNTI allocation, or scheduler resource allocation. The result
was accepted and then scheduled against a stale RAR response window because the
delayed collection still reported the nominal PRACH occasion.

## Interpretation

The requested CP1775 trace proves the accepted PRACH detections were not lost;
they were stale at RAR scheduling because the nominal PRACH occasion was about
30.6 ms behind the delayed collection window.

CP1781 validates the coherent timing-compensation branch: when
`GNB_PRACH_TIMING_COMPENSATION_SAMPLES=352536` is active, accepted real p0
rows are attributed far enough forward to schedule RAR and Msg3 without the
CP1775 stale-window expiry.

Therefore the immediate blocker is no longer the PRACH collection window,
accepted-result handoff, or RAR scheduling window. The active frontier is
Msg3/PUSCH: either the UE is not actually receiving/using the RAR as expected,
or the Msg3 UL timing/power/reference remains wrong after the PRACH-only timing
compensation.
