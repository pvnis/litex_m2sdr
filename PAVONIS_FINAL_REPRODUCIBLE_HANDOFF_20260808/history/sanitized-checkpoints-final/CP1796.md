# Checkpoint 1796 - No-RF Global Offset Timing Audit

Date: [date-redacted] Europe/Zurich

## Purpose

Audit the source-level timing path after CP1795 before spending another RF run.
The question is whether the active CP1795 setting,
`PAVONIS_LOWER_PHY_UL_RX_TIMESTAMP_OFFSET_SAMPLES=-352536`, is equivalent to
the CP1779/CP1794 compensation path that already moved accepted PRACH rows into
RAR scheduling.

## Inputs

CP1794 is the current positive-control RF baseline for the new binary:

```text
PAVONIS_LOWER_PHY_UL_RX_TIMESTAMP_OFFSET_SAMPLES=0
GNB_PRACH_TIMING_COMPENSATION_SAMPLES=352536
PRACH_COLLECTION_EXTRA_SAMPLES=12000
GNB_POWER_CONTROL_OFFSET_SS_DB=6
```

It decoded SIB1/RACH config, emitted seven UE Msg1 attempts, and the gNB saw a
real preamble-0 accept reach RAR plus Msg3 PUSCH receive attempts. The UE still
did not log `Setting RAR Grant`, `Set TA RAR`, or Msg3 preparation.

CP1795 ran the requested nonzero global-offset shape:

```text
PAVONIS_LOWER_PHY_UL_RX_TIMESTAMP_OFFSET_SAMPLES=-352536
GNB_PRACH_TIMING_COMPENSATION_SAMPLES=0
PRACH_COLLECTION_DELAY_SAMPLES=0
PRACH_COLLECTION_EXTRA_SAMPLES=0
GNB_POWER_CONTROL_OFFSET_SS_DB=6
```

The knob was active and TX gates were clean, but the run was void for RAR/Msg3:
the UE had one PBCH-positive cell-search hit, then failed SFN sync, decoded no
SIB1/RACH config, and emitted no Msg1. The gNB log still showed stale false
PRACH rows with `Could not transmit RAR within the window`.

## Source Path

The global offset parser and signed helper are in
`ocudu/lib/phy/lower/lower_phy_baseband_processor.cpp` lines 39-61. Negative
values subtract from the hardware RX timestamp:

```text
offset >= 0 -> timestamp + offset
offset < 0  -> timestamp - abs(offset)
```

The offset is applied in `ul_process()` before SFN0 normalization and before
the lower uplink processor:

```text
rx_metadata.ts -> ul_rx_ts -> apply_timestamp_sfn0_ref(ul_rx_ts)
uplink_processor.process(..., adjusted_rx_ts)
```

This is at `lower_phy_baseband_processor.cpp` lines 203-218 and 306-312. The
raw `last_rx_timestamp` remains `rx_metadata.ts + rx_buffer_samples` at lines
218-221, so DL/TX throttling was intentionally left on the raw timestamp path.

`apply_timestamp_sfn0_ref()` in
`lower_phy_baseband_processor.h` lines 173-181 wraps timestamps below
`start_time_sfn0` forward by a hyperframe before subtracting `start_time_sfn0`.
Therefore a negative offset is not just a local sample delta near startup; it
can also change the normalized slot phase through that wrap logic.

The downlink path still uses the unshifted timestamp:

```text
downlink_processor.process(apply_timestamp_sfn0_ref(timestamp))
result.metadata.ts = timestamp + tx_time_offset
```

That is `lower_phy_baseband_processor.cpp` lines 168-174. Downlink TTI
boundaries are generated in `downlink_processor_baseband_impl.cpp` lines
130-135 from that downlink slot path.

The lower uplink slot is derived directly from the shifted timestamp in
`uplink_processor_impl.cpp` lines 126-161. That same `current_slot` is used for
PRACH symbol context at lines 386-389 and for UL half/full-slot notifications
at lines 421-430.

The CP1779 PRACH-specific compensation does two separate things in
`prach_processor_worker.cpp`:

```text
collection_delay_samples = compensation_samples
notify_context.slot += compensation_samples / samples_per_slot
```

The delay/slot-offset pieces are visible at lines 535-550 and 245-248. For the
measured `352536` samples at `11.52 Msps` and 15 kHz SCS, this is `30` slots
plus `6936` residual samples.

Once a PRACH result is accepted, the reported slot is carried upward unchanged:

```text
upper PHY: ul_results.context = context
FAPI: builder.set_slot_point(result.context.slot)
MAC: rar_req->prach_slot_rx = msg.slot_rx
MAC: rar_req->rar_window_ref_slot = msg.slot_rx + pavonis_rar_window_offset_slots
```

These are in `upper/uplink_processor_impl.cpp` lines 240-245,
`phy_to_fapi_results_event_fastpath_translator.cpp` lines 59-76, and
`ra_scheduler.cpp` lines 258-316. The stale warning in `ra_scheduler.cpp` lines
462-484 fires when the current PDCCH slot is already beyond that computed RAR
window.

## Finding

The CP1795 lower-PHY setting `-352536` is not source-equivalent to the CP1779
path that passed PRACH-to-RAR scheduling.

CP1779/CP1794 delayed the PRACH collection window by `352536` samples and then
reported the accepted result about `30` slots later. That matched the measured
RF sample-domain latency and avoided stale RAR windows for real preamble-0
accepts.

CP1795 instead labeled each received UL sample about `30.6 ms` earlier before
the lower uplink processor derived `current_slot`. With PRACH-specific
compensation disabled, this removes the explicit delayed collection plus
forward report-slot behavior that made CP1779 work. If a sample physically
arrives late because live downlink RF is delayed, subtracting the offset maps
that sample back toward the nominal pre-delay slot rather than toward the
currently schedulable RF-time slot.

The split is also broader than PRACH: the shifted uplink timestamp changes
PRACH/PUSCH/PUCCH/SRS symbol context and UL half/full-slot notifications, while
the downlink TTI and transmit timestamp path remain raw. CP1795's SFN-sync
regression and stale false RAR-window warnings are consistent with this being
an unsafe mixed timebase, not just an unlucky no-Msg1 datapoint.

## Conclusion

CP1795 remains void for the user-requested UE RAR/Msg3 verdict because no Msg1
was emitted. However, this no-RF audit rejects rerunning the exact
`-352536` lower-PHY timestamp-offset shape unchanged as the next best step:
the source semantics do not match the already validated CP1779 compensation
semantics.

Do not [interface-redacted] `PRACH_COLLECTION_DELAY_SAMPLES`, `PRACH_COLLECTION_EXTRA_SAMPLES`,
or scheduler-only RAR offset from CP1795/CP1796. The next useful work is a
source-level global timing fix that preserves CP1794's zero-offset/no-op RF
baseline but generalizes CP1779's sample-domain compensation coherently across
uplink channels: delay/listen at the measured RF-late sample time and report or
schedule against the corresponding RF-time slot, rather than subtracting that
latency from the lower-PHY RX timestamp.
