# CHECKPOINT 1805 - RAR PDCCH TX Lead No-RF Audit

Date: [date-redacted]

## Goal

Explain CP1804's first valid UE-side RAR trace result without spending another RF run:
SIB1/RACH config and seven Msg1 attempts were present, the gNB accepted two real p0
PRACH rows and scheduled RAR/Msg3 attempts, but the UE never decoded RA-RNTI PDCCH.

## What Passed

- CP1804 remains a valid trace baseline:
  - UE decoded SIB1/RACH config.
  - UE emitted seven `Random Access Transmission` / `PRACH-TX` rows.
  - UE opened seven RA response windows and made `77` RA-RNTI PDCCH checks.
  - gNB accepted two real preamble-0 rows and scheduled RAR plus Msg3 receive attempts for
    `0x4602` and `0x4603`.
- Source-level search-space audit did not find an obvious RA search-space mismatch:
  - OCUDU uses RA search-space ID `1`, CORESET0, one AL4 candidate, CCE0, DCI format `1_0`.
  - srsUE copies SIB1 `ra_search_space`, forces common type 1, searches only that RA space
    for RA-RNTI, and records one candidate per CP1804 RA check.
  - OCUDU and srsUE RA-RNTI DCI 1_0 packing both include frequency assignment, time resource,
    VRB mapping, MCS, TB scaling, and 16 reserved bits.

## What Failed

- Every CP1804 UE RA-RNTI PDCCH check still had `n_dl=0`; no UE RA DCI, RA PDSCH grant,
  RAR grant, TA, or Msg3-preparation marker was observed.
- The decisive timing join shows a TX-lead problem, not a simple search-space problem:
  - SIB1 control: gNB generated SIB1 slot `[0.1]` at `[date-redacted]`; UE decoded SI PDCCH
    as slot `1` at `[date-redacted]`, about `+32.7 ms` later. Repeated SIB1 tolerates
    this live TX lead.
  - First real RAR: UE PRACH `tti=2254` was transmitted at `[date-redacted]`.
    UE RA window checks ran for slots `2257..2267` starting around `[date-redacted]`.
    The gNB scheduled the matching RA PDCCH at host log slot `[229.0]` at
    `[date-redacted]`. With the same live TX lead class, the RF RAR would arrive around
    `[date-redacted]`, after the UE's 10-slot RA response window.
  - Second real RAR is the same class: UE `tti=5614`, UE window `5617..5627`, gNB RAR
    host slot `[565.1]` at `[date-redacted]`; estimated RF arrival is again outside the
    10-slot UE RA response window.
- The gNB Msg3 CRC-KO rows remain scheduled receive attempts after local RAR scheduling,
  not proof that the UE decoded RAR or transmitted Msg3.

## Conclusion

CP1804 is best explained by live all-timed downlink TX lead/pipeline latency exceeding the
configured `ra_resp_window=10` slots. The UE is opening the right RA-RNTI window for its
own PRACH, but the corresponding live RF RAR is generated far enough ahead in gNB host slot
time that it reaches the UE after the 10 ms response window has already closed.

This is not another PRACH collection delay, extra-width, or scheduler-only RAR-offset knob.
The next decisive RF test should keep the CP1804/CP1794 positive-control shape and advertise
a longer UE RA response window, preferably `ra_resp_window=40`, then judge on:

- UE `ra_pdcch_dci > 0`
- UE `Setting RAR Grant`
- UE `Set TA RAR`
- UE Msg3 preparation marker
- gNB Msg3 CRC

## Implementation Note For Next Checkpoint

OCUDU supports ASN.1 `sl40`/`sl80`, and the CLI schema accepts `ra_resp_window` values
`1/2/4/8/10/20/40/80`, but the current licensed-band config validator rejects windows above
10 ms. A diagnostic-only env-gated validator bypass or equivalent is needed before the
`ra_resp_window=40` RF test can run on band 3.

- Do not [interface-redacted] `PRACH_COLLECTION_DELAY_SAMPLES`, `PRACH_COLLECTION_EXTRA_SAMPLES`, or
