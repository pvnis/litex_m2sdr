# CP1810 - CP1808 RAR Handoff No-RF Audit

Date: [date-redacted] Europe/Zurich

## Goal

Audit CP1808 without new RF to explain why the UE decoded one RA-PDSCH with
CRC OK but still emitted no `Setting RAR Grant`, no `Set TA RAR`, and no Msg3
preparation marker.

## Findings

CP1808's gNB side is valid through RAR scheduling. The binary-safe gNB log has
the real preamble-0 accept and RAR at the exact UE RA-PDSCH slot:

```text
[501.0] PRACH: ... detected_preambles=[{idx=0 ...}]
[501.1] Processed slot events pci=1: prach(ra-rnti=0x39 preamble=0 tc-rnti=0x4601)
[501.1] Slot decisions pci=1 ... RAR: ra-rnti=0x39 rb=[0..3) tbs=9
[501.1] PDSCH: rnti=0x0039 ...
[501.1] PDCCH: rnti=0x0039 ss_id=1 format=1_0 cce=0 al=4
```

The gNB then schedules Msg3 receive attempts for `0x4601`, starting at slot
`501.7`, and all observed attempts are CRC KO. This means CP1808 is not blocked
at detector-to-RAR scheduling.

The UE side reaches the same RA-RNTI slot and decodes the RA-PDSCH:

```text
PAVONIS_SRSUE_RAR_TRACE event=ra_pdcch ... slot=5011 rnti=0x39 n_dl=1 ... max_corr=0.725194
PAVONIS_SRSUE_RAR_TRACE event=ra_pdsch_grant ... slot=5011 rnti=0x39 ... tbs_bits=72
PAVONIS_SRSUE_RAR_TRACE event=ra_pdsch_decode ... slot=5011 rnti=0x39 ... crc=1 tbs_bytes=9
```

The UE trace just before this slot reports `state=4`, and source enum mapping
shows `4 == WAITING_FOR_RESPONSE_RECEPTION`. Therefore the UE was still inside
the intended RA response state when it searched and decoded the RA transport
block.

The UE config sets `all_level = error`, and `ue_ota.detail.log` contains only
the wrapper command line. Existing `logger.info`/`logger.warning` lines from
RAR parsing and RA state handling were not captured. The configured UE MAC PCAP
was not included in the fetched [host-redacted] tarball, so CP1808 artifacts do not
currently expose the RAR payload bytes.

Source path:

- `cc_worker::decode_pdsch_dl()` sets `mac_dl_result.ack` from
  `pdsch_res.tb[0].crc` and passes the payload to `phy.stack->tb_decoded(...)`
  when CRC is true.
- `mac_nr::tb_decoded()` should call `proc_ra.handle_rar_pdu(result)` when
  `proc_ra.has_rar_rnti()` and `grant.rnti == proc_ra.get_rar_rnti()`.
- `proc_ra_nr::ra_response_reception()` only installs the grant, TA, and Msg3
  when the decoded RAR PDU unpacks and contains a RAPID matching
  `preamble_index`.

## Conclusion

CP1808 moves the active failure point to the UE-side RAR handoff:

1. MAC did not dispatch the decoded RA-RNTI TB to `proc_ra`, or
2. `proc_ra` received it but unpack failed, or
3. the RAR unpacked but no subPDU RAPID matched the UE's `preamble_index=0`, or
4. the decoded payload was a rare CRC-positive but semantically wrong RAR.

The gNB accepted-p0-to-RAR "missing log" discrepancy is closed: the normal gNB
log does contain the RAR scheduling evidence when searched as binary-safe text.
