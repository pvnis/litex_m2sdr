# CP1819 - Low-Impact Trace-Off Control Voids At Pre-UE TX-Late Gate

Date: [date-redacted] Europe/Zurich

## Goal

Run the CP1818-recommended control on the CP1816 low-impact `srsue` binary:
disable only the RAR trace environment while keeping the same
`ra_resp_window=40` RF shape. This was meant to separate a persistent trace-on
effect from current SIB1/RF scatter or a CP1816 binary regression.

Key settings:

- `PAVONIS_SRSUE_RAR_TRACE=0`
- `PAVONIS_SRSUE_RAR_TRACE_LIMIT=0`
- `PAVONIS_SRSUE_RAR_WINDOW_TRACE=0`
- all-timed/native-continuous gNB TX, PCOSS `+6`
- PRACH timing compensation `352536`, extra `12000`
- lower-PHY global offset `0`

## Result

CP1819 is void before UE startup. Both NUC SSH preflights passed, gNB start and
the initial TX readback gate passed, but the strict pre-UE TX-late gate failed
after the 60 s delayed wait:

```text

```

## Interpretation

CP1819 does not answer the CP1818 trace-off control question. The strict gate
correctly prevented starting the UE once the all-timed TX path showed a pre-UE
release-late event.

Together with CP1817, this is the second recent run in the CP1816/CP1818
validation branch to void at the same pre-UE late gate. CP1818 still shows the
same shape can pass that gate, so this is intermittent rather than a hard
startup failure. A same-shape trace-off retry is still the direct control, but
if another retry also fails before UE start, stop burning RF on RAR trace
controls and inspect the recurring all-timed pre-UE late-gate condition.

## Conclusion

CP1819 is a strict-gate void, not a RAR/SIB1 datapoint. The next valid RF move
is one same-shape trace-off retry on the CP1816 binary; a repeated pre-UE late
void should switch the branch to TX-health diagnosis before further UE/RAR
controls.
