## Interpretation

Saved config, wrapper env, generated gNB YAML, UE config radio parameters, and
TX-health counters do not explain the CP1815-vs-CP1820 SIB1 split. The only
clear no-RF discriminator is the UE build/source generation:

- CP1815 used the CP1811 UE binary, with RAR trace disabled at runtime.
- CP1820 used the CP1816 low-impact UE binary, also with RAR trace disabled.

This does not prove CP1816 caused the no-SIB1 result, because this branch has
known SI/SIB1 RF scatter. But it is now the leading source-level variable to
audit before more RF: CP1816 changed `mac_nr.cc`, `proc_ra_nr.cc`, and
`cc_worker.cc`, and trace-off mode should be a no-op for pre-SIB1 behavior if
the low-impact patch is clean.

## Conclusion

Do not run another RAR-handoff RF attempt from CP1820. Next stay no-RF and
compare CP1816 source against the CP1816 backup/CP1811 source state, especially
the `cc_worker.cc` addition and any trace-off path that can execute before or
during SIB1 acquisition. If that audit finds no plausible always-on effect,
the next RF control should be explicitly framed as SI/SIB1 scatter/binary
A/B, not as a RAR handoff datapoint.
