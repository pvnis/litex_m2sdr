## Source Findings

The CP1816 source delta is narrow:

- `PAVONIS_SRSUE_RAR_TRACE` enable state is cached once per process instead of
  checking `getenv()` on every trace opportunity.
- `PAVONIS_SRSUE_RAR_TRACE_LIMIT` is cached once per process.
- A new `PAVONIS_SRSUE_RAR_WINDOW_TRACE` gate was added.
- High-volume RA-window summary events are now behind both
  `PAVONIS_SRSUE_RAR_TRACE` and `PAVONIS_SRSUE_RAR_WINDOW_TRACE`:
  `dl_sched_rnti`, `rar_opportunity`, `rar_window_start`, and `ra_pdcch`.
- Decisive handoff events remain behind `PAVONIS_SRSUE_RAR_TRACE` only:
  `tb_decoded`, `ra_response_entry`, `ra_response_unpack`,
  `ra_response_subpdu`, `ra_response_accept`, and `ra_response_no_match`.

No CP1816 hunk changes SI-RNTI scheduling, SI PDCCH decode, SIB1 PDSCH decode,
BCCH handling, cell selection, or SFN sync code directly.

## Trace-Off / Pre-SIB1 Audit

With `PAVONIS_SRSUE_RAR_TRACE=0`, `pavonis_rar_trace_take()` returns false in
both CP1811 and CP1816 source states. CP1816 should reduce env polling rather
than add trace work.

The relevant pre-SIB1 scheduling path also stays ordered correctly:

- `mac_nr::get_dl_sched_rnti_nr()` returns SI-RNTI first when `search_bcch` is
  active.
- RA-RNTI search is checked only after SI and paging priority.
- `proc_ra_nr::is_rar_opportunity()` only returns true once the RA procedure is
  in `WAITING_FOR_RESPONSE_RECEPTION`, which requires prior RACH config and
  PRACH transmission.
- `cc_worker::decode_pdcch_dl()` only enters the new RA-window trace block when
  the selected RNTI type is RA-RNTI.

Therefore CP1816 does not expose a credible source-level path that should
break CP1820 before SIB1 when trace is explicitly off.

## Conclusion

CP1822 does not find a CP1816 source-level pre-SIB1 mechanism explaining why
CP1820 trace-off on the CP1816 binary failed SIB1 while CP1815 trace-off on the
CP1811 binary passed. The CP1815/CP1820 split remains real, but the saved
source diff points away from RAR trace logic as the direct pre-SIB1 cause.

This does not prove the deployed binary/build state is innocent. It means the
next useful check is an explicit [host-redacted] binary/source A/B rather than another
RAR-handoff RF run.
