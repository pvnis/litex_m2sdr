## Purpose

Stay no-RF and answer the next prerequisite before more delay/offset work:
instrument the shifted non-PRACH PUxCH path so a valid Msg3 run can prove

Added default-off `PAVONIS_PUXCH_ORDER_TRACE=1`, capped by
`PAVONIS_PUXCH_ORDER_TRACE_LIMIT` (default `500`). Trace lines are one-line
stderr records:

- `puxch_request_selected`
- `puxch_grid_symbol_written`
- `nonprach_shift_symbol_return`
- `upper_pusch_ready`
- `upper_pusch_enqueue`
- `upper_pusch_task_start`
- `upper_pusch_task_return`

The key ordering marker is `puxch_grid_symbol_written`: it is emitted after the
lower PUxCH demodulator writes the resource grid for that symbol and before
`notifier->on_rx_symbol(...)` can trigger upper PHY PUSCH handling. The upper
markers include slot, system slot, RNTI, HARQ ID, allocation start, allocation
length, and allocation end symbol. This makes the next valid Msg3 run
joinable by slot/RNTI/HARQ and precise enough to detect an executor-ordering
bug.

The runner now exports/logs/manifests `PAVONIS_PUXCH_ORDER_TRACE`,
`PAVONIS_PUXCH_ORDER_TRACE_LIMIT`, and `PAVONIS_UL_SYMBOL_SUMMARY_MAX`.
The gNB start helper default for `PAVONIS_UL_SYMBOL_SUMMARY_MAX` was raised
from `160000` to `260000`; CP1837 showed the old cap can stop before the real
Msg3 epoch.

## Saved-artifact Msg3 audit

CP1837 had a valid UE Msg3 supply, but its saved UL symbol manifest is not a
valid sample-domain Msg3 offset dataset:

- Manifest path: `cp1733_nuc4_artifacts_[date-redacted]CP1837_NONPRACHSHIFT_RARESP40_MSG3_RF_RETRY/tmp/pavonis_ul_symbol_manifest.tsv`
- Size: `36564263` bytes.
- Last manifest row: wall `[hex-value-redacted]`, slot `519.2`, symbol `7`.
- First confirmed UE Msg3 encode (`0x4602`, `tti_tx=5817`): wall
  `[hex-value-redacted]`.
- The manifest ends `651.481 ms` before that first confirmed Msg3 encode.

Rows for the nominal slots `581.7`, `585.7`, and `693.7` do exist in the file,
but they are the prior SFN cycle, not the real Msg3 epoch:

- `581.7` symbol 13 wall `[hex-value-redacted]`; UE `5817` encode is
  `10266.361 ms` later.
- `585.7` symbol 13 wall `[hex-value-redacted]`; UE `5857` encode is
  `10265.401 ms` later.
- `693.7` symbol 13 wall `[hex-value-redacted]`; UE `6937` encode is
  `10266.464 ms` later.
- Those rows are floor-class only, about `4e-05` raw RMS.

So CP1837 repeats the CP1833 failure mode: same SFN/slot labels from an earlier
cycle are present, but the real Msg3 epoch is not covered. It cannot prove or
reject Msg1-to-Msg3 arrival stability within a cyclic prefix (`~50` samples).

## Result

CP1839 passes as a no-RF source/build checkpoint and closes the immediate
instrumentation gap. Source ordering is structurally sane: the grid-write trace
point is before the upper notifier, and the upper PUSCH task cannot be
legitimately enqueued for a symbol before that symbol's grid write point. The
next valid run still needs runtime per-slot proof with the new trace enabled.

Do not reuse CP1837's saved UL manifest for the 50-sample Msg3 stability
decision. The next valid Msg3-supply run should keep the CP1837 coherent
non-PRACH-shift shape, enable `PAVONIS_PUXCH_ORDER_TRACE=1`, keep
`PAVONIS_PUXCH_ORDER_TRACE_LIMIT=500`, and use
`PAVONIS_UL_SYMBOL_SUMMARY_MAX=260000` so the actual Msg3 epoch is covered.
Judge the run first on ordering (`puxch_grid_symbol_written` before
`upper_pusch_task_start` for the allocation end symbol), then on sample-domain
Msg1-to-Msg3 offset stability. Keep the `~125k` Soapy TX timeout and `~3.4k`
downlink-late storm as an active jitter co-suspect.
