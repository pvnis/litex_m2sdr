# CHECKPOINT 1844 - No-RF hardware-time sample-counter rollover fix

Date: [date-redacted]

## Purpose

Stay no-RF after CP1841/CP1843 repeated the pre-UE late-gate failure and audit
the single `~372.8 s` LiteX TX release-late signature before spending another
unchanged trace-enabled RF retry.

## Finding

CP1841 and CP1843 each stopped before UE start because the pre-UE late gate saw
one timed TX packet released late:

- CP1841: `slipNs=372796572136`
- CP1843: `slipNs=372778328907`

At the active `11.52 Msps` rate, a 32-bit sample-counter wrap is:

```text
2^32 / 11.52e6 = 372827022222 ns
```

The observed slips are one 32-bit wrap minus small offsets:

- CP1841: wrap minus slip = `30450086 ns`
- CP1843: wrap minus slip = `48693315 ns`

That makes the recurring gate failure much more consistent with a torn/glitched
64-bit sample-counter read than with a truly stale queued TX packet. The Soapy
driver's `getHardwareTime()` read path was a single latched 64-bit CSR read,
then the TX worker compared that value against each all-timed chunk's release
timestamp. A one-word rollover glitch can therefore create a false
`nowNs - timeNs ~= 2^32/rate` late event.

## Patch

Changed:

`litex_m2sdr/litex_m2sdr/software/soapysdr/LiteXM2SDRDevice.cpp`

The `getHardwareTime()` sample-counter path now:

- takes three latched sample-counter reads,
- sorts them and uses the median sample count,
- logs a warning if the read span exceeds `2^31` samples:
  `Hardware time sample-counter rollover read glitch filtered: ...`

This filters a single high or low torn read at the 32-bit boundary without
changing timestamp generation, TX scheduling, PRACH/RAR logic, or RF settings.
