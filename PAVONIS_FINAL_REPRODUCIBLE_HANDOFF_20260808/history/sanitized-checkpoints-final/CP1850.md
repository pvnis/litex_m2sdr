# CHECKPOINT 1850 - No-RF hardware-time read-order audit and fix

Date: [date-redacted]

## Purpose

Pause RF after CP1849 and audit why all post-CP1844 patched-module runs
(CP1845, CP1846, CP1848, CP1849) were valid-mechanics no-SIB1/no-Msg1, while
CP1840 was the closest same-shape pre-patch SIB1 success.

## Findings

The pre-UE TX health summaries do not show a discriminator between CP1840 and
the post-patch failures. CP1840 and CP1845/1846/1848/1849 all have:

- zero release-late traces
- zero worker `late_count`
- same class of timeout and partial-return counts
- same class of negative TX slip ranges

The narrow old-vs-current [host-redacted] source diff did find a concrete CP1844 patch
bug. The intended CP1844 change was to median-filter three latched sample
counter reads, but the patch also changed the per-read register order:

```diff
- const uint32_t lo = readl(READ_VALUE + 4);
- const uint32_t hi = readl(READ_VALUE + 0);
+ const uint32_t hi = readl(READ_VALUE + 0);
+ const uint32_t lo = readl(READ_VALUE + 4);
```

That register-order change was unintended. Even if the latch should make the
order harmless, it is a plausible post-CP1844 splitter because CP1840 used the
old lo-then-hi order and all post-CP1844 RF attempts used the new hi-then-lo
order.

## Fix

Updated `LiteXM2SDRDevice.cpp` to preserve the old per-read order inside each
median-filtered sample-counter read:

```cpp
const uint32_t lo = litex_m2sdr_readl(_dev, CSR_SAMPLE_COUNTER_READ_VALUE_ADDR + 4);
const uint32_t hi = litex_m2sdr_readl(_dev, CSR_SAMPLE_COUNTER_READ_VALUE_ADDR + 0);
return (static_cast<uint64_t>(hi) << 32) | lo;
```

The median filter and rollover-glitch warning remain in place.

Local corrected source hash:

```text

```
