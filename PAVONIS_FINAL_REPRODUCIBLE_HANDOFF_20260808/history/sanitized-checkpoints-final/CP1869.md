# CHECKPOINT 1869 - No-RF day-scale SI/P0 join

Date: [date-redacted]

## Purpose

Run the requested cheap no-RF join across today's saved RF summaries before
spending another RF attempt. The hypothesis was that downlink SI-PDCCH
correlation and uplink PRACH p0 correlation may co-decline over the day,
indicating a shared AD9361/LiteX clock-chain coherence problem rather than a
detector-path issue.

The all-run time-vs-p0 value is not decisive because many late no-SIB1 runs have
only idle PRACH detector windows, not real UE Msg1. Their p0 is therefore a
floor/false-window metric, not a real uplink burst metric.

```text

```

That rejects a simple day-scale PRACH p0 decay on real Msg1 opportunities.

```text
CP1857 14:30  Msg1=7  p0_max=0.367  rssi_max=-46.27  accepted=0

CP1862 15:15  Msg1=7  p0_max=0.333  rssi_max=-47.80  accepted=0  SI max_corr=0.390
CP1868 15:58  Msg1=0  p0_max=0.182  rssi_max=-89.41  accepted=0  SI max_corr=0.234
```

PRACH amplitude holds for real Msg1 runs (`rssi_max` around `-46..-48 dB`),
while p0 flips from low to very high and back again. CP1860 is the strongest
counterexample to monotonic day-scale PRACH coherence decay: it is late-day and
has the best p0 by far in the current metadata-only branch.

SI/SIB1 evidence also does not cleanly co-vary with PRACH p0. SI summaries are
often absent on fast SIB1 successes, which weakens any direct SI-vs-p0 join.
Where present, SI max_corr does not predict p0 strongly (`+0.128` all-run
correlation). CP1862 has SI max_corr `0.390` but p0 stays failed at `0.333`;
CP1868 has low SI max_corr `0.234`, but it is no-Msg1 and cannot judge PRACH.

## Decision

The saved evidence does not support the strong version of the shared day-scale
coherence-decay theory:

```text
real Msg1 PRACH p0 does not monotonically decline with run start time
SI max_corr and PRACH p0 do not co-vary strongly run-to-run
real Msg1 PRACH RSSI remains in the same amplitude class while p0 changes
```

This does not rule out intermittent shared coherence/jitter, especially given
the recurring Soapy timeout/downlink-late storm. It does mean detector-path
instrumentation is not merely chasing a proven day-scale hardware decay.

Next step remains the user's requested segment-trace discriminator, but it
should be late-armed after UE `phy_set_config_ok` instead of using a larger row
cap. Also restore `PAVONIS_NON_PRACH_UL_RX_TIMESTAMP_OFFSET_SAMPLES=-352536`
before any RF run where Msg3 CRC is a criterion.
