## Conclusion

CP1885 does not support "bladeRF USB resets started at 15:30-16:00Z" as the
leading root cause. The kernel log shows frequent reset/LPM pairs all day, no
error-class USB messages around the transition, and the same three-reset
in-run pattern in both pass and fail classes.

The bladeRF USB cable/port should still be checked first in the physical audit,
because CP1883 found a real current [host-redacted] access/permission issue and the
kernel reset cadence is not ideal. But from CP1885 alone, UE-side USB is a
physical-check suspect, not the current leading unifying explanation for the
SI-PDCCH and PRACH coherence collapses.
