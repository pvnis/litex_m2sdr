# CP1901 No-RF CP1896 vs gNB Watcher Compare and Streaming Arm Patch

Date: [date-redacted]

## Purpose

Explain the CP1898/CP1900 zero-PRACH-accept pattern before spending another RF
run. Compare CP1896, CP1898, and CP1900 using only saved summaries, UE stdout
markers, and small PRACH detector traces, then remove any obvious observer
effect from the gNB-side arm watcher.

## Comparison

All three valid hardware runs reached the same UE supply class:

| Checkpoint | Cell-search SNR | Cell-search CFO | RSRP | SI max_corr | UE PRACH bursts |
| --- | ---: | ---: | ---: | ---: | ---: |
| CP1896 | 11.428 dB | -3588.742 Hz | 4.649 | 0.620186 | 7 |
| CP1898 | 10.692 dB | -3559.248 Hz | 4.636 | 0.622400 | 7 |
| CP1900 | 11.492 dB | -3520.240 Hz | 4.746 | 0.595693 | 7 |

UE PRACH generation also stayed stable. Each run emitted seven PRACH bursts,
with per-burst PRACH CFO in the small `-0.023..+0.012 kHz` class and PRACH-TX
`max_abs` around `1.02`.

The gNB detector-side p0 quality diverged:

| Checkpoint | Accepted | Max p0 ratio | Max p0 SFN | Max p0 delay | Max p0 RSSI | Mean trace RSSI |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| CP1896 | 1 | 15.028 | 260 | 99 | -46.24 dB | -93.30 dB |
| CP1898 | 0 | 0.354 | 244 | 30 | -51.63 dB | -93.32 dB |
| CP1900 | 0 | 0.326 | 36 | 110 | -51.15 dB | -93.32 dB |

Host/TX health does not explain the split. All valid hardware runs had SIB1,
seven UE PRACH bursts, native-continuous TX, similar timeout counts, and good
host-state gates. CP1898 and CP1900 also proved [host-redacted] bladeRF USB
`power/control=on`, runtime `active`, speed `5000`, authorized `1`, and
`bladerf_usb_power_bad=0`.

## Finding

The main shape difference is the gNB-side arm watcher. CP1896 used
`PAVONIS_UL_SYMBOL_DUMP_ARM_MODE=after_rar`, which watched UE stdout on
[host-redacted] and never saw live markers because that trace is flushed at exit. It
still accepted one real PRACH row and reached Msg3/PUSCH CRC KOs.

CP1898 and CP1900 used `after_gnb_prach`, which started a [host-redacted] process that ran
`grep` over the full growing binary-safe gNB mirror every 10 ms for up to
120 s. The mirror contains the high-rate gNB TX timeout/downlink-late stream.
That repeated full-file scan is a plausible [host-redacted] observer effect and violates
the hot-path instrumentation standard even though it is outside the lower-PHY
source code.

## Patch

The CP1807-family RF runner now keeps the same gNB-side trigger semantics but
uses a streaming watcher:

- wait for `/tmp/gnb_m2sdr_band3_ota.log` to exist
- run `tail -n 0 -F "$GNB_MIRROR" | grep -aEm1 "$pattern"`
- touch the UL-symbol arm file only on the first live match
- on timeout, inspect only a bounded `tail -[date-redacted]` diagnostic window

Local validation:

- `bash -n cp1807_run_stage6_raresp40_realue_rar_msg3.sh` passed.
- A local wrapper-style quoting smoke test for the `tail -F | grep -m1` command
  matched a synthetic `prach(ra-rnti=...)` line and returned `rc=0`.

## Interpretation

The saved data does not show a downlink acquisition, UE PRACH transmit, host
state, or bladeRF USB-power regression across CP1896 to CP1900. It shows a
detector-input collapse at the gNB only in the two runs with the [host-redacted]-side
full-file watcher.

Therefore the next RF run should repeat the CP1900 shape with the patched
streaming watcher. It should be judged in this order:

1. gNB PRACH p0 acceptance returns or not.
2. If accepted, the streaming watcher arms before Msg3 and produces bounded
   UL-symbol manifest/raw files.
3. If Msg3 occurs, reuse CP1896's closed ordering result and judge on gNB Msg3
   CRC plus sample-domain offset stability.
