# CHECKPOINT 1905 - No-RF CP1896 vs CP1904 UE PRACH SC16 Waveform Compare

Date: [date-redacted]

## Purpose

Compare the saved UE-side bladeRF TX debug SC16 buffers and gNB PRACH detector traces from the accepted CP1896 run and the zero-accept CP1904 run before spending more RF. The question was whether CP1904's `~50x` p0-ratio collapse was caused by a different UE-generated PRACH waveform.

## Inputs

- CP1896 summary: `cp1733_stage6_realue_sib1_rachcfg_summary_[date-redacted]CP1896_MSG3_PUSCH_ORDER_LATE_ULRAW_NOAPPEND_RF.json`
- CP1904 summary: `cp1733_stage6_realue_sib1_rachcfg_summary_[date-redacted]CP1904_MSG3_PUSCH_INPROCESS_RARARM_ULRAW_NOAPPEND_RF.json`
- CP1896 UE TX debug: `cp1733_sensnuc7_artifacts_[date-redacted]CP1896_MSG3_PUSCH_ORDER_LATE_ULRAW_NOAPPEND_RF/.../run_[date-redacted]/pavonis_rf_blade_tx_dbg_*.sc16`
- CP1904 UE TX debug: `cp1733_sensnuc7_artifacts_[date-redacted]CP1904_MSG3_PUSCH_INPROCESS_RARARM_ULRAW_NOAPPEND_RF/.../run_[date-redacted]/pavonis_rf_blade_tx_dbg_*.sc16`
- CP1896 PRACH detector trace: `cp1733_nuc4_artifacts_[date-redacted]CP1896_MSG3_PUSCH_ORDER_LATE_ULRAW_NOAPPEND_RF/tmp/pavonis_prachdet_trace.log`
- CP1904 PRACH detector trace: `cp1733_nuc4_artifacts_[date-redacted]CP1904_MSG3_PUSCH_INPROCESS_RARARM_ULRAW_NOAPPEND_RF/tmp/pavonis_prachdet_trace.log`

## Result

CP1905 closes the UE-generated-PRACH-waveform theory.

Both runs generated the same PRACH shape at the UE TX-buffer level:

- CP1896 has 8 saved TX debug buffers: 6 PRACH-like buffers and 2 lower-RMS PUSCH/Msg3-class buffers around the RAR epoch.
- CP1904 has 7 saved TX debug buffers, all PRACH-like.
- PRACH-like SC16 nonzero count is `10404` in both runs, matching `N_seq=9216`, `N_cp=1188`, `len=10404`.
- CP1896 PRACH-like SC16 RMS range: `0.575416741..0.578517589`; peak range: `1.017600266..1.023264281`.
- CP1904 PRACH-like SC16 RMS range: `0.576963785..0.579076928`; peak range: `1.020430362..1.024192473`.
- CP1896 intra-PRACH best-correlation range over +/-32 samples: min/mean/max `0.998696556 / 0.999689337 / 0.999990902`.
- CP1904 intra-PRACH best-correlation range over +/-32 samples: min/mean/max `0.999490710 / 0.999881136 / 0.999999876`.
- Each CP1896 PRACH-like buffer best-matches a CP1904 PRACH-like buffer at essentially unity correlation, zero integer lag, and no meaningful CFO correction:
  - best cross-run correlations: `0.999989865`, `0.999999861`, `0.999999896`, `0.999996159`, `0.999999788`, `0.999999868`
  - best lags: all `0`
  - best CFO grid points: `0` or `25 Hz`, too small to explain detector collapse

The detector traces still split sharply:

- CP1896 accepted one p0 row: `sfn=260 slot=4`, `rssi=-46.24 dB`, `p0_delay=99`, `p0_ratio=15.028`, threshold `0.6100000143`.
- CP1904 accepted zero rows; max p0 row: `sfn=196 slot=4`, `rssi=-46.37 dB`, `p0_delay=115`, `p0_ratio=0.311`, threshold `0.6100000143`.
- The strong-window RSSI class is comparable (`~-46 dB`) while p0 correlation differs by about `48x`.

## Conclusion

The CP1904 zero-accept result is not caused by a malformed or different UE PRACH TX buffer. The collapse happens after the saved bladeRF TX debug buffer point: OTA path, M2SDR RX/predemod input, PRACH demod/detector sensitivity to CFO/fractional timing/phase, or run-scale coherence.

No live-run [interface-redacted] is justified from CP1905 alone. The next rung is to capture bounded strong PRACH predemod CF32 windows in both accepted-class and rejected-class runs, then replay those exact windows offline through the detector with CFO/fractional-timing/phase sweeps.
