# CHECKPOINT 1911 - No-RF Strong Predemod Offline Replay / CFO-Timing Sweep

## Objective

Replay the exact bounded strong-predemod CF32 windows from the fresh rejected
CP1909 run and accepted CP1910 run through the OCUDU PRACH demodulator/detector,
then sweep detector-input CFO, integer/fractional timing, and constant phase
offline before changing any live setting.

## Inputs

- Accepted class: CP1910 strong predemod manifest
  `cp1733_nuc4_artifacts_[date-redacted]CP1910_STRONG_PREDEMOD_CP1896_SHAPE_CLEANED_RF/tmp/pavonis_prach_strong_predemod_manifest.tsv`
- Fresh rejected class: CP1909 strong predemod manifest
  `cp1733_nuc4_artifacts_[date-redacted]CP1909_STRONG_PREDEMOD_CP1896_SHAPE_CLEANED_RF/tmp/pavonis_prach_strong_predemod_manifest.tsv`
- Optional rejected comparator: CP1907 strong predemod manifest
  `cp1733_nuc4_artifacts_[date-redacted]CP1907_STRONG_PREDEMOD_CP1896_SHAPE_RF/tmp/pavonis_prach_strong_predemod_manifest.tsv`

## Harness

Built `cp1911_strong_predemod_sweep_replay.cpp`, a standalone no-RF replay
harness that:

- reads packaged strong-predemod CF32 windows from each manifest;
- applies bounded CFO, integer timing, fractional timing, and constant phase
  transforms;
- calls the same OCUDU OFDM PRACH demodulator and PRACH detector path;
- enables `PAVONIS_PRACHDET_TRACE` and folds `p0_ratio`, `best_ratio`,
  threshold, SCS, and delay-gate fields into compact JSONL.

Important replay correction: the first baseline attempt used
`prach_subcarrier_spacing::kHz1_25` and falsely accepted CP1909 windows because
that path uses `ra_scs=4`, `threshold=0.147`. Live CP1909/CP1910 detector traces
use `ra_scs=0`, `threshold=0.6100000143`, `win_margin=12`. The final CP1911
harness forces the live-trace-compatible `prach_subcarrier_spacing::kHz15`,
after which the offline baseline reproduces the live accept/reject split.

## Results

Corrected baseline replay:

| Dataset | Baseline accepts | Baseline RSSI class | Baseline p0 ratio class |
| --- | ---: | --- | --- |
| CP1910 accepted | `3/6` | `-47.23..-46.24 dB` | `0.200..4.230`; accepted rows `2.046/4.230/3.044` |
| CP1909 rejected | `0/6` | `-49.24..-46.41 dB` | `0.141..0.484` |
| CP1907 rejected comparator | `0/6` | same strong-window class | max `0.767` |

CP1909 direct sweeps:

- CFO-only: `2` accepting variants, all from window `idx=1`; best
  `p0_ratio=3.528` at `+3000 Hz`.
- Integer timing only: `5` accepting variants, all from window `idx=1`; best
  `p0_ratio=1.641` at `-96 samples`.
- Fractional timing only: `0` accepts, max `p0_ratio=0.501`.
- Constant phase only: `0` accepts, unchanged max `p0_ratio=0.484`.

CP1909 combined timing+CFO grid:

- `177` accepting variants, all from window `idx=1`.
- Best CP1909 recovery: `idx=1`, `p0_ratio=6.810`, `p0_delay=0`,
  `integer_shift=-96`, `fractional_shift=-0.5`, `cfo=+1500 Hz`.
- Other CP1909 windows stayed sub-threshold under the bounded grid:
  `idx0=0.575`, `idx2=0.913`, `idx3=0.422`, `idx4=0.368`, `idx5=0.277`.

CP1910 accepted-class behavior:

- Baseline reproduces the live `3` accepted p0 rows.
- CFO and timing sweeps strongly increase p0 ratios in the already-good windows;
  e.g. combo-grid maxima include `43.141`, `35.414`, and `39.886`.
- Phase-only sweeps do not materially change p0 ratios, as expected for this
  detector metric.

CP1907 optional rejected comparator:

- Baseline remains rejected (`0/6`, max `0.767`).
- Direct sweeps recover only two windows. The largest p0 ratio observed
  (`55.427`) is delay-gate rejected at `p0_delay=116`; the best accepted variant
  is `p0_ratio=19.649` at `cfo=-2750 Hz`, `p0_delay=100`.

## Conclusion

The saved strong predemod windows are not missing-energy cases: CP1909 has the
same RSSI class as CP1910, but its p0 correlation is far below threshold when
replayed with the live detector configuration.

The offline sweeps rule out constant phase and fractional-sample timing as
global explanations. Integer timing alone is weak and only rescues one CP1909
window. Coherent phase progression / residual CFO is the only swept variable
that materially restores a rejected window, so the next code-side branch should
be a no-RF/source-level PRACH detector-input CFO/phase-progression compensation
or bounded CFO search, not more live delay [interface-redacted].

However, CP1909 is not fixed by one static CFO: only one of six rejected windows
crosses threshold under the bounded grid. Treat the result as "CFO/phase
progression is the named dominant variable class" rather than "apply a single
live CFO knob". The likely next rung is per-window/per-burst detector-input
CFO estimation or bounded sweep, still judged offline first and still with no
live RF [interface-redacted] until the detector replay path predicts acceptance.
