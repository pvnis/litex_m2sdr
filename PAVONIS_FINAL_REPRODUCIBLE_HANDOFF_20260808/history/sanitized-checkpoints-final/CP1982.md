## Executive Recommendation

**No-go for immediate migration.**

Upstream `main` is strategically attractive, but it is not a drop-in
replacement for the current Pavonis branch while the SI/SIB1 supply regression
is unresolved. It changes the TX timing model from local FPGA sample-count
gating to software placement on the board-time axis, deletes the local
`TimedTXArbiter`/`SampleCounter` gateware, and changes RX timestamp provenance.

Recommended path:

1. Keep current Pavonis RF ladder frozen on migration work until SI/SIB1 supply
   is back to a reproducible baseline.
2. After supply is stable and the user approves, create a separate migration
   branch and test it with no-RF build checks first.
3. Only then run a small RF ladder: TX/RX timestamp sanity, SSB/PBCH, SIB1,
   Msg1, RAR/Msg3.

## Main Finding

The June gateware timed-TX work was not simply upstreamed as-is. Upstream
`main` has superseded it:

- Local `[host-redacted]` still has:
  - `litex_m2sdr/gateware/timed_tx.py`
  - `litex_m2sdr/gateware/sample_counter.py`
  - `TimedTXArbiter` wired between TX header extraction and AD9361 TX
  - RX DMA header timestamp from `sample_counter.count_sys`
  - Soapy `getHardwareTime()` preferring the sample-counter CSR when present
- Upstream `main` deletes:
  - `litex_m2sdr/gateware/timed_tx.py`
  - `litex_m2sdr/gateware/sample_counter.py`
- Upstream `main` instead:
  - wires TX header output directly into loopback/RFIC TX
  - timestamps RX DMA headers from `time_gen.time`
  - implements timed TX in `LiteXM2SDRStreaming.cpp` by software zero-fill,
    timeline tracking, and late-write rejection
  - uses `m2sdr_get_time()` / `m2sdr_set_time()` for Soapy hardware time

## Poll-Timeout Fix Status

The local branch already has a simpler libm2sdr stream timeout path:

- `m2sdr_get_buffer(..., timeout_ms)` exists.
- Local wait helpers use timeout checks and `poll()`.

Upstream supersedes this with a broader, cleaner transport stack:

- Soapy streaming routes through `m2sdr_get_buffer()` and `m2sdr_submit_buffer()`
  in `LiteXM2SDRStreaming.cpp`.
- `m2sdr_stream.c` has bounded RX/TX buffer waits using `poll()`, per-stream
  timeout configuration, `M2SDR_TIMEOUT_NOWAIT`, and LiteEth timeout recovery.
- Kernel/user APIs include additional DMA stats and SATA timeout handling.

Assessment:

- The poll-timeout idea is upstreamed/superseded in a cleaner libm2sdr-centered
  form.
- Migrating likely retires local ad hoc Soapy poll/backpressure experiments,
  but requires adapting Pavonis wrappers to upstream libm2sdr semantics and
  retesting every timeout health gate.

## `getHardwareTime()` Status

Local `[host-redacted]`:

- If `CSR_SAMPLE_COUNTER_CONTROL_ADDR` exists, Soapy reads the FPGA
  sample-counter CSR and converts samples to nanoseconds using the active sample
  rate.
- Fallback is `m2sdr_get_time()`.
- This was built to make the gateware `TimedTXArbiter` and RX timestamps share
  a sample-domain reference.

Upstream `main`:

- Soapy `getHardwareTime()` always calls `m2sdr_get_time()`.
- RX DMA headers use `time_gen.time`, not `sample_counter.count_sys`.
- Upstream docs frame hardware time as board time, with optional PTP ownership.

Assessment:

- The local sample-counter `getHardwareTime()` fix is **not upstreamed as-is**.
- It is superseded by upstream's board-time model.
- This is probably the right long-term architecture if the board-time axis is
  coherent enough for srsRAN, but it is not proven against our current Stage 6
  CP1972/CP1979 supply instability.

## Timed-TX Knob Mapping

Upstream Soapy timed TX supports:

```text
timed_tx=software|off
tx_lead_buffers=N
tx_latency_ns=K
tx_late_margin_ns=M
```

Semantics from source/docs:

- `timed_tx=software` is default.
- `timed_tx=off` preserves timestamps as metadata but does not software-place
  gaps.
- `tx_lead_buffers` defaults to `0`. Upstream explicitly warns to keep it at
  `0` for srsRAN because nonzero lead shifts actual emission before requested
  timestamps.
- `tx_latency_ns` is a constant trim for DMA/RFIC pipeline latency; negative
  values are allowed and it must be calibrated.
- `tx_late_margin_ns` is the lateness tolerance before timed writes return
  `SOAPY_SDR_TIME_ERROR`; default is one MTU duration.

Mapping to Pavonis current controls:

- Current `M2SDR_SOAPY_TX_TIME_OFFSET_NS=30000000` and the recurring
  `~352536` sample UL timing family are approximately the same scale:
  `352536 / 11.52e6 = 30.60 ms`.
- This does **not** map to upstream `tx_lead_buffers`; upstream says not to use
  lead buffers for srsRAN absolute timing.
- It should be treated as a `tx_latency_ns`/timeline calibration question,
  but the sign and final value must be measured by loopback after migration.
- Current all-timed cadence and reanchor/env experiments do not map 1:1.
  Upstream software timed TX owns zero-fill and late rejection instead.

## What Migration Would Retire

If upstream timed TX is validated on our hardware, it should retire or sharply
reduce:

- local gateware `TimedTXArbiter`
- local gateware `SampleCounter`
- local Soapy sample-counter `getHardwareTime()` path
- Pavonis all-timed/reanchor/continuous-stream branch plumbing:
  `PAVONIS_SOAPY_TX_ALL_TIMED_CHUNKS`,
  `PAVONIS_SOAPY_TX_REANCHOR_INTERVAL_SAMPLES`,
  continuous-helper-as-working-cadence controls
- most custom Soapy timeout/backpressure policy variants, replaced by upstream
  libm2sdr bounded buffer waits and timeout reporting
- the static UL compensation family, if RF validation proves one coherent
  board-time axis:
  `PAVONIS_PRACH_TIMING_COMPENSATION_SAMPLES`,
  `PRACH_COLLECTION_DELAY_SAMPLES`,
  `PAVONIS_LOWER_PHY_UL_RX_TIMESTAMP_OFFSET_SAMPLES`,
  `PAVONIS_NON_PRACH_UL_RX_TIMESTAMP_OFFSET_SAMPLES`,
  and the associated `~352536` sample Msg1/Msg3 timing shims

That retirement is conditional. It only becomes valid if migrated TX placement
and RX timestamps reproduce SIB1/Msg1 supply and align Msg3/PUCCH without
static out-of-band shifts.

## Migration Risks

- Upstream removes the exact gateware mechanism that our current branch used
  to obtain stable all-timed behavior.
- RX timestamp provenance changes from sample count to board-time nanoseconds.
- The sign/value of `tx_latency_ns` cannot be inferred safely from the current
  `30 ms` lead and `352536` sample compensation; it must be measured.
- Our active blocker is not the old timed-TX cadence alone. CP1980 found a
  CP1972-vs-CP1979 SI-era level/coherence split with no gNB config/readback or
  initial cell-search explanation.
- Migrating now would mix a large timing-stack replacement into an unresolved
  RF/supply regression and erase the ability to attribute cause.

## Suggested Approved Migration Plan

Only after supply regression is closed and the user approves:

1. Create a separate migration branch from upstream `main`; do not modify the
   current Pavonis branch in place.
2. Port only Pavonis-required runbook wrappers and reporting hooks, not the old
   timed-TX compensation stack.
3. Build no-RF locally and on [host-redacted]; verify Soapy module strings/options expose:
   `timed_tx`, `tx_latency_ns`, `tx_late_margin_ns`, `rx_dma_header`.
4. Read-only hardware preflight:
   clock source, ref lock, board time monotonicity, RX DMA header support,
   host realtime state.
5. No-RF smoke:
   Soapy open/setup/readback, `getHardwareTime()` monotonicity, TX buffer
   timeout behavior.
6. RF ladder:
   self-RX tone, SSB/PBCH, SI/SIB1, Msg1/RAR, Msg3 CRC, then PUCCH/HARQ ACK.
7. Only if Msg1/Msg3 alignment works without static `352536` shims, retire the
   old compensation family.

## Recommendation

**No-go now.** Upstream is a credible long-term replacement for the current
Pavonis timed-TX branch, but it should be treated as a new timing architecture,
not a patch update. The current active blocker remains CP1979/CP1980 SI-era
EPRE/coherence supply regression, with [host-redacted] now prepared in CP1981 for a
pre-CP1978 UE-binary A/B if RF is later approved.
