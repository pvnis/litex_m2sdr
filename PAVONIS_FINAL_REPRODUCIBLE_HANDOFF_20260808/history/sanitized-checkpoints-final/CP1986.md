# CHECKPOINT 1986 - No-RF SI Candidate Trace Hot-Path Source Audit

Date: [date-redacted]

## Purpose

Continue CP1985's no-RF provenance split by inspecting the source-level behavior
of `PAVONIS_SRSUE_SI_CANDIDATE_TRACE`. The question was whether CP1951's
candidate-trace enablement is effectively inert when no candidate rows print,
or whether it still changes the UE SI-PDCCH hot path.

No source was edited. No RF, rebuild, deploy, or gateware action was performed.

## Source Path

Relevant file:

- `srsRAN_4G/srsue/src/phy/nr/cc_worker.cc`

The SI-RNTI path does this per SI-PDCCH search:

1. Calls `srsran_ue_dl_nr_find_dl_dci(...)`.
2. Computes `max_epre` and `max_corr` over `ue_dl.pdcch_info`.
3. If the slot is in the traced SI window, calls:
   `pavonis_si_candidate_trace_take(max_corr, n_dl)`.
4. Only if that returns true, emits the expensive
   `PAVONIS_SRSUE_SI_CANDIDATE_TRACE event=si_pdcch_candidates` row and loops
   over every candidate for detailed fields.
5. Calls the aggregate `pavonis_sib1_trace_pdcch_summary(...)`.

The trace-take helper is not cached:

- `pavonis_si_candidate_trace_enabled()` calls
  `std::getenv("PAVONIS_SRSUE_SI_CANDIDATE_TRACE")`.
- `pavonis_si_candidate_trace_limit()` calls
  `std::getenv("PAVONIS_SRSUE_SI_CANDIDATE_TRACE_LIMIT")` and `std::strtoul`.
- `pavonis_si_candidate_trace_min_corr()` calls
  `std::getenv("PAVONIS_SRSUE_SI_CANDIDATE_TRACE_MIN_CORR")` and `std::strtof`.

When trace is disabled, the helper returns after the first `getenv`. When trace
is enabled but the current window does not cross threshold, it still performs
the enabled check, limit lookup/parse, and min-corr lookup/parse before returning
false.

## CP1950/CP1951 Implication

CP1985 found the actual env split:

| Env | CP1950 | CP1951 |
| --- | --- | --- |
| `PAVONIS_SRSUE_SI_CANDIDATE_TRACE` | `0` | `1` |
| `PAVONIS_SRSUE_SI_CANDIDATE_TRACE_LIMIT` | `200` | `400` |
| `PAVONIS_SRSUE_SI_CANDIDATE_TRACE_MIN_CORR` | `0.40` | `0.35` |

CP1951 emitted zero `event=si_pdcch_candidates` rows because its SI
`max_corr` never reached `0.35`. But it still had `800` aggregate summary rows
covering `160000` SI-PDCCH samples. Therefore the enabled candidate-trace path
likely performed on the order of `160000` repeated env/parse checks before
returning false.

That is much less severe than per-candidate logging or raw-sample work, but it
is not a no-op. It violates the spirit of the Pavonis hot-path rule: diagnostic
configuration should be parsed once or event-triggered, not repeatedly parsed in
the lower/PHY worker loop.

## Conclusion

CP1986 upgrades the CP1951 candidate-trace delta from "probably not heavy I/O"
to "real low-impact hot-path observer candidate." It still does not prove
causality for CP1951's low/scattered state, because the same low class appears
in several other runs and there was no controlled A/B with only this flag
changed. But the source path is weak enough that future RF runs should not use
`PAVONIS_SRSUE_SI_CANDIDATE_TRACE=1` unless the trace settings are first cached
or made event-triggered.
