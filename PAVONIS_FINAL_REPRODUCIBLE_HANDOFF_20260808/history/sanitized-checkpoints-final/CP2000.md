# CP2000 No-RF PDCCH DMRS Measurement Audit

Date: [date-redacted] Europe/Zurich

## Scope

No RF, rebuilds, deploys, source edits, wrapper edits, or gateware changes were
made in this checkpoint.

CP1996/CP1997 moved the active blocker to scheduled-phase SI-PDCCH DMRS
correlation: high/no-SIB1 runs have normal SI EPRE but candidate `norm_corr`
tops out around `0.458..0.464`, below the default `0.5` predecode gate. CP1998
and CP1999 scoped a cached candidate trace that would print per-candidate
`cfo_hz` and `sync_error_us`. CP2000 audits the DMRS measurement implementation
before relying on those fields.

## Measurement Path

`srsRAN_4G/lib/src/phy/ch_estimation/dmrs_pdcch.c`:

- Lines `337-361`: `srsran_dmrs_pdcch_estimate()` extracts PDCCH DMRS least
  square estimates for every CORESET symbol before blind decoding.
- Lines `409-526`: `srsran_dmrs_pdcch_get_measure()` measures a single
  candidate location.
- Lines `460-467`: the candidate measurement estimates synchronization error
  across the candidate's DMRS pilots and precompensates that phase slope before
  measuring correlation.
- Lines `475-481`: per-symbol coherent DMRS correlation is the average of the
  compensated pilot estimates; RSRP is the squared coherent average and EPRE is
  average pilot power.
- Lines `511-515`: `norm_corr = RSRP / EPRE`.

This means the CP1996 separator is a coherent-pilot-quality separator, not an
energy separator. At comparable EPRE, a drop from early-pass `0.62..0.67` to
high/no-SIB1 `0.46` means more of the DMRS pilot energy is incoherent under the
expected candidate/symbol/frequency mapping before DCI decode.

## CFO Field Issue

The source computes an inter-symbol CFO accumulator:

- Lines `483-490`: `cfo_avg_Hz += cargf(corr[l] * conjf(corr[l - 1])) /
  (2*pi*Ts)`.

But the store path appears wrong:

- Lines `497-499`: when `coreset.duration > 1`, the code executes
  `measure->cfo_hz /= (float)(q->coreset.duration - 1);`.

It never assigns `cfo_avg_Hz` to `measure->cfo_hz`. In the UE path,
`srsRAN_4G/lib/src/phy/ue/ue_dl_nr.c` line `253` zeroes the whole
`srsran_ue_dl_nr_pdcch_info_t` before calling `srsran_dmrs_pdcch_get_measure()`,
so `measure->cfo_hz` will likely remain `0` for duration-2 CORESET0 candidates.

The existing unit test does not catch this:

- `srsRAN_4G/lib/src/phy/ch_estimation/test/dmrs_pdcch_test.c` lines
  `103-116` zero-initialize `measure` and only asserts ideal zero CFO, so a
  zero result caused by the store bug still passes.

## Interpretation

For the next trace branch, printing `sync_error_us` is immediately meaningful:
it is assigned from `sync_err_avg` at lines `504-505`.

Printing `cfo_hz` without fixing the store bug would be misleading. A row of
zeros would not prove candidate CFO is absent; it would likely reflect the
implementation bug. Therefore the next approved one-file trace patch should be
expanded to include the one-line CFO store correction:

```text
measure->cfo_hz = cfo_avg_Hz / (float)(q->coreset.duration - 1);
```

This remains no-threshold, no-gate-relaxation, and diagnostic-only. It changes
the reported measurement field from effectively stale/zero to the value the
existing estimator already computes.

## Frontier

correlation is below the `0.5` predecode gate in high/no-SIB1 runs. CP2000
