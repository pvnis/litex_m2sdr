# CP2002 No-RF Existing PDCCH Log Diagnostic Audit

Date: [date-redacted] Europe/Zurich

## Scope

No RF, rebuilds, deploys, source edits, wrapper edits, or gateware changes were
made in this checkpoint.

CP1998-CP2001 scoped a cached, row-capped SI-PDCCH candidate trace plus a PDCCH
DMRS CFO store fix. CP2002 checks whether existing srsRAN PHY-lib logging can
provide the same diagnostic with no patch.

## Existing Reject Logs

`srsRAN_4G/lib/src/phy/ue/ue_dl_nr.c` already logs PDCCH candidate rejection:

- Lines `265-269`: invalid measurement.
- Lines `271-279`: EPRE below threshold.
- Lines `281-290`: correlation below threshold, including candidate `L`,
  `ncce`, `norm_corr`, corr threshold, EPRE, and RSRP.

`srsRAN_4G/lib/src/phy/ch_estimation/dmrs_pdcch.c` also logs every candidate
measurement through `DMRS_PDCCH_INFO_RX`:

- Lines `518-523`: `L`, `ncce`, RSRP, EPRE, and corr.

These logs are not equivalent to the proposed trace:

- They do not print active CORESET/search-space context, RNTI, DCI format,
  candidate bit count, CRC result, active row cap, `sync_error_us`, or fixed
  `cfo_hz`.
- The reject message prints corr with `%.1f`, which rounds the critical
  `0.458..0.464` high/no-SIB1 class to `0.5`, hiding the exact margin.
- The logs are emitted for the whole PHY-lib INFO stream, not just SI-RNTI
  scheduled-phase candidate rows.

## Runtime Log Control

The C `INFO()` macro routes through the PHY-lib log handler when one is
registered:

- `srsRAN_4G/lib/include/srsran/phy/utils/debug.h` lines `74-80`.
- `srsRAN_4G/srsue/src/phy/phy_nr_sa.cc` lines `101-107`: the handler is
  registered when `phy_lib_level` is not `none`.

srsUE accepts log settings:

- `srsRAN_4G/srsue/src/main.cc` lines `175-199`: `log.phy_lib_level`,
  `log.all_level`, and `log.filename`.
- Lines `580-590`: `log.all_level` fills unset `phy_lib_level`.

But the current Pavonis UE config preparation explicitly suppresses most logs:

- `pavonis_toolkit/scripts/pavonis_prepare_srsue_best_config_sensnuc7.sh`
  line `31` sets `all_level=error`, `phy_lib_level=error`,
  `filename=$OUT/ue_ota.detail.log`, and `file_max_size=-1`.

The Stage 6 [host-redacted] helper then runs `srsue "$CONF"` and redirects stdout/stderr
to `srsue.stdout.log`, while detailed srslog output goes to
`ue_ota.detail.log`:

- `cp193_sens_start_stage6_high_peak_tx_now_ue_remote.sh` lines `37-81`.
- Lines `189-194` record `UE_STDOUT` and `UE_DETAIL`.

Therefore existing PDCCH reject logs could only be collected by changing the UE
log configuration to `phy_lib_level=info` or equivalent. That is config-only,
but it is global, uncapped, and would add large PHY-lib log volume during the
same SI window where observer effects have repeatedly mattered.

## Conclusion

Existing PHY-lib INFO logging is a poor substitute for the planned candidate
trace. It can confirm that candidates are discarded below the corr threshold,
but CP1997 already proved that from source and CP1996 summaries. It cannot
answer the next question: whether high/no-SIB1 differs from early-pass in
candidate `sync_error_us`, fixed `cfo_hz`, candidate identity, or exact
sub-threshold correlation margin.

The preferred next approved branch remains:

1. Fix the PDCCH DMRS `cfo_hz` store.
2. Cache the existing `PAVONIS_SRSUE_SI_CANDIDATE_TRACE*` env settings.
3. Extend the row-capped SI candidate trace with active thresholds,
   `sync_error_us`, and fixed `cfo_hz`.

Do not spend an RF run on `phy_lib_level=info` as a "no-code" shortcut unless
the user explicitly accepts the global uncapped log-volume risk.
