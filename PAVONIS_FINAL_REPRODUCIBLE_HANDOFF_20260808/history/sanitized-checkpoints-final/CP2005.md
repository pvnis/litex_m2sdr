## Interpretation

Because `pdcch_info` is zeroed before measurement and `result` is assigned only
after decode, `cand%u_crc=0` is ambiguous unless it is interpreted with the
candidate measurements and active thresholds:

- If `cand%u_epre < epre_thr`, the candidate was not decoded; `crc=0` is just
  the zero-initialized result.
- If `cand%u_corr < corr_thr`, the candidate was not decoded; `crc=0` is just
  the zero-initialized result.
- If EPRE and corr clear their thresholds and `cand%u_crc=0`, then decode ran
  and the CRC comparison failed.
- If EPRE and corr clear their thresholds and `cand%u_crc=1`, then decode ran
  and the DCI CRC matched.

This matters for the current high/no-SIB1 class. CP1997 showed its best
scheduled rows top out at `0.458..0.464`, below the active `0.5` corr gate. In
that class, all `cand_crc=0` values should initially be read as predecode
rejects unless a candidate trace row proves a candidate cleared the active
thresholds.

## Patch Refinement

The future approved cached trace patch should either:

- print row-level `corr_thr` and `epre_thr` so the parser can infer whether each
  candidate was decode-attempted; or
- additionally print a derived per-candidate flag such as
  `cand%u_decode_attempted=%u`, computed from `isnormal(corr)`,
  `epre >= epre_thr`, and `corr >= corr_thr`.

This adds no new env variables or wrapper plumbing and stays metadata-only. It
prevents future reports from overstating `crc=0` as a true decoded CRC failure.
