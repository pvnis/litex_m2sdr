# CP2058 No-RF RA-RNTI Decode Source Audit

Date: [date-redacted]

## Purpose

CP2057 showed that CP2054's first gNB RAR slot had strong UE RA-PDCCH metrics
at the exact expected slot/RNTI, but still produced `n_dl=0`. CP2058 audits
the UE RA-RNTI decode path in source to identify the next no-RF instrument.

No RF was run and no source was changed in this checkpoint.

## Source Path

The UE MAC chooses RA-RNTI only during the active RAR window:

- `srsue/src/stack/mac_nr/mac_nr.cc`
  - `get_dl_sched_rnti_nr()`
  - priority order is SI-RNTI, P-RNTI, RA-RNTI, Temp-RNTI, C-RNTI
  - if `proc_ra.is_rar_opportunity(tti)`, it returns
    `{proc_ra.get_rar_rnti(), srsran_rnti_type_ra}`

The UE PHY then searches RA-RNTI via:

- `srsue/src/phy/nr/cc_worker.cc`
  - `decode_pdcch_dl()`
  - calls `srsran_ue_dl_nr_find_dl_dci(&ue_dl, &dl_slot_cfg, rnti.id, rnti.type, ...)`
  - for RA-RNTI, current trace prints only:
    `slot`, `rnti`, `n_dl`, `candidates`, `max_epre`, `max_corr`

The library RA search path is:

- `lib/src/phy/ue/ue_dl_nr.c`
  - `srsran_ue_dl_nr_find_dl_dci()`
  - if `q->cfg.ra_search_space_present && rnti_type == srsran_rnti_type_ra`,
    it searches only `q->cfg.ra_search_space`
  - otherwise it searches all configured common/UE search spaces

The RAR search-space source is:

- `lib/src/asn1/rrc_nr_utils.cc`
  - when `ra_search_space_present` matches a common search-space ID, it copies
    that search space, sets `type=common_1`, `nof_formats=1`, and
    `formats[0]=dci_format_nr_1_0`
- `srsue/src/stack/rrc_nr/rrc_nr.cc`
  - copies the selected configured search space into `phy_cfg.pdcch.ra_search_space`
    and sets `type=common_1`

The DCI 1_0 RA-RNTI size path is:

- `lib/src/phy/phch/dci_nr.c`
  - `dci_nr_format_1_0_sizeof()`
  - for RA-RNTI it includes frequency assignment, time-domain assignment,
    VRB mapping, MCS, TB scaling, and `16` reserved bits

## Threshold/Decode Behavior

Per candidate, `ue_dl_nr_find_dci_ncce()` records:

- DCI context: aggregation, NCCE, CORESET, format, RNTI type/RNTI
- DCI bit count
- DMRS measurement: EPRE, RSRP, normalized correlation, CFO, sync error
- decode result: CRC

It then applies:

- EPRE threshold: `m->epre_dBfs < q->pdcch_dmrs_epre_thr` skips decode
- correlation threshold: `m->norm_corr < q->pdcch_dmrs_corr_thr` skips decode
- otherwise it calls `srsran_pdcch_nr_decode()` and stores `pdcch_info->result`

CP2054's SI candidate row proves live thresholds in this run were:

```text
corr_thr=0.500000
epre_thr=-80.000
```

CP2057's first exact RAR slot measured:

```text
slot=10130 rnti=0x39 n_dl=0 candidates=1 max_epre=30.178 max_corr=0.721001
```

Assuming the same thresholds apply, that candidate is above both gates and
should have reached `srsran_pdcch_nr_decode()`. Since `n_dl=0`, the likely
remaining source-level outcomes are:

- PDCCH decode was attempted but CRC failed under RA-RNTI `0x39`
- DCI size/format/search-space geometry differs between gNB RAR transmission
  and UE RA-RNTI search
- a candidate-level value not printed by the current RAR trace separates it
  from the successful SI candidate path

The current RAR trace cannot distinguish those outcomes because it does not
print candidate identity, DCI bit count, decode-attempt status, or CRC.

## Verdict

PASS, no-RF source audit.

CP2057's strong first RAR candidate should not trigger another RF run or a
threshold change. The next rung should be a minimal default-off RA-PDCCH
candidate trace, mirroring the already deployed SI candidate trace fields:

- active `corr_thr` and `epre_thr`
- RA search-space ID/type, CORESET ID, DCI format, DCI bit count
- per-candidate aggregation level, NCCE, EPRE, RSRP, normalized correlation,
  CFO, sync error
- `decode_attempted`
- CRC result

That trace should be metadata-only, env-read-once, row-capped, and active only
inside RA-RNTI/RAR windows. It should not alter thresholds, scheduler behavior,
RAR payloads, gateware, or RF cadence.

The applied-CFO repeat remains a separate RF item pending explicit approval
after CP2056's env propagation gate.
