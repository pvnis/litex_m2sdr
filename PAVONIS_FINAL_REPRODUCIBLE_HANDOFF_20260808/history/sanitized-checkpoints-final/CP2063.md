## Findings

1. The current upper PRACH detector does not contain a stage-1 policy. It only
   has diagnostic detector trace support, `PAVONIS_PRACHDET_THRESHOLD_OVERRIDE`,
   and the in-process accepted-PRACH arm-file hook.

2. CP1966's stage-1 code is not a detector-file patch. It patches the lower PHY
   `prach_processor_worker.cpp` at the raw CF32 `demod_cf_buf` insertion point,
   before `demodulator->demodulate(*buffer, demod_cf_buf, config)`.

3. The current lower PRACH worker already has reusable transform plumbing:
   `pavonis_demod_input_transform_buffer`, PRACH-format gating, helper env
   readers, a static `PAVONIS_PRACH_DEMOD_INPUT_CFO_HZ`/`PHASE_DEG` transform,
   and an opt-in CFO-only search
   `PAVONIS_PRACH_DEMOD_INPUT_CFO_SEARCH`.

4. The current lower PRACH worker does not contain
   `PAVONIS_PRACH_DEMOD_INPUT_STAGE1_POLICY` or
   `PAVONIS_PRACH_DEMOD_INPUT_STAGE1_TRACE`.

5. Existing current knobs cannot reproduce CP2062:
   - `PAVONIS_PRACH_DEMOD_INPUT_CFO_SEARCH` searches CFO only.
   - `PAVONIS_PRACH_DEMOD_INPUT_OFFSET_SAMPLES` only drops a positive prefix.
   - `PAVONIS_PRACH_DEMOD_INPUT_CFO_HZ`/`PHASE_DEG` applies a static CFO/phase
     transform but no timing/fractional shift search.
   - CP2062's successful CP2060 corrections require combined negative integer
     shifts (`-96..-352` samples), fractional `+/-0.5`, and CFO `+21..+37 kHz`.

6. CP1966's important selection rule remains valid for the current port:
   select the best accepted/in-gate p0 candidate, not the highest raw p0 tail
   peak. CP1965 and CP2062 both show tail peaks can be larger while failing the
   live detector delay gate.

## Verdict

The current branch does not already provide an equivalent safe CP2062 recovery
mechanism. The already-present CFO-only and static transform paths are
insufficient because the recovered CP2060 class needs a coupled timing+CFO
search.

The minimal next implementation is a default-off current-branch port inside
`ocudu/lib/phy/lower/processors/uplink/prach/prach_processor_worker.cpp`, not
an upper-detector threshold change, RAR/scheduler change, collection-delay
[interface-redacted], gateware change, or migration branch.

## Safe Implementation Shape For The Next Checkpoint

Implement only a default-off stage-1 block at the current raw CF32
`demod_cf_buf` point, preserving all current code paths when disabled:

- Env gate: `PAVONIS_PRACH_DEMOD_INPUT_STAGE1_POLICY`, default off.
- Trace gate: `PAVONIS_PRACH_DEMOD_INPUT_STAGE1_TRACE`, row-capped, default off.
- Strict scope: `nof_ports == 1`, PRACH format zero, start symbol zero, one TD
  occasion, one FD occasion.
- Candidate grid defaults: shift `-448..-96` step `32`, fractional `-0.5/+0.5`,
  CFO `+20000..+50000 Hz` step `1000`, max candidates `1024`.
- Energy gate defaults retained from CP1966 (`rms >= -70 dB` or
  `peak >= -55 dB`) to avoid scanning empty windows.
- Candidate evaluation: create a temporary PRACH buffer and detector, demodulate
  each transformed candidate, and select only accepted preamble-index-0 results
  by best detection metric.
- Apply only the selected candidate transform to `demod_cf_buf` before the real
  demodulation.
- Do not alter detector thresholds, RAR contents, scheduler timing, PRACH
  collection timing, PDSCH phase-ramp behavior, or gateware.

Implementation should be a minimal port into the current file, not a wholesale
restore of CP1966's older file, because the current branch has later strong
predemod capture, collection timing, CFO-search, and arm-file instrumentation
that must be preserved.
