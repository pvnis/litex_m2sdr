## Proven From Data In Hand

CP2060 and CP2065 match at the run/config/readback level:

- `gnb-run.yml` files are byte-identical by SHA-256.
- Both logs show `PAVONIS_GNB_SI_PDSCH_POWER_SIGN_COMPAT active`.
- Both logs show `PAVONIS_GNB_POWER_CONTROL_OFFSET_SS_DB active value=6`.
- TX readback core is identical.
- TX channel readback is identical.
- Native continuous/all-timed cadence gate is identical.
- Runtime health is same-class:
  - CP2060: `126093` TX timeouts, `160` downlink-late lines
  - CP2065: `125073` TX timeouts, `195` downlink-late lines

Both use the same all-timed CS16 TX class, `11.52 Msps`, `1842.5 MHz`, TX gain `5 dB`, `30 ms` TX time offset, no reanchor, and no forced continuous stream.

## Not Proven From Data In Hand

The packaged [host-redacted] logs do not contain the requested per-SI FAPI/PDCCH/PDSCH PDU fields.

Targeted searches of CP2060 and CP2065 `gnb.log` found:

- `SI-RNTI`: `0`
- `rnti=0xffff` / `0xffff`: `0`
- `FAPI` / `DL_TTI`: `0`
- `PDCCH`: `0`
- `PDU`: `0`
- `SIB1`: `0`
- `PDSCH`: `1` in each run, but only in the `PAVONIS_GNB_SI_PDSCH_POWER_SIGN_COMPAT active` banner, not in a per-occasion PDU record.

`qcore.log` and `gnb-run.yml` also do not contain per-SI PDU records. Therefore the artifact set cannot prove:

- same SI FAPI PDUs;
- same SI PDCCH/PDSCH power fields at each SI occasion;
- same scheduler/FAPI SI cadence.

## Verdict

Existing [host-redacted] artifacts confirm same run config, same power-sign/power-offset activation, same TX readback, and same cadence class between CP2060 and CP2065. They do not contain enough per-SI scheduler/FAPI evidence to decide whether the CP2065 scheduled-lattice deficit was born in scheduler/FAPI emission or later in the TX/RF path.

This is an evidence gap, not a contradiction of CP2068/CP2069.
