## Source Provenance

Live CP2074B local source:

- File: `litex_m2sdr/litex_m2sdr/software/soapysdr/LiteXM2SDRStreaming.cpp`
- Hash: `dd962af362651316fa162a07da734ececa083f7e83d44906e5d8c016916702ae`

The marker is emitted inside `SoapyLiteXM2SDR::writeStream()` when all of these
are true:

- `_tx_stream.remainderHandle >= 0`.
- `M2SDR_SOAPY_TX_ALIGN_HAS_TIME_REMAINDER` is enabled.
- Incoming write has `SOAPY_SDR_HAS_TIME`.
- Incoming `timeNs > 0`.
- `_tx_stream.remainderOffset > 0`.
- Existing partial remainder is not already timed.
- `_tx_stream.samplerate > 0`.
- `_tx_stream.remainder_timeNs > 0`.
- Incoming sample timestamp is within one MTU of
  `remainder_timeNs + remainderOffset`.

When that branch fires, it logs through `SoapySDR_logf(SOAPY_SDR_INFO, ...)`
and then clears `SOAPY_SDR_HAS_TIME` from `effective_flags`. The marker text is:

`M2SDR TX HAS_TIME remainder align: keeping contiguous untimed buffer`

The marker cap is `16` process-local emissions, controlled by a static
`std::atomic<uint64_t> keep_log_count`.

The old split branch logs:

`M2SDR TX HAS_TIME remainder align: releasing partial ... buffer`

That branch also uses `SoapySDR_logf(SOAPY_SDR_INFO, ...)`, also capped at
`16` emissions by `align_log_count`, and fires when a timed incoming write
forces a remainder release instead of being treated as contiguous.

Other HAS_TIME suppression path found in the live source:

- `releaseWriteBuffer()` has the older duplicate-timestamp de-dup path.
- It is enabled by default through `m2sdr_env_tx_dedup_time_enabled()`.
- If `M2SDR_SOAPY_TX_DEDUP_TIME` is unset, it returns true.
- It clears `SOAPY_SDR_HAS_TIME` when a descriptor has the same timestamp as
  the previous HAS_TIME descriptor.
- It does not print the CP2074B "keeping" marker.
- It increments `dedup_suppressed` and is visible in the worker trace/release
  summary.

No other TX-side `effective_flags &= ~SOAPY_SDR_HAS_TIME` path was found in
the live source. RX paths also set/clear HAS_TIME metadata, but they are not
part of this TX descriptor question.

For CP2073 and CP2075, `dedup_suppressed=0`, so the duplicate-timestamp
suppression path does not explain either run's HAS_TIME collapse.

## Runner Shape Mismatch

The CP2073 full-ladder wrapper readback had:

- `write_timeout_us=1000`
- `env_M2SDR_SOAPY_TX_TIME_OFFSET_NS=30000000`
- `tx_all_timed_chunks=1`

The CP2075 detached gNB-only runner readback had:

- `write_timeout_us=200`
- `env_M2SDR_SOAPY_TX_TIME_OFFSET_NS=` empty
- `tx_all_timed_chunks=1`

Source of the mismatch:

- The full wrapper `cp1807_run_stage6_raresp40_realue_rar_msg3.sh` defaults
  `TX_TIME_OFFSET_NS=30000000` and `TX_WRITE_TIMEOUT_US=1000`, then injects
  them into the remote [host-redacted] environment as
  `M2SDR_SOAPY_TX_TIME_OFFSET_NS` and `OCUDU_SOAPY_TX_WRITE_TIMEOUT_US`.
- CP2075 bypassed that wrapper and invoked the detached [host-redacted] start helper
  directly without exporting those two variables.

This mismatch mechanically explains the large HAS_TIME population change.
CP2075 did not enter the same dense timed-descriptor/partial-remainder regime
that produced CP2073's short non-EOB rows.

## Verdict

The correct explanation is:

`trigger absent in this run shape, fix unexercised`

It is not:

`fix fired massively, marker defective/misrouted`

Reasons:

- CP2075 `pre_has_time_rows` equals `post_has_time_rows` (`82` each), so there
  is no hidden mass HAS_TIME suppression in the worker trace.
- CP2075 `dedup_suppressed=0`, so the markerless duplicate-timestamp path did
  not suppress HAS_TIME.
- Both CP2074B marker strings have runtime count `0`, consistent with the
  CP2074B branch never being reached.
- CP2075 has no partial/short descriptor rows and no mixed write-size pattern,
  so the untimed-remainder trigger condition did not arise.
- CP2075's gNB-only runner omitted the full-wrapper `30 ms` TX time offset and
  `1000 us` write timeout that were present in CP2073.
