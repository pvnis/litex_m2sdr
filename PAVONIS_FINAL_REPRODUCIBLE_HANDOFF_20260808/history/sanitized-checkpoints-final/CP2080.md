- `556`: `707`

The six CP2073 release-marker samples are all the old sub-MTU path:

This ties the visible old marker samples directly to the short descriptor

but it is positive evidence that CP2073 exercised the pre-fix
untimed-remainder release path in the trace window.

## Correlation

Using `10 ms` bins over the CP2073 trace:

- Same-bin timeout vs short-row Pearson: `-0.6427`
- Same-bin timeout vs HAS_TIME-row Pearson: `-0.3024`
- Same-bin short-row vs HAS_TIME-row Pearson: `+0.7966`
- Short rows in bins with timeouts: `319`
- Short rows in bins without timeouts: `1022`
- HAS_TIME rows in bins with timeouts: `7194`
- HAS_TIME rows in bins without timeouts: `13856`
- Dense HAS_TIME bins, threshold `>=42` HAS_TIME rows per `10 ms`: `100`
- Mean timeout count in dense HAS_TIME bins: `0.0`
- Mean timeout count in non-dense bins: `4.47`

Same-bin data therefore rejects the simple model "timeout line and short
descriptor happen in the same 10 ms bin." Timeout bins are often no-submit or
low-submit gaps, which is expected because a timeout does not produce a worker
descriptor row.

Lagged CP2073 correlations show a periodic catch-up pattern:

- Best timeout-to-HAS_TIME lag: `+10 ms`, Pearson `+0.8708`
- Best timeout-to-short lag: `-20 ms`, Pearson `+0.7106`
- Selected lag samples:
  - `0 ms`: timeout vs short `-0.6427`, timeout vs HAS_TIME `-0.3024`
  - `+10 ms`: timeout vs short `+0.4599`, timeout vs HAS_TIME `+0.8708`
  - `+20 ms`: timeout vs short `+0.7021`, timeout vs HAS_TIME `+0.3328`
  - `+100 ms`: timeout vs short `+0.6956`, timeout vs HAS_TIME `+0.3254`

Interpretation: CP2073's dense regime is not a same-instant timeout effect; it
is consistent with timeout/catch-up feedback on the 10 ms write cadence. Timeout
gaps are followed by HAS_TIME-dense catch-up stretches, and the old
untimed-remainder release path turns some of those stretches into short
non-EOB descriptors. CP2077/CP2079 have lower timeout rates, no old release
markers, no keep markers, and no short descriptors.

## Silent-Suppression Source Audit

Fetched and verified source inputs:

- True pre-CP2074 source from the first CP2074 backup:
  `89a4ac7ebe8b6541dc11c4967d53e22abc129c9be128b5ee49f5f741d0df122f`
- Superseded strict CP2074 source:
  `3bfe2a82da8f349b4bfd751a852f2b27f19d04526bb968246e8e9b1d477d6c2e`
- Live CP2074B source:
  `dd962af362651316fa162a07da734ececa083f7e83d44906e5d8c016916702ae`

The true pre-CP2074 to CP2074B diff is localized to `writeStream()`:

- Adds `int effective_flags = flags`.
- Removes the old unconditional untimed-remainder release behavior for
  incoming timed writes.
- Computes `sample_delta` even when the existing remainder is untimed.
- For untimed partial remainders, treats `abs(sample_delta) <= MTU` as
  contiguous.
- In that contiguous branch, emits the keep marker and then clears
  `SOAPY_SDR_HAS_TIME` from `effective_flags`.
- Larger discontinuities still use the old release path and release marker.
- Later uses of `effective_flags` are limited to:
  - deciding whether to merge HAS_TIME into the existing partial buffer,
  - merging END_BURST into the existing partial buffer,
  - seeding `buffer_flags` for a newly acquired buffer.

No `releaseWriteBuffer()` behavior changed in the true pre-CP2074 to CP2074B
diff. No other assignment changes `effective_flags`.

Silent-suppression verdict:

- There is no separate markerless branch where `effective_flags` can change
  descriptor flags or write handling.
- Every flag-changing use of `effective_flags` depends on the single contiguous
  untimed-remainder branch.
- That branch emits the keep marker before clearing HAS_TIME, but the marker is
  capped at `16` log lines. After the cap, additional intended suppressions
  would be behaviorally silent in logs, though still within the intended branch.
- Therefore a run with keep-marker count `0` in a fresh gNB process, such as
  CP2077/CP2079, did not exercise the CP2074B suppression branch at all.

## Verdict

The forensics support the timeout-fragmentation feedback hypothesis:

- CP2073 has a much higher timeout rate inside the trace window.
- CP2073 has old sub-MTU untimed-remainder release markers with offsets that
  match the short descriptor families.
- Short and HAS_TIME-dense rows are strongly coupled to each other.
- Timeout bursts are not same-bin with short rows, but lagged correlations show
  the expected timeout-gap then catch-up-write cadence.
- CP2077/CP2079 are post-fix sparse/clean controls with lower timeout rates and
  no markers/short descriptors.

The source audit rules out CP2074B as a markerless behavior change beyond its
intended branch. Absence of keep markers in CP2077/CP2079 means the suppression
branch did not fire in those sparse regimes; it does not mean the source fix is
misrouted.

This is strong enough to treat CP2073's dense descriptor regime as churn
feedback that CP2074B removes at the source when it occurs. Per the user's
unlock rule, one additional CP2079-shape sparse+clean gate is the next
checkpoint to confirm the post-fix sparse/clean state before unlocking the full
ladder RF run by explanation.
