## Findings

The chain preserves one `STAMP`:

- CP2087 sets `STAMP="${STAMP:-...CP2087_SIGNED_STAGE1_POLICY_RF_ANALYZED}"`.
- CP2085 uses `STAMP="${STAMP:-...CP2085_SIGNED_STAGE1_POLICY_RF}"`, so it
  preserves CP2087's exported stamp.
- CP2035 exports the inherited `STAMP`.
- CP2031 uses `STAMP="${STAMP:-...CP2031_SI_CANDIDATE_SYNC_ERROR_TRACE_RF}"`,
  so it also preserves the inherited stamp.
- CP1807 uses `STAMP="${STAMP:-...CP1807_RARESP40_REALUE_RARMSG3}"`, so the
  inherited stamp is preserved through the final runner.

The summary path is identical at the two critical points:

- CP2087 expects:
  `cp1733_stage6_realue_sib1_rachcfg_summary_${STAMP}.json`
- CP2035 expects:
  `cp1733_stage6_realue_sib1_rachcfg_summary_${STAMP}.json`
- CP1807 writes:
  `cp1733_stage6_realue_sib1_rachcfg_summary_${STAMP}.json`

CP1807's Python summary writer receives that exact path as its first argument
and writes it with:

```text
out.write_text(json.dumps(summary, indent=2, sort_keys=True) + "\n")
```

CP2087 then runs the CP2086 analyzer against the same path and records:

- `RF_RC`
- `ANALYSIS_RC`
- `SUMMARY_JSON`
- `ANALYSIS_JSON`
- `ANALYSIS_MD`

This closes the script-level mismatch risk for the next approved RF checkpoint:
if CP2087 completes, the PRACH/RAR interpretation will be based on the same
summary JSON generated by the RF run.
