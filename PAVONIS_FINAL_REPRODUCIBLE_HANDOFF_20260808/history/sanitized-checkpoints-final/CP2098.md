## Interpretation

CP2098 proves the CP2097 `shift=-96 / +21 kHz` recovery point is not stable
enough to freeze as the live policy. The current run's saved live-energy
window instead points to a near-zero-CFO, `shift≈-176` class.

This reinforces the user's warning that the stage-1 "CFO" axis is likely
absorbing per-occasion timing/phase structure rather than a physical LO error:
successive valid runs have pointed at materially different apparent CFOs.

## Decision

Next RF checkpoint should keep the full frozen ladder shape and change only
the stage-1 envelope to a very low-cost CP2098-derived point:

- `shift=-176`
- `CFO=0 Hz`
- `max_candidates=4`
- RAR candidate trace on

This keeps search latency in the CP2098 class while testing the strongest
saved-window recovery point. If it accepts and RAR still lands after the UE
window, the result-delivery/scheduler timing source must be revisited. If it
rejects, the static-envelope approach is likely chasing a run-varying timing
presentation effect, and the next source work should make the detector derive
the correction from each window or fix the upstream time/phase presentation.
