# CHECKPOINT 2108 - No-RF RAR visibility comparison identifies missing scheduler geometry

Date: [date-redacted] Europe/Zurich

## Goal

Compare the CP2101 RA-PDCCH-CRC-OK RAR slot against CP2106/CP2107
RAR-transmitted-but-UE-`n_dl=0` slots without new RF. The purpose was to decide
whether the next step should be more PRACH envelope work, a config-only RAR
timing change, or gNB-side RAR scheduling instrumentation.

## Inputs

- CP2101:
  `[date-redacted]CP2101_STAGE1_SHIFTM352_CFO33_49_RARTRACE_RF`
- CP2106:
  `[date-redacted]CP2106_STAGE1_NEGGRID_RARPATH_RF`
- CP2107:
  `[date-redacted]CP2107_STAGE1_NEGGRID_REPEAT_RARPATH_RF`

All three runs are early-pass downlink rolls with SIB1 decoded, UE Msg1
attempts, gNB RAR PDU trace enabled, and UE RA-RNTI/RAR traces enabled.

## Findings

The CP2101 successful RA-PDCCH candidate is real:

- UE candidate trace row:
  `slot=6291`, `rnti=0x39`, `n_dl=1`, `max_epre=33.324`,
  `max_corr=0.680412`, `decode_attempted=1`, `crc=1`,
  identity `L=2,ncce=0,coreset=0,format=2,bits=37`.
- Matching UE RAR window:
  `prach_tti=6254`, `ra_window_start=6257`, `ra_window_length=40`.
- gNB RAR PDU near the same event:
  RAPID `0`, temp C-RNTI `0x4604`, TA `35`,
  `pdu_hex=[nas-redacted]`.

CP2101 also contains no-candidate RAR opportunities in the same run:

- Earlier RAR-window rows at slots such as `694`, `1814`, and `2934` have
  scheduled-looking EPRE around `32 dB` but `n_dl=0` and low correlation
  (`0.059..0.090` class).
- Therefore CP2101 is mixed: it proves the UE can decode an RA-PDCCH candidate
  under this shape, but the same run also has RAR slots that look like the
  CP2106/CP2107 no-candidate class.

CP2106/CP2107 repeat the no-candidate class:

- CP2106 expected UE slot `8857`:
  `n_dl=0`, `max_epre=31.774`, `max_corr=0.031554`.
- CP2107 first RAR window `5297..5337`:
  no candidate/path rows; strongest nearby scheduled-looking row
  `slot=5334`, `max_epre=21.577`, `max_corr=0.047700`; exact late rows remain
  `n_dl=0`.
- CP2107 second RAR window `7537..7577`:
  no candidate/path rows; strongest nearby scheduled-looking row
  `slot=7574`, `max_epre=21.597`, `max_corr=0.021077`; exact late rows remain
  `n_dl=0`.

The existing gNB trace is insufficient for a hard geometry verdict:

- `PAVONIS_GNB_RAR_PDU_TRACE` is emitted from
  `ocudu/lib/mac/mac_dl/rar_pdu_assembler.cpp`.
- It prints payload-level fields only: RA-RNTI, RAPID, temp C-RNTI, TA, RAR
  grant fields, and PDU hex.
- It does not print the scheduler's chosen RAR PDCCH slot, RAR PDSCH slot,
  PDSCH time-domain resource, symbols, CRBs, search-space/aggregation choice,
  response-window start/stop, or Msg3 slot/delay.
- Inferring RAR DL timing from later Msg3 PUSCH trace rows is useful but not
  decisive enough for another RF rung.

The existing RAR-window offset knob is the wrong direction for this failure:

- Source audit found `PAVONIS_RACH_RAR_WINDOW_OFFSET_SLOTS` in
  `ocudu/lib/scheduler/common_scheduling/ra_scheduler.cpp`.
- It accepts only `0..1000` and sets
  `rar_window_ref_slot = msg.slot_rx + offset`.
- That moves the schedulability window later. It does not provide a
  default-off way to force the RAR DL allocation earlier inside the UE's
  existing response window.

## Decision

Stop PRACH stage-1 envelope iteration. Msg1/RAR supply is good enough for the
next rung.

Do not change thresholds, RAR payloads, scheduler policy, delay constants, or
gateware yet. The immediate next step should be a no-RF default-off
metadata-only gNB RAR scheduling trace at the scheduler boundary, not another
RF run. It should emit, per allocated RAR:

- RA-RNTI, RAPID, temp C-RNTI, TA
- PRACH slot, response-window start/stop, and current `pdcch_slot`
- RAR PDSCH slot (`pdcch_slot + k0`), time-domain resource index, symbols, CRBs
- RA search-space ID, aggregation level, and any CCE/nCCE if available at that
  layer
- Msg3 slot(s), delay/K2, temp C-RNTI, and selected PUSCH resource index
- failed-attempt counters when a pending RAR is postponed or expires

Once build/deploy proof passes, one bounded RF diagnostic can answer whether
CP2106/CP2107 are no-candidate because the RAR is scheduled too late or in an
unexpected slot/resource, versus because the DL/RF presentation at RAR
occasions is bad despite correct scheduler geometry.
