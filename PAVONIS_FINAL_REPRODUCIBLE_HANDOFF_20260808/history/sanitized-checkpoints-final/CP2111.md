## Data Comparison

Both CP2101 and CP2110 used `PAVONIS_PRACH_TIMING_COMPENSATION_SAMPLES=352536`.
The strong-window manifests show:

```text
timing_compensation_samples=352536
timing_compensation_samples_per_slot=11520
timing_compensation_report_slot_offset=30
timing_compensation_residual_samples=6936
timing_compensation_collection_override=1
```

So the lower-PHY PRACH worker collects around the actual/source PRACH slot but
reports the detection 30 slots later.

CP2110 decisive row:


The gNB RAR PDCCH is `+43` slots from the UE actual PRACH slot and lands at the
UE response-window edge.

CP2101 contrast:

```text
source slot 625:4 -> reported slot 628:4
selected baseline shift=0 frac=0 cfo=0 metric=4.412389 search_time_us=2628
```

For the CP2101 visible candidate, the RAR PDCCH is `+37` slots from the UE
actual PRACH slot, still inside the live UE response window with margin. CP2101
also had earlier RARs whose detailed RAR-window trace was capped, so CP2101 is
not a pure success case; it is the only proof so far that the RA-PDCCH can be
visible with the current geometry.

## Source Audit

`prach_processor_worker.cpp` derives the reported slot from the timing
compensation value:

```text
timing_compensation_report_slot_offset = timing_compensation_samples / samples_per_slot
pavonis_notify_context = prach_context
pavonis_notify_context.slot += timing_compensation_report_slot_offset
notifier->on_rx_prach_window(..., pavonis_notify_context)
```

`phy_to_fapi_results_event_fastpath_translator.cpp` then builds the FAPI
`RACH.indication` with that slot:

```text
builder.set_slot_point(slot)
```

`fapi_to_mac_indications_fastpath_translator.cpp` copies it into MAC:

```text
indication.slot_rx = msg.slot
```

`mac_rach_handler.cpp` copies it into the scheduler message:

```text
sched_rach.slot_rx = rach_ind.slot_rx
```

`ra_scheduler.cpp` uses it directly as the RAR reference:

```text
rar_req->prach_slot_rx = msg.slot_rx
rar_req->rar_window_ref_slot = msg.slot_rx + pavonis_rar_window_offset_slots
rar_req->rar_window = {rar_window_ref_slot + prach_duration, ...}
```

Therefore the timing-compensation report offset is not just metadata. It moves
the scheduler's RAR response-window reference by `+30` slots even though the UE
starts its RA response window from the actual PRACH transmission time.

## Interpretation

The CP2110 no-candidate RAR is best explained as a slot-attribution bug induced
by the coupled timing-compensation path:

- Delayed collection is still needed to put the live Msg1 energy inside the
  PRACH detector input.
- Reporting the delayed slot to FAPI/scheduler shifts the RAR response window
  later by 30 slots.
- The shifted gNB window overlaps the UE's real response window only at the
  tail. CP2110's selected non-baseline stage1 search took `5226 us` and the
  scheduler placed the RAR on the UE window edge, where the UE saw no candidate.
- CP2101's visible candidate occurred with the same `+30` report offset but
  earlier relative placement (`+37` slots from actual PRACH), leaving some
  margin.

This is not a RAR payload, RAPID, RA-RNTI, DCI-size, or PDSCH-resource finding.
The immediate issue is that PRACH collection delay and PRACH slot attribution
are coupled when they should be separable.

## Decision

Implement a default-off diagnostic knob in the PRACH worker to override the
reported slot offset independently of the collection delay. The first RF test
should keep `PAVONIS_PRACH_TIMING_COMPENSATION_SAMPLES=352536` but report the
source PRACH slot to FAPI/scheduler by setting the new override to `0`.

Expected result: if the scheduler receives the PRACH indication before the
actual UE response window closes, it should schedule RAR earlier in the UE
window and the UE should either decode RAR or at least produce RA-PDCCH/PDSCH
candidate/path rows. If the RAR becomes unschedulable because detector latency
still exceeds the real UE window, the next target is stage1 search-time
reduction, not PRACH envelope retuning.

Do not change RAR payloads, RA-RNTI semantics, thresholds, PRACH envelope,
delay constants, downlink power, or gateware for the next rung.
