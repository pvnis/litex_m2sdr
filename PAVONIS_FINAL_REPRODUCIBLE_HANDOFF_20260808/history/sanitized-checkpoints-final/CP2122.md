# CHECKPOINT 2122 - RAR Postponed Trace Deploy

Date: [date-redacted] Europe/Zurich

## Purpose

Follow up CP2121's no-RF conclusion that RAR scheduled-slot phase is the
leading discriminator. Audit the RAR scheduler source and add a telemetry-only
trace extension so the next RF run can explain why earlier in-window RAR slots
were skipped before the successful CP2120 slot `6614`.

No RF was run in this checkpoint.

## Source Audit

Relevant source:

```text
ocudu/lib/scheduler/common_scheduling/ra_scheduler.cpp
ocudu/lib/scheduler/common_scheduling/ra_scheduler.h
```

Findings:

- Existing Pavonis timing knob is only
  `PAVONIS_RACH_RAR_WINDOW_OFFSET_SLOTS`.
- That knob accepts integer `0..1000` and moves the RAR window reference later;
  it cannot choose an earlier in-window RAR slot or target `mod160=51`.
- `max_dl_slots_ahead_sched` is `8`.
- The scheduler processes pending RARs by trying candidate PDCCH slots from the
  current scheduler slot through the lookahead window.
- Candidate rejection reasons are only `logger.debug()` by default. CP2120's
  final scheduler trace had `failed_pdsch=2` before the successful allocation,
  but it did not say which earlier slots failed or why.

Therefore, before a RAR-slot advance/target knob, the missing evidence is a
bounded per-candidate postponed trace.

## Source Change

Touched source:

```text
ocudu/lib/scheduler/common_scheduling/ra_scheduler.cpp
```

Change:

- Extend existing `PAVONIS_GNB_RAR_SCHED_TRACE` in
  `ra_scheduler::log_postponed_rar()`.
- When the trace is enabled and below its row cap, emit:

```text
PAVONIS_GNB_RAR_SCHED_TRACE event=rar_postponed
```

Fields include cause, RA-RNTI, PRACH slot, RAR window ref/start/stop, optional
PDCCH slot, and current failed PDCCH/PDSCH/PUSCH counters.

Disabled behavior remains normal. The patch does not change RAR scheduling,
payloads, RA-RNTI, response-window semantics, thresholds, or gateware.

## Decision

CP2122 passes the no-RF patch/deploy gate. The next bounded RF run should use
the CP2120 shape with `PAVONIS_GNB_RAR_SCHED_TRACE=1` as before. The new trace
should answer:

1. Which slots before the successful RAR slot are considered.
2. Whether the `mod160=51` slot is reached.
3. If it is reached, whether it fails PDCCH monitoring, PDSCH resources, CSI-RS,
   Msg3/PUSCH availability, or PDCCH space.

Do not add a RAR-slot advance/target knob until this postponed-candidate trace
names the blocking reason.
