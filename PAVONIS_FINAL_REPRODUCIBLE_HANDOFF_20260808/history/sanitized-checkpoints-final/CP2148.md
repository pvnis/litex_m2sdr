## Purpose

post-upgrade baseline before any CP2142 deploy or new ladder debugging:

## Verdict

The hardware/tone baseline is stable versus CP2144, but the frozen CP2137
ladder baseline is not clean. The valid RF ladder run completed mechanically
with healthy host gates and postchecks, but srsUE failed at cell search:
`cell_search_done result=0 trials=100 nonempty=0`, with no SIB1, no PRACH TX,
and no RAR. This blocks CP2142 candidate-list deploy and ladder resume.

The requested old-kernel fallback is not actionable as a kernel split: both
hosts remained on the pre-upgrade kernel `6.8.0-101-lowlatency` after reboot,
so there is no different "old kernel" state to boot back to for this failure.

## Interpretation

The post-upgrade maintenance did not break the controlled RF path: both CW tone
directions remain in the CP2144 final-position class. The regression is specific
to the live gNB/srsUE acquisition path in the frozen CP2137 shape.

Because both hosts still booted the same pre-upgrade kernel, the old-kernel
fallback cannot distinguish this regression. The most useful next discriminator
is a no-config-change acquisition sanity control or independent srsUE-matched
DL capture, but it should be treated as maintenance-regression triage, not as
normal ladder progress. Do not deploy CP2142 or resume Msg1/RAR work until this
baseline is clean again.
