# CHECKPOINT 2159 - RAR PDCCH Geometry Audit

Date: [date-redacted]

Mode: no-RF source/report audit.

## Question

CP2158 produced the first useful RAR-candidate trace after the current Msg1
reliability work:

- gNB transmitted one RAR for RA-RNTI `0x39`, RAPID `0`, temp C-RNTI `0x4601`.
- Scheduled RAR PDCCH/PDSCH system slot was `5494` (`SFN 549 slot 4`).
- gNB trace reported search-space ID `1`, aggregation level `4`, NCCE `0`.
- UE trace at slot `5494` saw RA-RNTI `0x39`, high EPRE `31.627`, RSRP
  `23.424`, but corr only `0.151242 < 0.5`; `decode_attempted=0`, `crc=0`.
- UE candidate row was `L=2`, NCCE `0`, CORESET `0`, DCI bits `37`.

The audit question was whether this is a SearchSpace/CORESET/DCI geometry
mismatch, or a true high-energy/low-correlation RA-PDCCH failure.

## Source Findings

1. UE `cand*_L` is not the actual aggregation level. It is
   `info->dci_ctx.location.L` from `srsue/src/phy/nr/cc_worker.cc`, and the
   decoded-candidate info is populated from the DCI context in
   `lib/src/phy/ue/ue_dl_nr.c`.

2. `location.L` is the aggregation-level index/exponent. Multiple source paths
   confirm actual CCE span is `1U << L`:

   - `srsgnb/src/stack/mac/test/sched_nr_common_test.cc` checks
     `location.ncce + (1U << location.L)`.
   - `lib/src/phy/ch_estimation/test/dmrs_pdcch_test.c` expects DMRS RE count
     proportional to `(1U << aggregation_level)`.
   - `srsgnb/src/stack/mac/sched_nr_pdcch.cc` stores
     `node.dci_pos.L = record.aggr_idx` and fills CCE masks with
     `1U << record.aggr_idx`.

   Therefore UE `L=2` means actual aggregation level `4`. It matches the gNB
   report `aggregation level=4`; it is not a mismatch.

3. RAR search-space selection is aligned:

   - UE `srsran_ue_dl_nr_find_dl_dci()` searches `q->cfg.ra_search_space` when
     `rnti_type == srsran_rnti_type_ra`.
   - gNB `alloc_rar_pdcch()` allocates into `bwp_cfg.cfg.pdcch.ra_search_space`.
   - The local scheduler test configuration sets RA SearchSpace to common type
     `common_1`, CORESET `0`, and candidate index `L=2`.
   - CP2158's recorded exact slot has UE `CORESET=0`, `NCCE=0`, `L=2`, matching
     the gNB RAR allocation after translating `L=2` to AL4.

4. DCI length is aligned at the UE and has no identified source-level mismatch.
   The UE exact-slot candidate reports `bits=37`; UE obtains this from
   `srsran_dci_nr_size()` for the RA common search space. The gNB RAR PDCCH
   and the UE PDCCH decoder use the same shared NR DCI library for DCI 1_0
   common-search-space sizing/pack/unpack. For RA-RNTI DCI 1_0 the formula is
   `freq_resource_bits + 28`, so `37` corresponds to a 9-bit type-1 frequency
   resource field, consistent with the configured CORESET0/common-space path.

5. The UE trace gate is definitive for the CP2057 split. In
   `ue_dl_nr_find_dci_ncce()`, a candidate is discarded before PDCCH decode if
   EPRE is below threshold or DMRS correlation is below threshold. CP2158's
   exact-slot candidate has high EPRE but corr `0.151242`, so
   `decode_attempted=0` is a correlation-gate skip, not CRC-KO.

## Verdict

CP2158 is not explained by RAR PDCCH geometry:

- RA-RNTI matches: `0x39`.
- Slot matches: `5494`.
- CORESET matches: `0`.
- NCCE matches: `0`.
- Aggregation matches after notation translation: gNB AL4 == UE `L=2`.
- DCI size is consistent at `37` bits; no source evidence of a gNB/UE size split.

The RAR failure class is therefore:

`RAR transmitted; UE sees high EPRE at the right RA-PDCCH candidate; DMRS
correlation is too low; decode is skipped before CRC.`

This is not a threshold, payload, RAPID, RNTI, NCCE, or aggregation-level issue
based on available evidence. The remaining suspect is the RAR-epoch downlink
presentation/coherence path: reactive RAR PDCCH energy reaches the UE at the
right place, but not with a matching/coherent PDCCH DMRS.
