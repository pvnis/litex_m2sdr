# CP2168: PRACH late-context trace, no RF

Date: [date-redacted] Europe/Zurich

## Question

CP2165 and CP2167 enter a persistent PRACH-request-late regime after only
24-27 startup collection windows when the 50 us LiteX full-ring refresh is
enabled. Before changing collection delay, determine the exact requested-slot
versus current-RX-context displacement at the existing late-return branches.

## Patch

`prach_processor_worker.cpp` now has a cached, default-off
`PAVONIS_PRACH_LATE_CONTEXT_TRACE` instrument. It writes at most
`PAVONIS_PRACH_LATE_CONTEXT_TRACE_LIMIT` rows, default 64, to
`PAVONIS_PRACH_LATE_CONTEXT_TRACE_PATH`, default
`/tmp/pavonis_prach_late_context_trace.tsv`.

Each event-only metadata row records:

- branch (`delayed_pre_anchor` or `undelayed`)
- request SFN/slot
- current RX-context SFN/slot/symbol/timestamp
- current input sample count
- collection delay, target-valid state and target timestamp
- active timing compensation
- wall-clock timestamp for joining to the existing timeout summaries

There is no sample scan, matching loop, or per-sample formatting. The code is
only reached on the two existing late exits and is row-capped. Environment
configuration is read once through a function-local static configuration.

The frozen CP1807 runner propagates and records the three controls. The [host-redacted]
detached launcher removes and exports the selected trace path, and the package
helper includes the fixed default path. The existing `remote_env_prefix`
formatter remains balanced at 106 `%q` fields and 106 arguments. All three
shell scripts pass `bash -n`.
