## Result

The accepted CP2172 shape was repeated with one runtime change:
`M2SDR_SOAPY_TX_WORKER_PKT_COUNT=64`. Timed lead remained 20 ms, full-ring
refresh 50 us, and retry/carry/deadline modes remained off. No UE was started.

Host-state, launch, readback, pre-UE, stop, package, and postcheck gates pass.
The summary records 393 normal empty PRACH windows, no late-context trace file,
and binary-safe downlink-late/release-late counts of `0/0`. Thus the CP2172
no-lateness result remains intact.

The strict startup gate fails:

- `write_deficit=data_write_deficit=21942` samples (`1.9046875 ms`)
- `timeouts=21`
- `partial_ret=1`
- all retry/carry/deadline counters remain zero

All counters are already present at logical write 100 and remain unchanged
through the stop summary at logical 62913. The larger pool improves CP2172's
23896-sample/23-timeout deficit by only 1954 samples and CP2173's
22874-sample/22-timeout deficit by only 932 samples. It does not absorb the
startup burst as predicted.

## Activation proof status

The wrapper logs `settings_m2sdr_tx_worker_pkt_count=64`. Source inspection
shows the value is propagated through the main remote environment, captured by
the detached launcher, and exported into the generated gNB runner. That runner
also fixes `SOAPY_SDR_PLUGIN_PATH` to the rebuilt CP2174 module directory.

The expected INFO marker
`M2SDR TX worker packet pool override active: ...` is absent from both packaged
log routes. Because CP2164 already established that some Soapy INFO markers are
not preserved by these routes, absence is not proof that the branch was off;
however, it means this run did not meet CP2174's explicit mechanism-proof gate.

## Verdict and next

FAIL, bounded and mechanically healthy. Do not raise the pool value or change
lead/timing. Stay no-RF and audit every remaining `kWorkerPktCount` use, FIFO
capacity semantics, worker creation timing, plugin selection, and marker log
route. The next action must distinguish an override that was unexercised from
one that was active but aimed at the wrong queue. Keep the 20 ms lead result;
there is no PRACH request-late regression.
