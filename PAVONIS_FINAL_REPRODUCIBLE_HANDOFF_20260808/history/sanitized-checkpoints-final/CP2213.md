# CP2213: PRACH coarse / UE TX timestamp provenance (no RF)

Date: [date-redacted]

## Question

Explain why the same negative stage-1 family needed materially different
non-PRACH lower-PHY offsets in CP2205 and CP2212, and identify whether the
remaining Msg3 displacement is produced by the gNB collection timeline or the
UE transmit timeline.

## Inputs and method

- Reused only saved CP2205, CP2210, and CP2212 artifacts; no RF was run.
- Correlated each accepted gNB strong-predemod PRACH window against the exact
  corresponding srsUE bladeRF SC16 transmit dump.
- Corrected the preliminary CP2210 join to use accepted host burst `000004`
  with strong window `000002`; the result remained waveform start `-874`, CFO
  `+4075 Hz`, correlation `0.942965`.
- Joined each accepted PRACH and its first Msg3 bladeRF metadata. The comparison
  separates the srsUE-requested timestamp (`tx_guard_old_timestamp`) from the
  timestamp actually submitted to bladeRF (`timestamp`).
- Normalized the saved Msg3 raw-symbol correlations to the common lower-PHY
  non-PRACH offset `-241118` samples.

Reproducible compact outputs:

- `cp2213_measure_prach_coarse_position.py`
- `cp2205_prach_coarse_r200.json`
- `cp2210_prach_coarse_r200.json`
- `cp2212_prach_coarse_r200.json`
- `cp2213_join_tx_metadata.py`

## Results

| Run | PRACH waveform start | Requested interval error | Emitted interval error | Observed Msg3 residual | Predicted residual |
|---|---:|---:|---:|---:|---:|
| CP2205 | +3578 | -21 | +203 | 0 | 0 |
| CP2210 | -874 | -664 | +1336 | -3320 | -3319 |
| CP2212 | -3177 | -8 | -674 | -7632.5 | -7632 |

The prediction is, relative to CP2205:

`PRACH coarse-position change + emitted PRACH-to-Msg3 interval-error change`.

It matches the measured Msg3 residual to at most one sample across all three
runs. This is not an approximate class correlation; it is an exact decomposition
of the saved sample-domain observations.

The pre-guard scheduler timestamps are coherent:

- CP2205: requested interval `403179` vs nominal `403200` (`-21`).
- CP2210: requested interval `414056` vs nominal `414720` (`-664`), consistent
  with the run's nonzero TA rather than millisecond scheduling jitter.
- CP2212: requested interval `403192` vs nominal `403200` (`-8`).

The bladeRF debug path destroys that coherence. The frozen shape sets:

- `PAVONIS_RF_BLADE_TX_DBG_TX_GUARD_SAMPLES=40000`
- `PAVONIS_RF_BLADE_TX_DBG_PRACH_TIME_OFFSET_SAMPLES=-16000`
- `PAVONIS_RF_BLADE_PRACH_BURST_ONLY=1`
- `PAVONIS_RF_BLADE_TX_DBG_HIGH_PEAK_TX_NOW=0`

In `srsRAN_4G/lib/src/phy/rf/rf_blade_imp.c`, every high-peak buffer forced to
SOB by `PRACH_BURST_ONLY` is independently compared with the current bladeRF TX
hardware timestamp. If late, its scheduler timestamp is replaced by
`pre_tx_timestamp + 40000`; the generic amplitude-gated "PRACH" offset then
subtracts `16000`. Therefore both PRACH and Msg3 are independently retimed to
`pre_tx_timestamp + 24000`, even though Msg3 is not PRACH.

The independently recomputed guard corrections differ between PRACH and Msg3:

| Run | PRACH guard correction | Msg3 guard correction | Difference |
|---|---:|---:|---:|
| CP2205 | 26331 | 26555 | +224 |
| CP2210 | 22036 | 24036 | +[date-redacted] |
| CP2212 | 19665 | 18999 | -666 |

Those differences exactly create the emitted interval errors above. The
`HIGH_PEAK_TX_NOW` branch is not active and is not the cause.

## Verdict

CP2211's sign-only dynamic mapping is rejected. Stage-1 fine-shift sign does not
encode the run's coarse PRACH position, and the UE debug TX path independently
adds a second per-burst timing error.

The immediate source fix is on the UE bladeRF path: add a default-off coherent
guard-bias mode that derives one timestamp correction at the first eligible
high-peak burst and applies that same correction to later forced high-peak
bursts. This preserves the scheduler's PRACH-to-Msg3 interval, including TA,
while retaining the first-burst lead that made PRACH transmit reliably. Keep
the existing `-16000` adjustment common to both bursts for this diagnostic so
it does not reintroduce a relative shift.

This source fix does not by itself remove the separate run-to-run PRACH coarse
position (`+3578`, `-874`, `-3177`). After coherent UE emission is proven, the
gNB non-PRACH collection offset must be derived from the accepted run's actual
coarse PRACH position, not from stage-1 shift sign or another static table.
