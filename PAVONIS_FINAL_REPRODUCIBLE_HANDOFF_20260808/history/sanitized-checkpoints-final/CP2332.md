# CP2332 - Queued/current TA handoff trace deployed (no RF)

Date: [date-redacted] Europe/Zurich

## Question

Can one frozen milestone run distinguish a worker timestamp queued before the
RAR timing-advance update from a worker transmitted after that update, without
changing UE timing behavior or adding sample-level work?

## Patch

The current CP2008-era srsUE baseline records the TA already included in each
worker context's transmit timestamp. At `worker_end()`, a default-off,
environment-cached, metadata-only trace compares that queued value with the
current TA and emits only nonzero differences:

`PAVONIS_SRSUE_TA_HANDOFF_TRACE event=mismatch ... queued_ta_sec=... current_ta_sec=... delta_samples=...`

The trace is controlled by `PAVONIS_SRSUE_TA_HANDOFF_TRACE` and capped by
`PAVONIS_SRSUE_TA_HANDOFF_TRACE_LIMIT` (default 64). The configuration uses a
function-local static initializer, so environment parsing occurs once. With the
flag off, timing, TA application, transmit timestamps, and radio writes are
unchanged; the disabled path is one cached branch and no trace I/O. This patch
does not restore the commented current-TA subtraction and does not edit
`ue_sync_nr.c`.

CP193 and CP1807 propagate both variables through the nested remote launch and
record them in the result sidecars. The CP2332 wrapper enables `1/64` over the
otherwise frozen CP2329/CP2330 milestone shape.

## Verdict and next

PASS no-RF. One frozen milestone RF attempt is unlocked while both NUCs remain
reachable. Health and sidecar propagation are judged first. A supplied run then
tests whether Msg3 is queued with old TA and transmitted after RAR TA changes,
while later connected-mode PUSCH is queued with the new TA. No timing semantic
change is approved until that ordering is observed live.
