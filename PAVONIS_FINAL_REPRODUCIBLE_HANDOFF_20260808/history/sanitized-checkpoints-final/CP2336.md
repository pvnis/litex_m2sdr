## Decisive TA row

At TTI2675 the trace recorded:

```text
queued_ta_sec=0.000032292 current_ta_sec=0.000013021
delta_samples=-222 tx_enable=1 apply_current=1 applied=1
```

The queued value is exactly the Band 3 fixed offset plus the RAR command:

- `N_TA_offset=25600` -> 150 samples;
- RAR command 37 at mu0 -> `37 * 6 = 222` samples;
- queued total -> 372 samples / `32.2917 us`.

Before that worker transmitted, an RRC PHY `set_config()` called
`sync.add_ta_offset(config_nr.t_offset)`. `ta_control::add_ta_offset()` assigns
`next_base_nta = ta_offset / 64`, replacing the complete TA state with the
150-sample fixed offset and discarding the 222-sample RAR contribution. CP2335
correctly reconciled the one already-queued worker to the new current value,
but all later connected-mode workers were queued with the persistently wrong
150-sample TA. That is why Msg3 and Msg4 pass while all data PUSCH remains
floor/CRC KO.

This also explains CP2331 exactly: command 52 contributes `52 * 6 = 312`
samples, matching the `+301..+343` Msg3-to-data timestamp step when the RRC
reconfiguration discarded that contribution.

## Correct next fix

Separate or preserve the fixed-offset component when `add_ta_offset()` is
re-applied. Replacing an unchanged `N_TA_offset` must not discard accumulated
RAR/MAC TA commands. Implement behind a default-off cached flag in the NR
`set_config` path, keep CP2335's delta correction enabled for in-flight
workers, and add no gNB timing/RF change in the same checkpoint.
