## Msg1 result

Six strong PRACH windows selected the same stage-1 transform:
`shift=16`, `frac=-0.5`, `cfo=-25000 Hz`. Search time was
`3016..3144 us`; metrics were `1.393820, 1.436884, 3.376807, 5.364295,
4.407181, 2.565577`.

The normal detector accepted preamble zero in all six windows at nominal
slots `33.4, 145.4, 257.4, 369.4, 481.4, 593.4`, with RSSI about
`-49.9 dB` and TA `53.91..54.69 us`. This is a valid Msg1-supply datapoint,
not a detector reject.

## Why no RAR was scheduled

Each accepted indication reached the scheduler at nominal PRACH slot plus
about 31 slots, for example `33.4 -> 36.5`. Every pending RAR then expired at
the end of its existing 40-slot window with zero allocation attempts:

`Could not transmit RAR within the window=[33.5..37.5), ... failed_attempts={pdcch=0, pdsch=0, pusch=0}`

The immediate cause is a wrapper semantics bug. The CP2362 wrapper intended
to disable the diagnostic RAR phase selector but exported
`PAVONIS_GNB_RAR_TARGET_SLOT_MOD160=0`. The deployed scheduler treats every
integer `0..159`, including zero, as an active target. Only unset or empty
disables it. All six PRACH occasions had the same modulo-160 phase; their RAR
windows covered phases `15..54`, so active target phase zero could never be
selected. This mechanically explains six detector accepts, six scheduler
window expiries, and zero `rar_alloc`/RAR PDU rows.

## PUCCH trace judgment

No RAR was encoded, so the late arm never fired and no PUxCH order trace was
created. CP2364 is void for the CP2362 PUCCH ACK-order discriminator.
