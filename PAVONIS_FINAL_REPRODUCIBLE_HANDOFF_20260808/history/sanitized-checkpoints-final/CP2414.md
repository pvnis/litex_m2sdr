# CP2414: TX_ATT is not a live attenuation axis

Date: [date-redacted] Europe/Zurich
RF transmitted: no

## Result

The proposed CP2413 follow-up was stopped before RF. A dynamic stubbed-chain
probe initially showed that a default-preserving CP2188 assignment could carry
explicit `TX_ATT=0` to CP1807. The required final semantic audit then proved
that this value does not configure RF attenuation.

The live [host-redacted] generator uses `TX_ATT` only in output-directory/config names and
summary text. Its config transform always writes `tx_gain: 0`, independently of
`TX_ATT`. CP2413's generated YAML confirms `tx_gain: 0`, while its direct Soapy
readback reports the hardware/plugin minimum class of 5 dB. Therefore a launch
spelled `TX_ATT=0` would retain the same generated radio setting and the same
5 dB readback; it would not be a 5 dB RF-power experiment.

The temporary CP2188 `TX_ATT` forwarding edit was reverted. The only retained
production change remains CP2412's valid default-preserving `TX_BACKOFF` fix;
the CP2188 SHA-256 is restored to `26d40401...`.

## Interpretation

Hardware TX attenuation is already at the minimum exposed by this path and is
not an available remote lever. Do not run or label a `TX_ATT=0` comparison as
a power bracket. CP2413 closes the safe global baseband-backoff headroom at 7
dB; further down would exceed the approximately 3 dB peak headroom that
motivated the bracket.

Stay no-RF next and audit whether there is a real SSB-specific amplitude/power
control with bounded headroom. If not, the channel1 phone branch requires a
physical link-budget improvement or a calibrated cabled phone path before
another registration attempt.
