## Path audit

The CP2395 phone controller reaches CP1807 through 22 thin wrappers. No earlier
wrapper sets a Soapy module root or plugin path. CP1807 launches the gNB with:

```text
SOAPY_SDR_ROOT=/tmp/empty-soapy-root-cp1733
SOAPY_SDR_PLUGIN_PATH=/home/[host-redacted]/CLionProjects/m2sdr/litex_m2sdr/software/soapysdr/build
```

The frozen CP2401 phone binary remains
`9cbf0969a7d2d0c0b6b34b88ad6f6779f4fb536467861c8ac4879394403e27fb`
and links system `libSoapySDR.so.0.8`, but the explicit launch environment
isolates plugin discovery to the source-tree build.

The exact frozen environment passes `SoapySDRUtil --info` and device discovery,
finds only the source-tree LiteXM2SDR plugin, enumerates `/dev/m2sdr0`, and
proves:

- module SHA-256:
  `adde048f2b6a202b50f46181f3021f10fa7863c8f4992dcbf46b83fe61783418`;
- source SHA-256:
  `19cb6246f938f1935a316e87a7ab221ac7eae3255c9b4c963003c2aaaa78d409`.

These are the CP2429 lane-fixed artifacts used by CP2430 and CP2432B. No gNB
rebuild or phone-controller change is required.

## Default-path alignment

Before the full wrapper chain was traced, the default Soapy search path was
also audited and aligned. It previously selected the old `/usr/lib` module
`eeff3bdd...` before rejecting a stale `/usr/local` duplicate `f13e4985...`.
All files were backed up under:

`/home/[host-redacted]/pavonis_backups/cp2433_live_gnb_soapy_[date-redacted]`

The first-loaded `/usr/lib/x86_64-linux-gnu/SoapySDR/modules0.8/` module was
atomically replaced by the validated `adde048f...` build. Default device
enumeration now passes and names that `/usr/lib` path as the active duplicate
owner. The stale `/usr/local` file was retained unchanged and backed up. This
alignment is redundant for the frozen runner but removes the old behavior from
unisolated tools without changing the explicit CP1807 path.
