# CP2510: Operator UI resources mapped; physical unlock is the active blocker

The phone remains locked on the third consecutive frontier check. ADB is still
authorized, `NotificationShade` owns current focus, and the prepared standard
`com.android.phone/.simsettings.NetworkSetting` activity remains focused behind
the keyguard. No phone setting or RF state changed.

The installed TeleService resources close the remaining offline UI ambiguity:

- screen title: `Carrier`;
- automatic preference key/text: `oplus_button_auto_select_key` / `Auto select`;
- result group key/title: `list_networks_key` / `Available networks`;
- scan progress: `Searching...` / `Searching…` depending widget path;
- confirmation titles include `Turn off Auto select?` and
  `Turn off "Auto select"?`;
- confirmation body states that the manually selected carrier will be used for
  registration;
- the dialog uses the standard positive-button path;
- restoration is the already-proven native `setNetworkSelectionModeAutomatic()`
  path.

This is enough to define, but not safely validate, the next controller. It must
require an unlocked/automatic/full-mask start, extend and later restore the
screen timeout, start the exact CP2506 frozen NR-only RF shape, tap the `Auto
select` row, confirm through the standard dialog, capture the first real
`Available networks` UI tree without selecting a row, and restore automatic
mode plus the exact full RAT mask in independent traps. Only after that scan
checkpoint identifies the real Pavonis row should a later run select it.

One unlocked UI tree is required before implementing coordinate/node matching:
OnePlus preference rows commonly place text and the clickable switch in
different XML nodes, and guessing the node would weaken the restoration gate.
No keyguard, permission, carrier-policy, or vendor-engineering bypass is
permitted. The operator must unlock the phone and leave it unlocked; CP2509's
probe can then resume immediately with a fresh stamp.
