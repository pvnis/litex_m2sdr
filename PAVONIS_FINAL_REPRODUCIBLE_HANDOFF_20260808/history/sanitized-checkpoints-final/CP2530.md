# CP2530: App-driven NR-only before RF still stops before Msg1

This is the first valid frozen phone run with the installed `5G Switch` app
changing the actual subscription preference. Preparation proves full mode 33
to app-driven `NR only`, live RAT set `NR`,
`preferred_network_mode6=23`, and Oplus user mode still `33` before the frozen
CP2500 phone controller starts.

The phone again identifies the exact Pavonis cell on air: 46 radio rows contain
ARFCN 367930, `SENS`, and NCI 5439488. Of those, 34 report
`NOT_REG_SEARCHING`, none are denied, and none carries a nonzero reject cause.
The higher-level monitor remains out of service. The gNB records 1144 empty
PRACH occasions, zero nonempty detections, no Msg1, and no RAR. TX health is
clean: zero Soapy timeouts, zero downlink-late events, and zero sample deficit.

The RF result is valid and negative for applying mode 23 before gNB startup.
It does not yet reproduce a person selecting `NR only` after the cell is
already on air; the app was applied roughly two minutes before the phone
observation window while gNB preflight/startup ran.

Cleanup exposed a wrapper defect, not a phone/RF regression. RadioInfo shifts
dropdown rows according to the selected item, so the fixed full-mode tap left
the popup open and the phone at mode 23. Immediate readback caught this, and a
row dump located the full mode at its actual coordinate. Manual recovery then
restored the exact full RAT mask and both mode keys to 33. No setting remains
changed. The CP2529 fixed-coordinate restore must not be reused.

The replacement CP2531 helper locates `NR only` and the full mode by exact UI
text/bounds. Its deployed SHA-256 is
`08462904d74a5822e224a76383891e2128853dc468c2ee4caeabace239a2eabd`;
an app-driven NR-only -> direct full no-RF round trip passes. Next gate a
late-apply run: start the unchanged frozen gNB at full mode 33, wait for the
propagation proof, then use the app to select NR-only while the cell is live.
