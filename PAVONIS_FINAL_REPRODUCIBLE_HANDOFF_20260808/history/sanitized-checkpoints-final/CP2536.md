# CP2536: CarrierConfig shell denial is a production-build gate

Read-only `cmd phone cc get-value` tests under Android UIDs root (`0`), system
(`1000`), radio (`1001`), and shell (`[date-redacted]`) all return the same permission
denial. SELinux-context substitution cannot execute a shell in the radio or
system_server domain and does not change the result.

Android's own `TelephonyShellCommand` explains the behavior: the CarrierConfig
subcommand rejects a caller unless it is UID 0 **and**
`TelephonyUtils.IS_USER` is false. This CPH2409 is a production `user` build,
so no UID choice can expose the command. Primary source:
<https://android.googlesource.com/platform/packages/services/Telephony/+/master/src/com/android/phone/TelephonyShellCommand.java>.

Magisk `resetprop` is present at `/product/bin/resetprop`, current
`ro.build.type=user`, and `com.android.phone` is a separate restartable radio
process. A default-closed no-RF helper is prepared to set only the runtime
property to `userdebug`, restart only `com.android.phone`, perform one
CarrierConfig read, then restore `user`, restart the phone process again, and
require the command to be denied afterward. EXIT/INT/TERM/HUP restoration also
requires full RAT and both mode keys at33.

Local and [host-redacted] syntax/hash plus remote closed-gate checks pass. Helper
SHA-256 is
`87ed0ca9054fde98402d555054c807c538e6cd8401c630c0eee29d53d26c2319`.
No RF, property change, process restart, or persistent change occurs in this
checkpoint. Execute once no-RF with
`PAVONIS_CP2536_USERDEBUG_READ_APPROVED=1`; do not write a CarrierConfig value
until the read and restoration verdict is recorded.
