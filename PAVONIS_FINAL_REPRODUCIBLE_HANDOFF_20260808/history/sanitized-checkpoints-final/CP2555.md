# CP2555 - Phone registration-state and persisted-modem audit

## Question

Does a software-readable forbidden-TA/PLMN or vendor SA state explain why the
phone camped Pavonis n3 in CP2554 without producing an accepted Msg1?

## Method

- Exercised eight Oplus `ISubsysRadio` getters from a bounded, get-only helper:
  NAS system info, system-selection preference, RF-band info, NR voice support,
  NR support, NR serving-cell info, capability, and NR-band preference.
- Copied the live, backup, and prebuilt Qualcomm `qcrilNr` SQLite databases
  read-only and inspected them through SQLite schema and row queries.
- Audited the actual OCUDU MIB/SIB1 cell-access defaults used by CP2554.
- Re-read the CP2554 filtered RIL log and PRACH stage-1 trace with compact
  parsers.
- Pulled and decompiled the relevant Oplus framework/telephony JARs read-only.
  No local caller or public documentation establishes safe argument semantics
  for `clearForbiddenTai` or `performPlmnUnblock`, so neither setter was used.

## Results

### Vendor getter transport

All eight get-only requests returned without a reply (`reply=false`). The
phone remained automatic selection mode `1`, full RAT including NR, and both
preferred-mode values `33`. This matches CP2551: the Oplus getter interface is
not a usable state instrument on this firmware.

### Qualcomm persisted state

All three SQLite snapshots pass `PRAGMA integrity_check`.

- No database contains a forbidden TAI, forbidden PLMN, NAS mobility,
  registration, or equivalent persistence table.
- The live and backup databases have identical row counts and row-content
  hashes for every table.
- Relevant property rows are defaults only. The `5g_mode_pref` properties have
  default `0` and no stored value.
- There is no MCC [network-id-redacted] emergency-number row that would explain the Pavonis
  cell being singled out.

The databases are Qualcomm emergency-number/config/property stores, not the
missing forbidden-registration state store. This closes them as evidence for
the CP2554 behavior; it does not prove that inaccessible modem NV has no such
state.

### Broadcast access fields

The live OCUDU source emits `cellBarred=notBarred` and SIB1
`cellReservedForOperatorUse=notReserved`. The encoded selection thresholds are
far below CP2554's measured signal. MIB `intraFreqReselection=notAllowed` is
present, but it does not by itself bar initial cell selection and is not a
specific explanation for the observed state.

### CP2554 interpretation correction

The framework-level text `registrationState=NOT_REG_SEARCHING` was misleading.
The raw RIL row is:

`NOT_REG_MT_SEARCHING_OP_EM`, NR, reason-for-denial `NONE`, cell `001/01`,
PCI `1`, TAC `1`, ARFCN `367930`, band `3`.

Android's radio AIDL defines that state as not registered but currently
searching for an operator, with emergency service enabled. The modem was not
quiescent and a second radio-cycle control is therefore low-value.

The CP2554 PRACH stage-1 trace has `567` rows, `565` energy-gate passes, zero
selected candidates, mean raw RMS `-67.301 dB`, and maximum `-62.657 dB`.
Splitting at the approximate n3-apply boundary changes mean RMS only from
`-67.367` to `-67.233 dB`; no obvious phone-era energy step appears. The
configured strong-predemod capture produced zero files because its arm file was
tied to the absent srsUE start event, not because no window crossed its floor.

## Verdict

No software-readable forbidden-registration state was found, the vendor getter
path is unusable, and opaque vendor setters remain unjustified. CP2554 proves
active n3 operator search, but not whether the phone emitted a PRACH waveform
that the srsUE-calibrated collection/detector path missed.

The next bounded RF discriminator is therefore CP2556: preserve the frozen
CP2554 n3 shape and detector settings, but touch the already-existing bounded
strong-predemod arm exactly once immediately after n3 apply. Replay those exact
phone-era raw windows offline before changing any PRACH delay, stage-1 envelope,
gain, threshold, or modem setting.
