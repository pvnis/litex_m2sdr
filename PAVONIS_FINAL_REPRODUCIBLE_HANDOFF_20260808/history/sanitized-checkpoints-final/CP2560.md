# CP2560 - Phone NR-only and SA/NSA mode audit

## Question

Is the phone identifying Pavonis but refusing random access because the
installed 5G-only app or Oplus's separate NR mode leaves the modem in an
NSA-only profile?

## Method

- Inventoried user and system phone packages over authorized ADB.
- Took hash-pinned, read-only APK copies of the installed 5G utility,
  `OplusEngineerNetwork`, and `OplusNrMode`; decompiled them locally.
- Audited the exact CP2531 radio-info helper and CP2559 n3-apply log.
- Audited Oplus's NR-mode mapping, test-SIM behavior, SA backoff controls, and
  Smart5G state.
- Built a minimal reflection-only Android helper that exposes no setter and
  calls only `getIfTestSim`, `getNrModeChangedAllow`,
  `getNrModeChangedEvent`, and `getNrModeToCheck`.
- Snapshotted allowed RAT, both mode-6 settings, airplane state, and call state
  before and after the helper and required exact equality.

No RF run, modem restart, radio cycle, settings write, or NR-mode setter was
used.

## App and RAT result

The user-installed package `com.sladjan.sava.petg`, version `4.0.1`, is the
expected **5G Switch - Force 5G Only** app. Its source does not implement an
Oplus SA/NSA control. It opens Android's
`com.android.phone.settings.RadioInfo` screen.

The deployed CP2531 helper does the same thing, either directly or through the
app, then selects the exact `NR only` spinner row and proves:

- allowed-network mask is exactly `NR`;
- `preferred_network_mode6=23` during the active n3 window;
- `oplus_user_preferred_network_mode6=33` remains the user's full-RAT restore
  preference;
- the post-run controller restores both values and the full RAT mask to `33`.

CP2559's n3-apply log confirms those active values. The phone was not merely
left in the restored full-RAT mode during RF.

## Oplus NR-mode result

The phone contains Oplus's separate NR-mode plugin and hidden engineering
network package. Decompiled mode mapping is:

- `0`: NSA preferred;
- `1`: NSA only;
- `2`: SA only;
- `3`: SA preferred.

`00101` is deliberately classified as a test SIM. This classification is not
a rejection path: the plugin's RAT-fallback and registration-timeout controls
explicitly return without SA backoff for a test card. Smart5G and light-Smart5G
switches are off for the active slot.

The successful read-only helper reports:

```text
test_sim=true
changed_allow=true
events=[Slot0>RUS与CarrierConfig配置>SA_PRE>Passed]
```

The direct `mode_check` bundle is empty on this firmware, so it does not expose
a current numeric modem value. The recorded slot-0 configuration event does,
however, prove the Oplus RUS/CarrierConfig path applied `SA_PRE` successfully;
there is no evidence of `NSA_ONLY`. Initial and final phone state are exactly
equal: authorized ADB device, full RAT mask, mode `33/33`, airplane off, and
idle call state.

The first helper candidate never reached the API because the local sandbox
blocked SSH. The first on-phone helper build then failed during read-only
context creation because `app_process` had no prepared looper; its state gate
still passed. The versioned v2 helper adds only `prepareMainLooper`, succeeds,
and preserves both earlier artifacts.

## Verdict

The missing-app/NSA-only theory is closed. CP2559 used genuine NR-only RAT
selection, while Oplus's independent mode controller is SA-preferred and
test-SIM handling bypasses vendor SA-demotion policies. Launching or manually
operating the 5G Switch app again would repeat the helper's existing action.

The active branch remains above PHY but moves to the air-interface content the
commercial modem uses for suitability and access. Next decode the actual live
MIB/SIB1 and `ServingCellConfigCommon` emitted by the frozen phone gNB, then
compare every access, selection, initial UL BWP, and RACH field against the
known-working CP2392 config and commercial-UE requirements. Do not set Oplus NR
mode, alter phone policy, or resume detector/RF [interface-redacted] before that audit.
