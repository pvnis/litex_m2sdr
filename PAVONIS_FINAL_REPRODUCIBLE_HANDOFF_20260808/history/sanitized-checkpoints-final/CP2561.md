# CP2561: Golden config match and FPLMN reconciliation

## Question

Did the phone branch drift from CP2392's successful broadcast configuration,
or did the earlier illegal-UE event leave Pavonis PLMN [network-id-redacted] forbidden?

## Result

The packaged CP2392 and CP2559 gNB YAML files are byte-identical. Both hash to
`950694cb99a54ee001e62087b59757baaef5626b6b7fdae7cb15a30e256355de`.
CP2392's UE trace proves that this configuration decodes end to end as SIB1:

- PLMN [network-id-redacted], TAC `1`, PCI `1`
- PRACH config index `1`
- msg1 frequency start `8`
- zero-correlation zone `0`
- long-sequence root `1`
- 64 preambles
- RA response window `40`
- SIB1 PDSCH `80` bytes, MCS `5`, CRC OK

The first CP2561 shell-context `TelephonyManager.getForbiddenPlmns()` helper
returned null for both USIM and SIM application types. That is not an empty
list verdict. Review of the grouped branch map then recovered CP2550's already
authoritative root/Binder read of the same active USIM: it returned 13 actual
EF_FPLMN entries and `00101` was absent. CP2550 therefore remains the verdict;
do not clear or rewrite EF_FPLMN. The CP2561 helper is retained only as an
append-only record of the calling-context difference.

The phone's current subscription remains loaded with HPLMN `00101`, all RATs
including NR allowed, and Android has previously reported the exact Pavonis
NR-SA cell as `001/01`, PCI1, TAC1, n3. The failure remains before Msg1.

## Verdict

No gNB configuration drift is present between the srsUE golden and phone
runs, and USIM FPLMN remains closed negative. Do not repeat manual PLMN,
FPLMN, app-mode, detector, delay, gain, or radio-cycle experiments unchanged.
The next bounded discriminator is a modem restart followed by the frozen
NR-only+n3 phone shape, testing stale modem/NAS state while preserving the
proven cell and RF configuration.
