# CP2607: start1 phone run is supply/controller void

This bounded RF run used the CP2606 shape with only
`cell_cfg.prach.prach_frequency_start: 1` added.

## Propagation and health

- stage propagation records `gnb_prach_frequency_start=1`;
- packaged YAML hash is the expected
  `1346d29f5de8bf98371e1d7e22bb0f6e80b5d8f0081dff2b049fd60f721fb386`;
- parsed profile remains PLMN90170, PCI500, TAC7, CORESET0-6/SS0-0,
  PRACH index1, response window40, and frequency start1;
- both host realtime gates pass;
- TX has zero timeout, zero downlink-late, zero returned-sample deficit and
  zero errors;
- qcore cleanup is `2 -> 0` and final phone restoration passes automatic
  selection, full RAT/mode33, roaming0, and voice true/true.

## Why the run is void

The phone's 270-second monitor has 82 rows: 62 report NR-SA, but all 82 have
empty operator and `0/82` have valid NR RSRP. The separate radio log still has
156 exact PCI500/TAC7/ARFCN368410/90170 identity rows, but only two signal
records, one floor `-140 dBm` and one unavailable sentinel. The production
Oplus network scan remains incomplete after about 262 seconds and emits no
operator row. Therefore no row tap or modem selection request occurs.

The gNB correspondingly records 1,904 empty PRACH occasions, zero nonempty,
zero stage-1 selections, no RAR and no RRC/NAS. Those zeros are expected when
the selection controller never reaches its request and cannot judge the
frequency-start hypothesis.

## Verdict

Classify CP2607 as `phone_supply_or_scan_void`, not a negative start1 result.
The exact packaged configuration and host/TX health are valid, but the required
production selection stimulus is absent. Retry the identical CP2606 wrapper
once with a fresh stamp. Do not change PRACH index, response window, preamble
count, power, identity, RF settings, detector, or controller logic before that
scatter retry.
