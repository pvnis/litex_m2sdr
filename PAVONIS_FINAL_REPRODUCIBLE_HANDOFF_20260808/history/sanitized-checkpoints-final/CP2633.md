# CP2633: bladeRF gNB TX input is present but its timeline collapses

Date: [date-redacted] Europe/Zurich

## Purpose

Stay below the phone and distinguish zero baseband handoff from failed
bladeRF stream/timestamp presentation. Use only the isolated plugin's existing
default-off TX diagnostic, with all behavior-changing debug options disabled.

## Run

Fresh stamp `CP2633_TXDBG_[date-redacted]` ran qcore plus the same isolated
srsENB/X2 gNB. TX debug was capped to the first 512 calls:

- `PAVONIS_RF_BLADE_TX_DBG=1`;
- first/max rows `512/512`;
- minimum-peak selector `100`, so no later peak-selected rows;
- no sample dump, forced SOB/EOB, TX_NOW, restart, skip, guard, time shift, or
  frequency rotation.

Start/status/stop and cleanup passed. Packages are [host-redacted] `45596480...` and
[host-redacted] `6da533e2...`.

## Result

The baseband handoff is not empty:

- 512 calls, `1,056,004` submitted samples;
- 26 nonzero input calls;
- mean/max CF32 RMS `0.00387469 / 0.286691`;
- maximum CF32 peak `1.41330`, converted SC16 peak `2816`;
- nonzero calls are exactly `1, 21, 41, ... 501`.

Every `bladerf_sync_tx` call returns status `0`, metadata status `0`;
mean/max call time is `15.2 / 61.3 us`. All 512 calls say
`has_time=1`, but only call 1 carries SOB/timestamp; the remaining 511 are
untimestamped continuation metadata, as expected for one continuous burst.

The decisive defect is call geometry/time:

- call 1 submits `11,520` samples at requested timestamp `214,998`;
- calls 2 through 512 submit only `2,044` samples each;
- requested-time delta histogram is `11,520:1`, `2,044:510`;
- call 1's post-TX device timestamp is already `259,596`, so its scheduled
  start is about `44,598` samples / `3.87 ms` late.

Source audit explains the 2,044 count. `radio.cc::tx_dev()` trims overlapping
samples before the RF call. The upstream TX timestamps advance by 2,044
samples while each baseband buffer begins as an 11,520-sample subframe, so it
discards 9,476 samples on every continuation and preserves only 2,044. This
accounts for the no-TX-like air capture despite successful RF API returns.

The likely source is now the bladeRF RX metadata path that drives the gNB
timeline: `rf_blade_recv_with_time()` records `meta.actual_count`, advances
its internal next timestamp by that count, but converts/returns the full
requested `nsamples`. A recurring short `actual_count=[date-redacted]` would produce
the exact TX-time collapse measured here.

## Decision

The fault is not phone policy, qcore, gNB scheduling, zero baseband, physical
RF, or a failed `bladerf_sync_tx` return. Next run one short existing
RX+TX metadata trace to prove requested RX count, `actual_count`, and
timestamp increments directly. Do not patch count semantics until that trace
confirms the hypothesis.
