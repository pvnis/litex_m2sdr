# CP2643: MCS4 makes Msg3 reliable and exposes stale-UE PUCCH exhaustion

Date: [date-redacted] Europe/Zurich

## RF Run

Fresh stamp `CP2643_[date-redacted]` ran the CP2641 phone procedure with the
CP2642 isolated configuration. The only radio configuration change from
CP2641 remained `nr_pdsch_mcs=10 -> 4`; `nr_pusch_mcs=10`, the cell, qcore,
phone policy, and the CP2639 bladeRF single-channel-layout plugin were frozen.

Mechanics, both host gates, service startup, packaging, cleanup, and phone
restore passed. Package hashes are:

- [host-redacted]: `b327fba9f10c0dc6db233883f44c3642d1d57651ad6fd445abdca999feae340d`;
- [host-redacted]: `dc30dc89b1f6c9c0fa0e88e3f11148f76e91e4fc2ad3b75a6901a8dc84f1ae07`.

The phone observed the exact PCI 500 cell in 49/59 monitor rows. Three rows
carried valid NR quality at `-85 dBm` RSRP, `-11 dB` RSRQ, and `+9 dB` SINR;
the remaining exact-cell rows carried Android's unavailable signal-detail
sentinels. Voice and data registration remained out of service for all rows.

## Ladder Result

The gNB accepted eight PRACH attempts. The MAC PCAP contains 16 records:
eight 11-byte UL C-RNTI Msg3 PDUs and eight matching 437-byte DL C-RNTI
contention-resolution/RRCSetup PDUs. Every Msg3 reached CRC OK and every
temporary RNTI received one RRCSetup. This improves the CP2641 result from
3/7 CRC-OK Msg3 attempts to 8/8 and reduces the RRCSetup transport block from
960 to 437 bytes.

No RRCSetupComplete followed. qcore still saw zero UE contexts,
registrations, PDU sessions, or user data. MCS4 therefore improves the ladder
supply but does not by itself complete RRC setup.

## PUCCH Exhaustion Audit

The gNB log contains 11,412 exact
`SCHED: Cannot fit pending UCI into PUCCH` warnings. Compact line-order analysis
shows the first warning immediately after temporary RNTI `0x4605`, the fifth
RACH-created UE. Source audit explains that boundary exactly:

- `mac_interface_phy_nr::MAX_GRANTS` is four;
- `sched_nr_worker.cc` allocates one PUCCH entry per UE with pending ACK, CSI,
  or SR and warns when the per-slot bounded vector is full;
- the vector is correctly cleared every slot, so this is UE-count pressure,
  not an uncleared per-slot list;
- after RRCSetup, the inactivity path asks NGAP to release the UE;
- these UEs have not sent SetupComplete, so no NGAP context exists;
- `ngap::user_release_request()` logs `Released UE ... not found` and returns
  without removing the RRC/MAC/scheduler UE.

The resulting stale pre-NGAP users permanently occupy all four PUCCH grants.
This explains the warning flood and makes later attempts invalid for PUCCH,
but it does not explain why the first RRCSetup attempt failed: the warning did
not exist for the first four UEs.

## Decision

Keep MCS4 as the phone diagnostic fixture. Gate a minimal no-RF cleanup fix for
RRC users whose setup/inactivity timer expires before an NGAP context exists,
then run a fresh bounded attempt so each retry starts with usable PUCCH
capacity. In parallel, inspect the phone-side radio diagnostics and the first
UE's RRCSetup/PUCCH semantics; do not attribute SetupComplete failure solely to
the fifth-UE warning.
