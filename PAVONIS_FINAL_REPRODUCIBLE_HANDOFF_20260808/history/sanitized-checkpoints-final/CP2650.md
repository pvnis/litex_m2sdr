## Stimulus Verdict

`PAVONIS_NR_SR_PRB0_COMPAT=1` is present in the live process, but the active
marker appears zero times across six RRCSetup creations. The intended PRB0
stimulus therefore did not alter the transmitted RRCSetup or gNB PHY config.
CP2650 is void for the PRB0 hypothesis and must not be counted as a failed
resource A/B.

## Actual Standalone Path

Source tracing explains the miss:

1. Standalone `rrc_nr` builds one master-cell-group at initialization via
   `fill_master_cell_cfg_from_enb_cfg()`.
2. That path calls `fill_pucch_cfg_from_enb_cfg()` in
   `cell_asn1_config.cc` and copies the prebuilt result into each UE.
3. CP2649 patched the older per-UE PUCCH builder in `rrc_nr_ue.cc`; that
   function is not used for this standalone RRCSetup path.

The live builder creates 18 resources. Resource set 0 maps HARQ indices 0..7
to resource IDs 0..7, all on PRB51. The successful RRCSetup HARQ uses resource
ID 0 (`starting_prb=51`, cyclic shift 0, OCC 0). The configured SR refers to
resource ID 2, also on PRB51 but with cyclic shift 8 and OCC 0.

This supersedes CP2648's PRB0-versus-PRB51 explanation. CP2648's primary
finding remains valid: SR is the missing transition. The edge-frequency theory
is now closed because HARQ succeeds strongly on the same PRB51.

The 18-resource layout also matches the RRC dump in upstream issue #1107,
confirming that this is the relevant code family.

## Decision

Gate a default-off compatibility change in the actual
`cell_asn1_config.cc` path that changes only
`schedulingRequestResourceConfig.resource` from ID 2 to ID 0. This reuses the
exact PRB51/cyclic-shift/OCC resource already proven by the phone's positive
RRCSetup ACK. Keep sl40 offset 8, RF, MCS, traces, cleanup, and scheduler frozen.
