# CP2653: exact RRCSetup decodes; proactive UL grant is the discriminator

Date: [date-redacted] Europe/Zurich

## Exact Offline Decode

The first CP2652 CRC-OK Msg3/RRCSetup exchange was parsed directly from
`srsenb_nr_mac.pcap`. The custom NR pseudoheader is 31 bytes; the DL MAC PDU
contains a contention-resolution CE followed by a 277-byte DL-CCCH RRCSetup.
A local-only decoder built against this checkout's `rrc_nr_asn1` library
successfully unpacked both the outer RRCSetup and the embedded
`CellGroupConfig`.

The active CP2652 masterCellGroup includes SRB1, schedulingRequestID 0,
`sr-TransMax=n64`, a permanent TAG, dynamic HARQ codebook, the dedicated
PUCCH/PUSCH configuration, and the live CP2651 SR reference to resource 0 at
`sl40:8`. This proves the over-air bytes match the intended active builder and
are syntactically decodable by the implementation's own ASN.1 codec.

Artifacts:

- decoder source: `db400169...`;
- decoder binary: `5c9d0bd7...`;
- exact 277-byte RRCSetup: `7844758b...`;
- complete outer/master decode: `3865a689...`.

## Upstream Join

srsRAN_4G issue 1107 documents the same COTS frontier and the same generated
configuration family: the phone decodes RRCSetup and sends HARQ UCI, but no
RRCSetupComplete follows, and later attempts produce the same PUCCH-capacity
warning. The issue includes the same SRB1, PUCCH resource table, scheduling
request ID/periodicity, PUSCH, and CSI configuration and remains open without a
fix or linked change: <https://github.com/srsran/srsRAN_4G/issues/1107>.

One concrete semantic oddity remains visible: all generated PUCCH resources
carry `secondHopPRB` even though `intraSlotFrequencyHopping` is absent. TS
38.331 describes secondHopPRB as applicable to intra-slot frequency hopping.
That is a candidate setup-application defect, not yet a proven cause.

## Decisive Next Test

Do not sweep masterCellGroup fields yet. Add a default-off, one-shot diagnostic
that calls the existing scheduler `ul_sr_info(rnti)` after the first valid
positive setup HARQ ACK for each RNTI. This produces the UL grant that a decoded
SR would have requested without changing the transmitted RRCSetup.

- SetupComplete PUSCH appears: the phone accepted RRCSetup and the missing
  transition is SR transmission/reception.
- The grant is scheduled but the phone sends no PUSCH: the phone ACKed the
  transport block but did not queue SetupComplete, strongly proving a
  masterCellGroup/application rejection.
- PUSCH appears with CRC KO: the setup was accepted and the remaining fault is
  post-setup UL PHY timing/geometry.

Gate this patch no-RF with the normal default-off, cached-env, isolated-build,
deploy/hash, and disabled-path proofs before one bounded phone run.
