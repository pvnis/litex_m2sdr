# Checkpoint 2733: OCUDU bladeRF channel-1 RF startup gate

Date: [date-redacted] Europe/Zurich

## Purpose

Gate OCUDU on the exact bladeRF RX2/TX2 path that produced the CP2674 phone
golden before using it as the decisive OCUDU-versus-M2SDR discriminator.

## Frozen radio profile

The YAML is structurally identical to CP2731 except for the required host and
radio transport fields: remote AMF/bind addresses, `driver=bladerf`, TX gain
45 dB, RX gain 50 dB, no M2SDR clock-ppm correction, and a checkpoint-local
log filename. All cell identity, PCI, frequency, bandwidth, MIB/SIB1,
SearchSpace0, n0/20 ms cadence, power controls, PRACH and scheduler geometry
remain frozen. Config hash:
`a5224f2a8e05aaad7cf415d7dce1a51053881ef5d8e6316c631580547cd89507`.

## Portability fixes

Two host-side assumptions blocked the first starts before producing a valid RF
result:

1. OCUDU's customized Soapy validator applied the M2SDR TX attenuation range
   `[-89,0] dB` to every Soapy device. A driver-aware profile now applies the
   probed bladeRF2 ranges only when `device_args` parses to
   `driver=bladerf`; the default/M2SDR branch is unchanged. Patched source hash
   is `eda83fa29b3cd18a3848b23cfa0e9078f14d8f37d01c6f3ecf139a1c79635cec`.
2. SoapyBladeRF 0.4.1 advertises two channels but rejects a SISO stream whose
   channel vector is `{1}`. An isolated upstream-tag build permits `{1}` with
   the existing X1 layout and enables physical channel 1. Patched source hash
   is `e53e64f0f3fc4f9757409d0e512e5a35d520d0957ceb3c20e87ef709c7b7862d`;
   private module hash is
   `ce38158513857d40bd0a0022d3f1e80a4cc99a3029f7cfe9f4436c735032e64b`.

Both changes are isolated. `SOAPY_SDR_ROOT` selects only the private module;
the system module remains hash `06b88315...`. The isolated OCUDU binary is
hash `c522d302...`. The [host-redacted] source tree and CP2392 gNB were restored to their
recorded hashes after the native build, and the CP2674 srsENB stack was not
modified.

## RX API finding

The first stream-capable run exposed a 5,282,398-line error loop because
OCUDU's direct-buffer RX API is unsupported by SoapyBladeRF. This run is
startup-instrumentation void and its 486 MB temporary log was deleted after a
streaming template count. Enabling the existing
`OCUDU_SOAPY_RX_USE_READSTREAM=1` path removed the loop completely. No new RX
implementation was added.

## Final bounded RF gate

The final 20-second CP2733E run used realtime privileges and completed by the
expected timeout (`REMOTE_RC=124`):

- bladeRF TX channel 1: 11.52 Msps, 1842.5 MHz, gain 45 dB, 18 MHz filter;
- bladeRF RX channel 1: 11.52 Msps, 1747.5 MHz, manual gain readback 60 dB,
  18 MHz filter;
- channel map: one TX and one RX stream, both first channel 1;
- N2 connection and AMF PLMN [network-id-redacted] connection established;
- zero `acquireReadBuffer` errors, TX timeouts, downlink-late/real-time
  failures, underflows, time errors, generic errors, or exceptions;
- no realtime-priority warnings under the final `sudo` launch.

The RX readback is 60 dB because that is the bladeRF driver's maximum; this is
not a config drift and does not affect the known-good TX-side discriminator.
