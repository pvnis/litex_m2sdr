# Checkpoint 2734: OCUDU/bladeRF phone run is no-cell

Date: [date-redacted] Europe/Zurich

Stamp: `[date-redacted]CP2734_OCUDU_BLADE_PHONE`

## Result

The first real-phone run with OCUDU driving the CP2674 bladeRF RX2/TX2 path
completed all wrapper mechanics, phone restore, process cleanup, and two-host
packaging. It is a valid RF negative:

- qcore, OCUDU, and the phone lifecycle all started successfully;
- OCUDU remained running for the complete observation/selection interval;
- the phone monitor recorded 92 rows but summarized `nr_seen=0`,
  `private_plmn_seen=0`, `in_service_seen=0`, `nr_camped_seen=0`, and no
  cellular interface;
- operator selection did not complete and restored the phone's prior state;
- OCUDU saw zero PRACH events, RAR traces, PUSCH, or CRC-OK uplink events;
- qcore saw zero registration request, authentication, security mode,
  registration accept/complete, or user-plane activation events.

## Transmit-side health

The retained OCUDU log has 180,671 rows spanning the run. Compact parsing
finds 35,622 scheduled SSB rows and 17,811 scheduled SIB1 slot decisions. The
runtime health counters are all zero: unsupported RX-buffer calls, Soapy TX
timeouts, downlink-late events, underflows, and time errors. The only two error
level rows are the expected inability to register stdin under a detached
`nohup` launch; they do not affect radio execution.

## Interpretation

This does not exonerate the M2SDR or isolate a semantic OCUDU-versus-srsENB
difference. CP2731 proves the same OCUDU waveform/config on M2SDR is strongly
phone-visible at PCI 500 with about -67 dBm and +28/+30 dB reported SINR,
whereas CP2734 is not visible as NR at all. The CP2734 startup gate proves
Soapy API acceptance and clean return codes, but not that the patched
SoapyBladeRF SISO-channel-1 stream puts a decodable waveform on air.
