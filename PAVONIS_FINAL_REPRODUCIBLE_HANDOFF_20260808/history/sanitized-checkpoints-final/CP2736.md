# Checkpoint 2736: normalized CF32 does not restore OCUDU/bladeRF visibility

Date: [date-redacted] Europe/Zurich

Stamp: `[date-redacted]CP2736_OCUDU_BLADE_CF32_PHONE`

## Result

The existing OCUDU CF32 normalization path was the only transmit change from
CP2734. The bounded startup gate and the full phone run both passed their
mechanical and runtime checks. The live gNB emitted the required marker:

```text
OCUDU_SOAPY_TX_FORMAT_CF32 enabled: stream=0 scale=32767 mtu=4096 channels=1
```

The full run used the frozen channel-1 bladeRF geometry, TX gain 45, backoff
10, readStream RX, exact OCUDU cell/SIB1 controls, and the private qcore. It
recorded zero acquire errors, TX timeouts, downlink-late events, underflows, or
time errors.

Despite that clean execution, all 92 phone monitor rows remained cell-absent:
no NR cell, private PLMN, camp, service, or cellular interface was observed.
The gNB recorded zero PRACH, RAR, PUSCH, or CRC-OK events, and qcore recorded
no NAS registration activity. Wrapper mechanics, phone restore, process stop,
and two-host packaging passed.

## Verdict

CP2736 exonerates the CS16/Q11 scale mismatch as the sole explanation for
CP2734. Normalized CF32 reaches SoapyBladeRF without API or realtime errors but
is still not phone-visible, while the immediately preceding CP2735 direct
srsENB/bladeRF control completes attach and bidirectional data on the same
phone, TX2 path, and core.

The remaining OCUDU/bladeRF discriminator is below the generated waveform and
above the physical path: stream activation/reconfiguration order, continuous
versus burst metadata, or write cadence. The successful direct bladeRF path
reconfigures/enables TX after RX setup, while the current Soapy path sets up TX
before RX and leaves it active. Audit and test that presentation difference in
a bounded private-driver branch before carrying the result back to the final
OCUDU/M2SDR phone path.
