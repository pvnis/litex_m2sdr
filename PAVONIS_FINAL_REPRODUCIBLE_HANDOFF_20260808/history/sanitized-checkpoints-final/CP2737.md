# Checkpoint 2737: SoapyBladeRF TX rearm passes the no-RF gate

Date: [date-redacted] Europe/Zurich

## Source finding

The current successful direct bladeRF control and the failing OCUDU Soapy path
do not leave the device in the same stream state:

- CP2735 direct bladeRF configures RX, reconfigures TX, enables RX and TX, then
  configures and enables TX again at TX start;
- CP2734/CP2736 SoapyBladeRF configures and enables TX first, configures and
  enables RX second, then never rebuilds the TX synchronous stream;
- both paths use physical channel 1, 11.52 Msps, TX gain 45, and SC16-Q11 at
  the libbladeRF boundary after CP2736's normalized CF32 conversion.

This leaves stream lifecycle as a concrete discriminator after sample scaling
was closed.

## Patch

A default-off private SoapyBladeRF branch now caches the TX sync geometry at
TX setup. When `PAVONIS_SOAPY_BLADERF_TX_REARM_AFTER_RX_SETUP=1`, RX setup
re-runs that TX sync configuration and re-enables the already selected TX
channel. The branch is setup-time only; it adds no work to `writeStream()` or
any sample hot path.

The remote Release build passed against libbladeRF 2.6.0. Its isolated module
is:

```text
96830b9d36be0d5181ffae73a396cd1c186577af84e3acd06fcc854e85a425ec
```

The CP2733 private module and the system module remain separate and unchanged.

## Disabled and enabled proof

A setup-only harness opened TX1 CF32 and RX1 CS16 at 11.52 Msps, closed both
streams, and wrote no samples. Results:

```text
disabled_pass=1 disabled_requested=0 disabled_active=0
enabled_pass=1 enabled_requested=1 enabled_active=1
```

The CP2738 wrapper is syntax-clean, fresh-stamp guarded, pins the new module
hash, requires the env and active marker in the live process, and rejects a
closed RF gate before remote work.
