# CP2894 - Continuous M2SDR tracks phone but produces zero Msg1

CP2894 is the first continuous srsENB-to-coherent-M2SDR phone run. The MCS4
primer passes with one RACH, one qcore user-plane activation, and
`[interface-redacted] [ip-redacted]/30`. Qcore and phone policy remain live while only the
RAN is swapped.

The CP2892 M2SDR service passes every startup gate: one-shot marker `11->12`,
N2 connected to the preserved qcore at `[ip-redacted]:38412`, discontinuous
TX off, forced continuous stream on, all-timed writes on, SSB+6/NR-only apply
active, and zero Soapy timeout, downlink-late, underflow, or time-error lines.

The target bearer does not activate within the bounded 90-second event window.
Compact saved-artifact counters localize the failure before Msg1:

- gNB: `0` PRACH, `0` RAR, `0` PUSCH, `0` CRC-OK PUSCH.
- Qcore: one primer activation, zero target RAN connections, zero target
  activation, and zero reject.
- Phone: `41/47` primary-NR and valid-RSRP rows, all `41` in `ROAMING`, mean
  RSRP `-91.927 dBm`, mean RSRQ `-11.200 dB`, mean SINR `+14.000 dB`, with
  valid NR tracking from elapsed second `20` through `152`.
- The HTTP server armed, but the phone client correctly never ran because no
  target activation event occurred.

This is not weak/no downlink, N2 failure, host-health failure, or target data
failure. It reproduces CP2845's M2SDR-specific state more strongly: the phone
tracks the exact NR cell continuously but never enters detector-visible Msg1.
The next work is no-RF comparison of the target broadcast/access configuration
and transmitted PRACH/SIB1 semantics against the successful CP2869/CP2885
OCUDU/bladeRF target before changing receive timing or gain.

Cleanup passes: M2SDR stop, `dma_reader_program_mode=N`, phone N3/full-mode
restore, phone policy restore, and qcore stop. Manual packaging was required
because the wrapper exits at the target-activation gate before its normal
package stage.
