# CP2925: srsENB/M2SDR air gate is capture-order void; TX attenuation semantics identified

Date: [date-redacted]

## Purpose

Run the exact phone-working srsENB/MCS4 waveform through the isolated M2SDR
stage from CP2924 and observe it with the established bladeRF RX2 snapshot.

## Result

The srsENB/M2SDR process itself started cleanly: NG setup and Soapy selection
passed, the M2SDR TX worker ran, and the bounded status had zero Soapy timeout,
time-error, underflow, and late events. No phone was manipulated and no RACH
was expected.

The air observation is void. The 250 ms bladeRF snapshot ran from
`[date-redacted]` through `[date-redacted]`; srsENB did not emit its
`eNodeB started` marker until `[date-redacted]`. The snapshot therefore ended
about 1.16 seconds before the target became ready. Its `0` PBCH rows,
`-43.640907 dB` RMS relative to [date-redacted], and max component `60` describe the
pre-transmit floor, not M2SDR output. Do not use CP2925 as an RF-path failure.

## No-RF finding

The CP2924 M2 copy set `tx_gain = 0` to request zero attenuation. srsENB's
radio initialization only applies an explicit TX gain when the value is
strictly positive. For zero it instead calls `set_tx_gain(rx_gain)`, here
`40`. The LiteX Soapy API interprets its TX gain argument as positive
attenuation in dB. The log consequently contains the open-loop warning, and
the request has the opposite semantics from the intended near-zero
attenuation.

The next stage must keep CP2924 immutable, pass a small positive override such
as `--rf.tx_gain=0.1`, prove the warning is absent and the active attenuation
is near zero, and arm the bladeRF capture only after the gNB-ready marker.

CP2925 is execution-valid but RF-observation-void. It discovers a separate,
