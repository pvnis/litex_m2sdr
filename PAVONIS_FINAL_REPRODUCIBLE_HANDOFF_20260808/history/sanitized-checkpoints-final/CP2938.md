# CP2938: phone reaches registration on srsENB/M2SDR channel 1

Date: [date-redacted]

Stamp: `[date-redacted]CP2938_PHONE_SRSENB_M2SDR_CH1_ACCESS`.

The CP2937 wrapper completes mechanics, FPLMN audit/restore, target cleanup,
and packaging. Physical channel 1 changes the result decisively: the gNB sees
12 PRACH detections. The final attempt (`temp_crnti=0x460c`) produces a
CRC-OK 11-byte Msg3 at `+9.292 dB`, valid PUCCH ACK/SR, and a later CRC-OK
512-byte PUSCH at `+4.919 dB`. Qcore receives a new RAN UE connection and the
real phone's Registration Request, accepts its private-lab subscriber path,
and starts registration. The phone reports NR-SA Band 3, `90170`, data
`IN_SERVICE`, valid NR signal (`-75 dBm`, RSRQ `-18 dB`, SINR `-3 dB`), but
does not obtain a private interface before the context is released for
inactivity. No Authentication Response or user-plane activation is observed.

The run also exposes a deterministic uplink defect. Startup reports RX channel
1 `PGA: 0.00 dB`, then `m2sdr_set_rx_gain_chan(RX) failed: io`; aggregate
PUSCH is only `2/64` CRC OK with mean `-12.785 dB`. In LiteX 1R1T mode, the
AD9361 API accepts logical channel 0 and internally maps it to configured RX2.
CP2931 currently passes physical channel 1 to gain control after selecting RX2,
which maps past the valid channels and leaves the requested 40 dB unapplied.

This is an attach milestone, not completion. Correct the isolated channel-1
RX gain control mapping, rebuild natively on [host-redacted], establish a fresh phone
modem epoch (the missing Authentication Response matches CP2867), then rerun
the frozen access shape.
