# Checkpoint 2976: one-shot DL HARQ retry unlocks NAS to the IMS-DNN block

Date: [date-redacted] Europe/Zurich

## Purpose

Run the frozen CP2974 phone lifecycle once from the CP2975 fresh epoch. Test
whether one bounded scheduler-NACK after the first valid setup ACK makes the
reactive SRB1 downlink reliably reach the phone, then judge registration and
private data without changing RF, qcore credentials, thresholds, or timing.

## Run

- Stamp: `[date-redacted]CP2976_PHONE_SRSENB_M2SDR_FOLLOWUP_GRANT_DL_RETX_SERVICE_DATA`
- Wrapper mechanics, qcore start, srsENB start, phone preparation, capture,
  restore, FPLMN pre/post audits, and both service stops: PASS.

  not complete.
- Frozen controls: ATT16, RX gain 40, CP2967 follow-up UL grants, and one
  CP2973 DL HARQ retry per valid setup remain the only active diagnostic

## MAC discriminator

The structured NR MAC PCAP has 128 packets across seven temporary RNTIs. The
important connected sessions are:

| RNTI | UL/DL packets | UL/DL LCID1-bearing packets | Result |
|---|---:|---:|---|
| `0x4602` | 22/16 | 14/15 | Sustained bidirectional SRB1/NAS exchange |
| `0x4622` | 23/3 | 4/2 | Initial response, then zero-BSR grants |
| `0x4637` | 17/6 | 3/5 | Registration/security exchange starts |
| `0x4639` | 21/11 | 10/10 | Sustained exchange through PDU-session request |

For `0x4602`, the original 15-byte reactive DL LCID1 payload retains the
CP2971/CP2972 hash `e0c9efd43d4c`; a new 36-byte UL LCID1 response follows
about 61 ms later, then the session carries many more UL and DL LCID1 PDUs.
This is the response absent in CP2971.

The predicted second MAC-PCAP copy is not present. That prediction was too
strict: the patch forces a retransmission through the scheduler's existing
HARQ process, while this PCAP records newly assembled MAC transport blocks,
not every PHY HARQ transmission. The four explicit `forced_nack` markers plus
the restored phone responses are the valid execution proof.

## Core result

Qcore records multiple real NAS frontiers rather than the CP2971 stall:

- first registration reaches a sustained SRB exchange;
- another connection is rejected as an unknown stale TMSI service request;
- a later registration reaches NAS security activation before radio
  inactivity release;
- the final connection registers the private test subscriber and reaches a
  PDU-session request for DNN `ims`.

Qcore then explicitly sends 5GMM Status and ignores that session request
because `ims` is unsupported. This final connection happened after the
wrapper's compact status snapshot, which explains why its legacy qcore event
counters read zero despite the archived log and PCAP evidence.

## Verdict

CP2976 is a valid milestone, not scatter. The one-shot post-setup DL HARQ retry
restores the missing phone response and moves the frontier from first reactive
NAS delivery to DNN/session establishment. Keep the branch default-off, but
retain it in the working M2 phone shape until a native replacement is proven.

The active blocker is now the phone's automatic `ims` DNN request versus
qcore's current DNN policy, plus the remaining inactivity sensitivity in
earlier attempts. Stay no-RF next: audit qcore DNN handling and the phone APN
profile, then gate the smallest isolated change that either supports the
private-lab `ims` request or makes the phone request the already-supported
private data DNN. Do not change subscriber credentials or RF/timing controls.
