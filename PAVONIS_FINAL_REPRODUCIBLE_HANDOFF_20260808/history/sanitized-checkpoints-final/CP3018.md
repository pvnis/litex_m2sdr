# CP3018: qcore loopback RF roll stops before PDU activation

Date: [date-redacted]

Stamp: `[date-redacted]CP3018_PHONE_HTTP_QCORE_N3_LOOPBACK`.

The frozen CP3016 phone/HTTP lifecycle runs with the sole intended path change
`PAVONIS_QCORE_RAN_INTERFACE_NAME=lo`. The qcore start marker proves the value,
and CP3017 already proved the corresponding XDP/TC attachments. This run does
not reach the user-plane condition needed to judge the path correction.

Radio access is strong rather than scattered. The gNB records six RACH
attempts, PUSCH CRC OK on 46/64 rows with `+13.511 dB` maximum SINR, valid
PUCCH ACK on 54/64 rows up to `+18.533 dB`, and valid SR on 11/64 rows up to
`+17.430 dB`. The phone monitor has 84/93 rows on the target with valid NR and
service. Qcore sees six new RAN connections, but registration does not complete,
no PDU session activates, and the phone never acquires the private interface.
The PDU-session gNB markers are correspondingly absent.

Both HTTP endpoints arm. The phone waiter never sees an interface and times
out without invoking the client; the qcore server times out without accepting.
The repaired counter path works: uplink N3 packets and bytes are zero. Ten
downlink candidates reach qcore's N6 program before a UE mapping exists; all
are rejected as either non-IPv4-header or unknown-UE input. These counters do
not judge N3 loopback because no active user-plane session exists.

The late restore reports action RC1 for restoring full mode even though its
readback is already automatic/full mode33. This makes the inner wrapper return
RC1 after the protocol axis is already void; FPLMN restoration, process cleanup,
packaging, and final M2 state still pass. Apply the standard single unchanged
retry without reboot. Keep the loopback control and every RF/core/phone/retry
setting frozen. Only a run with qcore user-plane activation can judge the N3
fix.
