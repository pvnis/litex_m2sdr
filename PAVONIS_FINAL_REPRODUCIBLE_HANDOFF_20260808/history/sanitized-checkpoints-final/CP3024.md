# CP3024: Native SIB1 compatibility provokes phone UL energy but no Msg1 accept

Date: [date-redacted]

CP3024 ran the unchanged CP3021 local-M2-primer handoff with only the CP3023
native OCUDU target made effective. The srsENB/M2 primer again passed: the
phone acquired its private interface, the gNB saw one RACH procedure, qcore
reported one user-plane activation, and the radio stream stayed free of
timeouts, late writes, underflows, and time errors.

The OCUDU/M2 target started from the isolated native gNB
`9c28a111ac86a795d02ad43f29a1f71954734e8494f915b2edaba01a912c95d2` on
the CP3013 Soapy source/module pair. Its startup log and preserved snapshot
prove one live `PAVONIS_GNB_SRSENB_SIB1_COMPAT active` marker, one live
`PAVONIS_GNB_SIB1_USE_N0 active value=1` marker, and the expected period-20
fixture. This closes the remaining uncertainty from CP3023: the compatibility
branch reached the running native gNB.

The target did not complete Msg1 in 240 seconds. Compact target counts are zero
for accepted PRACH, RAR, PUSCH, CRC-OK PUSCH, and RRC progress, with zero Soapy
timeout/late/underflow/time-error events. This is therefore a valid OCUDU
access-supply datapoint and void for RAR, registration, and user-data judgment.

Unlike CP3021, the stage-1 detector input is no longer nearly empty. The final
CP3024 segment has 1390 rows, 34 energy-gated windows, 238 candidate
evaluations, zero selected candidates, maximum RMS `-57.835 dB`, and maximum
peak `-48.767 dB`. CP3021 had one energy-gated window, seven candidate
evaluations, maximum RMS `-68.692 dB`, and maximum peak `-58.973 dB`.
Effective SIB1 compatibility therefore increased the strongest phone uplink
presentation by roughly 10--11 dB and caused repeated bounded detector work,
but the current stage-1 envelope still selected no candidate. The frontier has
moved from "phone emits no target-stage UL" to the already-known PRACH
timing/phase envelope problem.

The bounded strong-predemod capture did not produce CP3024 artifacts. Its
manifest on [host-redacted] still has the CP2845 timestamp and arm path even though 34
CP3024 rows crossed the configured capture floor. The first shutdown theory is
rejected: the gNB reached its normal `Stopping...` path and emitted the Soapy
stop summary. Source and launch audit instead show that the strong capture
falls back to the shared `PAVONIS_PRACH_DUMP_ARM_FILE`; the stage removes that
file at start, and this shape creates it only after an accepted PRACH/RAR event.
With zero accepted PRACH, the capture never armed. The absence of saved windows
is an arm-lifecycle defect, not evidence that the stage-1 rows were false.

Cleanup passed: qcore N3 loopback teardown returned RC0, the phone restored to
automatic/full mode with roaming and voice policy restored, and [host-redacted] returned
to idle with M2 program mode N.

Next stay no-RF and add a default-off strong-capture trigger that reuses the
already-computed stage-1 energy gate. It must copy only bounded energetic
windows, add no second per-sample scan, and preserve all disabled-path behavior.
Build/deploy/prove that instrumentation gate, then repeat the same handoff once.
Replay the newly saved strong windows offline through the existing CP1965/
CP2062 detector tooling before changing a live search envelope. Do not repeat
CP3024 unchanged: it would lose the same bounded raw evidence again.
