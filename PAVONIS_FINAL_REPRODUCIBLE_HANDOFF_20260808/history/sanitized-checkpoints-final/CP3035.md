# Checkpoint 3035: golden srsUE cannot acquire the current target

Date: [date-redacted]

## Question

Can the preserved CP2392 srsUE/bladeRF receive path decode normal PBCH/SIB1
from the exact current native-compatibility OCUDU/M2SDR target?

## Shape

- Exact CP3034/current OCUDU target, including gNB hash `dbc7cb79...`, Soapy
  source `644e7858...`, deployed module `81b8cb2e...`, and CP3027 launcher.
- Preserved srsUE binary
  `b9d353901646614be03fb8b9225905964787e98c1ebb173e44729c4fbb619c94`.
- The established prepared bladeRF configuration and plugin were used.
- All sample-heavy and candidate/debug traces were disabled. The process was
  bounded to 90 seconds and judged only on ordinary acquisition output.
- No phone operation, source edit, rebuild, target setting, threshold, or
  protocol setting changed.

## Execution

The srsUE initialized the bladeRF normally, changed to `11.52 Msps` with
`9.22 MHz` bandwidth, applied the established 300-sample manual offset, [interface-redacted]
to `1842505998 Hz`, completed PHY initialization, and entered attach. It did
not report a cell, PBCH, or SIB1 success before the bound. No PRACH or random
access followed.

The timeout wrapper forced process exit after its normal shutdown grace, so
the UE result is `137`; this is the expected bounded no-acquisition exit, not a
startup failure.

The gNB-side SI trace proves the upper path remained active:

- 4,096 capped rows
- 1,474 `slot_summary` rows
- 1,311 `si_pdcch` rows
- 1,311 `si_pdsch` rows
- 163 SI-lattice rows

The gNB snapshot has zero Soapy deadline-write timeout, downlink-late,
underflow, time-error, and RACH-indication events.

The top-level wrapper returned nonzero after the UE result was complete because
the first artifact-copy invocation did not complete. A direct retry copied the
same completed `launch.env`, `result.env`, stdout, detail, and gNB snapshot
without RF. Both final host gates pass, bladeRF remains present, and M2SDR is
back in program mode N. This artifact-transfer issue does not void the RF data.

## Verdict

This is a valid current-target downlink acquisition failure. Three independent
observations now agree:

1. CP3033: the phone sees strong PCI-500 PSS/SSS measurements but never camps.
2. CP3034B: the unclipped independent bladeRF RX1 capture has no PBCH.
3. CP3035: the preserved golden srsUE/bladeRF stack initializes correctly but
   acquires no cell/PBCH/SIB1.

The current target schedules SI correctly at the FAPI boundary and has clean
reported transport health, so phone policy and PRACH search are not the active
frontier. The defect is in current PBCH/SIB1 delivery below FAPI, or in the
shared bladeRF/path control used by the two software receivers.

## Next rung

Before modifying the current target, run a bounded preserved CP2392-era
OCUDU/M2SDR plus srsUE acquisition control on the same hardware. A pass
exonerates the bladeRF/path and isolates a current target/runtime regression; a
failure means the receive/cabled control path itself has changed and must be
restored first. Do not retry CP3034 or CP3035 unchanged.
