# CP3044: bounded early predemod capture passes no-RF gate

Date: [date-redacted] Europe/Zurich

## Question

CP3043's 64 saved windows began 57.58 s after the phone's last observed
UL-CCCH access record. Can the existing predemod tap capture the first two
access epochs without adding unbounded sample work to the lower-PHY path?

## Change

`prach_processor_worker.cpp` now supports the default-off environment control
`PAVONIS_PRACH_EARLY_PREDEMOD_CAPTURE_MAX`. When nonzero, it sends only the
first capped predemod windows to the existing memory-buffered, exit-flushed raw
capture. The CP3044 runner accepts at most 128 windows. Once the cap is reached,
the path performs only one relaxed atomic load per opportunity; it does no
sample scan, copy, formatting, or file I/O. Regular strong-window capture is
suppressed while this mutually exclusive early capture is active.

The remote helper also gained hash-pinned, default-preserving gNB binary
selection. With no override it still selects the CP3025 binary and capture max
zero. CP3044 explicitly selects an isolated native [host-redacted] binary, sequence mode
`off`, and cap 128. The CP3025 binary was not overwritten.

## Verdict and next rung

PASS, no RF used. CP3045 may run exactly one bounded phone/QCSuper measurement
with phase mode off and early cap 128. It is explicitly void for live PRACH,
RAR, and Msg3 detector conclusions because sample-level capture is enabled.
Judge only whether the saved window timestamps overlap the target UL-CCCH
epochs and what baseline/stage-1 offline replay finds in those exact windows.
