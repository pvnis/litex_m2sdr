# Checkpoint 3137: uplink bottleneck characterized

Date: [date-redacted]

RF executed: no

Verdict: the large downlink/uplink asymmetry is bounded primarily by the
radio-side UL service envelope. Marginal PHY quality and protocol recovery are
material secondary costs, but CRC loss alone does not explain the result.

## Method

`cp3137_analyze_uplink_bottleneck.py` verifies all 20 valid phone attempt
summaries and gNB snapshots from CP3133. For each run it parses exactly the
first 256 metadata-only PUSCH result rows, unwraps the slot counter, sums
scheduled and CRC-good transport-block bytes, and joins them to the bounded
one-megabyte upload and download.

The HTTP probe is not rate limited. Android `curl` sends a pre-created local
file with `--data-binary`; the core reads up to 64 KiB per socket call. The
same interface, host path, and private user plane carry both directions.

## Measured bounds

| Metric | N20 median |
|---|---:|
| application download | 786864 B/s |
| application upload | 12012 B/s |
| down/up ratio | 65.32x |
| capped PUSCH trace span | 2.198 s |
| PUSCH grant/result rate | 116.50/s |
| mean TBS per run | 399.93 bytes |
| scheduled PUSCH payload | 45285 B/s |
| CRC-good PUSCH payload | 31899 B/s |
| application upload / CRC-good envelope | 38.66% |
| PUSCH CRC yield, pooled | 90.72% |
| CRC-good SINR, median | 3.807 dB |

The initial trace therefore offers tens of kilobytes per second, not the
roughly 0.8 MB/s seen downlink. This radio-side envelope establishes most of
the asymmetry before HTTP, IP, PDCP, RLC, and retransmission costs.

The application upload consumes about 39% of the median initial CRC-good
payload envelope. That remaining factor is consistent with headers, scheduling
gaps, HARQ/RLC recovery, TCP feedback, and the fact that the short initial
trace is not the full 75-95 second upload.

## What does not explain it

Pooled PUSCH CRC loss is about 9%. Even eliminating every failed PUSCH cannot
turn 12 kB/s into 787 kB/s. Across N20, upload throughput also has near-zero
linear correlation with:

- CRC yield: `r=0.096`;
- median CRC-good SINR: `r=0.086`;
- grant rate: `r=-0.163`;
- mean TBS: `r=0.059`;
- initial CRC-good payload rate: `r=0.004`.

Within the observed operating range, run-to-run PHY variation is not the
throughput-setting variable.

The primer's 512 follow-up grants are not in the measured data path. The srsENB
primer is stopped before OCUDU attach and data transfer. The reverse direction
also reaches the 0.8 MB/s class on the same hosts and user plane, so a generic
MTU, route, socket, or core-host limit is not a credible primary explanation.

## Engineering interpretation

The supported conclusion is:

> UL is first bounded by a small-grant, limited-opportunity radio service
> envelope; marginal PHY and protocol recovery then reduce useful TCP payload
> to about 12 kB/s.

The data does not completely separate scheduler allocation policy from
HARQ/RLC/TCP recovery over the full transfer. Doing that would require a
bounded, low-overhead counter spanning the complete upload rather than raising
the existing verbose per-PUSCH trace cap. That additional profiling is not
required to explain the headline asymmetry and was not run here.

No source, binary, configuration, RF, host, phone, or proven baseline changed.
