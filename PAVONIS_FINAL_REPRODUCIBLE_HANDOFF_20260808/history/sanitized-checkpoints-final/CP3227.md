# Checkpoint 3227 - Explicit PRACH context retry closes

## Verdict

**SECOND CONSECUTIVE PRACH-SUPPLY FAILURE. NO THIRD UNCHANGED RETRY.**

The exact CP3226 shape was repeated with only fresh artifact identity and
private benchmark port. It reproduced the same outcome:

- healthy cell selection and SIB1;
- exact explicit-context propagation;
- one successful real PRACH write;
- six real PRACH writes rejected as `TIME_PAST`;
- zero gNB Msg1 detections, RARs, Msg3, connected PUSCH, or user data.

This remains void for throughput, but two consecutive identical failures make
the current PRACH submission behavior a repeatable blocker rather than
single-run scatter.

## Frozen Shape

Runtime again proves the CP3222 coherent timing trio:

- UE TX guard: `56000` samples;
- gNB PRACH timing compensation: `253336` samples;
- non-PRACH scheduler error: `16000` samples.

The cell reports `14.570 dB` SNR and `-4090.141 Hz` CFO. gNB Soapy TX timeout
and downlink-late counts are both zero.

## Context And Timing

All `23` bounded context rows join their TX debug rows:

| Context class | Rows | Guard/offset/forced burst | RF result |
|---|---:|---|---|
| ordinary startup, selected false | 16 | absent on all rows | 16 OK |
| real PRACH, selected true | 7 | present on all rows | 1 OK, 6 `TIME_PAST` |

The real-PRACH lead spans `30972..41775` samples with median `40000`. The gNB
records `1931` empty detector rows and zero nonempty rows.

CP3226 and CP3227 therefore have the same decisive signature: one timely
PRACH followed by six late submissions. The feature is reaching the intended
branch; the branch's timestamp/restart construction is not reliably meeting
the hardware deadline.

## Decision

Do not retry this RF shape unchanged and do not increase the static guard.
CP3224 already showed that a larger fixed lead does not survive the coherent
bias and host scheduling drift.

Stay no-RF and audit the true-PRACH path in this order:

1. construction order of requested time, guard, coherent bias, stream restart,
   and the negative PRACH offset;
2. why coherent bias initializes only after the first restart and still leaves
   later rows at a rejected nominal lead;
3. whether the plugin can use the current hardware timestamp to enforce a
   bounded minimum lead per true PRACH while reporting the exact added delta;
4. how any dynamic delta is paired coherently with gNB PRACH collection
   timing without changing connected PUSCH.

The explicit-context split remains useful and default-off, but its connected
throughput effect is still unmeasured.
