# Checkpoint 3235 - bladeRF USB TX worker timeout

## Verdict

**FAIL FOR THE LADDER; PASS FOR THE FAILURE DISCRIMINATOR.**

Both post-PRACH continuation transitions are mechanically valid:
`START|TX_NOW` (`flags=0x5`), zero-energy, status `OK`, marker cleared. The
first transition remains healthy through the next PRACH. The second remains
healthy for 45 more one-millisecond writes, then libbladeRF reports:

`Transfer timed out for TX buffer`

All 117 later ordinary writes return status `-1` because the sync worker is
already dead. This is not an immediate flag rejection and not a gNB PRACH
detector result.

## Evidence

- Propagation: explicit context, restart-each, continuation, and error logging
  are all `1` in the archived launch environment.
- Cell/SIB1: pass at `14.660 dB`, CFO `-3991.790 Hz`.
- PRACH calls: `1278`, `2404`; both restart/status `OK`.
- Transition calls: `1279`, `2405`; both flags `0x5`, status `OK`.
- First failed ordinary call: `2451`.
- Status-`-1` rows: `117`; mean call duration `[date-redacted].924 ms`.
- libbladeRF errors: exactly one USB TX transfer timeout.
- gNB detector: `1959` empty, `0` nonempty; no RAR.
- gNB TX timeout/downlink-late: `0/0`.

## Interpretation

Immediate TXNOW establishes no scheduled queue headroom. The srsUE producer
then feeds one millisecond at a time at real-time cadence. The delayed USB
worker timeout is consistent with that queue eventually starving after the
second reopen. The transition must be scheduled in the future, not started
immediately.

## Decision

Stay no-RF for the next gate. For a pending zero-energy continuation, read the
current bladeRF TX hardware timestamp and start the new burst at
`current_tx + tx_guard_samples` using the already-proven `56000`-sample guard.
Retain the existing timed path for nonzero buffers. Keep marker clearing on
status `OK`; keep all PRACH, gNB, RF, scheduler, gain, bandwidth, and MCS
settings frozen.
