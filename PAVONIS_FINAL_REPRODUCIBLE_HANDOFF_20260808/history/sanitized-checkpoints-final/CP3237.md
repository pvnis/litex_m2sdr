# Checkpoint 3237 - libbladeRF stale TX timestamp root cause

## Verdict

**FAIL FOR THE LADDER; ROOT CAUSE FOUND IN THE EXACT INSTALLED SOURCE.**

The first hardware-guarded continuation passes exactly as designed:
`BURST_START`, no `TX_NOW`, status `OK`, and TX-domain lead exactly `56000`
samples. The second PRACH is nevertheless rejected with
`BLADERF_ERR_TIME_PAST`.

## Evidence

- Cell/SIB1: pass at `12.501 dB`, CFO `-4071.536 Hz`.
- First PRACH call `1155`: status `OK`.
- First continuation call `1156`: flags `0x1`, status `OK`, lead `56000`.
- Second PRACH call `2281`: status `-14` (`TIME_PAST`).
- Later USB TX transfer timeouts: `1`.
- Later ordinary status-`-1` rows: `117`.
- No gNB Msg1 detection or RAR; not a throughput datapoint.

## Root cause

The installed library identifies exact upstream commit:

`[hex-value-redacted]`

In that commit,
`host/libraries/libbladeRF/src/streaming/sync.c::sync_init()` resets the TX
sync metadata fields `msg_timestamp`, `in_burst`, and `now`, but does not reset
`curr_timestamp`.

The Pavonis PRACH restart calls `bladerf_sync_config()` again. The new sync
worker therefore inherits the previous worker's software timestamp even
though the hardware TX clock and burst state were restarted. On the second
PRACH, a timestamp that is demonstrably `40000` samples ahead of hardware is
still behind stale `curr_timestamp`, so libbladeRF returns `TIME_PAST`.

This explains why first-restart-only tests succeeded and later PRACH writes
failed despite positive hardware lead.

## Decision

Stay no-RF. Build an isolated library from the exact installed commit with the
one-line TX initialization fix:

`sync->meta.curr_timestamp = 0;`

Do not replace `/usr/local/lib` or modify the proven system library. Stage the
candidate under a checkpoint-specific prefix, prove exact source commit,
one-line diff, ABI/SONAME, dependency resolution, plugin/srsUE load path, and
default-path identity before one bounded RF control.
