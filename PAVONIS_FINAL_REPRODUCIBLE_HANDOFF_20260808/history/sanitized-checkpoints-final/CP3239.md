# CP3239 - libbladeRF timestamp fixed; USB TX worker lifecycle still fails

## Verdict

**PARTIAL / TRANSPORT FAIL / LADDER VOID.**

The isolated CP3238 dependency fix does exactly what it was intended to do:
both restarted true-PRACH writes return status zero, including the second
restart that CP3237 rejected as `TIME_PAST`. Both following ordinary-stream
continuations return status zero at exactly 56,000 samples of hardware-domain
lead.

The full acceptance gate still fails. Forty-six ordinary 1 ms writes after the
second continuation, all eight libbladeRF USB TX buffers time out together.
The next 117 bounded trace rows return status -1. This is a remaining stream
worker teardown/restart lifecycle defect, separate from the now-fixed stale
`curr_timestamp`.

The run selected the cell and decoded SIB1 but produced no gNB PRACH accept,
RAR, PUSCH, or traffic. It is void for ladder and throughput conclusions.

## Evidence

- Candidate-library propagation: PASS.
- Cell/SIB1: PASS, 14.504 dB cell-search SNR and normal run-scale CFO class.
- gNB TX health: zero Soapy timeouts and zero downlink-late events.
- True-PRACH restart calls: 2/2 status zero; all disable/start substeps zero.
- Prior CP3237 failure signature: zero `TIME_PAST` rows in CP3239.
- Guarded continuation applies: 2/2 status zero, each at +56,000 samples.
- First worker failure: call 2429, 46 calls after the second continuation.
- libbladeRF errors: eight `Transfer timed out for TX buffer` events, one for
  every configured TX transfer buffer.
- Subsequent bounded failures: 117 status -1 rows.
- PRACH supply: two UE Msg1 transmissions, 1,960 empty and zero nonempty gNB
  detector rows; 16 bounded strong-predemod windows saved.

The timestamp reset is therefore retained in the isolated candidate for the
next source-level worker-lifecycle experiment, but it is not promoted to the
system dependency and is not claimed as a complete transport fix.

## Decision

Do not retry CP3239 unchanged. The failure reproduces the same deterministic
post-second-transition worker timeout with a more precise split:

1. stale TX metadata caused the second restart's immediate `TIME_PAST`;
2. a separate restart/USB-worker lifecycle problem kills all transfer buffers
   after the restarted stream resumes.

Stay no-RF and audit the exact libbladeRF `sync_config` teardown/restart order
against Pavonis's module-disable/config/module-enable sequence. The next run
must change one lifecycle variable and retain the isolated timestamp reset,
frozen radio shape, and all existing transport telemetry.
