# CP3257 - Capture diagnostic voids

## Verdict

VOID FOR THE ACTUAL-MSG1 CAPTURE QUESTION.

Two infrastructure faults prevented the approved capture diagnostic from
running as specified. Neither attempt changes the RF, detector-envelope, or
continuous-PRACH-transport conclusions.

## Attempt 1

The laptop-built gNB was deployed to [host-redacted] and failed before radio startup
because [host-redacted] does not provide `libmbedcrypto.so.16`. The UE was never started.
This is the campaign's known native-vs-cross-build ABI signature.

The prior isolated gNB was restored immediately. The same source was then
built natively on [host-redacted] with `-j16`, dependency-checked, installed into the
isolated runtime path, and help-smoked. The active native gNB SHA-256 is:

`c0c2ace85b9021b1b6b61bb536edd23518de6b2271cfa2694fd53312073411e5`.

## Attempt 2

Radio and transport are valid:

- Cell selection: 16.278 dB, CFO -4107 Hz.
- Soapy timeout/downlink-late: 0/0.
- PRACH: 7/7 status 0.
- Metadata: one `0x3` initial row, then six `0x8` updates.
- Continuation: one row, status 0.
- USB timeout or nonzero bladeRF TX status: zero.

The capture axis is void. CP2188, an older wrapper in the 24-script chain,
unconditionally replaced CP3257's requested cap 64 with 16 and replaced its
distinct delayed arm path with the shared pre-UE arm. The manifest therefore
has 16 rows and records the shared arm path. It filled before the actual Msg1
window sequence and cannot answer the offline-envelope question.

The run also produces a third valid live zero-selection result, but no new
detector conclusion is drawn because its purpose was sample acquisition.

## Decision

Change only CP2188's five strong-capture assignments to default-preserving
forms. With no overrides, its historical `1/16/-65/-55/shared-arm` behavior
remains unchanged. Add an end-to-end chain parser proving that cap 64 and the
distinct arm survive to CP1807 before spending another RF run.
