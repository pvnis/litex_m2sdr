# CP3274 - CP3273 Scheduler and BSR Audit

Date: [date-redacted]

## Scope

This is a no-RF analysis of the already-complete CP3273 hardware run. A compact
parser selects the densest 45-second scheduled-uplink interval and joins
scheduler grants, PUSCH decode results, and short-BSR CEs. No source, binary,
configuration, or hardware state changed.

The remembered normal-throughput USB LiteX result was not produced by this
project. It remains qualitative external precedent and is not used as a
Pavonis baseline or quantitative comparison.

## Active Uplink

The scheduler was not cadence- or resource-block limited:

```text
newTx grants:                    5341
scheduled bytes:             3143723
gross scheduled rate:       0.558884 Mbit/s
median positive grant gap:         1 slot
median / maximum RB width:       52 / 52
median / maximum TBS:           512 / 4737 bytes
```

The PHY also proves that the modal grant is robust:

```text
PUSCH CRC OK / total:          5216 / 5816
overall CRC yield:               89.68%
CRC-OK median SINR:               5.4 dB
512-byte QPSK CRC OK / total:  2602 / 2604
512-byte QPSK CRC yield:          99.92%
```

Larger transport blocks are demonstrably possible. The run includes
16QAM/1633-byte grants at `41/55` CRC OK and 64QAM/4737-byte grants at `20/52`
CRC OK. The 64QAM rows are marginal, but they prove that neither the 52-PRB
allocation nor a fixed 512-byte PHY cap explains the steady envelope.

## Demand Feedback

Every short BSR in the selected sustained-uplink interval reports index zero:

```text
short BSR rows:                 1050
index zero:                     1050
nonzero:                           0
```

The sustained client writes 256-KiB chunks, so this is not an application
write-size limit. OCUDU consequently sees no BSR-backed pending bytes and
repeatedly uses the native-SR fallback floor. This explains why prior isolated
tests behaved as they did:

- Raising the SR fallback from 512 to 4096 bytes did not persistently increase
  grants because each grant clears pending SR.
- Shortening the SR period increased opportunities but did not materially
  increase useful bytes per opportunity.
- ZMQ reaches 33.379 Mbit/s with median 4612-byte TBS because its BSR-backed
  demand path escapes this shallow-feedback state.

## Source Audit

The UE samples RLC queue state in `mac_nr::run_tti()`, stores that snapshot in
`proc_bsr_nr::step()`, and later uses the stored snapshot in
`proc_bsr_nr::generate_sbsr()` after the PHY grant has entered the MUX path.
The MUX may have consumed RLC data between those points. There is no refresh of
the RLC queue state at BSR-CE assembly.

That asynchronous snapshot boundary is the next specific testable defect. The
next no-RF rung is a default-off, env-read-once BSR refresh at CE assembly,
with a capped metadata trace of cached bytes, fresh bytes, and encoded field.
A focused unit test must reproduce a stale-zero snapshot with fresh RLC
backlog before any deployment or RF run.

## Verdict

**PASS: the remaining CP3273 uplink ceiling is demand-feedback starvation, not
an RF, fixed grant-size, scheduler-cadence, or resource-allocation ceiling.**

The active working transport and timing shape stays frozen.
