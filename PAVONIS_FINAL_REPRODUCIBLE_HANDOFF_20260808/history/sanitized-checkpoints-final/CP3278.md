# CP3278 - Fast-RAR Fresh-BSR Measurement Not Reached

Date: [date-redacted]

## Scope

CP3278 kept the CP3273 radio, transport, timing, scheduler, MCS, traffic, and
fresh-BSR controls unchanged. It reordered the same 21 stage-1 transforms so
the two CP3276 recovery classes were evaluated first.

## Attempt Table

| Stamp | UE Msg1 | gNB PRACH accepts | Stage-1 result | RAR | BSR rows |
|---|---:|---:|---|---:|---:|
| `[date-redacted]` | 7 | 0 | 0/1938 rows selected | 0 | 0 |
| `[date-redacted]` | 7 | 6 | `-448/-0.5/+22000`, candidate 6, 3.047-3.251 ms | 0 | 0 |

The first attempt was the standard clean pre-access scatter void. The standing
single-void retry found a different already-listed run-scale recovery class.
All six accepted RACH indications then reached the scheduler at the exact end
of the 40-slot RAR window and were rejected as stale.

Both runs passed SIB1 with seven UE Msg1 transmissions. Both had zero Soapy TX
timeouts, zero downlink-late events, and only the known 480-sample terminal
partial-return deficit. Neither produced a RAR, UL grant, PUSCH, BSR, session,
or user-data transfer.

## Finding

Moving the CP3276 transforms forward does not cover every run-scale recovery
class. CP3278's accepted class was sixth because four other unchanged
transforms remained ahead of it. Its 3.05-3.25 ms wall-clock search time was
still too slow for the current RAR window.

This supports, rather than rejects, the search-order latency model: CP3273
succeeded at 1.885 ms, while CP3276 and CP3278 accepted at 3.05 ms or later
and expired. The next order-only gate should move the newly observed
`-448/-0.5/+22000` transform first while retaining all 21 transforms and all
non-order controls.

## Verdict

**VOID FOR FRESH-BSR AND THROUGHPUT JUDGMENT.**

The no-RF order change behaved as intended, but the run rolled a third
recovery class that remained too late. Do not run CP3278 unchanged again.
Fresh BSR remains source/build validated but unmeasured over user traffic.
