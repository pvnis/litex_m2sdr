# Checkpoint 3309: Attach and Downlink Pass, Uplink Start Timeout

Date: [date-redacted]

RF executed: yes, one bounded run

## Verdict

**PARTIAL.** The frozen radio chain attaches cleanly and completes sustained
downlink. The benchmark client times out while starting its separate uplink
connection set, so no sustained uplink result is produced.

## Radio and Ladder

Cell SNR is `15.032 dB`; TX timeout/downlink-late counts are `0/0`. Stage 1
selects three PRACH occasions using established classes: the first search
takes `3668 us`, its sticky reuse takes `760 us`, and a later baseline accept
takes `829 us`. The new CP3307 candidate is not selected and does not disturb
fallback coverage.

The gNB encodes two RAR PDUs. The UE reaches Random Access Complete, RRC
Connected, and the private data session. PUSCH is `81/128` CRC OK
(`63.281%`), with accepted median SINR `16.036 dB` and median TBS `544 B`.

The corrected PUCCH bank remains healthy: `128/128` rows are valid, and the
corrected ACK candidate is `51/51` valid with mean metric `19.986`.

## Traffic

Four-stream downlink completes `17,972,576 B` in `45.0009 s`, or
`3.195061 Mbit/s` at the UE receiver. This matches the CP3302 downlink class
and is a valid sustained result.

The client then raises a parallel-worker timeout while entering uplink. The
server result contains no completed uplink direction. No RRC loss occurs
before teardown, so this does not prove an RF or scheduler uplink failure; the
current benchmark establishes its uplink TCP connections only after 45 seconds
of downlink and cannot distinguish connection-establishment starvation from
sustained UL capacity.

## Next Step

Stay no-RF and build a benchmark variant that establishes both four-connection
sets before traffic starts, then runs the same sequential 45-second directions.
Loopback-gate it first. A bounded RF run on the otherwise frozen CP3309 shape
will answer whether only the post-downlink TCP handshake is fragile or whether
sustained uplink data itself remains blocked.
