# Checkpoint 3325: hardware timeline provenance

Date: [date-redacted]

## Verdict

**PASS (no RF): the hardware HARQ delay is explained by the active timestamp
transform to within 0.285 ms.**

CP3322 did not consume the static `-241118`-sample non-PRACH offset during
connected uplink. Its accepted PRACH caused the dynamic edge path to publish
and consume `-352108` samples:

```text
-237332 - (-412) - 115200 + 12 = -352108 samples
```

At 11.52 Msps this is `-30.564931 ms`. Adding the configured `k2=4` slots
predicts `34.564931 ms` from scheduling to PUSCH result. CP3324 measured a
median `34.850 ms`; the remaining `0.285 ms` is consistent with symbol
completion, decode, and task dispatch. The timing transform therefore explains
the measured result latency directly.

## Source Provenance

The current timeline is assembled at three different layers:

1. The lower PHY generates downlink content for its RX-driven logical
   timestamp and passes that timestamp in TX metadata.
2. The LiteX Soapy worker changes the programmed DMA descriptor time to
   `pkt->timeNs + M2SDR_SOAPY_TX_TIME_OFFSET_NS`. CP3322 used `+20 ms`, so this
   is an actual RF-time displacement rather than deadline-only bookkeeping.
3. After an accepted PRACH, the dynamic non-PRACH path retimestamps PUSCH,
   PUCCH, and SRS samples by the measured edge calibration and a fixed 10 ms
   scheduler term. This lets the PHY decode late samples against old slot
   assignments, but does not move the MAC scheduler's current time backward.

The 40-slot receive/assignment depth is therefore necessary under the current
design: it keeps the old assignment alive until the retimestamped samples
arrive. It does not create the delay.

## Proposed Coherent Fix

Add a default-off paired virtual timebase at the OCUDU Soapy boundary:

- `read_current_time()` returns physical hardware time minus a configured lead;
- RX activation converts the requested virtual start back to physical time by
  adding that lead;
- RX metadata timestamps are returned as physical time minus the lead;
- TX metadata remains in virtual time, while the existing LiteX worker adds the
  same lead when programming the physical descriptor.

This preserves the queue headroom that all-timed M2SDR TX needs, but aligns the
lower PHY, MAC scheduler, downlink slot content, UE-relative uplink timing, and
received UL timestamps in one logical clock. It differs from the current
demod-only shift: the scheduler itself advances with the received sample
timeline, so HARQ processes should return near `k2 + decode time`.

The implementation must be explicit and paired. Applying an RX timestamp shift
without converting RX activation, or using a virtual offset that differs from
the LiteX descriptor lead, would create another incoherent clock domain.

## Gate

Before RF:

- default-off behavior must compile to the existing path;
- environment parsing must occur once, outside the receive hot path;
- focused tests must prove hardware-to-virtual, virtual-to-hardware, and
  round-trip timestamp arithmetic;
- the gNB binary must expose the feature string and the deployed config must
  prove both paired offsets are equal;
- existing non-PRACH demod and dynamic-edge offsets remain available but must be
  disabled for the first coherent-timebase diagnostic.

The first live judgment is not throughput. It is a bounded attach/data run that
must show scheduler-to-PUSCH-result latency and HARQ reuse collapsing toward the
ZMQ class while TX timeout/late health remains clean. Only then is a sustained
throughput roll justified.
