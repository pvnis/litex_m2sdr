# CP3339: deadline-break trace gNB-only gate

## Verdict

**VALID DISCRIMINATOR.** CP3339 rejects a large upstream producer pause,
in-Soapy stall, or M2SDR hardware-time jump for its observed failure cluster.
All seven breaks occur while the real hardware deadline is still positive;
the configured 2 ms guard is the immediate reason they are abandoned.

This does not yet prove that a zero guard is clean. CP3328 previously retained
loss at a 0.5 ms guard without this trace, so the actual-deadline boundary still
needs one bounded test.

## Trace Finding

All seven events occur in one bounded cluster. Compact distributions:

```text
entry_gap_us_min_mean_max=988_1290.7_1433
tx_to_break_us_min_mean_max=96_540.0_1371
raw_lead_us_min_mean_max=1886_1969.0_1996
guarded_lead_us_min_mean_max=-114_-31.0_-4
md_delta_expected_11520=7/7
sent_samples_zero=3/7
```

Every current-to-previous metadata timestamp delta is exactly 11,520 samples,
one 1 ms slot. Entry gaps never exceed 1.433 ms and time spent inside the call
never exceeds 1.371 ms. There is no multi-millisecond producer stop and no
timestamp discontinuity. The hardware deadline remains 1.886–1.996 ms ahead,
but subtracting the 2 ms guard makes every event fail by 4–114 us.

Three events fail before a sample is sent. Four fail after partially writing a
mean 6,387.5 samples; those consume some of the positive lead inside the normal
chunk loop and then reach the guard boundary.

## Decision

The next run should preserve this exact shape and set only the deadline guard
to zero. It will answer the real mechanism:

- zero breaks/timeouts: the 2 ms reservation was the 5 ms wall;
- zero pre-write breaks but write timeouts: actual Soapy/DMA service cannot
  complete within the remaining lead;
- negative-deadline breaks: a genuine producer/hardware timing miss remains.

Do not change lead, write timeout, cadence, RT state, or summary policy in that
run.
