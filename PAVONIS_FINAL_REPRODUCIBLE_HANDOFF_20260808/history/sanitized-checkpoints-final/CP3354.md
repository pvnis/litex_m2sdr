# CP3354: 6 ms period-10000 MCS16 valid partial

## Verdict

**VALID PARTIAL.** The full stack attaches, both sustained-traffic endpoints
complete, and the 6 ms policy reduces scheduler-to-PUSCH-result latency.
Uplink throughput is not a valid capacity result because the long run records
42 TX deadline breaks and 327,474 missing stream samples.

## Break geometry

All 42 event rows are present in the binary-safe mirror:


The events form seven clusters. Five cluster intervals retain the known
approximately 23-second cadence family. There is no metadata timestamp jump,
large producer stall or actual Soapy write timeout. Unlike CP3341's 5 ms
guard-zero run, every CP3354 raw deadline remains positive. The 500 us
reservation alone converts the observed events into pre-write loss.

## Latency and cadence

The same CP3324 parser selects the densest 45-second hardware window:

```text
scheduler_to_PUSCH_result_median=21.340 ms
CP3322_20ms_lead=34.850 ms
CP3332_10ms_lead=24.897 ms
CP3324_ZMQ=3.409 ms
```

The 20-to-6 ms lead reduction improves result latency by 13.510 ms, closely
tracking the 14 ms lead change. A residual approximately 18 ms gap to ZMQ
therefore remains even after physical TX lead is accounted for.

The first deadline break occurs two seconds before the selected window:

```text
scheduled_newTx_gross=0.200507 Mbit/s
median_newTx_gap=20 slots
median_HARQ_reuse_gap=36 slots
```

This is much worse than CP3322's healthy 3.975805 Mbit/s scheduled gross and
is consistent with frame-timeline loss, not a new grant-size ceiling.

## Decision

Do not credit the zero uplink or rerun unchanged. Test 6 ms with a 200 us
deadline guard over a long no-UE run that spans at least 420 seconds. The
observed minimum raw lead would retain 44 us; this must be tested for actual
write timeouts rather than assumed safe.

Acceptance requires zero pre-write breaks, actual write timeouts, deficit,
late and error counters for the full duration. If guard 200 us fails, move to
6.5 ms / 500 us. If it passes, use that lower-latency shape for the next OTA
run. Independently, the approximately 18 ms residual hardware-versus-ZMQ
result latency remains the parity frontier after stream continuity is restored.
