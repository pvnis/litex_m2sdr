# CP3411 - Inside-guard MCS20 no-RF gate

## Verdict

**PASS.** One bounded MCS20 hardware sensitivity is ready. RF was not used.

## Evidence

The fresh generated gNB config contains one PUSCH block with
`max_ue_mcs: 20`, retains PDSCH MCS9 and warning logging, and contains no
duplicate PUSCH or info-log block. Replacing that one MCS20 line with MCS19
produces CP3410's config hash exactly:
`e634d85b08e6ca24ae47d20c5f02654958cb1ebe1cf84f1f680063a398c5d942`.

After normalizing only checkpoint identity, launcher path/hash, result port,
and MCS label, the CP3412 runner is byte-identical to CP3410's runner. This
keeps the 8.5 ms lead, 100 us deadline guard, inside-guard source policy,
corrected PRACH/non-PRACH timing, RF controls, 23 stage-1 candidates, capture
settings, and 45-second four-stream traffic shape unchanged.

Deployment hash checks and both launcher validate modes pass. Controller
validate-only returns zero. Running without the explicit RF approval returns
two and prints the closed-gate marker.

## Decision

Run CP3412 once and judge health before throughput. MCS20 is promoted only if
it improves sustained uplink over CP3410's `14.9059 Mbit/s` without material
PUSCH CRC or TX-health loss. Otherwise CP3410 MCS19 remains the hardware
maximum and MCS20 is retired.
