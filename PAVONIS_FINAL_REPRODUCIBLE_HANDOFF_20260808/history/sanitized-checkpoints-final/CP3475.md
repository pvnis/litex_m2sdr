# CP3475 - Hardware MCS A/B launch propagation void

## Verdict

**VOID TWICE; NO RF TRANSMITTED.** Neither attempt started the gNB binary or
opened an SDR stream. They are launch-chain failures, not acquisition, channel,
or MCS results.

## Evidence

The first attempt and its one unchanged retry are byte-for-byte the same
failure class. Each gNB log is only three lines:

1. the CP3474 launcher starts with `selector_enable=0`;
2. the inherited PUSCH19 config launcher starts;
3. config generation completes with the historical PDSCH9 target.

The CP3474 runtime-export marker, selector startup marker, selector rows,
Soapy open/readback/summary, TX stop summary, and endpoint JSON are all absent.
TX timeout and downlink-late counters are zero because the transmitter never
started. The outer controller's “UE acquisition” classification is therefore
only the first unmet stage, not the root cause.

## Root Cause

The inherited hardware runner chain predates the caller-preserving PDSCH fix.
It rewrites the requested PDSCH10 control back to PDSCH9 and filters the new
selector environment variable before the remote gNB launcher. CP3474 then
correctly rejects the generated config because its no-RF contract required
PDSCH10. This occurs before the launcher exports runtime controls or executes
the gNB.

The selector itself is not implicated: it never ran. The retry reproduces a
deterministic propagation defect, so another identical attempt is forbidden.

## Decision

Keep the proven PDSCH9 source config and add the arm at the exact executable
boundary: a new default-off launcher that accepts the inherited config, plus a
small hash-pinned wrapper that explicitly enables the MCS9/MCS10 selector
before invoking it. Gate config-only output on `selector_enable=1`, then rerun
the hardware discriminator once. The source diagnostic remains default-off;
only the isolated, RF-gated wrapper is armed.
