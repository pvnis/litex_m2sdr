# Checkpoint 3487: Lead15 controller-expectation void

## Verdict

**PRE-UE CONTROL-GATE VOID; PRODUCER SHORT WINDOW CLEAN.** The gNB runs at the
intended lead15 shape, but the inherited controller rejects its readback and
never starts the UE. This is not an access or bandwidth datapoint.

## Evidence

- Genuine 15.36 Msps, ATT0, lead15 readback: present.
- UE process/log: absent; `ue_started=0`.
- Stop health over the bounded pre-UE window:
  - timeouts/breaks/abandoned/final-deficit: 0/0/0/0;
  - one 430-sample call partial fully recovered;
  - downlink-late/hard errors: 0/0.
- Controller step `gate_nativecontinuous_tx_readback`: rc1.

This is useful but limited: lead15 is clean in the short pre-UE window, while
CP3485 showed lead13 sample loss only during the longer reactive runtime.

## Root cause

The CP3456 controller still hard-codes lead13 in two places:

1. Its recorded RF shape expects 13,000,000 ns and the old four timing values.
2. Its runtime environment exports those same old values to the surrounding
   chain.

The lead15 launcher correctly reports 15,000,000 ns. Relaxing only the readback
gate would be wrong because the UE-side timeline would still receive stale
lead13 constants.

## Next gate

Copy the controller additively and replace all occurrences of the five coupled
values with the CP3486 lead15 values. Keep the launcher, RF, MCS, detector,
guard, and scheduler fixed. Prove the old constants are absent from active
controller fields, validate, and default-close before RF. Do not increase lead
beyond 15 ms.
