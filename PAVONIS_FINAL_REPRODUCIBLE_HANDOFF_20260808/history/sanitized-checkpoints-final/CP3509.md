# Checkpoint 3509: bounded queue rejected before second PRACH

## Verdict

**REJECTED.** Bounded queue propagates, but the 10240-sample queue cannot carry
the resumed exact-zero continuation stream in this shape. The UE emits only
one Msg1, so the intended second-PRACH update-timestamp branch is never
exercised.

## Evidence

- Both runtime env files record bounded queue1; RF state reads five buffers,
  four transfers, capacity10240 samples.
- First PRACH succeeds, and its guarded continuation SOB succeeds.
- The following exact-zero calls produce 118 unexpected-error returns, then
  three invalid SOB attempts around teardown/recovery.
- Only one random-access transmission occurs; zero RAR/PUSCH.
- Cell/SIB1 pass at 11.845 dB. gNB health has zero Soapy timeout,
  zero downlink-late, and zero stream deficit.
- Captured windows remain floor-class (-69.494 to -64.086 dBFS).

The failure occurs before a later true PRACH can reach the bounded-queue
`UPDATE_TIMESTAMP` conversion. Do not [interface-redacted] queue size: the source-level defect
is that continuation reopen eagerly opens on exact-zero idle calls.

## Next source fix

Add a default-off, env-read-once policy that defers the pending continuation
across exact-zero/low-energy non-PRACH calls and reopens only on the first real
non-PRACH waveform. With that policy, idle calls remain skipped while the
burst is closed; repeated PRACH can use normal timed SOB/EOB; the first PUSCH
gets the guarded continuation SOB without PRACH offset or EOB. Validate no-RF
and run with bounded queue returned to0.
