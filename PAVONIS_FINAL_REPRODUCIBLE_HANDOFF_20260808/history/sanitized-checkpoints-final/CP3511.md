# Checkpoint 3511: nonzero-reopen arm-clear source negative

## Verdict

**VALID SOURCE NEGATIVE; VOID FOR PRACH DETECTION, RAR, PUSCH, AND
THROUGHPUT.** The new policy propagates and marks the zero continuation as a
low-peak skip, but the same call still clears the pending reopen arm. The next
six PRACH writes therefore fail `TIME_PAST`. This is an exact source-ordering
defect in CP3510, not a radio or fixed-16 ms collection result.

## Propagation proof

Runtime configuration records explicit PRACH context=1, continuation
reopen=1, and nonzero-only=1. The plugin's one-time open readback records
bounded queue=0 and nonzero-only=1.

## Decisive transport sequence

1. Call 1268 is a true PRACH waveform (`peak=[date-redacted]`): forced SOB/EOB and the
   PRACH offset are applied, status is 0, and pending changes 0 to 1.
2. Call 1269 is exact-zero: `skip_low_peak=1`, but
   `prach_continuation_sob_applied=1` and pending changes 1 to 0. Status is 0.
3. The six later true PRACH calls retain forced SOB/EOB and the PRACH offset,
   but all return `TIME_PAST` (-14) because the continuation was never opened.

The Stage6 detector failure is consequently downstream of invalid UE transmit
timing and cannot judge the fixed-16 ms receive collection point.

## Source diagnosis

In `rf_blade_imp.c`, the new low-peak branch sets the existing skip flag, but
the `TX_BURST_START` flag and `prach_continuation_sob_applied` assignment are
outside the peak conditional. Later state handling sees “applied” and clears
the arm even though no reopen was transmitted.

The next correction is mechanical and no-RF first: put timestamp/TX_NOW,
`TX_BURST_START`, and the applied marker entirely inside the nonzero branch.
The low-peak branch must only set the skip marker and retain pending=1.
Default-off behavior and all frozen radio/detector/producer controls remain
unchanged. Do not [interface-redacted] queue depth, collection timing, or thresholds from this
run.
