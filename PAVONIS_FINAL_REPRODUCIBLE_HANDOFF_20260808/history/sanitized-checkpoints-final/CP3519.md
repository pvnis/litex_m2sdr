# CP3519 - Phase propagation and PUSCH timing provenance

## Verdict

**NO-RF PASS.** The two CP3518 provenance questions are resolved.

1. The six-phase PRACH list failed at the hardware-launcher boundary. The controller exported six entries, but it invoked the pinned CP3500 launcher, which unconditionally exports its own one-entry `245760:0` sequence. This mechanically explains CP3518's runtime `sequence_len=1` manifest.
2. The generic non-PRACH offsets were not copied unscaled from the 11.52 Msps baseline. Their checkpoint history derives and propagation-gates them on the 15.36 Msps branch.
3. The actionable PUSCH difference is on the UE transmit side. The last 15 MHz run with strong PUSCH, CP3451, applied the existing `-21333`-sample PRACH timestamp offset to every high-peak PUSCH because explicit PRACH context was off. CP3518's explicit-context correction correctly removed PRACH burst/restart/EOB semantics from PUSCH, but it also removed that timestamp correction. The same gNB non-PRACH collector family then changed from `128/128` CRC OK to `0/30`.

## Phase Propagation

- CP3518 controller declaration: six delays, 10 through 20 ms.
- Invoked hardware launcher SHA-256: `216da54cbd1cc0d3e2f3b3c1704f1dabb1faa461d3e3cc2d42dd341c0fc90b30`.
- That launcher hard-codes and exports `PAVONIS_PRACH_COLLECTION_PHASE_SEQUENCE='245760:0'` after controller setup.
- The previously working eight-phase launcher instead embeds and exports its complete list; SHA-256 `f2e5137726f436c98f42e06b2164774f73a1ccc0c0cfcca60a69c3965ff53ea9`.
- Runtime evidence is exact: all CP3518 collection rows have delay `245760`, sequence length `1`, index `0`.

The CP3517 no-RF gate was therefore incomplete: it validated the controller declaration but did not validate the final hardware-launcher export. No dynamic-phase RF retry is warranted now because fixed 16 ms produced six RARs in CP3518.

## Non-PRACH Offset Provenance

The live constants `-198611`, `-194184`, and `-199467` were derived during the 15 MHz / 15.36 Msps lead-retiming branch (CP3448-CP3451) and later explicitly restored as physical UL timing constants at CP3491-CP3492. CP3451 used this family and decoded `128/128` bounded PUSCH rows. This rejects the proposed 11.52-to-15.36 unscaled-copy explanation.

CP3518's dynamic edge path published one `-199855` offset and five `-198899` offsets. It consumed each generation before the associated PUSCH requests, and the PUxCH order trace proves all 30 task starts occurred after shifted grids were written. Decode ordering is not the failure.

Source confirms the boundary: `tx_dbg_prach_selected` is true for all traffic when explicit context is off, and only for true PRACH when it is on; that boolean gates the existing timestamp offset.

## Decision

Add one minimal, default-off, env-cached non-PRACH TX timestamp-offset policy to the current bladeRF source. It must:

- apply only to timed, non-PRACH, real-waveform buffers;
- preserve explicit PRACH context and the existing PRACH `-21333` behavior;
- not add SOB, EOB, restart, TX-now, or burst-only semantics;
- leave the disabled path unchanged;
- expose the selected/applied value in the existing bounded metadata trace.

Gate source/build/deploy no-RF first. Then run one bounded fixed-16 ms RF attempt with `-21333` as the sole semantic delta. Judge transport health, RAR supply, and PUSCH CRC before endpoints or throughput.
