## Verdict

Native-MTU 1022-sample CF32 writes do not recover external quality. Fourteen
complete periods remain at `-5.672 dB`, within `0.004 dB` of CP3568's
510-sample result. Sub-MTU write geometry is closed.

The next fork is not yet sample format. A no-RF provenance audit found that
the known-good CP3561 CS16 helper forced a different Soapy LiteX module from
the CF32 controls.

## Run health

The bounded controller returns zero. TX accepts 88,474,540 samples in 86,570
full 1022-sample writes with zero timeouts, partials, or errors. The entire
one-second bladeRF capture lies inside TX and has zero gaps, overruns,
underruns, or clips.

The correlation lock crosses the start of the capture, so the single-period
exact analyzer contains only six records. The modulo-period analyzer is the
authoritative metric: 14 complete periods, median `-5.672151 dB`, range
`-5.783..-5.584 dB`, standard deviation `0.062 dB`.

## Module provenance

CP3561's CP1166 helper explicitly set an empty Soapy root and forced:

`software/soapysdr/build/libSoapyLiteXM2SDR.so`

with SHA-256
`a15642a20c022d412a78fd27e922c27313e577c5f38c95adf1236c8b8008b0a2`.

CP3570 used default discovery. [host-redacted] currently has three different module
binaries:

- build tree: `a15642a...8b0a2`
- `/usr/lib/...`: `81b8cb2e...ff97c`
- `/usr/local/lib/...`: `f13e4985...430fb`

Default module listing registers `/usr/lib` first, and the runtime log reports
the `/usr/local` module as a duplicate of that registration. The active CF32
control therefore did not use the known-good CP3561 module.
