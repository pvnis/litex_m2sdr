# Checkpoint 3619: MCS17 run-split existing-evidence audit

Date: [date-redacted]

## Verdict

INSTRUMENTATION GAP, with a no-build path to close it. CP3613 and CP3618 are
valid, configuration-identical all-MCS17 runs, yet sustain 23.186008 and
11.102808 Mbit/s downlink respectively. Existing artifacts rule out selector,
dominant grant geometry, uplink decode, and producer delivery as the splitter,
but they do not record downlink HARQ outcomes over the traffic epoch.

Both runs contain 512/512 MCS17 selector rows and the same dominant 79-PRB,
6147-byte, one-layer grant. Both have 256/256 PUSCH CRC OK and zero TX timeout,
stream deficit, deadline break, or downlink-late event. In the first 512 traced
new transmissions, CP3618 carries 10.4477% fewer scheduled TBS bytes than
CP3613, far short of its 52.1142% throughput loss. This suggests more demand or
TCP stalls in the low run but cannot separate their cause from downlink BLER.

The filtered handset captures do not close that gap. Code `0xb821` is NR RRC
OTA in the installed QCSuper source; the installed parser does not decode the
other two filtered codes into PHY/HARQ metrics. Their record counts are not a
downlink-quality measurement.

OCUDU already accumulates the needed scheduler metrics: downlink ACK/NACK
counts, acknowledged TB bytes, MCS, CQI, PUCCH SNR, and PRB use. The frozen
configuration simply emits no scheduler metrics consumer. The next step is an
isolated config-only overlay enabling built-in scheduler metrics and stdout
autostart, with no source change or rebuild. Gate it no-RF, then run one MCS17
endpoint and compare scheduler goodput/BLER with HTTP throughput. If the metrics
track HTTP, the split is radio/HARQ; if scheduler goodput stays high while HTTP
falls, investigate application/TCP pacing.

Evidence is in `cp3619_compact_comparison.json` and
`cp3619_manifest.sha256`. No credential, subscriber identity, device identity,
host identity, NAS payload, or user payload is included.
